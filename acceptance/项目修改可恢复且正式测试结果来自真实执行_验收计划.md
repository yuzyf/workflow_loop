# 【验收主题】项目修改可恢复且正式测试结果来自真实执行

- 验收主题：项目修改可恢复且正式测试结果来自真实执行

## 1. 本次需求与验收目标

### 需求来源

- [实施并保护项目修改](../spec/功能_实施并保护项目修改.md)
- [编写并执行测试](../spec/功能_编写并执行测试.md)

### 验收目标

生产代码、测试代码和项目测试入口在修改前都有真实恢复依据，实际修改符合用户确认的最新计划；正式测试由程序在当前代码上执行并保存机器事实，不能由计划、局部检查或 AI 口头结论代替。

- [实施并保护项目修改：回退基线、实施和计划调整规则](../spec/功能_实施并保护项目修改.md)
- [编写并执行测试：追踪标识、登记、执行和结果规则](../spec/功能_编写并执行测试.md)

## 3. 验收范围

### 本主题验收

- 统一测试入口、生产代码、测试代码和配置的真实修改前内容。
- 按最新确认计划实施、同阶段调整计划和实施后真实记录。
- 测试代码到主题、验收条件、测试项和产品代码的追踪。
- 正式测试登记、跨平台参数执行、失败处理、机器记录和结果文档。

### 本主题不验收

- 主题人工验收、最终全量回归、整体验收和正式收工。
- 实施环节中的局部测试、构建、类型检查或静态检查是否可以替代正式测试。

## 4. 验收条件

### AC-01：修改前保存真实恢复依据

- 条件与触发：统一测试入口、生产代码、测试代码或相关配置准备在本轮第一次修改。
- 预期结果：已有文件保存真实原内容、原哈希和副本路径，本轮新增文件记录为原本不存在；只有哈希、缺少副本、路径不明确或保存前已经发生未说明变化时，程序拒绝继续修改。
- 产品设计依据：[实施并保护项目修改 R8 至 R11、R22、R23](../spec/功能_实施并保护项目修改.md#4-规则)

### AC-02：实施始终受当前确认计划约束

- 条件与触发：回退基线准备完成后实施代码，或者实施中发现代码改法需要调整。
- 预期结果：实际代码符合最新版确认计划并记录真实文件、代码符号、逻辑、数据、状态和输出变化；只调整代码改法时先停止修改、更新计划并重新确认，只为尚未修改的新路径补副本，最初原内容不被覆盖。
- 产品设计依据：[实施并保护项目修改 R12 至 R18](../spec/功能_实施并保护项目修改.md#4-规则)

### AC-03：测试代码能够追踪到产品要求

- 条件与触发：根据已确认实施代码和测试计划编写自动化或混合测试。
- 预期结果：每个测试函数、测试类或场景带有 `Workflow-Test` 工作流测试追踪标识，写清主题、主要测试项、主要验收条件、测试方式、测试层级、测试目标、测试入口和产品代码入口；测试代码环节不修改产品代码。
- 产品设计依据：[编写并执行测试 R1 至 R5](../spec/功能_编写并执行测试.md#4-规则)

### AC-04：正式执行范围可以审查

- 条件与触发：测试代码确认后，准备登记正式主题测试。
- 预期结果：用户能够看到每个自动化或混合测试项的入口、工作目录、超时、依赖和命令参数数组；每条任务只绑定一个 `TC-xx` 测试项，纯人工测试项不登记命令，登记动作不运行测试或生成结果。
- 产品设计依据：[编写并执行测试 R6、R7、R9](../spec/功能_编写并执行测试.md#4-规则)

### AC-05：程序跨平台真实执行并保存机器事实

- 条件与触发：正式测试任务登记完整，AI 启动统一测试运行。
- 预期结果：程序在 macOS、Linux 和原生 Windows 上直接使用参数数组启动测试，不解析 Shell 命令字符串；保存环境、开始结束时间、退出码、代码与测试版本。失败或超时清除旧成功记录，超时后终止对应进程组或 Windows 进程树。
- 产品设计依据：[编写并执行测试 R8、R10、R11](../spec/功能_编写并执行测试.md#4-规则)

### AC-06：正式测试结果与机器记录一致

- 条件与触发：当前主题的全部正式测试任务已经执行，AI 准备生成主题测试结果。
- 预期结果：只有全部相关测试函数和登记命令执行且退出码均为零才建立当前成功记录；结果文档中的测试位置、命令、环境、时间、时长、退出码和实际结果与机器记录一致。混合主题明确保留待人工验收内容，局部开发测试不进入正式结果。
- 产品设计依据：[编写并执行测试 R10 至 R15](../spec/功能_编写并执行测试.md#4-规则)

## 5. 完成判定

- AC-01 至 AC-06 全部通过，本主题才算完成。
- 无真实回退副本、未经确认改变计划、测试未由程序执行或结果与机器记录不一致时，本主题均不通过。
