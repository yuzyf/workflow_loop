# 【验收主题】计划路径非法时门禁一次说清而不是抛异常

- 工作流编号：2026-09-02-1012-bugfix
- 验收主题：计划路径非法时门禁一次说清而不是抛异常

## 1. 本次需求与验收目标

### 需求来源

- 用户要求修复上一轮记录在待修复缺陷登记中的 BUG-13：计划文件路径非法时门禁抛异常而不是进问题清单，导致多跑一轮。

### 验收目标

- 本主题完成后，实施记录里的计划路径写错时，用户和 AI 在一次门禁输出里就能看到它的具体位置和改法，和同一次发现的其它问题一起列出，不再多花一轮。

## 2. 产品设计依据

- 缺陷记录第 6 节给出根因位置：解析计划路径的函数已构造完整结构化诊断，对外入口只取证据字段抛异常。
- 推进并确认工作环节 R20 要求一次列出全部可独立确认的问题，R22 要求每项写清位置、预期、实际、证据、影响和下一动作。

## 3. 验收范围

### 本主题验收

- 计划路径非法时第二道门的失败呈现方式，以及它与同一次其它问题的合并输出。
- 现有捕获该失败的三处调用方在改动后的行为。

### 本主题不验收

- 什么样的路径算非法这一判定口径本身，本轮不改。
- BUG-14 发布脚本版本清单问题，由单独一轮 product_change 处理。
- 其它环节的失败呈现方式，本轮只改计划路径这一条链路。

<a id="4-验收条件"></a>
## 4. 验收条件

<a id="ac-01"></a>
### AC-01：计划路径问题进问题清单

- 开始前状态：一个启用工作记录表的代码实施环节，实施记录表的代码修改计划行把工作流过程文档路径填在文件列。
- 触发动作：AI 执行 workflow gate impl 做第二道门检查。
- 可检查结果：命令 stdout 的问题清单，以及每条问题是否带检查标识、位置、预期、实际、证据、影响和下一动作七项。
- 通过标准：该问题作为一条错误出现在问题清单里，七项齐全，位置精确到表文件、行号和列名；命令不打印“命令执行失败”这类兜底文字。
- 不通过标准：命令以一行异常文字结束，或该问题完全不出现在清单里。
- 产品设计依据：[推进并确认工作环节 R22](../spec/功能_推进并确认工作环节.md#r-22)

<a id="ac-02"></a>
### AC-02：与其它问题一次列全

- 开始前状态：同一份实施记录表里同时存在计划路径非法和另一处可独立确认的问题。
- 触发动作：AI 执行一次 workflow gate impl。
- 可检查结果：这一次命令输出的问题清单条目。
- 通过标准：两类问题在同一次输出里都出现；修完其中一条后再执行，不会冒出上一次本该报出却没报的问题。
- 不通过标准：一次只报出其中一类，另一类要等这一类改完后再执行才出现。
- 产品设计依据：[推进并确认工作环节 R20](../spec/功能_推进并确认工作环节.md#r-20)

<a id="ac-03"></a>
### AC-03：判定本身不变

- 开始前状态：两份实施记录表，一份代码修改计划的文件列全部是项目内真实源码路径，另一份含工作流过程文档路径。
- 触发动作：分别对两份表取计划路径集合。
- 可检查结果：两次取值的返回内容与失败情况。
- 通过标准：合法路径那份正常返回全部路径且不产生任何诊断；非法路径那份仍被判为错误，判定口径与修改前一致。
- 不通过标准：合法路径被误判为错误，或非法路径被放过。
- 产品设计依据：[实施并保护项目修改 R33](../spec/功能_实施并保护项目修改.md#r-33)

<a id="ac-04"></a>
### AC-04：现有调用方行为不变

- 开始前状态：计划路径非法，且实施记录文档已经存在。
- 触发动作：分别调用当前会捕获该失败的三处入口：阶段责任文件清单、主题归属路径和既有实现路径校验。
- 可检查结果：三处入口各自的返回值与是否抛出异常。
- 通过标准：三处仍按原有方式处理该失败，不抛异常给调用方，也不因为无法解析计划而退回全项目扫描。
- 不通过标准：任一处开始抛异常，或改为扫描全项目文件。
- 产品设计依据：[返回上游重新处理 R20](../spec/功能_返回上游重新处理.md#r-20)

## 5. 完成判定

- AC-01 至 AC-04 四条验收条件在一次真实执行中全部得到通过结论，本主题才算完成。
