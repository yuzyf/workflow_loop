# 已有项目设计初始化规范

## 目的

首次处理已有代码项目时，查清用户当前能够使用的产品行为和对应代码实现，一次建立：

- `spec/产品总说明.md`（产品总说明）。
- 多个 `spec/功能_<功能文件标识>.md`（功能说明文档）。
- `spec/代码架构设计.md`（代码架构设计文档）。
- `spec/项目设计初始化证据.md`（本次代码调查、测试运行和文档校准证据）。

功能文档的标题和正文保留用户确认的完整中文显示名称；文件名使用程序生成并保存的稳定中文文件标识（只保留中文、字母、数字、下划线、连字符，其它字符替换为下划线），两者可能不同。

本阶段只适用于 `product_change`（修改产品）或 `bugfix`（修复缺陷）且 `project_design_initialized=false`（项目设计尚未初始化）的情况。`from_scratch`（从零创建项目）不执行本阶段。

## 一、强制调查范围

开始讨论前，必须自行查看当前项目中实际存在的内容：

1. 项目说明和约束，例如 `AGENTS.md`、`README`、设计文档和已有决定记录。
2. 构建、依赖、启动和配置文件，确认项目怎样安装、启动和测试。
3. 用户实际进入产品的入口，例如命令行命令、页面、接口、定时任务或系统事件。
4. 入口之后的主要调用链，直到用户可见结果、文件输出、状态写入或外部系统响应。
5. 核心状态、数据存储、外部输入输出和失败处理。
6. 自动化测试、测试数据和测试辅助代码，确认哪些行为已有验证。

不能只根据目录名、文件名、类名或函数名猜测产品和架构。

调查完成后，先形成入口清单，再生成设计文档：

1. 列出全部真实用户操作入口和系统触发入口，并为每项附上可复核的代码、运行、测试或文档证据。
2. 每个入口只能归入一个可以独立完成的用户事情，或者写一个具体排除理由；不能重复归属、同时归属和排除，也不能留空。
3. 把入口归属、排除项和去重后的功能名称一次完整展示给用户。用户没有确认整份清单时继续调查，不得开始生成正式文档。
4. 用户确认后，证据文档中的功能清单成为本次初始化唯一功能基准。后续步骤不得根据代码目录、模块或另一份临时清单自行增减或重命名功能。

## 二、必须运行和验证

项目具备安全的本地运行条件时，必须实际运行，用真实表现校准代码理解。

- 已有本地启动说明、依赖和测试数据时，按项目说明执行。
- 至少运行现有自动化测试；具备条件时还要构建项目并走主要产品入口。
- 对主要功能走一遍成功路径，并在安全条件下检查关键失败路径。
- 运行后对照实际输出、状态文件、日志或界面结果，确认代码阅读是否正确。
- 缺少普通本地依赖时，按照项目已有说明准备依赖后继续，不因为需要安装普通依赖就直接放弃运行。

出现以下情况必须先取得用户同意：

- 需要生产账号或真实用户数据。
- 会产生付费调用。
- 会修改远程系统、生产环境或外部数据。
- 会执行项目没有说明且可能破坏现有数据的操作。

无法运行时，必须说明具体原因、已经尝试什么，以及哪些产品行为因此没有得到运行确认。不能把“阅读代码后认为可以”写成“已经运行验证”。

## 三、调查证据文档

调查证据按照 `Template_Repository/code_design/project_design_init_evidence.md` 写入 `spec/项目设计初始化证据.md`。本规范负责说明怎样取得真实证据，文档模板负责规定最终字段和章节。

程序会检查：

- 工作流编号必须等于当前工作流编号。
- “代码检查状态”必须是“已完成”。
- “初始化范围确认状态”必须是“已确认”。
- “入口清单”必须覆盖全部已发现入口；每行恰好填写一个功能归属或一个具体排除理由，并写明调查证据和用户确认状态。
- “功能清单”必须与用户确认内容相同，名称不重复，每个功能写清独立完成的用户事情、覆盖入口和确认状态。
- “产出文件清单”必须列全产品总说明、每个基准功能各自唯一的功能文档、代码架构设计和初始化证据自身；路径必须真实存在且状态为“已生成”。
- “已检查代码”至少列出一个项目中真实存在的代码文件，不能只列目录、文档或不存在的路径。
- 每个代码文件必须写清检查内容和得到的事实。
- 运行条件写“具备”时，必须写实际命令、执行结果和结果摘要。
- 运行条件写“不具备”时，必须写具体原因和未验证范围。
- 产品设计、代码设计和调查证据都必须在本阶段发生变化。

程序可以检查文件、字段、路径和内容哈希，但不能判断记录是否说谎。用户在第三道门确认前，必须核对命令与结果是否真实。

## 四、按实际入口追踪完整行为

对每个用户可见入口，沿实际调用关系追踪：

1. 谁或什么事件触发入口，传入什么。
2. 哪个文件中的哪个函数、类或接口接收。
3. 代码按什么顺序判断、路由和调用。
4. 哪一步读取配置、文件、数据库、内存状态或外部服务。
5. 哪一步写入状态、数据、日志或产物。
6. 成功时用户或调用方得到什么。
7. 失败时在哪里判断，是否重试、回滚或停止，用户得到什么。
8. 哪个测试或运行结果可以证明这条调用链。

必须阅读关键函数的具体逻辑，不能只记录调用关系或函数名称。

## 五、判断什么属于当前产品

当前产品功能以用户实际可以进入并完成的行为为准。发现代码中的能力时，按以下方式判断：

- **可达功能**：有实际入口，运行或测试能够到达，写入正式产品文档。
- **受条件限制**：只有明确配置、权限或环境满足时可达，写清使用条件。
- **隐藏功能**：代码可达但没有面向当前用户公开，不能直接当成普通正式功能。
- **未完成功能**：调用链缺失、关键分支未实现或无法产生完整结果，不能写成已经支持。
- **废弃或失效代码**：没有入口、不会被调用或已经被替代，不写成当前产品功能。
- **未确认**：仅凭现有证据无法判断时，明确记录并询问用户。

代码和运行结果可以证明产品现在怎样工作，但不能单独证明产品当初为什么诞生，或者当初为什么选择某种规则。历史原因只能使用明确历史文档或用户确认。

## 六、记录证据状态

对产品现状和代码架构中的关键结论，使用以下证据状态：

- **运行确认**：已经实际启动或执行，并观察到对应结果。
- **测试确认**：现有自动化测试覆盖并通过。
- **代码确认**：已经阅读真实调用链和关键逻辑，但没有实际运行到该行为。
- **文档或用户确认**：明确文档或用户说明了该事实。
- **未确认**：现有证据不足。
- **冲突**：文档、代码、测试、运行结果或用户说明互相不一致。

证据等级不是用来装饰文档。重要行为只有代码确认而没有运行或测试确认时，要明确说明验证缺口。

## 七、同步建立产品与代码设计

用户确认入口清单和唯一功能基准后，再整理一份内部对应关系：

- 每个用户可见功能对应哪些真实入口和调用链。
- 每条产品通用规则由哪些共享代码落实。
- 每个功能的规则、使用步骤和异常分别在哪段代码实现。
- 哪些代码属于多个功能共同经过的架构关键节点。
- 哪些产品行为缺少测试，哪些代码行为无法在产品文档中找到依据。

随后向用户总结当前产品、代码架构、未确认内容和冲突。每次只讨论一个需要用户决定的问题。用户确认共同理解后，一次生成四类初始化产物：产品总说明、每个基准功能各自唯一的功能文档、代码架构设计和初始化证据。

四类产物必须使用完全相同的功能集合：

- 产品总说明列出的当前功能集合、被当前清单引用且真实存在的功能文档集合、代码架构设计第 6 章的功能段集合、初始化证据中的功能清单，名称和数量必须分别与用户确认基准精确相等。
- 每个基准功能在产品总说明中出现一次、对应一份功能文档，并在代码架构设计第 6 章出现一个完整功能段；不能缺少、额外增加、名称不一致或重复。
- 每个代码功能段必须写清触发和输入、具体代码处理、产生的状态或输出、失败结果以及真实代码或运行依据，不能只有标题或文件名。
- 初始化证据的产出文件清单必须覆盖本次应有的全部四类文件，不能用“已有部分文档”代替完整产出。

内容还必须保持一致：

- 产品功能名称和场景名称一致。
- 产品边界与代码接口实际支持范围一致。
- 产品规则与代码判断条件一致。
- 产品使用过程与代码调用顺序一致。
- 产品异常结果与代码失败分支一致。
- 产品通用规则与共享代码职责一致。

`project_design_initialized`（项目设计是否已初始化）只表示上述检查是否全部完成，不保存另一份功能清单。只有四个功能集合、产出文件、入口处理、调查证据和用户确认全部通过后，才能把它写为 `true`（已完成）；任一项不通过时必须保持 `false`（未完成）。

产品总说明和功能文档面向用户，只写用户可见对象、用户或系统动作、产品规则、状态和可观察结果。明确的内部源码路径、接口路由、数据库表或字段声明、程序类、函数和代码模块定位不能写入产品背景或其它产品章节。用户实际选择、上传、下载、导入、导出或查看的 Markdown 文档、图片、表格和其它文件类型属于产品内容，可以正常写。仅凭词语无法确定是否为内部实现时，不按关键词自动拒绝；智能体必须说明歧义并让用户确认。

## 八、禁止事项

- 禁止只生成 `spec/代码架构设计.md`。
- 禁止把产品调查和代码调查拆成两轮互不校准的工作。
- 禁止用旧文档存在代替本次调查和生成。
- 禁止只看目录结构猜架构。
- 禁止具备安全运行条件却不运行。
- 禁止只在聊天中说看过代码或运行过，不写调查证据。
- 禁止把无法运行的行为写成已经验证。
- 禁止把不可达、未完成、隐藏或废弃代码直接写成正式产品功能。
- 禁止在用户确认唯一功能基准后由后续环节自行增减、重命名或重复功能。
- 禁止遗漏产品总说明、任一基准功能文档、任一代码功能段或初始化证据产出项。
- 禁止把内部源码路径、接口路由、数据库对象、程序类、函数或代码模块定位写入产品文档。
- 禁止仅因出现“文件”“Markdown”“图片”“表格”等词语而拒绝正常的用户可见文件描述。
- 禁止调查期间修改代码或顺手重构。
- 禁止把计划修改写成当前实现。
- 禁止根据当前代码推断产品诞生背景和历史设计原因。

## 九、完成前对抗性审查

- 是否真正查看了入口、关键调用链、状态、外部输入输出和测试。
- 是否在具备安全条件时运行了测试、构建和主要产品入口。
- 无法运行的原因和未验证范围是否写清。
- 每个正式产品功能是否有真实可达入口和完整结果。
- 每个真实入口是否恰好有一个功能归属或一个具体排除理由，并已经由用户确认。
- 产品总说明功能、当前引用的功能文档、代码架构设计第 6 章功能段、初始化证据功能清单是否与用户确认基准精确相等，没有缺少、额外、名称不一致或重复。
- 产出文件清单是否列全产品总说明、每个基准功能文档、代码架构设计和初始化证据自身，且文件真实存在。
- 每个产品功能是否能映射到具体代码，代码流程是否与产品使用过程一致。
- 每个架构关键节点是否有真实路径、符号、逻辑和证据。
- 是否把函数名当成逻辑说明，遗漏了关键判断和状态写入。
- 是否把隐藏、未完成或废弃代码误写成正式功能。
- 产品文档与代码架构文档中的名称、规则、边界、流程和异常是否一致。
- 产品文档是否只写用户可理解和检查的内容，没有明确内部实现定位；用户可见文件格式是否被正常保留，语义歧义是否交给用户确认。
- 是否仍有冲突或未确认内容被写成事实。
- 四类初始化产物是否全部生成，并且相对讨论完成时的基线确实发生变化。
