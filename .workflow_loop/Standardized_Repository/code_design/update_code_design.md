# 最终代码架构更新规范

## 目的

在实施、主题测试、主题验收、最终全量回归和整体验收都完成后，把已经验证的真实代码写回 `spec/architecture_code_design.md`，让维护者看到产品设计怎样落到实际代码。

最终文档结构使用 `Template_Repository/code_design/code_design.md`。本文件只说明本阶段怎样调查和更新，不重复架构文档模板。

## 调查范围

读取并相互对照：

- 已确认的产品总说明和功能文档。
- 当前架构设计文档中的计划内容和差异记录。
- 实际代码、真实文件路径、类、函数、类型和接口。
- 实施记录、主题测试结果、主题验收结果、最终全量回归状态和整体验收结果。
- 需求交付追踪表中当前工作流的全部阶段结果。

## 更新要求

- 用实际代码替换已经完成并验证的计划代码；不能只写“已完成”。
- 每个产品功能都要写清真实入口、关键代码环节、判断、调用、状态或数据处理、异常结果和验证位置。
- 每个架构模块都要说明它服务哪些产品功能、产品通用规则或系统约束。
- 架构图只表达实际代码分层、职责和依赖方向；功能流程图表达一个具体场景的执行过程。
- 仍未实现、未验证或文档与代码冲突的内容必须保留在差异记录中，不能写成最终事实。
- 不在本阶段新增产品规则，不根据代码擅自修改产品设计。

## 结束前检查

- 每项代码设计是否能追溯到产品功能、产品通用规则或系统约束。
- 每个功能流程节点是否能定位到真实代码和具体逻辑。
- 计划、当前实现、测试证据和验收结果是否区分清楚。
- 是否记录仍存在的产品、代码、测试或运行差异。
- 追踪表的最终代码设计列由程序在阶段确认时更新，不在文档中伪造链接结果。
