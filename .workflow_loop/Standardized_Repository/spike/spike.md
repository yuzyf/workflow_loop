# 穿刺阶段规范

## 目的

在进入实施计划或修复计划前，找出仍缺少真实证据、并会改变后续决定的技术不确定性。用户决定执行哪些穿刺项，AI 使用真实场景取得证据，随后把结论同步到受影响的产品设计和代码设计。

穿刺的对象是不确定性，不是功能名称，也不是所有技术问题。已经能从现有事实确认的内容不需要穿刺。

## 一、先调查，再判断是否存在不确定性

1. 读取已经确认的 `spec/产品总说明.md`、其中链接的功能文档和 `spec/代码架构设计.md`。
2. 改产品和修 bug 时，必须查看相关代码、现有测试、日志、依赖文档和已有运行结果。
3. 项目具备运行条件时，必须先运行与当前问题有关的现有功能。运行已经能回答的问题，不得再列为穿刺候选。
4. 修 bug 时还要读取当前缺陷记录和复现结果。不要在穿刺阶段重复已经确认的 bug 表现和根因。
5. 无法运行时，写清缺少什么条件，以及因此仍无法确认什么。
6. 从零开发且代码尚不存在时，不强制运行项目，但仍要检查产品设计、代码设计和已经选定的依赖。

技术不确定性必须同时满足：

- 当前缺少事实证据，无法直接确认。
- 必须通过真实调用、真实运行或实际测量才能确认。
- 不同结果会改变产品设计、代码设计、实施计划、修复计划、测试或验收方式。

不满足上述条件时，不进入穿刺候选。

## 二、整理候选并消除重复

AI 必须比较每个候选的：

- 真实场景。
- 当前不确定的内容。
- 准备取得的证据。
- 验证结果用于决定什么。

这些内容实质相同，或者一个只是另一个的验证问句时，合并成一个穿刺项。程序门禁不能判断语义重复，这项检查由 AI 完成，最后由用户确认。

后一项必须等前一项结果出来才知道是否需要时，不把后一项提前列为必做项。先完成当前不确定性，再向用户说明是否需要新增后续穿刺。

## 三、逐项和用户确认候选

可以先给用户候选概览，但每次只让用户决定一个候选。每个候选必须用直白话说明：

1. 候选名称。
2. 真实场景。
3. 已经确认的事实。
4. 当前不确定的具体行为、返回内容或限制。
5. 为什么现有事实不能回答，必须实际验证。
6. 准备使用什么真实请求、文件、平台、数据规模或操作路径验证。
7. 验证结果用于决定什么。
8. 是否会修改外部数据、产生费用或带来其他实际影响。
9. AI 是否建议执行，以及建议理由。

候选尚未被用户选择时，不写入 `spec/穿刺清单.md`，也不分配 `SP-001` 这类正式编号。

AI 认为没有需要穿刺的不确定性时，也必须说明检查了哪些文件、代码和运行结果，以及为什么这些事实已经足够。只有用户明确决定本次全部跳过，才能执行：

```text
workflow gate spike --skip
```

跳过时不生成穿刺清单和结论文档，也不修改产品设计和代码设计。

## 四、确认执行清单

用户逐项决定后，AI 汇总最终清单，说明每项是否互相独立、是否存在执行顺序，并让用户确认清单完整。

用户确认后执行：

```text
workflow gate spike --discuss-done
```

第一道门只表示用户确认了本次执行清单。它不表示程序能够理解候选是否语义重复。

第一道门通过后：

1. 创建 `spec/穿刺清单.md`。
2. 为每个已选项目分配 `SP-001`、`SP-002` 等编号。
3. 把每项穿刺状态先写为“待验证”。
4. 创建对应的 `spec/穿刺_<穿刺项文件标识>.md`，先填写第一至第四部分。结论文档的标题和正文保留用户确认的完整中文显示名称；文件名使用程序生成并保存的稳定中文文件标识（只保留中文、字母、数字、下划线、连字符，其它字符替换为下划线），两者可能不同。

## 五、选择最小且真实的验证方法

穿刺不强制编写临时代码。按以下顺序选择方法：

1. 现有命令、现有程序或已有日志可以取得证据时，直接使用。
2. 第三方工具或真实接口调用可以取得证据时，直接使用。
3. 只有现有手段不能暴露所需结果时，才编写最小脚本、逻辑原型、界面原型、解析程序、构建探针或性能测量程序。

临时代码、真实场景样本和原始输出统一放入：

```text
.workflow_loop/spike_tmp/<穿刺项文件标识>/
```

原型方法只是一种验证手段。可以吸收“目标明确、使用现有技术栈、暴露关键状态”等做法，但不能照搬“默认不接真实数据”。验证对象必须来自真实场景。

执行方式不强制压成一条命令。必须记录最少且可以重复执行的完整命令步骤。

## 六、真实场景要求

验证必须使用产品实际会遇到的接口、输入文件、运行平台、数据规模、操作路径或故障条件。

允许编写最小驱动程序观察真实对象，但不得使用以下内容证明真实行为：

- 自己编造的接口响应。
- 模拟业务数据。
- 手工构造的理想文件。
- 与目标平台无关的玩具环境。
- 小数据结果直接推断实际规模性能。

真实数据可以脱敏或裁剪，但不能改变本次要验证的格式、结构、规模或故障特征。无法取得真实场景时，只能写“仍未确认”。

## 七、外部影响和敏感信息

用户选择穿刺项，只表示同意验证该不确定性，不自动授权扣费、发送内容、创建或修改外部数据、删除数据。

只读验证可以在穿刺项确认后执行。存在外部影响的步骤必须在执行前再次说明：

- 操作对象。
- 实际影响。
- 预计费用。
- 能否撤销。

取得用户明确确认后才能执行。用户不同意且没有其他真实验证方法时，结论写“仍未确认”。

密钥、令牌、密码和会话信息不得写入穿刺文档、临时文件或保留的命令输出。

## 八、执行并记录证据

互不影响的穿刺项可以一起执行。每完成一项，立即填写对应结论文档的第五至第八部分，并更新清单中的穿刺状态。

必须记录：

- 实际执行时间。
- 操作系统、目标平台、工具和依赖版本。
- 实际命令。
- 真实输入或样本来源、类型、大小、数量或哈希。
- 关键原始输出、返回字段或测量数据。
- 实际失败、重试和限制。
- 根据证据得到的结论。

执行前不预测未知结果。只有产品设计已经给出明确指标时，才提前写处理时间、内存、正确率等判断线。

执行中出现新的不确定性，或者前置结果表明原先未选择的后续候选现在需要执行时，先向用户说明，再由用户决定是否加入清单。AI 不得自行扩展范围。

## 九、形成结论并处理阻塞

结果状态只能是：

- `已确认`：证据足以确认真实行为。
- `限制已确认`：原方案不可行或只能部分满足要求，但限制已经查明。
- `仍未确认`：证据仍不足。

结果状态只说明证据确认到了什么。“是否阻塞后续”单独说明当前能不能进入验收计划。

任何穿刺项写“是否阻塞后续：是”时，都不能通过第二道门。必须继续验证，或者让用户决定怎样修改产品、代码设计或范围。

`仍未确认`但不阻塞时，必须写清：

- 剩余风险。
- 后续处理阶段。
- 后续需要检查什么。

用户在第三道门最终确认是否接受这些风险。

## 十、把结论同步到设计

穿刺只负责取得真实证据，不修改正式代码。证据确认后，用户决定采用什么实现或修复办法。

从零开发和修改产品时：

- 结果需要改变用户可见行为、功能范围或产品规则时，先由用户决定，再更新 `spec/产品总说明.md` 或对应功能文档。
- 结果影响接口、数据结构、模块、函数、调用过程、算法、性能限制、平台限制或异常处理时，更新 `spec/代码架构设计.md`。

修 bug 时：

- 原产品行为保持不变，只修改修复方法或代码设计时，可以更新代码设计并继续。
- 只有改变产品行为、产品规则或功能边界才能继续时，不能在当前 `bugfix` 流程修改产品设计。结束当前流程后，改用 `product_change`。

实现或修复办法仍未决定时，说明当前仍然阻塞，不能进入 `acceptance_plan`。

## 十一、三道门

三道门都只能操作当前正在进行的 `spike` 阶段。当前阶段不是 `spike` 时，不得提前调用穿刺门禁。

### 门1：确认执行清单

命令：

```text
workflow gate spike --discuss-done
```

用户确认执行哪些穿刺项后调用。随后写清单、结论文档并执行验证。

### 门2：程序校验产物

命令：

```text
workflow gate spike
```

程序检查：

- 清单和结论文档属于当前工作流。
- 清单中每项都有对应结论文档。
- 固定字段和值合法，清单中没有“待验证”。
- 没有任何项目仍阻塞后续。
- `仍未确认`项目写清剩余风险、后续阶段和后续检查。
- 写“需要修改”的产品设计或代码设计已经相对穿刺开始时发生变化。
- 当前工作意图是 `bugfix` 时，没有项目写“产品设计影响：需要修改”。

旧工作流已经进入 `spike` 但没有保存入场设计基线时，不得使用当前文件补造旧基线。全部设计影响为“无需修改”时可以继续；任何项目要求修改设计时，门2必须失败并说明无法证明前后变化。

程序只能检查明确字段、文件和内容哈希，不能判断语义重复、证据是否真实或设计修改是否正确。

### 门3：用户统一确认

命令：

```text
workflow gate spike --confirmed
```

用户一起检查穿刺清单、全部结论、剩余风险和更新后的产品设计、代码设计。执行门3时，程序必须重新校验当前文件；门2后文件被改坏时，清除旧通过状态并停留在 `spike`。重新校验通过后才能进入 `acceptance_plan`，并清理 `.workflow_loop/spike_tmp/`、记录实际清理内容。

## 十二、穿刺代码边界

- 可以读取、导入和运行现有代码。
- 可以在穿刺临时目录中建立隔离副本。
- 不修改正式源代码、正式页面、正式配置或数据库迁移。
- 后续正式代码可以使用穿刺确认的接口形状、状态逻辑、算法约束和失败条件。
- 不把缺少正式错误处理、测试和边界设计的临时代码直接复制进生产代码。
- 某个样本或验证逻辑需要成为正式测试资产时，在后续 `impl` 实施阶段重新确认后放入正式测试目录。
