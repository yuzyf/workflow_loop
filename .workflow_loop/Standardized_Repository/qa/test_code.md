# 测试验证阶段：测试代码工作规范

## 1. 位置和边界

本文件规定 `qa`（测试验证）内部怎样完成或复用测试代码。测试范围已经在 `workflow gate qa --discuss-done` 由用户一次确认；本步骤不重新设计范围，也不再让用户确认测试落点或测试代码。

本步骤只修改测试代码、fixture（测试准备复用代码）、测试样本和测试配置，不修改产品代码，不生成正式测试结果，不执行人工验收。具体编码规则还必须遵守 `Standardized_Repository/qa/test_code_implementation.md`。

## 2. 开始前读取

AI 必须读取并核对：

1. 当前工作流编号、验收主题和主题关系。
2. `acceptance/索引.md` 和全部主题验收计划。
3. `qa/索引.md` 和全部主题测试计划。
4. `impl/索引.md` 和全部主题实施记录，重点核对代码结果。
5. `需求交付追踪表.md`、有效穿刺结论和可复用资产。
6. 测试项对应的真实产品入口、代码入口、调用关系、状态变化和错误处理。
7. 现有测试、fixture、辅助函数、样本、配置和统一测试入口。

能从代码和文件查明的事实先自行查明，不让用户重复说明。使用可复用穿刺资产时，从原目录按登记方法重新运行；旧结论不能直接证明当前代码。

## 3. 复用既有测试

已有测试可以直接复用，但必须逐项核对：

- 当前 `AC-xx`（验收条件）和 `TC-xx`（测试项）仍然一致。
- 产品入口、代码入口、测试入口、准备数据、执行动作、断言和证据要求与当前计划一致。
- 测试依赖、隔离方式和清理方式仍然成立。
- 完整 `Workflow-Test` 标识存在且内容与计划一致。

全部一致时保留测试代码，不为了制造变化改空格、注释或无关写法。复用只表示代码仍可用，不表示本轮已经通过；后面仍必须重新登记并真实执行受影响测试。

测试范围的开始确认已经包含计划中的测试入口；测试代码核对完成后直接进入任务登记。

## 4. 测试方式和层级

测试计划中的测试方式只能是：

- `自动化测试`：必须有可执行测试代码。
- `人工验收`：不编造测试代码，交给 `topic_acceptance`（主题验收）。
- `自动化测试 + 人工验收`：只实现机器可以稳定判断的部分，人工部分交给主题验收。

自动化测试不等于全部使用单元测试。选择能够可靠证明验收结果的最低测试层级，但不能为了方便绕过用户真实使用的产品入口。

## 5. 追踪标识

每个新增、修改或复用的测试函数、测试类或测试场景必须包含完整标识：

```text
Workflow-Test
主题：<验收主题名称>
测试项：TC-xx <测试项直白名称>
验收条件：AC-xx <验收条件直白名称>
测试方式：自动化测试 | 自动化测试 + 人工验收
测试层级：单元测试 | 模块测试 | 集成测试 | 命令测试 | 接口测试 | 端到端测试
产品入口：<与测试计划完全一致的真实产品入口>
测试入口：<与测试计划完全一致的 项目相对文件::测试函数、类或场景>
代码入口：<与测试计划完全一致的 项目相对文件::产品函数、类或命令入口>
准备数据：<与测试计划完全一致的执行前数据和状态>
执行动作：<与测试计划完全一致的产品入口动作>
关键断言：<与测试计划“预期结果”完全一致>
预期证据：<与测试计划“证据要求”完全一致>
```

一个测试函数只绑定一个主要验收条件和一个主要测试项。一个测试项需要多个场景时可以由多个测试函数共同执行；相同准备过程使用 fixture 或辅助函数共享。

测试代码必须真实调用标识中的产品入口并观察计划指定的位置。只比较常量、手工设置并读取属性、检查对象存在或绕过产品入口伪造结果，都不算覆盖产品行为。

## 6. 允许的开发反馈

可以运行与当前正在编写内容直接相关的单个测试函数、类或文件，也可以做语法、类型、静态和 lint 检查。

这些运行只是开发反馈：

- 不运行整个测试目录或项目全量入口。
- 不用 `workflow test prepare` 登记，不用 `workflow test run` 执行。
- 不生成正式机器记录或 `qa/<主题文件标识>_测试结果.md`。
- 不更新追踪表的正式测试结果。
- 不声称测试项或验收条件已经通过。

正式测试事实只来自后续 `workflow test run` 的当前机器记录。

## 7. 发现问题时处理

- 产品代码缺少实现或必要测试接缝：返回 `impl`。
- 测试范围、方式、通过标准或测试入口需要改变：回到 QA 范围步骤，修改计划并重新执行 `workflow gate qa --discuss-done`。
- 只是测试代码缺少或写错：留在 QA 测试代码步骤修正。
- 验收条件不明确：返回 `acceptance_plan`。
- 产品行为没有定义：返回 `spec`。
- 必须运行真实外部场景才能确定技术事实：由用户决定是否返回 `spike`。

不能通过固定返回值、无依据 mock（模拟对象）或绕过产品入口制造“测试通过”。

## 8. 完成判断

进入任务登记前检查：

- 每个自动化或混合测试项至少有一个完整 `Workflow-Test` 标识。
- 标识中的主题、测试项、验收条件、测试方式和七个计划字段都与当前测试计划一致。
- 测试入口可以由测试执行器直接定位。
- 测试优先验证产品可观察结果，不只检查私有实现细节。
- fixture、辅助代码、样本和配置只服务测试。
- 产品代码没有变化。
- 局部运行没有被写成正式结果。

检查完成后直接使用 `workflow test prepare` 登记任务，不增加测试代码用户确认或独立门禁。
