# 测试代码阶段工作规范

## 1. 阶段职责

本阶段把已经确认的验收条件和测试计划落实为真实测试代码。它先调查实施后的真实代码和现有测试，再和用户确认每个测试项的测试落点，最后编写测试代码。

本阶段不重新制定验收条件和测试范围，不生成正式测试结果，也不执行主题验收。测试代码写作规则另见 `Standardized_Repository/qa/test_code_implementation.md`。

## 2. 开始前必须读取

AI 必须使用文件读取和代码搜索工具，读取：

1. 当前工作流编号、验收主题和主题关系。
2. `acceptance/索引.md` 和当前全部 `acceptance/<主题文件标识>_验收计划.md`。
3. `qa/索引.md` 和当前全部 `qa/<主题文件标识>_测试计划.md`。
4. `impl/索引.md` 和当前全部 `impl/<主题文件标识>_实施记录.md`，重点核对实施后记录。
5. `需求交付追踪表.md` 和 `spec/代码架构设计.md`。
6. 测试项对应的产品代码入口、调用关系、状态变化和错误处理。
7. 现有测试、fixture、测试辅助函数、测试样本、测试配置和统一测试入口。

不能只根据文档中的文件名猜测试写法，也不能把整个代码库打印到命令行代替调查。能从代码确定的事实先自行查明，不让用户重复说明。

### 上游变化后重新进入本阶段

如果终端说明本次是因为验收计划、测试计划或实施代码变化而重新进入 `test_code`（测试代码编写阶段），先核对现有测试代码是否仍覆盖最新测试项：

1. 逐项比较最新 `AC-xx`（验收条件）、`TC-xx`（测试项）和现有 `Workflow-Test` 标识。
2. 核对测试入口、断言、测试依赖和产品代码入口是否仍然成立。
3. 全部一致时不修改测试代码，由用户调 `workflow gate test_code --accept-existing-test-code` 明确确认继续使用现有测试代码。
4. 有新增、删除、改名或预期结果变化时，只修改实际受影响的测试代码。

不得为了满足“测试代码发生变化”的普通门禁而改空格、改注释或制造无意义测试。无论是否复用测试代码，旧测试执行记录都不能继续使用，后续 `test_execution` 必须重新执行。

## 3. 写代码前的测试落点确认

针对测试计划中每个标为 `自动化测试` 或 `自动化测试 + 人工验收` 的测试项，先向用户说明：

| 内容 | 必须说明什么 |
|---|---|
| 验收条件 | `AC-xx` 编号、直白名称和预期结果 |
| 测试项 | `TC-xx` 编号、直白名称和测试方式 |
| 产品代码入口 | 实际命令、接口、类或函数，以及具体文件位置 |
| 当前代码逻辑 | 当前入口怎样处理输入、状态、输出和错误 |
| 测试层级 | 单元、模块、集成、命令、接口或端到端测试，并说明理由 |
| 测试文件 | 新增或修改的具体测试文件 |
| 测试场景 | 输入、前置状态和需要覆盖的成功、拒绝、失败或边界情况 |
| 主要断言 | 具体检查的输出、状态、副作用或错误 |
| 测试依赖 | 使用的 fixture、真实样本、测试接缝或外部环境 |
| 隔离清理 | 怎样避免测试之间互相影响 |

用户确认当前工作流全部自动化测试项的测试落点后，才调用 `workflow gate test_code --discuss-done`，然后开始写测试代码。

## 4. 测试方式和测试层级

测试计划中的测试方式只能是：

- `自动化测试`：本阶段必须生成测试代码。
- `人工验收`：本阶段不编造测试代码，由 `topic_acceptance` 核对。
- `自动化测试 + 人工验收`：本阶段只实现可自动判断的部分，人工部分交给 `topic_acceptance`。

自动化测试不等于全部写成单元测试。选择能够可靠证明验收结果的最低测试层级，但不能为了方便而绕过用户实际使用的产品入口。

## 5. 追踪标识

每个新增或修改的测试函数、测试类或测试场景必须包含完整标识：

```text
Workflow-Test
主题：<验收主题名称>
测试项：TC-xx <测试项直白名称>
验收条件：AC-xx <验收条件直白名称>
测试方式：自动化测试 | 自动化测试 + 人工验收
测试层级：单元测试 | 模块测试 | 集成测试 | 命令测试 | 接口测试 | 端到端测试
产品入口：<与测试计划完全一致的真实产品入口>
测试入口：<与测试计划完全一致的 项目相对文件::测试函数、类或场景>
代码入口：<与测试计划完全一致的 项目相对文件::产品函数、类或命令入口>
准备数据：<与测试计划完全一致的执行前数据和状态>
执行动作：<与测试计划完全一致的产品入口动作>
关键断言：<与测试计划“预期结果”完全一致>
预期证据：<与测试计划“证据要求”完全一致>
```

每个测试函数只绑定一个主要验收条件和一个主要测试项。一个验收条件可以由多个测试项覆盖，一个测试项可以由多个测试函数执行。多个测试函数需要相同准备过程时使用 fixture 或测试辅助函数共享。

测试代码必须真实调用标识中的产品入口，并观察测试计划指定的位置。只比较角色字符串、只手工设置并读取属性、只检查返回对象存在，或者绕过产品入口直接伪造结果，都不能算覆盖实际行为。

## 6. 允许的开发反馈

写测试代码阶段可以做静态检查、语法检查、类型检查和 lint 检查。

也可以运行与当前正在编写内容直接相关的单个测试函数、单个测试类或单个测试文件，用来确认刚写的测试代码本身能不能跑起来、断言写得对不对。这类运行只是开发反馈，和正式测试是两回事：

- 只运行当前正在写的那部分，不运行整个测试目录，不运行全量测试入口。
- 运行结果只在聊天中说明，用来决定接下来怎样改测试代码。
- 不生成正式机器记录，不用 `workflow test prepare` 登记，不用 `workflow test run` 执行。
- 不生成或修改 `qa/<主题文件标识>_测试结果.md`。
- 不更新 `需求交付追踪表.md` 的正式测试结果。
- 不声称主题测试已经通过，也不据此写出任何验收结论。
- 不进入主题验收。

局部运行通过不代表测试项通过。正式执行只发生在 `test_execution`（主题测试执行阶段），由受控进程执行器统一登记和运行，只有那里产生的记录才是正式测试事实。

## 7. 发现问题时返回

- 产品代码缺少必要测试接缝：返回 `impl`。
- 测试范围或测试方式不正确：返回 `test_plan`。
- 验收条件的预期结果不明确：返回 `acceptance_plan`。
- 产品行为没有定义：返回 `spec`。
- 必须运行真实外部场景才能确认技术事实：由用户决定是否返回 `spike`。
- 只有测试文件位置尚未确定、但现有测试框架能够支持：留在 `test_code` 解决。

不能通过固定返回值、无依据 mock 或绕过产品入口制造“测试通过”。

## 8. 完成前检查

- 每个自动化或混合测试项是否至少有一个完整 `Workflow-Test` 标识，且产品入口、代码入口、测试入口、准备数据、执行动作、关键断言和预期证据逐字对应测试计划。
- 标识中的主题、测试项、验收条件和测试方式是否与测试计划完全一致。
- 测试目标、测试入口和产品代码入口是否写到开发者可以直接定位和理解。
- 测试代码是否优先验证产品可观察结果，而不是私有实现细节。
- fixture、测试辅助代码、测试样本和测试配置是否只服务测试。
- 是否没有修改产品代码。
- 局部运行是否只覆盖当前正在编写的测试，没有跑整个测试目录或全量入口。
- 是否没有提前生成正式测试结果或主题验收结果。

用户确认测试代码后调用 `workflow gate test_code --confirmed`。程序保存确认后的测试代码和测试配置哈希，后续正式测试只接受这一份测试代码。

门禁失败时一次列出所有能独立确认的问题；后续检查被前置错误阻断时明确写“未检查”及原因。最后只给一条当前可执行的下一命令，并写明执行者、副作用、成功条件和成功后进入的阶段。

上游变化后，如果用户已经通过 `workflow gate test_code --accept-existing-test-code` 确认现有测试代码仍覆盖最新计划，第二道门允许测试代码相对本次重新进入阶段时保持不变；确认后测试代码再次变化时，必须重新核对或修改后再过门禁。
