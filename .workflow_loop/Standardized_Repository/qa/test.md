# 主题测试执行阶段工作规范

## 1. 阶段目的

本阶段把已经确认的测试计划和测试代码真正运行起来，得到可以复核的机器事实。

本阶段不重新设计测试范围，不修改产品代码或测试代码，不执行人工验收。正式结果使用 `Template_Repository/qa/test.md`。

## 2. 两个命令的分工

- `workflow test prepare` 是“登记待执行测试”。它只把一个测试项要执行的命令、工作目录和超时时间记录下来，不运行任何东西，也不产生任何执行结果。
- `workflow test run` 是“正式运行已登记测试”。它按登记内容启动受控进程，把真实执行事实写成机器记录。

只有 `workflow test run` 产生的记录才是正式测试事实。登记本身不是执行，登记完成不等于测试通过。

## 3. 开始前必须调查

AI 必须读取并核对：

1. 当前工作流编号、全部验收主题和主题关系。
2. `acceptance/<主题文件标识>_验收计划.md` 中的验收条件。
3. `qa/<主题文件标识>_测试计划.md` 中的测试项、测试方式和前置测试项。
4. `impl/<主题文件标识>_实施记录.md` 中的实施后记录。
5. 测试代码中的完整 `Workflow-Test` 标识。
6. 当前代码、测试配置、真实测试入口和所需运行环境。
7. `需求交付追踪表.md` 中当前主题的上下游状态。

测试计划、测试代码标识和实际测试入口不一致时，不开始执行。

如果本阶段是上游变化后重新进入，必须向用户说明旧测试结果为什么失效。实施计划或测试代码可以经过核对后继续复用，但旧机器执行记录和 `qa/<主题文件标识>_测试结果.md` 不能代表最新代码与计划，必须重新登记并执行受影响主题。不能因为之前曾经通过就直接进入主题验收。

## 4. 执行前和用户确认

针对每个自动化或混合测试项，AI 必须用直白话说明：

- 这是哪个主题、哪个 `TC`，要证明哪个验收条件。
- 实际会执行哪些测试函数、测试类或测试场景。
- 是否依赖同一主题中的其他测试项；没有依赖写“无”。
- 实际执行的参数数组命令、项目内工作目录、环境要求和超时时间。
- 自动化能证明什么；混合测试还需要用户在主题验收阶段确认什么。

用户确认后，用 `workflow test prepare --topic <主题> --tc <TC编号> --cwd <项目内工作目录> --timeout <秒数> --report-adapter <报告适配器> -- <命令和参数>` 逐项登记。`report-adapter` 的中文含义是“结构化测试报告适配器”，只支持 `vitest-junit` 和 `pytest-junitxml`；必须按项目真实测试框架二选一，不能省略。

### 4.1 工作目录

每次登记都必须包含项目内工作目录。默认是项目根；测试必须在子目录中运行时，写该子目录相对项目根的路径。

- 工作目录只能在项目内，不能指向项目外的绝对路径。
- 工作目录写进机器记录，正式结果文档必须照抄它。
- 不能靠“在哪里执行都一样”跳过登记；不同工作目录会改变相对路径、配置查找和测试发现结果。

### 4.2 命令是参数数组

登记的命令是参数数组，直接交给进程执行器，不经过 Shell。

- 不接受管道、重定向、命令串联、命令替换和通配符展开。
- 需要这些能力时，把它们放进项目自己的脚本，再登记这个脚本作为命令。
- 登记命令必须直接包含该 `TC` 的测试入口、测试文件、测试类或测试函数定位参数。
- 不能登记 `python -c`、`node -e` 等临时代码，也不能用一个与测试入口无关但会返回退出码 `0` 的命令冒充测试通过。

全部自动化测试项登记完成后，再调用 `workflow gate test_execution --discuss-done`。这个门禁只检查登记是否完整，不运行测试。

## 5. 正式执行

调用 `workflow test run` 执行已经登记的任务：

- 同一主题按照 `前置测试项` 顺序执行。
- 程序先读取 `qa/索引.md` 的前置主题关系。有前置主题时，先完成前置主题在本阶段需要执行的自动化测试；前置主题没有自动化测试项时，本阶段无需等待。
- 没有前置主题且环境互不影响的主题可以并行；默认最多同时执行两个主题。
- 共用数据库、端口、设备、账号或临时目录的主题必须串行。
- 每个 `TC` 必须执行当前所有带相同主题和 `TC` 标识的测试入口。
- 同一前置测试项在当前有效记录没有失效时只执行一次。
- 当前测试项已经有未失效的成功记录时不重复执行；只运行待执行、失败后重试或已明确失效的项目。
- 单个任务默认超时 600 秒；AI 根据项目实际情况提出调整，由用户确认。

### 5.1 统一的受控进程执行器

主题测试和最终全量回归使用同一个受控进程执行器。同一个执行器意味着两个阶段的执行方式、超时处理、输出截断和记录字段完全一致，两处结果可以直接互相对照。

执行器统一负责：使用参数数组和 `shell=False` 启动进程、限制运行时间、超时后终止整棵进程树、截断并保存输出摘要、计算完整输出哈希，并记录平台标识和实际可执行文件。

程序还会按登记的报告适配器自动补充固定报告参数，清除同路径旧报告，再解析本次新生成的结构化报告。AI 不手工拼接报告参数，也不把终端文字中的“通过”当成测试执行事实。

程序把当前有效执行记录写入 State Snapshot（状态快照），把每次尝试写入 Journal（追加式历史）。完整终端输出只用于当次诊断，不保存到正式结果或状态文件。

### 5.2 成功记录绑定当时的代码

一次执行成功后，机器记录绑定执行当时的产品代码哈希和测试代码哈希。

产品代码或测试代码之后发生变化时，这条记录不再代表当前代码，必须重新执行才能作为正式依据。不能用旧记录证明新代码通过。

## 6. 成功结果

一个自动化测试项只有同时满足以下条件才算通过：

- 结构化报告中的测试入口集合与测试计划要求的当前入口集合精确一致，没有漏跑或多跑。
- 实际执行数大于 `0`，跳过数、失败数和错误数都等于 `0`。
- 实际命令、工作目录、测试入口和登记内容一致。
- 退出码为 `0`。
- 执行记录绑定的产品代码哈希和测试代码哈希与当前代码一致。

一个主题的全部自动化或混合测试项通过后，AI 根据机器执行事实生成 `qa/<主题文件标识>_测试结果.md`。没有前置主题或前置主题自动化部分已经完成的独立主题，可以先生成自己的结果，不必等待其他无关主题。

### 6.1 结果文档逐字段对应机器记录

正式结果文档中的机器记录编号、工作目录、测试入口、执行命令、超时（秒）、运行环境、开始时间、结束时间、时长（秒）、退出码、输出摘要、输出哈希、输出字节数、报告适配器、报告哈希、报告字节数、精确匹配测试入口、实际执行数、跳过数、失败数、错误数、产品代码哈希和测试代码哈希，必须逐字段与 State Snapshot（状态快照）中当前有效的执行记录一致。

- 测试入口和执行命令使用紧凑单行 JSON 数组；输出摘要使用 JSON 字符串，保留机器记录中的换行、引号和转义。
- 运行环境固定写成 `平台=<platform>；可执行文件=<executable>`；`platform` 是平台标识，`executable` 是实际可执行文件。
- 逐字段抄写，不改格式、不取整、不截短哈希、不合并字段。
- 任一机器字段没有记录时，不生成通过结果，必须重新执行。
- 文档里的“实际结果”只解释这些机器事实证明了什么，不能替换或改写机器事实本身。

混合测试的正式结果只能写“自动化测试结果：通过”和“人工验收状态：待主题验收”，不能提前写整体验收通过。

## 7. 失败、超时和阻塞

测试失败、超时、环境无法启动或前置测试项未通过时：

- 不生成当前主题的正式测试结果。
- 清除该测试项以前的当前成功记录，避免状态和最新执行事实冲突。
- 删除已经失效的 `qa/<主题文件标识>_测试结果.md`。
- Journal 只记录测试项、命令、时间、退出码或失败原因，不保存完整输出。
- 同一主题中依赖失败项的后续测试项停止；依赖失败主题的后置主题也停止；其他独立主题继续执行。

失败时的终端输出只用于当次诊断：帮助 AI 和用户找出失败原因。它不能被改写、节选或重新解释成通过结论，也不能作为正式结果写进 `qa/<主题文件标识>_测试结果.md`。退出码不是 `0` 就是没通过，不存在“基本通过”。

AI 调查失败原因并向用户说明事实。用户确认后再执行：

- 产品代码错误或实现遗漏：`workflow return --to impl`。
- 测试代码错误：`workflow return --to test_code`。
- 测试范围、方式或依赖设计错误：`workflow return --to test_plan`。
- 验收条件无法判断，但产品设计已经明确：`workflow return --to acceptance_plan`。
- 产品行为、规则或需求没有定义：`workflow return --to spec`。
- 临时环境问题：留在 `test_execution`，环境恢复后重新执行。

退回时必须写明受影响主题和原因。只有能从产品行为、代码符号或路径、共享状态、输入输出约定、数据约定或明确调用关系证明直接影响的主题，才列为受影响主题。仅仅在同一目录、同一文件或“可能有影响”不算证据。无法判断时由用户决定。

## 8. 主题重测范围

修正代码或测试后，只重新执行当前主题和用户确认的直接受影响主题。没有直接影响证据的其他主题保留当前有效结果，`workflow test run` 不重复运行这些有效记录；最终由 `regression_test`（最终全量回归阶段）统一检查。

修改共享测试运行器、共享测试配置或统一测试入口时，当前全部主题的测试执行记录都失效。

## 9. 人工验收交接

测试方式为“自动化测试 + 人工验收”时，AI 必须在正式测试结果中写清：

- 用户要看什么对象。
- 用户怎样操作或观察。
- 自动化已经证明了哪部分。
- 还需要用户明确回答什么。
- 人工结果写入哪个 `acceptance/<主题文件标识>_验收结果.md`。

本阶段只准备交接，不替用户回答，也不写人工验收通过。

## 10. 完成前对抗性审查

AI 在调用 `workflow gate test_execution` 前必须逐项检查：

- 每个自动化或混合测试项是否都有当前有效执行记录。
- 每个 `TC` 的结构化报告是否证明入口集合精确一致、实际执行数大于 `0`、跳过数/失败数/错误数为 `0`，且退出码为 `0`。
- 正式测试结果的机器事实字段是否逐字段与当前执行记录一致。
- 正式测试结果是否与测试计划和测试代码标识一致。
- 是否有失败、超时、阻塞或未执行项却写成通过。
- 是否把失败输出重新解释成了通过结论。
- 混合测试是否把人工验收部分错误写成已经通过。
- `qa/索引.md`、局部上下游链接和 `需求交付追踪表.md` 是否指向当前结果。

程序门禁负责检查固定字段、文件、编号、测试入口、命令、工作目录和状态一致性。AI 和用户负责判断实际结果、证据和人工验收说明是否真的能证明验收条件。

测试执行或门禁失败时，一次列出全部可以独立确认的问题；依赖前置结果而不能继续的检查写“未检查”，并说明被哪个问题阻断。输出末尾只给一条当前可执行的下一命令，写清由谁执行、会修改哪些状态或文件、什么结果算成功，以及成功后进入哪个阶段。

最终全量回归不使用本阶段命令。到 `regression_test`（最终全量回归阶段）时，先执行 `workflow gate regression_test --discuss-done` 完成讨论门，再只执行 `workflow gate regression_test`；第二条命令会自动运行项目统一测试入口并校验机器事实。不存在 `workflow regression` 命令，`workflow test run` 只用于本节的主题测试。
