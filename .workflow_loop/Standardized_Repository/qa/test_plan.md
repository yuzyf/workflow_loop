# 测试计划阶段规范提示词

## 1. 阶段职责

测试计划阶段只做测试覆盖审查，不执行本次需求的正式测试。

它必须从已经确认的验收条件出发，检查后续测试是否有办法判断每条验收条件通过或不通过，并确定本次修改需要覆盖的针对性回归范围。

它不能重新确定验收主题，不能新增产品规则，不能把测试计划写成测试结果。

## 2. 测试覆盖规则

- 本次工作流的每个验收主题都必须有同名的 `qa/<topic>_plan.md`。
- 每条验收条件都必须至少关联一个测试项。
- 测试项使用稳定编号和直白名称，例如 `TC-01 启动后生成工作流状态`。
- 一个测试项可以覆盖多条验收条件，但必须在每条验收条件下明确写出该测试项的覆盖关系。
- 测试项不是测试结果，不得在测试计划中填写通过、失败或实际执行时间。
- 测试项有前置依赖时，必须写清前置测试项和执行顺序；没有依赖的测试项不要求排序。
- 不强制使用“正常、异常、边界”等固定测试分类，分类只在当前验收条件和风险确实需要时使用。

## 3. 测试计划文档结构

每份 `qa/<topic>_plan.md` 必须包含以下部分：

```markdown
# <主题>测试计划

- 工作流编号：<workflow_id>
- 上游验收计划：[<主题>验收计划](../acceptance/<topic>_plan.md)

## 1. 验收条件覆盖

| 验收条件链接 | 测试项 | 验证方向 | 预期观察结果 | 证据要求 |
|---|---|---|---|---|
| [AC-01：完成条件](../acceptance/<topic>_plan.md#ac-01) | <a id="tc-01"></a>[TC-01 直白测试名称](#tc-01) | 检查什么 | 应观察到什么 | 保留什么证据 |

## 2. 针对性回归范围

## 3. 测试条件要求

## 4. 未决测试条件

## 5. 上下游文档

- 上游验收计划：...
- 下游实施计划：...
- 下游测试结果：...
```

具体测试命令、测试文件、测试数据和证据位置尚未确定时，必须写“实施后确认”，不得自行编造。

## 4. 各部分的写作边界

### 验收条件覆盖

只写验收条件链接、测试项、验证方向、预期观察结果和证据要求。验收条件的产品背景、产品规则和完整正文留在验收计划中。

验收条件链接必须指向对应验收计划中的具体 `AC`；测试项链接必须使用稳定的小写锚点，例如 `TC-01` 使用 `#tc-01`。这样 `traceability.md` 才能从验收条件直接跳到具体测试项。

### 针对性回归范围

只写本次修改直接影响的已有行为，以及为什么需要回归。与本次修改无直接关系的旧功能不在这里重复列出；所有主题完成后由最终全量回归统一检查。

### 测试条件要求

写测试需要具备的环境、样本、权限、外部服务或其他前置条件。普通已知产品行为可用可重复测试数据；真实外部行为必须使用真实样本或真实环境，不能只用 mock 数据。

### 未决测试条件

每项未决内容必须标明属于哪一种：

- 当前已经确定，但尚未开始执行。
- 只有实施代码完成后才能确定。
- 验收条件本身无法验证，需要退回 `acceptance_plan`。

不能把“实施后才能确定”写成测试失败，也不能用它掩盖无法验证的验收条件。

## 5. 全局检查顺序

AI 必须先读取全部验收主题、产品设计、代码设计、当前代码、已有测试和修改前基线，先向用户说明全局覆盖是否完整。用户确认全局范围没有遗漏后，再逐个主题讨论测试项。

修改前基线由测试计划门禁执行项目统一测试入口建立。该运行结果只记录在 State Snapshot（状态快照）和 Journal（追加式过程日志）中，不写成测试计划结果，也不生成额外的基线文档。项目还没有代码或已有测试时，状态记录为“暂无基线”，不把它当作测试失败。

## 6. 问题退回规则

- 产品行为没有定义：返回 `spec`。
- 产品行为已定义但验收条件无法判断：返回 `acceptance_plan`。
- 真实外部技术行为未知：返回 `spike`。
- 只有实施后的命令、文件、数据或证据位置未知：留在测试计划中，标记“实施后确认”。

## 7. 固定产出与索引

测试计划阶段必须产出：

- `qa/<topic>_plan.md`：每个验收主题一份。
- `qa/index.md`：只做测试计划、测试结果和最终全量回归的目录导航，不保存 AC、TC、结果的第二份映射，不保存测试执行顺序。

同时只更新 `traceability.md` 的“测试项”列。测试结果、实施记录和验收结果列保持初始状态，交给后续阶段更新。

## 8. 修改前全量测试门禁

项目必须提供一个统一的全量测试入口。已有稳定命令或脚本时优先复用；没有时由项目补充，例如 `scripts/test_all.sh`。门禁只执行这个已确认的入口，不猜测命令，不在门禁执行时临时创建脚本。

入口退出码为 `0` 才表示通过；非 `0` 表示测试失败或无法执行。项目还没有代码或已有测试时可以记录“暂无基线”；除此之外，修改前全量测试通过后才能继续，有失败时暂停，由用户决定如何处理。实施代码完成后必须重新执行最终全量回归，不能复用修改前基线代替最终结果。

## 9. 禁止事项

- 不能复制验收计划的产品背景、产品目标、产品规则和验收条件正文。
- 不能新增、删除、改名或拆分验收主题。
- 不能用模糊测试项覆盖全部验收条件。
- 不能在测试计划阶段填写测试通过、测试失败或最终回归结果。
- 不能把具体测试工具或代码层级当成测试范围本身。
