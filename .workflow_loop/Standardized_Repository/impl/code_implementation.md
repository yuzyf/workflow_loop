# 代码开发规范

## 1. 文件定位

本文件只规定“代码应该怎么写”。它不是实施计划模板，也不是实施阶段的流程规范。

- 代码计划、代码实施和代码结果文档的章节、字段和链接要求，写在 `Template_Repository/impl/impl.md`。
- 实施阶段怎样确认代码计划、连续完成实施、确认代码结果和返回上游，写在 `Standardized_Repository/impl/impl.md`。
- 代码实际怎样组织、怎样处理依赖、状态和错误，按本文件执行。

本文件只使用本项目已经确认的产品设计、验收条件、有效穿刺结论、现有代码设计、代码计划和项目代码约定，不引用其他项目的流程文件作为本项目规则。没有现有代码设计时，以代码计划中的最低实现设计为本轮编码约束。

## 2. 每段代码必须有来源

新增或修改的代码必须能回答下面三个问题：

1. 它实现了哪个产品行为？
2. 它对应哪条验收条件？
3. 它落在哪个实施主题的哪个文件、类或函数中？

如果一段代码无法对应产品行为、验收条件或明确的系统约束，不写入代码。不要因为“以后可能用到”提前增加接口、配置、抽象层或通用工具。

代码计划确认后，AI 按计划连续实施，不为每个文件或函数增加用户确认。需要改变计划文件集合、接口、核心逻辑、数据状态、错误结果或用户可见结果时，先停止实施并重新确认代码计划，不能先改完再补写计划。

## 3. 模块和接口怎么写

模块指有明确调用方式和内部实现的函数、类或代码包。接口指调用方为了正确使用模块必须知道的内容，不只是函数参数类型，还包括输入限制、返回结果、执行顺序、错误情况和必要配置。

- 一个模块对外只暴露完成职责所需的最小接口。
- 接口要写清输入、输出、不变量、顺序要求和错误行为；不能让调用方阅读实现代码才能知道怎么用。
- 复杂的判断、状态变化和错误转换放在模块内部，对外提供简单入口。
- 不新增只有一层转发的模块。删除该模块后，如果复杂度只是转移到多个调用方，才说明它有保留价值。
- 不把测试需要的私有函数直接变成公共接口。先检查公共接口是否能表达和验证真实行为。

## 4. 依赖、接缝和适配器怎么写

接缝指可以替换一部分行为而不修改调用方的位置。适配器指在接缝处接入具体实现的代码，例如文件系统、网络接口或第三方服务的具体调用。

- 只有确实存在两种实现、两种运行环境或生产实现与测试替身时，才增加接缝和适配器。
- 只有一种实现时，不为了形式上的“可扩展”增加接口、工厂或适配器层。
- 会变化或需要替换的依赖由调用方传入；不会变化且没有替换理由的依赖，不强行注入。
- 文件、网络、第三方服务等外部交互集中在适配器中；产品判断和业务规则不要散落在多个外部调用点。
- 测试替身只替换真实外部依赖，不用 mock 掩盖模块内部的调用关系。

## 5. 逻辑、数据和副作用怎么写

- 负责判断或计算的函数返回明确结果，不通过修改全局变量或隐藏对象状态传递结果。
- 写文件、发请求、更新状态等副作用要在代码中有明确位置，调用关系可以追踪。
- 同一条产品规则、状态转换或错误映射只在一个负责模块中定义；其他模块调用它，不复制一份近似逻辑。
- 一个函数不要同时承担无关的输入解析、业务判断、持久化和输出格式化；这些职责确实属于同一条用户行为链路时，才放在同一模块内。
- 数据结构表达真实业务含义。不要用多个布尔值或无含义字符串拼出调用方必须猜测的状态。

## 6. 错误和边界怎么写

- 对无效输入、文件不存在、外部接口失败、状态不允许等情况，明确写出处理结果。
- 不能静默吞掉异常，也不能把失败伪装成成功或空结果。
- 在模块边界把底层错误转换成调用方能判断的错误；保留足够上下文，能定位是哪个输入和哪个动作失败。
- 不在每一层重复处理同一个错误。由最接近错误来源的模块补充事实，由用户可见入口决定最终输出方式。
- 新增边界情况时，必须有对应的验收条件或已经确认的系统约束；没有依据就返回上游讨论。
- 开发检查或门禁需要报告失败时，底层代码保留位置、预期、实际和证据，不能把可确认的格式、路径或文件差异压缩成笼统字符串；命令入口再据此说明影响和改法。

## 7. 修改范围和代码风格

- 先遵守同一目录和同一模块已有的命名、异常、日志、配置和测试写法；只有现有写法无法满足已确认结果时才改变。
- 名称要说明业务角色或动作。避免使用无法判断含义的 `data`、`handler`、`manager`、`utils` 等泛名，除非项目已有明确约定。
- 修改应集中在完成当前验收主题所需的代码路径，不顺手重命名、搬目录或重构无关模块。
- 改公共接口时，必须同时检查所有调用方、状态变化、错误处理和测试；不能只改定义处。
- 注释只解释代码本身无法表达的原因、约束或取舍，不重复翻译代码。

## 8. 开发检查怎么选

- 优先运行项目已有的语法、类型、静态检查和与修改位置直接相关的局部检查。
- 开发检查从用户或调用方能触达的公共入口观察真实结果，不用固定返回值或无依据替身掩盖产品逻辑。
- 开发检查结果只说明实施期间发现的事实，不写成正式测试通过。代码结果确认后，在 `qa`（测试验证）阶段开始时根据验收计划、实施记录和真实代码确认测试范围，随后连续完成测试代码、任务登记、执行和结果。

## 9. 写完代码后的自检

完成一个代码切片后，逐项检查：

- 从代码入口到用户可观察结果的路径是完整的。
- 每个新增模块都有明确接口，复杂度没有被转移给调用方。
- 依赖、状态变化和副作用的位置可以从调用关系中找到。
- 错误不会被吞掉，失败结果不会被当成成功结果返回。
- 代码没有实现未确认的产品规则，也没有留下无法解释的占位抽象。
- 真实文件、覆盖本轮差异的最终文件行号范围和逻辑已经写入代码实施记录和代码结果。
- 启用表时实施记录由程序按表生成，固定字段自动同格；文档模式手写时“工作流编号”“验收主题”等固定字段的标签和值都在同一行。
- 门禁输出已列出全部可独立确认的问题；依赖不成立的检查明确为“未检查”并写真实依赖，所有诊断后只有一条可执行的下一步命令。
