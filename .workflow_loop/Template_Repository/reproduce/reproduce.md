# 缺陷复现文档模板

本模板定义缺陷复现阶段最终保存的两类文档：

- `bug/缺陷_<缺陷文件标识>.md`
- `bug/索引.md`

缺陷记录的标题和正文保留用户确认的完整中文显示名称；文件名使用程序生成并保存的稳定中文文件标识（只保留中文、字母、数字、下划线、连字符，其它字符替换为下划线），两者可能不同。

本模板只规定文档结构和内容边界。怎样调查、运行、复现和确认根因，由缺陷复现阶段工作规范说明。

## 一、缺陷记录模板

```markdown
# 【缺陷】<缺陷名称>

- 工作流编号：<当前 workflow_id，也就是当前工作流编号>
- 复现状态：已复现
- 根因状态：已确认
- 验收主题：<修复后用户应该得到的唯一结果名称>

启用工作记录表时本记录由程序按 bug_record 表生成（“缺陷信息”行清单 + 叙述栏“缺陷说明”“真实复现条件”“根因证据”“修复仍存在的不确定性”“修复与验收结果”），“工作流编号”“验收主题”来自表固定栏目。文档模式手写时固定字段标签和值必须写在同一行。

## 1. 缺陷现象

<用户在什么操作中看到了什么问题。>

## 2. 真实复现条件

- 运行环境：<系统、版本、配置、设备或外部服务条件>
- 真实输入：<真实文件、请求、状态或操作；敏感内容可以脱敏，但不能改造成虚构样本>

## 3. 复现步骤

1. <从真实入口开始的操作>
2. <直到缺陷出现>

## 4. 实际结果

<实际输出、状态、日志、界面或错误。>

## 5. 期望结果

<根据已确认产品设计，本来应该得到什么。>

## 6. 根因

- 根因说明：<导致缺陷的具体判断、状态、数据、配置或外部行为>
- 根因位置：<具体代码文件和符号，或配置、数据、外部服务位置>
- 根因证据：<运行输出、日志、测试、代码路径或用户确认怎样证明这个结论>

## 7. 修复仍存在的不确定性

<没有则写“暂无”；有则逐项写清未知事实，供后续穿刺讨论。>

## 8. 修复与验收结果

本节由后续阶段按实际结果追加。缺陷复现阶段不得填写，也不能改写前七节。

- 主题测试和主题验收通过后，追加实施记录、测试结果和主题验收结果链接，最终状态写“主题验收通过，待全量回归”。
- 最终全量回归失败后，追加“统一测试入口执行失败，详情见当前工作流 `state.json` 和 `journal.jsonl`”，最终状态写“回归失败，重新处理中”。
- 最终全量回归通过且用户完成整体验收后，追加“统一测试入口已通过，详情见当前工作流 `state.json` 和 `journal.jsonl`”以及“用户已确认整体验收”，最终状态写“已修复并验收”。
- 同一阶段重复确认时更新原阶段记录，不能重复追加相同内容。
```

## 二、缺陷索引模板

```markdown
# Bug 索引

| Bug 记录 | 现象 | 根因 | 状态 |
|---|---|---|---|
| [<缺陷名称>](./缺陷_<缺陷文件标识>.md) | <一句话现象> | <一句话根因> | 根因已确认 |
```

## 完成前检查

- 工作流编号是否与当前工作流一致。
- 是否明确写“复现状态：已复现”和“根因状态：已确认”。
- 是否使用真实场景和真实输入，而不是编造样本。
- 实际结果与期望结果是否明确不同。
- 根因是否写到具体位置，并有别人可以复核的证据。
- 一份缺陷记录是否只对应一个验收主题。
- `bug/索引.md` 是否链接本次缺陷记录。
