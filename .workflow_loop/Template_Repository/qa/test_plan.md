# 测试计划文档模板

本模板定义测试计划阶段最终生成的文档：

1. `qa/<topic>_plan.md`：每个验收主题一份测试计划。
2. `qa/index.md`：继承验收主题关系，并保存测试计划和测试结果入口。

本模板只规定文档怎样写，不规定 AI 怎样调查、讨论和决定测试范围。测试计划阶段的工作方法由对应的阶段规范说明。

## 一、`qa/<topic>_plan.md` 模板

```markdown
# <主题>测试计划

- 工作流编号：<workflow_id>
- 上游验收计划：[<主题>验收计划](../acceptance/<topic>_plan.md)

## 1. 验收条件覆盖

| 验收条件链接 | 测试项 | 前置测试项 | 测试方式 | 验证方向 | 预期观察结果 | 证据要求 |
|---|---|---|---|---|---|---|
| [AC-01：<验收条件名称>](../acceptance/<topic>_plan.md#ac-01) | <a id="tc-01"></a>[TC-01 <直白测试名称>](#tc-01) | 无或当前主题内的 TC 编号 | 自动化测试 \| 人工验收 \| 自动化测试 + 人工验收 | <准备检查什么> | <应观察到什么> | <保留什么证据> |

## 2. 针对性回归范围

- <本次修改直接影响的已有行为，以及需要回归的原因>
- <没有针对性回归时写“暂无”，并说明由最终全量回归统一检查>

## 3. 测试条件要求

- <需要的环境、样本、权限、外部服务或前置状态>
- <尚未能确定的命令、测试文件、测试数据或证据位置写“实施后确认”>

## 4. 未决测试条件

- <当前已经确定但尚未执行的内容，或“暂无”>
- <只有实施代码完成后才能确定的内容，或“暂无”>
- <验收条件无法判断时，写清需要返回验收计划阶段确认的内容，或“暂无”>

## 5. 上下游文档

| 关系 | 文档 | 说明 |
|---|---|---|
| 上游 | [<主题>验收计划](../acceptance/<topic>_plan.md) | 本测试计划依据的验收条件 |
| 全局 | [需求交付追踪表](../traceability.md) | 查看完整交付关系和状态 |
| 下游 | <实施计划路径> | 实施完成后使用本测试计划执行测试 |
| 下游 | <主题测试结果路径；纯人工验收时写“无自动化测试结果，转主题验收”> | 记录自动化测试结果和证据，或明确转主题验收 |
```

## 二、`qa/index.md` 模板

```markdown
# 测试计划索引

## <workflow_id>

### 主题关系

| 展示顺序 | 验收主题 | 前置主题 | 验收计划 | 测试计划 | 测试结果 |
|---|---|---|---|---|---|
| 1 | <主题 A> | 无 | [主题 A 验收计划](../acceptance/<主题 A>_plan.md) | [主题 A 测试计划](./<主题 A>_plan.md) | [主题 A 测试结果](./<主题 A>_result.md)，或“无自动化测试项” |
```

## 三、内容边界

- 验收条件覆盖表只写测试怎样覆盖已经确认的验收条件，不重复产品背景、验收目标和验收条件正文。
- 测试项必须有稳定编号、直白名称和测试方式。
- `前置测试项`只写当前主题中必须先通过的直接 `TC`；没有依赖写“无”，不重复间接依赖。
- 一个验收条件可以对应多个测试项；一个测试项只对应一条主要验收条件。多个测试项需要相同准备过程时，后续测试代码使用 fixture 共享。
- 测试方式只能是“自动化测试”“人工验收”或“自动化测试 + 人工验收”。能自动化判断的内容不能为了省事写成纯人工验收。
- 纯人工验收主题不生成 `qa/<topic>_result.md`；主题计划的下游位置写“无自动化测试结果，转主题验收”，`qa/index.md` 的测试结果列写“无自动化测试项”。
- 测试计划不记录实际通过、失败、执行时间或测试结果。
- 测试命令、测试文件、测试数据和证据位置尚未确定时，写“实施后确认”，不得编造。
- `qa/index.md` 继承 `acceptance/index.md` 的主题关系，只做主题关系和测试文档入口，不复制验收条件、测试项详情、测试覆盖范围或测试执行结果。
- `展示顺序`和`前置主题`必须与 `acceptance/index.md` 一致；测试项之间的执行顺序写在各主题测试计划中。

## 四、完成前检查

- 每个验收主题是否都有同名的 `qa/<topic>_plan.md`。
- 每条验收条件是否至少关联一个测试项。
- 每个测试项是否有稳定编号、直白名称和具体验证方向。
- 每个测试项是否写明合法的测试方式。
- 前置测试项是否存在、没有循环，也没有重复写间接依赖。
- 每条上下游链接是否指向真实或预期的对应文档位置。
- 是否没有写入测试通过、测试失败或实际测试结果。
- 是否没有把产品规则、实施步骤或代码实现写进测试计划。
