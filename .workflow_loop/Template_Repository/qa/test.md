# 主题测试结果文档模板

本模板只定义 `qa`（测试验证）内部真实执行完成后，由 AI 根据程序事实写入的 `qa/<主题文件标识>_测试结果.md` 结构。
它不是测试计划，也不是测试代码模板。测试命令、测试函数和测试结果必须来自本次 QA 的当前机器记录，不能根据计划、局部开发检查或历史通过记录猜测。

文档标题保留完整中文主题名称；文件名使用程序生成并保存的稳定中文文件标识，与该主题的验收计划和测试计划使用同一个标识。

```markdown
# 【主题测试结果】<主题名称>

- 工作流编号：<workflow_id>
- 验收主题：<主题名称>
- 自动化测试结果：通过
- 人工验收状态：无需人工验收 | 待主题验收
- 测试完成时间：<实际完成时间>

“工作流编号”“验收主题”“自动化测试结果”“人工验收状态”和“测试完成时间”是固定字段；每个标签和值必须写在同一行。标签后换行再写值视为固定字段缺值，不能由下一行内容补足。
```

## 一、机器事实字段

“机器记录编号”“工作目录”“测试入口”“执行命令”“超时（秒）”“运行环境”“开始时间”“结束时间”“时长（秒）”“退出码”“输出摘要”“输出哈希”“输出字节数”“报告适配器”“报告哈希”“报告字节数”“精确匹配测试入口”“实际执行数”“跳过数”“失败数”“错误数”“产品代码哈希”和“测试代码哈希”都是程序执行时记录的机器事实。它们只能从 State Snapshot（状态快照）中当前有效的执行记录逐字段抄写。

- 每个字段必须与程序记录完全一致，包括时间格式、秒数和哈希值。
- 测试入口和执行命令使用紧凑单行 JSON 数组，不增加空格；输出摘要使用 JSON 字符串，以便保留换行和引号。
- 运行环境固定写成 `平台=<platform>；可执行文件=<executable>`，其中 `platform` 是平台标识，`executable` 是实际可执行文件。
- 不四舍五入时长，不缩短哈希，不改写工作目录写法。
- 任一机器字段没有记录时，当前结果不能写成通过，必须重新执行。
- “机器记录编号”是后续主题验收引用这次执行的唯一依据，必须填写具体编号，不能写“见状态文件”。

“实际结果”是 AI 写给人看的解释：说明这些机器事实证明了验收条件的哪一部分。它只能解释机器事实，不能替换或改写机器事实。退出码是 `0` 时不能把实际结果写成失败；输出摘要显示失败时也不能把实际结果写成通过。

## 二、完成前检查

- 只在结构化报告证明测试入口集合精确一致、实际执行数大于 `0`、跳过数/失败数/错误数全部为 `0`、进程退出码为 `0`，且记录绑定当前产品代码和测试代码时生成正式结果。
- 每个 `TC` 的全部机器事实字段是否与程序登记的当前测试执行记录逐字段一致。
- `TC`、测试入口和命令是否与测试计划和当前执行记录对应。
- “实际结果”是否只解释机器事实，没有替换、改写或补充程序没有记录的内容。
- 混合测试必须保留人工验收交接内容；不能把自动化通过写成整条验收条件已经通过。
- 不能写“功能正常”“符合预期”这类没有实际观察内容的结论。
- 测试失败、超时、阻塞或未执行时，不生成“自动化测试结果：通过”的正式结果。
- 不在本结果文档中新增产品规则、验收条件或代码实现方案。
- 本文档通过程序校验后，AI 汇总测试范围、机器记录、自动化结果和人工待验收边界，用户只在 QA 结束时确认一次结果；第三道门不重新运行测试。
