# 主题验收结果文档模板

本模板定义 `acceptance/<主题文件标识>_验收结果.md` 最终记录什么。只有当前主题的全部验收条件都已经通过时，才生成正式结果文件；未通过、无法验证或受到阻塞时，不生成正式结果。

文档标题保留完整中文主题名称；文件名使用程序生成并保存的稳定中文文件标识，与该主题的验收计划使用同一个标识。

```markdown
# 【主题验收结果】<主题名称>

- 工作流编号：<当前 workflow_id>
- 验收主题：<主题名称>
- 验收结果：通过
- 验收完成时间：<实际时间>

## 1. 验收依据

| 关系 | 文档 | 说明 |
|---|---|---|
| 上游 | [主题验收计划](./<主题文件标识>_验收计划.md) | 本主题全部验收条件 |
| 上游 | [主题测试结果](../qa/<主题文件标识>_测试结果.md) | 自动化或混合主题使用；纯人工主题整行改为“无自动化测试项” |
| 上游 | [实施记录](../impl/<主题文件标识>_实施记录.md) | 本主题实际实施内容 |
| 全局追踪 | [需求交付追踪表](../需求交付追踪表.md) | 当前验收条件的完整上下游关系 |

## 2. 验收条件结果

### AC-01：<验收条件名称>

- 验收方式：自动化测试 | 人工验收 | 自动化测试 + 人工验收
- 验收条件：<写出具体条件，并链接到主题验收计划中的对应位置>
- 自动化依据：<对应 qa/<主题文件标识>_测试结果.md 中的测试项和结果；纯人工验收写“不适用”>
- 机器测试记录编号：<作为本条依据的精确机器执行记录编号，多条用顿号分开；纯人工验收写“不适用”>

#### 人工验收步骤

- 验收对象：<用户实际检查什么>
- 开始前条件：<执行验收前必须具备的状态或数据>
- 操作步骤：
  1. <具体操作>
  2. <具体操作>
- 观察内容：<用户实际观察什么>
- 预期结果：<验收条件要求看到的明确结果>
- 用户需要回答：<要求用户确认的具体问题>

纯自动化验收条件不需要人工操作时，本小节写“不适用”。

- 用户实际回答：<用户的原话；纯自动化写“不适用”>
- 人工确认：通过 | 不适用
- 确认时间：<程序记录的确认时间；纯自动化写“不适用”>
- 实际结果：<自动化结果、人工观察结果或两者组合>
- 判定：通过
- 验收证据：<实际观察说明、测试记录、运行输出、截图或文件；没有独立文件时写具体观察说明>
- 验收记录编号：<State Snapshot 中本条验收记录的 record_id>

## 3. 上下游文档

| 关系 | 文档 | 说明 |
|---|---|---|
| 上游 | [主题验收计划](./<主题文件标识>_验收计划.md) | 验收标准来源 |
| 上游 | [主题测试结果](../qa/<主题文件标识>_测试结果.md) | 自动化或混合主题使用；纯人工主题整行改为“无自动化测试项” |
| 上游 | [实施记录](../impl/<主题文件标识>_实施记录.md) | 被验收的实际实现 |
| 全局追踪 | [需求交付追踪表](../需求交付追踪表.md) | 本主题在完整交付链路中的位置 |
| 下游 | 最终全量回归 | 所有主题通过后执行 |
```

## 一、两种记录编号

一条验收条件可能同时引用两类程序记录，两者不能混写：

- **机器测试记录编号**：`qa`（测试验证）内部正式执行产生的记录编号。它指向一次精确的机器执行，包含当时的命令、工作目录、时间、退出码和输出哈希。自动化和混合验收条件必须列出作为依据的全部编号；一条验收条件由多次执行共同证明时，把编号都写出来，不只写最后一次。
- **验收记录编号**：本阶段调用 `workflow acceptance record` 后，程序为这条验收条件保存的记录编号。它是这条结论本身的编号。

纯人工验收条件没有机器测试记录编号，写“不适用”；但仍必须有验收记录编号。

不能写“见状态文件”“见测试结果”代替具体编号，也不能引用已经失效的旧执行记录。

## 二、人工条件必须保留的内容

需要用户判断的验收条件，必须原样保留：

- 用户实际回答：写用户的原话，不改写成“确认通过”，不概括成结论。
- 实际结果：用户实际观察到什么。
- 验收证据：可以复核的观察说明、输出、截图或文件。
- 确认时间：程序记录的时间。
- 验收记录编号：程序保存的记录编号。

这五项必须和 State Snapshot 中当前有效的验收记录一致。

## 三、总结果只有“通过”

文档头部的“验收结果”只允许写“通过”。

不允许出现“部分通过”“基本通过”“带条件通过”“通过（待观察）”“遗留问题不影响通过”等写法。只要有一条验收条件未通过、无法验证或受到阻塞，就不生成这份正式结果文件，改为返回对应阶段处理。

## 四、完成前检查

- 是否绑定当前工作流编号和当前验收主题。
- 是否覆盖验收计划中的全部适用验收条件，没有遗漏或增加条件。
- 每条条件是否写明验收方式、实际结果、判定、验收证据和验收记录编号。
- 自动化和混合条件是否写出作为依据的机器测试记录编号，且这些记录当前有效。
- 实际结果、验收证据、用户回答、确认时间和记录编号是否与 State Snapshot 完全一致。
- 自动化验收条件是否引用当前有效的主题测试结果。
- 需要人工验收时，是否写清验收对象、开始条件、操作、观察内容和预期结果。
- 人工条件是否记录用户原话和程序确认时间，且内容与当前有效程序记录一致。
- 纯自动化条件是否把用户回答、人工确认、确认时间和机器测试记录编号以外的人工字段写为“不适用”。
- 是否所有条件都明确通过，总结果固定为“通过”，没有出现部分通过、基本通过或带条件通过。
- 是否在存在未通过、无法验证或阻塞时错误生成了正式结果文件。
- 是否用“功能正常”“符合预期”等空泛结论代替实际结果。
- 是否混入新的产品规则、代码方案或实施步骤。
