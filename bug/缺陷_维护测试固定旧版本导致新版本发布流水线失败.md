# 【缺陷】维护测试固定旧版本导致新版本发布流水线失败

- 工作流编号：2026-08-09-1457-bugfix
- 复现状态：已复现
- 根因状态：已确认
- 验收主题：发布版本变化后维护版本判断测试仍按当前版本通过

## 1. 缺陷现象

发布 `0.3.0` 后，持续集成（CI，自动执行构建和测试的环境）安装当前代码并运行全量测试。维护命令版本判断测试失败，导致发布流水线在发布包之前停止。

## 2. 真实复现条件

- 运行环境：项目当前包版本为 `0.3.0`；Python 3.12；使用项目虚拟环境执行 `python -m pytest`。
- 真实输入：`tests/test_maintenance.py::test_update_version_resolution_accepts_only_matching_stable_releases` 中模拟 PyPI（Python 包索引）和 GitHub Release（GitHub 发布记录）的版本均为 `0.2.0`。

## 3. 复现步骤

1. 在项目当前版本为 `0.3.0` 的工作区安装开发依赖。
2. 执行 `PYTHONPATH=src .venv/bin/python -m pytest -q tests/test_maintenance.py::test_update_version_resolution_accepts_only_matching_stable_releases`。
3. 测试调用 `workflow_loop.cli._resolve_update_version`（解析可更新正式版本的函数），并传入模拟的 `0.2.0` 发布信息。

## 4. 实际结果

测试失败，异常为：`目标版本 0.2.0 低于电脑全局命令版本 0.3.0，不允许降级`。单项测试退出码为 1。

## 5. 期望结果

测试应使用当前包版本作为“同版本正式发布”样本，验证默认选择和显式选择同版本均通过，同时继续验证低版本、预发布版本、缺失版本和来源不一致时被拒绝。版本保护规则本身不应放宽。

## 6. 根因

- 根因说明：测试夹具把 PyPI 版本、GitHub 标签和断言固定为发布前的 `0.2.0`。发布后当前版本变为 `0.3.0`，夹具输入因此变成低于当前版本的降级场景，而测试仍把它当作可通过的同版本场景。
- 根因位置：`tests/test_maintenance.py` 的 `test_update_version_resolution_accepts_only_matching_stable_releases`；版本比较位置为 `src/workflow_loop/cli.py` 的 `_resolve_update_version`。
- 根因证据：在当前工作区真实运行该单项测试得到上述异常；`_resolve_update_version` 使用 `project_mod.PRODUCT_VERSION`（项目当前包版本）比较目标版本，`src/workflow_loop/__init__.py` 当前值为 `0.3.0`。

## 7. 修复仍存在的不确定性

暂无。修复边界已确定为只调整测试夹具的版本来源，不改变版本解析和降级拒绝逻辑。
