# 【功能】编写并执行测试

## 1. 背景

实施代码完成后，Workflow Loop 需要在一个测试验证环节内把验收条件落实为可执行测试计划和真实测试代码，再由程序实际执行并保存机器事实。测试代码存在、AI 口头说明运行过，或者一次全量测试通过，都不能代替当前主题、当前测试项的正式执行证据。

测试计划、测试代码和正式执行在同一个 `qa`（测试验证）环节内按固定内部顺序完成。用户在开始时确认一次测试范围和通过标准，AI 随后复用或修改测试代码、登记并执行正式测试；程序为每个测试项保存独立记录，并直接生成或回填结果文档中的固定机器事实。测试计划是预期范围，不是允许修改测试文件的白名单。全部测试完成后，用户只确认一次最终结果。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 编写自动化测试 | 项目维护者 | 代码实施已经完成，测试验证范围已在本环节开始时确认 | 根据真实产品入口编写或复用测试 | 每个自动化测试项都有可定位、可重复运行的测试代码 |
| 核对测试代码实际覆盖 | 项目维护者、验收人 | 测试范围已经确认，AI 正在准备正式执行 | 由程序和 AI 核对真实产品入口、准备、执行动作和断言 | 错误测试在执行前被阻止，不再增加一次独立用户确认 |
| 执行主题测试 | 项目维护者 | 测试计划、测试代码和执行登记已经通过内部检查 | 按主题和测试项正式运行测试 | 程序保存与当前代码、测试代码和命令绑定的执行记录 |
| 处理混合测试 | 项目维护者、验收人 | 一个条件同时有自动化和人工判断部分 | 先证明自动化部分，再交接人工部分 | 自动化通过不会被误写成整条验收条件通过 |
| 重测受影响主题 | 项目维护者 | 上游计划、代码或测试发生有效变化 | 只重做直接受影响的测试 | 受影响主题获得新记录，独立主题的有效记录按规则保留 |
| 发现额外测试文件 | 项目维护者 | 为证明已确认验收条件需要增加测试文件、夹具、辅助脚本或测试配置 | 直接修改并记录它覆盖的验收条件和正式执行证据 | 不重设测试代码基线、不重新确认测试范围；内部检查按实际测试改动验证 |
| 在原生 Windows 执行 | 项目维护者 | 项目在 Windows PowerShell 终端运行 | 使用 Windows 命令、路径和进程清理方式执行 | 命令无需经过 Unix 命令解释器，超时后不遗留测试进程 |

## 3. 功能边界

### 3.1 支持范围

- 读取当前验收计划、测试计划、代码计划和代码结果、现状架构基线（如有）、产品代码、现有测试和测试配置。
- 根据真实产品入口选择单元、模块、集成、命令、接口或端到端测试。
- 按“准备、执行、验证”组织每个自动化测试，准备必要前提后调用真实产品入口，再检查产品产生的可观察结果和证据。
- 在测试代码中保存验收主题、验收条件、测试项、测试目标、测试入口和产品代码入口的追踪标识。
- 编写测试代码和测试专用配置，并运行直接相关的局部测试作为开发反馈。
- 使用参数数组在 macOS、Linux 和原生 Windows 上正式执行已经登记的主题测试。
- 保存当前有效机器记录和历次执行历史，并生成 `qa/<主题文件标识>_测试结果.md`。
- 从机器记录生成或回填测试结果中的命令、测试入口、机器记录编号、时间、退出码、结构化报告和输出摘要，避免 AI 重复抄写。
- 允许互不依赖且环境隔离的主题受控并行执行。
- 测试验证读取可取得的实际测试改动表，要求每个实际测试文件、辅助脚本或测试配置都有覆盖的验收条件和真实执行证据；不要求实际文件与测试计划文件完全相等。
- 第一次进入测试验证时完整展示“测试计划是预期、额外测试文件可修改、实际测试改动需关联验收条件和正式执行证据”的过程；后续内部检查只展示本次实际测试改动和缺失证据。
- 测试恢复依据与测试门禁分开。Git 工作区、用户主动备份或其它可验证恢复点可以支持整轮作废；没有可靠依据时程序明确说明自动恢复范围，不把它伪装成测试门禁失败。

### 3.2 不支持范围

- 不重新制定产品规则或验收条件；测试范围只在测试验证开始时由用户确认，执行中发现范围有误时返回对应上游。
- 不在测试验证环节修改产品代码。
- 不把局部开发测试写成正式测试结果。
- 不用临时代码、无关成功命令、固定返回值或无依据模拟数据冒充通过。
- 不直接写入目标状态、返回值或结果文件，再断言刚写入的值来代替调用真实产品入口。
- 不用项目统一全量测试入口代替主题测试，也不执行人工验收或最终全量回归。
- 不遍历整个项目或根据 `test`、`spec` 等文件名自动扩大测试代码快照；构建和缓存目录中的同名文件不参与快照。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 开始测试验证环节 | AI 必须使用文件读取和代码搜索工具核对上游文档、真实代码、现有测试和配置，不能只根据文件名猜测试写法。 |
| R2 | 编写自动化或混合测试 | 每个测试函数、测试类或测试场景都要带 `Workflow-Test`（工作流测试追踪标识），写清主题、`TC-xx` 测试项、`AC-xx` 验收条件、测试方式、测试层级、测试目标、测试入口和产品代码入口。 |
| R3 | 一个测试项有多个测试函数 | 每个测试函数只绑定一个主要测试项和一条主要验收条件；同一测试项可以由多个测试函数覆盖，共同准备过程使用测试夹具或辅助函数。 |
| R4 | 编写期间需要反馈 | 可以运行单个测试或单个测试文件等局部测试，但结果不进入正式成功记录，也不生成主题测试结果。 |
| R5 | 测试代码仍符合更新后的计划 | 用户已经确认测试范围时，AI 记录复用决定，不为制造变化而改空格、注释或增加无意义断言；后续正式测试仍须重跑。复用是测试验证环节内的正常成功路径。 |
| R6 | 登记正式测试 | 用户确认测试范围后，AI 在测试工作记录表中为每个 `TC-xx` 测试项填写一行，含测试方式（自动化测试、人工验收或自动化测试 + 人工验收）、对应验收条件、正式目标名称，以及自动化或混合项的运行目录、超时和 `argv`（命令参数数组）。测试方式为人工验收时，命令参数数组、超时秒数和报告适配器可留空；程序读测试方式决定是否执行机器测试，不再把每行写死为自动化测试。程序从测试方式列读取每条测试项的验收方式，不得在构造测试项时硬编码为自动化测试。登记命令核对表完整并一次登记全部任务，不再逐条接受命令行登记参数；登记只保存待执行任务，不运行测试或生成结果。 |
| R7 | 确认登记完整 | 程序在测试验证环节内部检查全部自动化和混合测试项的主题、测试项、入口、命令和依赖已经登记完整，并确认纯人工测试项不需要执行任务。检查不要求用户再次确认，也不运行测试。 |
| R8 | 启动正式测试 | 第一道门通过后，AI 执行统一测试运行命令；程序直接使用参数数组启动，不经过 Shell（命令解释器），也不接受管道、重定向、命令串联或命令替换。Windows 使用 Windows 进程树终止方式，macOS 和 Linux 使用对应进程组方式。 |
| R9 | 建立执行记录 | 每条执行记录只绑定一个 `TC-xx`。同一测试项的多个函数可以合并为一条命令或拆成多条命令；不同测试项不能混用一条记录。 |
| R10 | 判断测试项通过 | 当前测试项的全部测试函数和登记命令都已执行，实际执行的正式目标名称与登记名称一致，执行数量大于 `0`，跳过数量为 `0`，退出码均为 `0`，并绑定执行时的产品代码和测试代码，才建立当前有效成功记录。 |
| R11 | 正式测试失败或超时 | 清除该测试项以前的当前成功记录，不生成通过结果；状态快照只保存当前有效成功记录，追加历史保存全部尝试。 |
| R12 | 生成主题测试结果 | 一个主题的全部自动化和混合测试项通过后，程序从当前机器记录判定每条测试项的执行结论（`passed` 或 `failed`）并填入测试结果表，再据实生成测试文件、测试函数、命令、环境、时间、时长、退出码、实际结果和证据等固定字段与总览结论；任一条 `failed` 时总览为失败，不写死通过。机器记录编号由程序从机器记录回填，先于表校验执行，不作为 AI 必填项；AI 留空不算未填，AI 手填的值会被程序覆盖并提示。AI 只能补充人能理解的说明，不能改写机器事实。 |
| R13 | 检查并确认测试验证结果 | 程序在测试验证环节结束时核对自动化和混合主题的结果文档与当前机器记录一致，并核对纯人工主题的测试计划和人工交接状态。全部主题的验证材料完整后，AI 一次展示测试范围、代码变化、执行结果和仍需人工验收的内容；用户确认一次最终结果后进入主题验收。结果检查和用户确认都不重新运行测试。 |
| R14 | 纯人工或混合主题 | 纯人工主题不生成测试结果文件；混合主题只写自动化通过和“待主题验收”，并说明仍需用户判断什么。 |
| R15 | 修正后确定重测范围 | 只重测当前主题和用户确认的直接受影响主题；不能只因整项目哈希变化删除独立主题记录，更广影响由最终全量回归检查。 |
| R16 | 环境、工具链或统一入口有问题 | AI 调查并给出建议；仍属于已确认测试范围内的临时环境问题时留在测试验证环节处理，需要改变范围或入口时重新确认测试范围或返回更上游。 |
| R17 | 项目需要全量测试入口 | 测试验证环节按 Python、Qt、Node 或其它真实技术栈确认项目专属入口；安装器不下发通用全量脚本，实施前也不强制运行修改前全量测试。 |
| R18 | 编写一个自动化测试 | 必须清楚分开准备、执行和验证：准备只建立运行该场景所需的前提；执行必须调用本测试项要证明的真实产品入口；验证必须检查入口产生的可观察结果、持久状态或外部证据。 |
| R19 | 准备阶段需要数据或状态 | 可以建立前置数据，但不能直接制造本测试项要证明的目标结果；只设置一个属性、角色或状态再原样断言，不算验证产品行为。 |
| R20 | 检查测试代码 | AI 和程序在测试验证环节内按测试项核对正式目标名称、产品入口、准备内容、执行动作、关键断言和预期证据。范围仍与用户开始时确认的计划一致时直接进入正式执行，不再次要求用户确认；发现范围变化时先重新确认。 |
| R21 | 正式执行发现目标不匹配、没有执行或被跳过 | 当前测试项判定为未通过，不得用退出码为零冒充成功；修正登记或测试代码后重新执行并取得新记录。 |
| R22 | 建立测试代码快照 | 只使用当前测试计划中的明确测试入口、项目统一测试入口和本轮确认修改的测试配置。未登记的测试样文件不参与快照。 |
| R23 | 已登记测试文件变化 | 程序逐文件比较确认时与当前内容，一次列出全部新增、修改、删除和类型变化，再使测试代码及后续结果失效。 |
| R24 | 结果文档固定字段 | 固定字段必须来自当前机器记录，文档模板中的空值或旧值由程序覆盖。机器记录缺失时拒绝生成通过结果，不能让 AI 手工补一个看似一致的值。 |
| R25 | 测试验证阶段的用户确认次数 | 正常路径只在开始时确认测试范围和通过标准，在全部测试完成后确认最终结果。计划检查、测试代码检查、任务登记和正式执行由 AI 与程序连续完成；额外风险动作仍单独取得用户同意。 |
| R26 | 登记测试超时 | 每条正式测试任务必须登记超时秒数。AI 优先依据已有耗时、项目说明或当前范围提出具体值；没有依据时默认 600 秒。超时后终止该命令及其子进程，清除该测试项的当前成功状态，不生成通过结果。 |
| R27 | 并行执行独立主题 | 项目级 `test_parallelism`（主题测试最大并行数）保存默认并行数量；没有配置时为 2。只有一个主题、主题存在前置关系或运行环境不能隔离时按 1 执行；用户可以在执行前明确指定其它正整数，但不能绕过主题依赖和共享环境限制。 |
| R28 | 开始测试代码工作 | 测试范围确认后可以直接修改测试代码、辅助脚本或测试配置；不要求准备测试代码基线，也不把测试计划中的文件清单当作白名单。 |
| R29 | 发现额外测试改动 | 额外测试文件、夹具、辅助脚本或测试配置服务于已确认验收条件时，直接记录它覆盖的验收条件和正式执行证据；不能因路径未写入最初测试计划阻止测试验证。 |
| R30 | 检查实际测试改动 | 每个能够确定属于本轮的实际测试改动必须有测试项、验收条件关联和真实机器执行证据；缺少任一事实时一次列出具体路径和缺失项。计划中未修改的文件、计划外但已说明的文件不是失败原因。 |
| R31 | 真实执行后测试代码变化 | 当前机器记录和旧内部检查失效，程序只要求重新检查受影响测试代码、重新登记并执行受影响测试项；不重新确认测试范围，也不重设测试代码基线。 |
| R32 | 已引入工作记录表的轮次制定测试计划或生成测试结果 | 测试项、命令、工作目录、超时和报告适配器填在程序生成的测试工作记录表中；测试计划和测试结果文档由程序按表和机器记录生成，AI 不手写固定标题、编号行和表格。详见[工作记录表与正式文档生成](./功能_工作记录表与正式文档生成.md)。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 程序、AI | 程序列出必读材料绝对路径，AI 逐份读取并调查相关代码和测试 | 测试工作建立在当前依据和真实代码上 |
| 2 | AI、用户 | AI 一次展示全部主题的正式目标名称、产品入口、测试层级、测试文件、准备内容、执行动作、关键断言、证据、依赖和隔离方式；纯人工项同时展示人工交接步骤；用户确认测试范围和通过标准 | 用户能够判断自动化测试是否真的执行产品行为并证明验收条件，也知道纯人工项要怎样交接；后续不再逐段确认 |
| 3 | AI、程序 | AI 按准备、执行和验证复用或修改测试代码并局部检查；发现额外测试文件时直接记录其测试项、验收条件和执行证据 | 程序按实际测试改动检查追踪和证据，不把测试计划文件清单当作限制，也不要求制造代码变化 |
| 4 | AI、程序 | AI 为自动化和混合测试项登记待执行命令；程序检查任务、依赖和纯人工交接完整 | 内部检查通过后直接进入正式执行，不增加用户确认和阶段切换 |
| 5 | AI、程序 | AI 执行正式测试运行命令 | 程序逐项运行并保存绑定唯一主题和测试项的机器记录 |
| 6 | 程序、AI | 程序根据当前有效记录生成或回填各主题测试结果，AI 补充人能理解的说明 | 文档能够回查实际命令、测试函数和证据，固定字段不会与机器记录分叉 |
| 7 | 程序、AI、用户 | 程序核对全部结果与记录一致，AI 展示最终测试结果和待人工验收内容，用户确认 | 门禁不重复运行测试；全部主题满足要求后进入主题验收 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 必读材料无法读取 | 文件不存在或读取失败 | 停止当前工作，不把路径清单当成已阅读 | 显示失败路径和需要修复的问题 |
| 计划与真实代码不一致 | 计划中的入口、方式或预期结果无法落实 | 在测试验证环节重新确认范围，或调查后经用户确认返回更上游环节 | 不用方便实现的测试替换已确认要求 |
| 产品代码缺少测试接缝 | 无法控制必要输入或观察结果 | 返回实施环节补充明确接缝 | 测试验证环节不偷偷改产品代码 |
| 登记记录混合多个测试项 | 一条记录同时绑定不同 `TC-xx` | 拒绝登记并按测试项拆开 | 每条机器事实只证明一个测试项 |
| 同一测试项漏跑函数 | 当前追踪标识下仍有函数未覆盖 | 不判定通过，补齐后重跑 | 一个通过函数不会代表整个测试项 |
| 正式目标名称不匹配 | 登记的测试名称与机器实际执行名称不同 | 不接受该记录，修正登记或测试目标后重新执行 | 相似名称或其它测试不会冒充当前测试项 |
| 没有执行或发生跳过 | 命令退出码为零，但执行数量为零或存在跳过 | 当前测试项不通过，查明选择条件、环境或测试实现后重跑 | 空跑和跳过不会形成成功证据 |
| 测试直接制造目标结果 | 测试只设置目标状态或返回值，再检查同一个值 | 拒绝确认测试代码，改为调用真实产品入口并检查其结果 | 权限、删除、清空、覆盖等行为不会被属性赋值冒充验证 |
| 测试失败或超时 | 退出码非零或超过确认时限 | 清除旧成功记录，停止相关依赖并输出错误摘要；超时时终止进程树 | 不生成伪造的通过结果 |
| 环境或工具链不可用 | 运行时、依赖、设备或入口无法启动 | 临时问题在测试验证环节处理；需要改变入口或范围时重新确认，涉及额外风险动作时先询问用户 | 不在多个测试阶段之间反复退回 |
| 结果文档与机器记录不一致 | 固定字段为空、来自旧执行或被人工改写 | 程序用当前机器记录重新生成固定字段；机器记录缺失时拒绝通过 | 用户不会因手抄命令、编号或输出错误而反复修文档 |
| 上游内容变化 | 计划、实施代码或测试代码变化 | 使直接受影响主题记录和结果失效 | 用户看到需要重测的主题和具体依据 |
| 构建目录出现测试名文件 | 范围外的构建或缓存目录中生成了名称像测试的代码文件 | 因该路径没有被测试计划登记，不进入测试代码快照 | 不会因构建产物误判测试代码变化 |
| 测试恢复依据不足 | 项目没有 Git 隔离工作区、用户备份或其它可信恢复点 | 显示不能自动恢复的范围，但继续按测试项、验收条件和真实机器记录判断测试门禁 | 用户知道恢复风险，不会被测试基线失败打断 |
