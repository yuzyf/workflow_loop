# 【功能】验证技术不确定性

## 1. 背景

产品设计和初步代码设计完成后，有些技术事实仍然无法从现有文档、代码或已有运行结果中确认。例如真实接口返回哪些字段、真实 PDF 能否正确解析、目标平台是否支持某项能力，或者实际数据规模下性能是否满足要求。

这些事实会改变代码设计、实施计划、修复方案或验证方式，因此需要在进入计划前使用真实场景取得证据。已经能够确认的事实不需要穿刺。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零开发前验证不确定性 | 产品提出者、项目维护者 | 产品设计和初步代码设计已经确认，仍有必须实际运行才能确认的技术事实 | 决定哪些不确定性需要验证并取得真实结果 | 实施计划不依赖猜测 |
| 修改产品前验证不确定性 | 产品提出者、项目维护者 | 产品变化和对应代码设计已经确认，但接口、文件、平台、性能或算法行为仍未知 | 使用真实场景确认设计假设 | 产品设计和代码设计根据真实结果保持一致 |
| 修 bug 前验证不确定性 | 项目维护者 | bug 已复现并确认根因，但修复依赖未知的接口返回、兼容性或其他技术事实 | 在修复计划前确认具体未知内容 | 修复计划使用真实证据；需要改变产品行为时停止修 bug |
| 跳过穿刺 | 产品提出者、项目维护者 | AI 调查后没有发现需要实际验证的不确定性 | 明确决定本次不执行穿刺 | 工作流不生成穿刺清单和结论文档，直接进入后续计划阶段 |

## 3. 功能边界

### 3.1 支持范围

- 查看已确认的产品设计、代码设计、相关代码、测试、日志、依赖文档和已有运行结果。
- 项目具备运行条件时，运行与当前问题有关的现有功能。
- 识别必须通过真实运行、真实调用或实际测量才能确认的技术不确定性。
- 验证真实接口、真实文件、目标平台、实际数据规模、实际操作路径和真实故障条件。
- 使用现有命令、项目现有程序、第三方工具、接口调用或最小临时代码取得证据。
- 记录用户选择的穿刺清单、实际执行、观察结果、结论和后续影响。
- 根据穿刺结论更新受影响的产品设计和代码设计。
- 用户确认结果后清理临时代码、样本和原始输出。

### 3.2 不支持范围

- 不验证已经能从现有事实确认的内容。
- 不用模拟接口返回、自造业务数据、理想化文件或脱离目标环境的玩具案例证明真实行为。
- 不在穿刺阶段修改正式源代码、正式页面、正式配置或数据库迁移。
- 不把未经生产级错误处理和测试的临时代码直接复制进正式代码。
- 不由 AI 代替用户决定执行哪些穿刺项或是否全部跳过。
- 不在修 bug 流程中改变产品行为、产品规则或功能边界。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | AI 准备提出穿刺候选 | 必须先查看已有事实；现有代码或运行结果已经能回答的内容不得作为穿刺候选。 |
| R2 | 一个候选包含多个问题 | 多个问题共同服务同一个后续决定时写成一个穿刺项；验证内容和结果用途实质相同时必须合并。 |
| R3 | 后一个候选依赖前一个结果 | 只先选择当前可执行项；前一个结果出来后，再由用户决定是否新增后续穿刺。 |
| R4 | AI 提出穿刺候选 | 必须说明真实场景、已知事实、具体不确定性、必须实际验证的原因、验证方法、结果用途和实际影响。 |
| R5 | 确定执行清单 | 用户逐项决定是否执行；AI 不得自动把候选加入清单。 |
| R6 | 用户决定不执行任何穿刺 | 执行明确的跳过操作，不生成穿刺清单和结论文档。 |
| R7 | 执行穿刺 | 必须使用真实场景；真实场景暂时无法取得时，结论只能是“仍未确认”。 |
| R8 | 选择验证方法 | 使用能取得真实证据的最小方法；现有命令或程序可以回答时，不额外编写临时代码。 |
| R9 | 验证操作会扣费、发送、写入或删除外部数据 | 执行前再次说明对象、影响、费用和能否撤销，并取得用户明确确认。 |
| R10 | 记录敏感内容 | 密钥、令牌、密码和会话信息不得写入穿刺文档、临时文件或保留的命令输出。 |
| R11 | 判断穿刺结果 | 只能使用“已确认”“限制已确认”“仍未确认”；原方案不可行但限制已经查明时可以写“限制已确认”。 |
| R12 | 任意穿刺项仍阻塞后续 | 不得通过穿刺阶段门禁；必须继续验证，或者由用户决定怎样调整设计和范围。 |
| R13 | 结果仍未确认但不阻塞 | 必须写清剩余风险、后续处理阶段和后续需要检查什么；用户是否接受该风险由第三道门确认。 |
| R14 | 穿刺影响产品设计或代码设计 | 更新对应文档后才能进入计划；用户尚未决定怎样修改时视为仍然阻塞。 |
| R15 | 修 bug 的穿刺需要修改产品设计 | 不能继续修 bug；结束当前流程后改为修改产品流程。 |
| R16 | 用户确认全部穿刺结果 | 清理穿刺临时目录，只保留穿刺清单、结论文档和更新后的设计文档。 |
| R17 | 调用穿刺门禁 | 只能操作当前正在进行的穿刺阶段，不能从前一个阶段提前通过穿刺门禁。 |
| R18 | 门2通过后准备执行门3 | 程序必须重新校验当前穿刺文档；文档已变成不完整、冲突或仍阻塞时，清除旧的门2通过状态并停止推进。 |
| R19 | 旧工作流已经进入穿刺但没有入场设计基线 | 不用当前设计冒充旧基线；全部设计都无需修改时可以继续，需要证明设计发生变化时停止并说明原因。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI | 读取产品设计、代码设计、相关代码、测试、日志、依赖文档和已有运行结果；具备条件时运行相关现有功能 | 区分已经确认的事实和仍需实际验证的不确定性 |
| 2 | AI | 比较候选的真实场景、不确定内容、所需证据和结果用途 | 重复内容被合并，有前置依赖的后续候选不会提前列为必做项 |
| 3 | AI | 每次向用户说明一个穿刺候选并给出建议 | 用户能看清为什么需要验证、准备怎样验证和结果会改变什么 |
| 4 | 用户 | 逐项决定是否执行，并确认最终执行清单；没有穿刺项时决定跳过 | 只有用户选择的项目进入穿刺清单 |
| 5 | AI | 为每个穿刺项写执行前内容，包括真实场景、不确定性、验证范围和方法 | 执行前不会编造未知结果 |
| 6 | AI | 使用真实场景执行验证；需要临时代码时放入穿刺临时目录 | 获得实际命令、输入、输出、测量数据、失败信息和限制 |
| 7 | AI | 完成一个穿刺项后立即填写实际执行、观察结果、结论和后续影响 | 每个穿刺项都有独立、可复核的结论文档 |
| 8 | AI、用户 | 根据证据决定产品设计和代码设计怎样修改 | 设计文档与穿刺结论保持一致；未决定的内容继续阻塞 |
| 9 | 用户 | 统一检查穿刺清单、全部结论和更新后的设计文档 | 用户确认后进入实施计划或修复计划，临时内容被清理 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 没有技术不确定性 | 已有文档、代码和运行结果已经能回答全部相关问题 | AI 说明调查范围并建议跳过，等待用户决定 | 用户确认后直接进入后续计划阶段 |
| 真实场景无法取得 | 缺少真实接口、业务文件、目标平台、实际数据规模或必要权限 | 不用假数据替代，结果写“仍未确认” | 用户看到缺少的条件、影响和后续处理选择 |
| 穿刺项仍然阻塞 | 结果不足，或者限制已确认但尚未决定处理方式 | 不通过门禁，继续验证或讨论调整方案 | 工作流不会带着未解决的阻塞进入计划 |
| 穿刺需要外部写入 | 验证会扣费、发送内容、创建、修改或删除外部数据 | 执行前再次取得用户确认；用户拒绝且无其他真实方法时写“仍未确认” | 不会因为选择穿刺项就自动执行有实际影响的操作 |
| 穿刺结果推翻产品要求 | 真实证据证明原产品行为无法成立 | 从零开发或修改产品时由用户决定并更新产品设计；修 bug 时停止当前流程 | 产品文档不会与真实限制或代码设计互相冲突 |
| 穿刺文档属于旧工作流 | 文档中的工作流编号与当前工作流不一致 | 当前门禁不接受旧文档 | 旧穿刺结果不会冒充本次完成结果 |
| 旧工作流缺少入场设计基线 | 旧状态没有保存进入穿刺时的产品设计和代码设计哈希 | 标记基线无法还原；不自动使用当前文件补录 | 无需修改设计的穿刺可以继续；要求修改设计时门禁明确失败 |
| 门2后文档被修改 | 门2通过后，清单、结论或设计被改成不符合要求 | 门3重新校验并清除旧通过状态 | 工作流停留在穿刺阶段，要求重新修正文档并执行门2 |
| 临时代码可以运行但证据不真实 | 使用模拟返回、自造数据或理想化文件得到结果 | 不接受该结果，重新使用真实场景验证 | 玩具案例不会被写成真实结论 |
| 临时内容包含敏感信息 | 输出中出现密钥、令牌、密码或会话信息 | 停止保留并脱敏；敏感内容不得进入结论文档 | 最终文档不泄露访问凭据 |
