# 【功能】处理无需开发任务

## 1. 背景

项目维护中有一类任务不需要改变产品规则、代码或运行配置，例如设计说明文档、调查项目，或执行已准备好的提交和发布。这些只是例子，是否适用取决于任务是否需要开发，不取决于任务名称或工作量大小。

用户仍需要与 AI 把需求聊清楚，并确认具体操作和结果；但不需要为此生成产品设计、验收计划、测试计划和实施记录，也不需要经过完整研发流程的每个环节。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 修改或生成文档 | 项目负责人、项目维护者 | 文档不会改变正式产品规则，也不会把未实施内容写成当前事实 | 逐题确认文档目的和设计后直接产出 | 文档符合用户确认的用途、内容和结构 |
| 调查、审查或运行现有检查 | 项目负责人、项目维护者 | 任务只需读取项目、执行现有工具或整理结果 | 得到有真实依据的结论 | 用户能看到调查范围、事实依据和结论 |
| 执行已准备好的操作 | 项目维护者 | 代码、文档、测试、版本号和配置已准备完毕，本次只需执行准确操作 | 明确是本地提交、推送远程、发布或其它操作后执行 | 实际对象状态与用户确认的操作一致 |

## 3. 功能边界

### 3.1 支持范围

- 支持不需要修改产品规则、源代码、测试代码或运行配置的项目任务。
- 支持长时间调查或多轮文档设计；工作量大小不决定是否适用。
- 支持 AI 调查可查事实，并与用户每次确认一个仍需决定的问题。
- 支持本地文件操作和经用户批准的提交、推送、发布、删除等操作。
- 支持根据任务本身核对结果，并等待用户确认完成。

### 3.2 不支持范围

- 不修改正式产品规则、源代码或测试代码。
- 不修改会改变运行、构建、测试、部署或依赖的配置。
- 不把未实施提案写成当前产品事实；需要改变正式产品设计时改走完整修改产品流程。
- 不生成本轮专用的验收计划、测试计划或实施记录。
- 不保存回退副本，不增加文件哈希门禁，不默认执行固定全量测试。
- 不在同一项目已有进行中轮次时再开一轮无关任务。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | AI 认为用户的需求无需开发 | 先说明判断理由并推荐 `light_task`（无需开发任务）；用户明确确认路线前不开始轮次。 |
| R2 | 判断是否适用 | 根据是否需要开发判断，不使用固定任务名称清单，也不根据工作量大小判断。 |
| R3 | 进入讨论 | AI 从用户真正要完成的结果出发，先自行调查可查事实；每次只问一个需要用户决定的问题，并给出推荐答案。 |
| R4 | 仍有未决问题 | 继续逐题讨论，不边问边执行。没有未决问题后，AI 总结目标、范围、准确操作和核对方法；只有用户明确确认讨论完毕才能执行。 |
| R5 | 用户使用“提交代码”等可能表示多种操作的说法 | 必须问清是只执行 `commit`（创建本地 Git 提交），还是在 `commit` 后继续执行 `push`（推送到远程仓库）；不从含糊说法自行扩大操作范围。 |
| R6 | 即将执行提交、推送、发布、删除或其它难以撤销的操作 | AI 先展示实际对象和影响，再取得一次针对该操作的明确批准；进入无需开发任务的确认不等于该批准。 |
| R7 | 讨论已完成 | AI 只执行共同理解中的操作，并使用讨论时确定的针对性方法核对结果；不机械增加全量测试。 |
| R8 | 操作成功 | 只说明本次操作和对应核对成功，不把本地提交、推送或发布成功表述为代码质量、产品测试或验收已通过。 |
| R9 | AI 展示实际结果 | 用户确认完成后立即正式收工，不再询问相同的结束问题；用户不接受时继续当前讨论和修正。 |
| R10 | 轮次进行中 | 只在 `state.json`（当前状态文件）和 `journal.jsonl`（追加操作日志）保存最基本的任务、确认、操作和结果状态；不生成研发过程文档、回退副本或文件哈希检查。 |
| R11 | 执行失败或用户作废轮次 | 保留项目和外部系统当时的实际状态，说明已完成、未完成和失败内容，不自动恢复或撤销。 |
| R12 | 讨论或执行中发现需要开发 | 停止无需开发任务，记录重新分类原因并结束当前轮次；AI 说明应转入的完整工作意图，用户再次确认后另开新轮次。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI、用户 | AI 说明为什么本次无需开发，用户确认进入 | 产品建立 `light_task`（无需开发任务）轮次 |
| 2 | AI、用户 | AI 先调查事实，再每次只讨论一个需要决定的问题；最后总结共同理解 | 用户确认讨论完毕后才允许执行 |
| 3 | AI、用户 | AI 按共同理解直接执行；难以撤销的操作在执行前再让用户确认准确对象 | 任务不进入完整研发环节，只完成已确认的工作 |
| 4 | AI、用户 | AI 核对并展示结果，用户决定接受或继续修正 | 用户确认完成时本轮结束 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 已有进行中轮次 | 同一项目已在处理其它工作 | 不新开无需开发轮次；相关操作归入当前轮次，无关任务等当前轮结束 | 当前轮次和下一步保持明确 |
| 任务实际需要开发 | 需要修改产品规则、代码、测试或会影响运行的配置 | 停止本轮并说明应转入的完整流程 | 用户确认新路线后才另开新轮 |
| 文档会造成事实冲突 | 文档准备改变正式产品要求，或把尚未实施的提案写成当前事实 | 不直接修改正式事实；改为明确标注的提案，或转入修改产品流程 | 产品文档不会先于真实产品宣称已支持 |
| 操作含义不清 | 用户使用“提交”等可能指向多个操作的说法 | 一次只询问一个需要决定的问题，直到准确操作和边界确定 | 不会把本地提交自动扩大为推送或发布 |
| 执行只完成一部分 | 文件、命令或外部操作中途失败 | 停在实际状态，不自动恢复；列出已完成、未完成和失败内容 | 用户根据真实结果决定继续、保留或作废 |
| 用户不接受结果 | AI 已展示执行和核对结果，但仍有需要调整的内容 | 不正式收工，继续逐题讨论并修正 | 用户最终确认后才结束本轮 |
| 用户中途作废 | 用户决定不再继续整个无需开发任务 | 将轮次标记为已作废，保留当时的文件和外部状态 | 明确看到本轮停在哪里，新轮次可以开始 |
