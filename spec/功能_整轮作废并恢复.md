# 【功能】整轮作废并恢复

## 1. 背景

用户在一轮工作尚未完成时，可能决定整轮不再继续。从零创建、修改产品和修复缺陷轮次会生成成套受管设计、计划、代码、测试或配置修改；只把状态改成“已作废”，会把未交付内容留在项目中。

因此，三种完整研发轮次作废时，必须把 Workflow Loop 管理的本轮修改恢复到开工前：恢复旧文件和项目级配置，删除本轮新文件，清理临时回退副本。无需开发任务不保存回退副本；该轮次作废时只结束状态、说明已完成和未完成内容，保留项目和外部系统的实际状态。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 中途放弃整轮工作 | 产品提出者、项目维护者 | 任一工作环节仍在进行，用户决定整个需求不再继续 | 取消本轮全部受管修改 | 项目受管内容恢复到本轮开工前 |
| 取消缺陷修复 | 项目维护者 | 修复缺陷轮次不再继续 | 放弃本次修复，不错误关闭缺陷 | 本轮修改被恢复，缺陷不能标记为已修复 |
| 修缺陷必须改产品 | 产品提出者、项目维护者 | 修复方案需要改变产品规则、边界或用户可见行为 | 结束错误类型的轮次，再按修改产品重新开始 | 修缺陷流程不会绕过产品设计确认 |
| 作废恢复中途失败后重试 | 项目维护者 | 一部分受管内容已经恢复，后续恢复或清理失败 | 继续完成剩余恢复 | 已成功恢复的文件不会被再次覆盖 |
| 作废无需开发任务 | 产品提出者、项目维护者 | `light_task`（无需开发任务）轮次不再继续 | 结束轮次但不自动撤销已做操作 | 保留当时实际状态，并清楚说明任务停在哪里 |
| 作废后开始新工作 | 产品提出者、项目维护者 | 整轮恢复和清理已经成功 | 解除进行中轮次限制 | 可以开始新的独立轮次 |

## 3. 功能边界

### 3.1 支持范围

- 支持在任一进行中环节作废整个工作流轮次。
- 恢复本轮修改或删除的产品设计、功能设计、代码设计、计划、实施记录、测试文档和验收文档。
- 恢复本轮修改的产品代码、测试代码、测试配置、项目统一测试入口脚本和项目级测试入口配置。
- 恢复本轮修改的项目级状态字段，删除本轮新建的受管文件。
- 只恢复已经登记在本轮回退清单中的内容，不影响开工前未登记的用户文件。
- 作废失败时保留进行中状态和真实副本，支持继续未完成的恢复动作。
- 作废成功后清理临时副本并允许开始新轮次。
- 支持无需开发任务不恢复内容而直接标记作废，同时保留已做操作和实际结果的日志。

### 3.2 不支持范围

- 不为作废内容建立历史文档目录，也不保留作废文件副本。
- 不复制或恢复整个大型项目压缩包。
- 不撤销未登记为本轮受管修改的用户工作。
- 不把只取消一个功能或一个主题等同于整轮作废。
- 不把恢复失败或只恢复一部分伪装成作废成功。
- 不对已正式收工、已作废或没有当前轮状态的项目执行静默空操作。
- 不通过作废命令把缺陷标记为已修复或把未通过需求标记为完成。
- 不声称无需开发任务能够恢复或撤销本轮文件及外部操作。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 三种完整研发轮次开始 | 保存当时存在的受管设计和过程文档内容、路径清单及相关项目级字段；本轮新建路径记录为“原本不存在”。 |
| R2 | 从零做需要清场 | 删除旧受管产物前先保存原内容，保证整轮作废可以恢复开工前状态。 |
| R3 | 测试计划准备修改统一测试入口 | 修改前保存入口脚本旧内容或“原本不存在”记录，并保存开工前已确认的项目统一测试入口；未保存不得写入或通过门禁。 |
| R4 | 实施准备修改产品代码 | 必须先执行准备代码回退基线的动作，按已确认实施计划保存真实文件原内容；新增文件记录为“原本不存在”。 |
| R5 | 测试代码准备修改 | 在写测试代码前把已有测试文件和测试配置加入同一回退清单，并登记本阶段新增文件。 |
| R6 | 用户决定整轮不再继续 | 智能体执行 `workflow abort`，用户不手工输入。完整研发轮次中，该命令表示“作废并恢复受管内容”；无需开发轮次中，该命令表示“作废并保留实际状态”。 |
| R7 | 开始恢复前 | 程序必须先检查回退清单、真实副本和“原本不存在”记录完整可用；缺少恢复依据时不能声称可以作废成功。 |
| R8 | 执行恢复 | 恢复本轮修改或删除的旧文件和项目字段，删除本轮新建的对应文件；只处理清单登记范围。 |
| R9 | 处理作废内容 | 不移入历史目录，不把文件正文写入状态快照或流水日志；状态和日志只记录恢复项目、结果、失败原因和副本校验信息。 |
| R10 | 全部恢复成功 | 删除本轮临时快照和回退清单，把轮次状态写为“已作废”，记录结束时间并解除进行中轮次限制。 |
| R11 | 任一步恢复失败 | 轮次继续保持“进行中”，保留尚需使用的副本和逐项恢复状态，不能删除恢复依据。 |
| R12 | 再次执行作废 | 只继续尚未完成的恢复和清理动作；已经成功恢复的文件不能再次覆盖，避免覆盖第一次恢复后产生的新修改。 |
| R13 | 只取消一个功能或主题 | 从零做或修改产品使用返回上游重新处理，不作废整轮；保留其它功能和仍被共享的代码。 |
| R14 | 取消修复缺陷 | 修复缺陷只对应一个具体缺陷，用户取消即作废整轮；缺陷原始现象、复现过程和根因不能被结果更新覆盖。 |
| R15 | 修复缺陷需要改变产品 | 作废当前修复轮次，恢复完成后以“修改产品”开始新轮次，不能返回本轮不存在的产品设计环节。 |
| R16 | 显示作废结果 | 必须用直白中文说明准备恢复什么、实际恢复了什么、是否成功以及用户下一步能做什么，不能只显示 `abort` 英文命令或状态值。 |
| R17 | 跨平台恢复 | macOS、Linux 和原生 Windows 都必须正确处理本机路径、项目配置和测试入口，不能把 Windows 路径当成无效路径。 |
| R18 | 正式产物命名 | 恢复清单中的面向用户正式产物最终使用中文文件名；程序固定目录、状态文件和代码标识仍保持英文。 |
| R19 | 无需开发任务作废 | 不检查或使用回退清单，不恢复、删除或撤销任何已做内容；记录已完成、未完成和失败内容后，把轮次标记为已作废并解除进行中限制。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 完整研发流程的各工作环节、产品 | 在真正修改受管文档、代码、测试、入口脚本或项目字段前保存原内容和路径状态 | 三种完整研发轮次的每项可恢复修改都有真实依据 |
| 2 | 用户 | 明确决定整个进行中轮次不再继续 | 智能体区分整轮作废和只取消单个功能，不擅自扩大范围 |
| 3 | 智能体 | 用直白中文说明作废的实际结果：完整研发轮次会恢复受管内容，无需开发轮次会保留实际状态；然后调用作废命令 | 用户知道本次作废是否会恢复内容 |
| 4 | 产品 | 无需开发轮次直接记录实际状态并结束；完整研发轮次检查回退清单、真实副本和新文件记录 | 简单轮次不增加恢复步骤，完整轮次继续保持可恢复 |
| 5 | 产品 | 恢复旧受管文件、项目级字段和统一测试入口配置，删除本轮新文件 | 项目逐项回到开工前状态 |
| 6 | 产品 | 记录每项恢复和清理结果 | 中途失败时可以只继续未完成动作 |
| 7 | 产品 | 全部恢复成功后删除临时副本，把轮次标记为已作废 | 作废内容不另存档，进行中轮次限制解除 |
| 8 | 用户 | 需要时提出新需求 | 新轮次可以在已经恢复的项目现状上开始 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 没有进行中轮次 | 没有当前状态，或轮次已经正式收工、已经作废 | 拒绝执行 | 明确说明没有可作废的进行中工作 |
| 回退副本缺失或校验不符 | 已登记旧文件无法读取，或内容与清单不一致 | 停止作废并保持进行中状态 | 列出无法恢复的具体路径和原因 |
| 只完成部分恢复 | 后续文件恢复或临时副本清理失败 | 保存逐项进度，不标记已作废 | 显示已完成和未完成项目，可再次继续作废 |
| 本轮新文件删除失败 | 文件被占用、权限不足或路径不可处理 | 保留进行中状态和恢复记录 | 不把仍残留本轮内容的项目说成已经还原 |
| 用户在部分恢复后修改文件 | 第一次作废已成功恢复某文件，之后用户又修改它 | 再次作废时跳过已完成项 | 不用旧副本覆盖用户的新修改 |
| 清单外存在用户修改 | 用户在本轮期间修改了未登记的无关文件 | 不处理该文件 | 作废只撤销工作流已登记的本轮内容 |
| 用户只取消一个产品主题 | 从零做或修改产品仍要继续其它主题 | 不执行整轮作废，改走返回上游 | 其它已确认内容和代码不会被整体恢复 |
| 修复缺陷需要改产品 | 当前修复不能在原产品规则内完成 | 恢复并作废修复轮次，再开始修改产品 | 不用修缺陷流程绕过产品设计确认 |
| 无需开发轮次要求恢复 | 用户作废时希望自动撤销本轮内容 | 明确该轮次没有保存回退副本，只能保留实际状态后结束 | 不会把“已作废”误解为文件或外部操作已恢复 |
