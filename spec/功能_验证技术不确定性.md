# 【功能】验证技术不确定性

## 1. 背景

产品设计完成后，有些技术事实仍然无法从现有文档、代码或已有运行结果中确认。例如真实接口返回哪些字段、真实 PDF 能否正确解析、目标平台是否支持某项能力，或者实际数据规模下性能是否满足要求。这些事实会影响验收条件或代码计划时，应在正式代码实施前取得证据。

这些事实会改变代码设计、验收条件、实施方案或后续验证方式，因此需要在进入验收计划和实施前使用真实场景取得证据。已经能够确认的事实不需要穿刺。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零开发前验证不确定性 | 产品提出者、项目维护者 | 产品设计已经确认，仍有必须实际运行才能确认并会影响验收或实施的技术事实 | 决定哪些不确定性需要验证并取得真实结果 | 验收条件和代码计划不依赖猜测 |
| 修改产品前验证不确定性 | 产品提出者、项目维护者 | 产品变化已经确认，但接口、文件、平台、性能或算法行为仍未知 | 使用真实场景确认设计假设 | 产品设计和代码计划根据真实结果保持一致 |
| 修复缺陷前验证不确定性 | 项目维护者 | 缺陷已复现并确认根因，但修复依赖未知的接口返回、兼容性或其他技术事实 | 在验收计划和代码计划前确认具体未知内容 | 验收与实施使用真实证据；需要改变产品行为时停止缺陷修复 |
| 跳过穿刺 | 产品提出者、项目维护者 | AI 调查后没有发现需要实际验证的不确定性 | 明确决定本次不执行穿刺 | 工作流不生成穿刺清单和结论文档，直接进入验收计划 |

## 3. 功能边界

### 3.1 支持范围

- 查看已确认的产品设计、首次接入时形成的现状架构基线、相关代码、测试、日志、依赖文档和已有运行结果。
- 项目具备运行条件时，运行与当前问题有关的现有功能。
- 识别必须通过真实运行、真实调用或实际测量才能确认的技术不确定性。
- 验证真实接口、真实文件、目标平台、实际数据规模、实际操作路径和真实故障条件。
- 使用现有命令、项目现有程序、第三方工具、接口调用或最小临时代码取得证据。
- 使用 `spec/穿刺清单.md` 和 `spec/穿刺_<穿刺项文件标识>.md` 记录用户选择的穿刺清单、实际执行、观察结果、结论和后续影响。
- 根据穿刺结论更新受影响的产品设计，或把技术结论和实现约束记录为后续代码计划的输入；进入代码实施环节时再由代码计划承接这些输入，不在穿刺阶段把未来代码方案写成最终代码设计。
- 将能够产生结论且以后可复用的代码及其最小非敏感依赖保存在 `.workflow_loop/spike_tmp/<工作流编号>/<穿刺项标识>/`（按工作流和穿刺项隔离的穿刺临时目录），并在需求交付追踪表登记；工作完成后不自动删除。

### 3.2 不支持范围

- 不验证已经能从现有事实确认的内容。
- 不用模拟接口返回、自造业务数据、理想化文件或脱离目标环境的玩具案例证明真实行为。
- 不在穿刺阶段修改正式源代码、正式页面、正式配置或数据库迁移。
- 不把未经生产级错误处理和测试的临时代码直接复制进正式代码。
- 不由 AI 代替用户决定执行哪些穿刺项或是否全部跳过。
- 不在缺陷修复流程中改变产品行为、产品规则或功能边界。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | AI 准备提出穿刺候选 | 必须先查看已有事实；现有代码或运行结果已经能回答的内容不得作为穿刺候选。 |
| R2 | 一个候选包含多个问题 | 多个问题共同服务同一个后续决定时写成一个穿刺项；验证内容和结果用途实质相同时必须合并。 |
| R3 | 后一个候选依赖前一个结果 | 只先选择当前可执行项；前一个结果出来后，再由用户决定是否新增后续穿刺。 |
| R4 | AI 提出穿刺候选 | 必须说明真实场景、已知事实、具体不确定性、必须实际验证的原因、验证方法、结果用途和实际影响。 |
| R5 | 确定执行清单 | 用户逐项决定是否执行；AI 不得自动把候选加入清单。 |
| R6 | 用户决定不执行任何穿刺 | 执行明确的跳过操作，不生成穿刺清单和结论文档。 |
| R7 | 执行穿刺 | 必须使用真实场景；真实场景暂时无法取得时，结论只能是“仍未确认”。 |
| R8 | 选择验证方法 | 使用能取得真实证据的最小方法；现有命令或程序可以回答时，不额外编写临时代码。 |
| R9 | 验证操作会扣费、发送、写入或删除外部数据 | 执行前再次说明对象、影响、费用和能否撤销，并取得用户明确确认。 |
| R10 | 记录敏感内容 | 密钥、令牌、密码和会话信息不得写入穿刺文档、临时文件或保留的命令输出。 |
| R11 | 判断穿刺结果 | 只能使用“已确认”“限制已确认”“仍未确认”；原方案不可行但限制已经查明时可以写“限制已确认”。 |
| R12 | 任意穿刺项仍阻塞后续 | 不得通过穿刺阶段门禁；必须继续验证，或者由用户决定怎样调整设计和范围。 |
| R13 | 结果仍未确认但不阻塞 | 必须写清剩余风险、后续处理阶段和后续需要检查什么；用户是否接受该风险由第三道门确认。 |
| R14 | 穿刺影响产品行为或实施依据 | 用户决定是否修改产品设计；技术结论、接口形状、状态逻辑、算法约束和失败条件先写入穿刺结论，作为验收计划和后续代码计划的输入。进入代码实施前，代码计划必须承接这些输入；用户尚未决定产品行为或实施方向时视为仍然阻塞。 |
| R15 | 缺陷修复的穿刺需要修改产品设计 | 不能继续缺陷修复；结束当前流程后改为修改产品流程。 |
| R16 | 用户确认全部穿刺结果 | 保留已登记的可复用穿刺资产；只清理未登记的临时样本、敏感内容、缓存、日志和纯结果输出。整个工作流完成后也不自动删除已登记资产，只有用户明确要求才清理。 |
| R17 | 调用穿刺门禁 | 只能操作当前正在进行的穿刺阶段，不能从前一个阶段提前通过穿刺门禁。 |
| R18 | 第二道门通过后准备执行第三道门 | 程序只核对第二道门保存的校验凭据与当前穿刺文档、状态和登记资产是否一致；凭据仍匹配时不重新完整校验，发生变化时列出具体变化并要求重新执行第二道门。 |
| R19 | 旧工作流已经进入穿刺但没有入场设计基线 | 不用当前设计冒充旧基线；全部设计都无需修改时可以继续，需要证明设计发生变化时停止并说明原因。 |
| R20 | 生成穿刺文件名 | 穿刺项显示名称保留完整中文；程序生成并保存稳定、跨平台安全的中文文件标识，不能直接把用户输入拼入路径。 |
| R21 | 从零创建或修改产品时，证据推翻当前设计 | AI 先说明证据、冲突位置和可选处理方式；用户决定是否修改产品设计，技术实现处理先记录为代码计划输入，进入代码实施时再写入代码计划；产品行为仍与结论冲突时不能通过。 |
| R22 | 修复缺陷时，证据证明必须改变产品行为 | 当前修复轮次不能退到不存在的产品设计环节。用户确认不再按缺陷修复继续后，由 AI 作废本轮，再开始修改产品轮次。 |
| R23 | 显示穿刺相关命令 | 命令由 AI 执行；同时向用户说明命令是在登记讨论完成、执行检查、确认结果还是跳过穿刺，以及用户是否需要参与，不能只显示技术命令。 |
| R24 | 穿刺结论用于后续交付 | 验收计划先根据结论写清所有相关行为的前提、触发、可观察结果和通过或不通过边界；代码实施先形成代码计划，再完成代码实施和代码结果；测试验证只能在实施后依据真实代码和实施记录制定计划并执行。 |
| R25 | 穿刺需要保留可复用代码 | 只有能够产生本次结论且以后可以重新运行的代码，连同重现结论必需的最小非敏感样本、配置、依赖说明和执行脚本，才能登记为可复用资产；敏感数据、缓存、日志和纯结果输出不得登记。 |
| R26 | 登记可复用穿刺资产 | 按 `.workflow_loop/spike_tmp/<工作流编号>/<穿刺项标识>/` 保存；在需求交付追踪表的“穿刺结论与可复用内容”记录结论文档、保留路径、用途和运行方法，并只关联实际支撑的验收条件。一项穿刺支撑多条验收条件时，在对应多行记录。 |
| R27 | 后续复用旧穿刺代码 | 必须在当前环境和输入下重新运行并检查结果，不能直接沿用历史结论；代码不能运行时在追踪表标记“待修订”，但不自动删除资产。 |
| R28 | 整轮作废 | 已形成结论并登记的可复用穿刺资产继续保留；尚未形成结论或未登记的半成品和临时输出随作废清理。 |
| R29 | 穿刺目录跨工作流复用 | 新工作流不得覆盖旧工作流目录；通过追踪表查找历史资产，确认仍适用后复制或直接运行，并在当前工作流记录新的使用关系。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI | 读取产品设计、现状架构基线、相关代码、测试、日志、依赖文档和已有运行结果；具备条件时运行相关现有功能 | 区分已经确认的事实和仍需实际验证的不确定性 |
| 2 | AI | 比较候选的真实场景、不确定内容、所需证据和结果用途 | 重复内容被合并，有前置依赖的后续候选不会提前列为必做项 |
| 3 | AI | 每次向用户说明一个穿刺候选并给出建议 | 用户能看清为什么需要验证、准备怎样验证和结果会改变什么 |
| 4 | 用户 | 逐项决定是否执行，并确认最终执行清单；没有穿刺项时决定跳过 | 只有用户选择的项目进入穿刺清单；决定跳过后由 AI 执行跳过命令，用户不需要手动输入 |
| 5 | AI | 为每个穿刺项写执行前内容，包括真实场景、不确定性、验证范围和方法 | 执行前不会编造未知结果 |
| 6 | AI | 使用真实场景执行验证；需要临时代码时放入穿刺临时目录 | 获得实际命令、输入、输出、测量数据、失败信息和限制 |
| 7 | AI | 完成一个穿刺项后立即填写实际执行、观察结果、结论和后续影响 | 每个穿刺项都有独立、可复核的结论文档 |
| 8 | AI、用户 | 根据证据决定是否修改产品设计；把技术结论、接口形状、状态逻辑、算法约束和失败条件写入穿刺结论，并标成后续代码计划输入；修复缺陷必须改产品时决定作废当前修复并另开修改产品轮次 | 产品行为和后续实施依据与穿刺结论一致；未决定的内容继续阻塞 |
| 9 | 用户 | 统一检查穿刺清单、全部结论、可复用资产登记和受影响的产品依据 | 用户确认后进入验收计划，随后按代码计划、代码实施、代码结果和测试验证顺序推进；已登记资产继续保留 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 没有技术不确定性 | 已有文档、代码和运行结果已经能回答全部相关问题 | AI 说明调查范围并建议跳过，等待用户决定 | 用户确认后直接进入验收计划 |
| 真实场景无法取得 | 缺少真实接口、业务文件、目标平台、实际数据规模或必要权限 | 不用假数据替代，结果写“仍未确认” | 用户看到缺少的条件、影响和后续处理选择 |
| 穿刺项仍然阻塞 | 结果不足，或者限制已确认但尚未决定处理方式 | 不通过门禁，继续验证或讨论调整方案 | 工作流不会带着未解决的阻塞进入计划 |
| 穿刺需要外部写入 | 验证会扣费、发送内容、创建、修改或删除外部数据 | 执行前再次取得用户确认；用户拒绝且无其他真实方法时写“仍未确认” | 不会因为选择穿刺项就自动执行有实际影响的操作 |
| 穿刺结果推翻产品要求 | 真实证据证明原产品行为无法成立 | 从零开发或修改产品时由用户决定并更新产品设计；修复缺陷时停止当前流程 | 产品文档不会与真实限制或代码设计互相冲突 |
| 穿刺文档属于旧工作流 | 文档中的工作流编号与当前工作流不一致 | 当前门禁不接受旧文档 | 旧穿刺结果不会冒充本次完成结果 |
| 旧工作流缺少入场设计基线 | 旧状态没有保存进入穿刺时的产品设计和代码设计哈希 | 标记基线无法还原；不自动使用当前文件补录 | 无需修改设计的穿刺可以继续；要求修改设计时门禁明确失败 |
| 第二道门后依据被修改 | 第二道门通过后，清单、结论、状态或资产登记发生变化 | 第三道门比较校验凭据；只有具体绑定内容变化时才清除旧通过状态并要求重新执行第二道门 | 未变化时不重复完整校验，变化时能看到具体差异 |
| 临时代码可以运行但证据不真实 | 使用模拟返回、自造数据或理想化文件得到结果 | 不接受该结果，重新使用真实场景验证 | 玩具案例不会被写成真实结论 |
| 临时内容包含敏感信息 | 输出中出现密钥、令牌、密码或会话信息 | 停止保留并脱敏；敏感内容不得进入结论文档 | 最终文档不泄露访问凭据 |
| 穿刺项名称不能安全用作路径 | 名称含路径分隔符、保留名、危险标点或与已有标识重名 | 程序生成并保存安全文件标识，必要时追加编号 | 正文标题不被改写，文件不会覆盖或在某个平台失效 |
| 修复缺陷需要改变产品行为 | 真实证据表明只有改变产品规则、边界或用户可见结果才能继续 | AI 说明为什么不再属于单纯修复；用户确认后作废当前修复轮次并新开修改产品轮次 | 不会从缺陷路径非法返回不存在的产品设计环节，也不会把产品变化伪装成修复 |
| 可复用资产无法运行 | 后续复用时环境、输入或依赖已经变化，代码不能重新取得结论 | 追踪表标记“待修订”，保留资产并说明缺少的条件；不得直接把历史结论当作当前事实 | 用户看到需要修订的具体资产和原因 |
| 穿刺目录存在未登记内容 | 临时目录中有一次性样本、敏感数据、缓存、日志或纯结果输出 | 清理未登记内容；已登记资产不受影响 | 不会因保留可复用代码而长期保存敏感或无用文件 |
