# 【功能】工作记录表与正式文档生成

## 1. 背景

完整研发环节需要 AI 在正式文档里提供程序可以核对的固定事实：工作流编号、验收主题、修改的文件和行号、测试项命令、验收条件编号等。过去这些事实和给人看的叙述写在同一份文档里，程序靠逐字匹配固定标题、字段行和表格来读取。AI 重新生成文档时措辞稍有偏差，门禁就找不到固定内容，于是反复出现"改一句、重查、又错在别处"的循环。

因此，本功能把"程序要核对的固定内容"和"给人看的叙述"分开：程序在环节开始时生成一份工作记录表，把固定栏目建好、把程序已知的事实（轮次编号、主题名）预先填好；AI 只在空位里填写数据和叙述；正式文档由程序按表生成。固定内容不再经过 AI 的手，门禁也不再在文章里找句子。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 开始填写环节事实 | 项目负责人、项目维护者 | 完整研发环节需要记录机器可核对的事实 | 拿到已经建好栏目、填好编号的工作记录表 | AI 只填空位，不复制模板或手写固定标题 |
| 生成正式文档 | 项目负责人、项目维护者 | AI 已经填完工作记录表 | 得到格式正确的正式文档 | 标题、编号行和表格由程序生成，叙述放进对应章节 |
| 检查环节事实 | 项目负责人、项目维护者 | AI 执行环节第二道门 | 程序核对表里的栏目、格式和编号 | 填错时指出具体栏目、预期格式和修改方法，不在文章里逐字找内容 |
| 修改已填写内容 | 项目负责人、项目维护者 | 用户看过正式文档后要求修改内容 | 修改被程序接受且不丢失 | AI 修改工作记录表，程序重新生成正式文档 |
| 处理被直接修改的正式文档 | 项目负责人、项目维护者 | 正式文档被绕过表直接编辑 | 保住手改内容，不悄悄覆盖 | 门禁指出文档与表不一致，要求把改动写回表后才放行 |
| 判断上游是否变化 | 项目负责人、项目维护者 | 后续环节核对上游内容是否被改动 | 只让真实变化使下游失效 | 失效判断按工作记录表内容计算，文档重新生成不等于内容变化 |
| 登记测试项 | 项目维护者 | 测试验证环节登记自动化测试任务 | 一次填完全部测试项 | 测试项、命令、工作目录、超时和报告适配器都填在表里，登记命令核对表而不再逐条手敲参数 |
| 查看主题清单 | 项目负责人、项目维护者 | 需要查看环节下的全部主题入口 | 打开索引文档 | 索引由程序按表汇总生成，AI 不手写 |

## 3. 功能边界

### 3.1 支持范围

- 在完整研发环节开始时，为本环节需要机器事实的每个主题生成一份工作记录表；表保存在 `.workflow_loop/records/<轮次编号>/` 下。
- 工作记录表预填程序已知的事实（轮次编号、主题名、表版本），每个空位写明要填的内容、格式和示例。
- 程序按表生成对应的正式文档：固定标题、编号行和表格由程序写入，AI 填写的叙述放进对应章节；产物目录中只出现正式文档，不出现机器文件。
- 门禁检查工作记录表：栏目名写错、多写、少写、编号重复、格式不符时，一次指出每个问题的位置、预期和修改方法。
- 程序在每次生成正式文档时记录文档内容；门禁发现正式文档与按表重新生成的结果不一致时，报告文档被直接修改，要求把改动写回表后重新生成，不直接放行也不直接覆盖。
- 第二道门检查前，程序先按当前表重新生成正式文档，再执行检查。
- 上游内容变化判定按工作记录表内容计算。
- 测试项的命令、工作目录、超时和报告适配器填写在测试记录表中；登记命令核对表并登记任务，不再逐条接受命令行参数。
- 索引文档由程序按各主题工作记录表汇总生成。
- 每份工作记录表带有表版本；一轮从开工到结束使用开工时的表版本，新表版本只对之后新开的轮次生效。
- 已经开始但未引入工作记录表的旧轮次继续按原有方式检查，不中途迁移。

### 3.2 不支持范围

- 不评判 AI 填写的叙述内容写得好不好；程序只按 R19 拦截无实质内容（占位词、空必填栏、不达标的最小信息量），文字质量高低由用户在第三道门确认。
- 不在产物目录（`spec/`、`acceptance/`、`qa/`、`impl/`、`bug/`）存放机器文件。
- 不允许 AI 绕过表直接生成或修改正式文档的固定部分。
- 不为无需开发任务生成工作记录表。
- 不自动迁移进行中的旧轮次。
- 不把工作记录表当成允许修改文件的白名单；额外文件仍按实际改动规则处理。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| <a id="r-1"></a>R1 | 完整研发环节需要记录机器事实 | 程序在 AI 首次加载该环节材料时生成工作记录表：栏目全部建好，轮次编号和主题名已预填，每个空位写明填写内容、格式和示例。首次加载时本环节主题尚未确定的，待主题确定后程序在下一次环节命令时补生成本环节各主题的工作记录表。表已存在时不重新生成空表，只补齐缺失的固定栏目，不覆盖已填内容。 |
| <a id="r-2"></a>R2 | AI 填写环节事实 | AI 只修改工作记录表的空位：数据填进数据栏，叙述一段存一条。AI 不修改程序预填的固定栏目，不在正式文档中手写固定标题、编号行或表格。 |
| <a id="r-3"></a>R3 | 生成正式文档 | 程序按当前表生成正式文档：固定部分由程序排版，叙述内容放进对应章节。产物目录只有正式文档。生成 Markdown 表格时，程序对每个单元格内容里的管道符 `|` 和换行做转义（管道符转义为 `\\|`，换行替换为 `<br>`），保证生成的表格列数和行数不被单元格内容破坏；转义在全部生成器出口统一执行，包括测试结果文档生成器。 |
| <a id="r-4"></a>R4 | 门禁检查表 | 程序检查栏目名、填写格式、编号唯一性，并逐列校验单元格的类型和枚举值：命令参数数组必须是 JSON 数组、超时秒数必须是整数、代码位置必须符合 `L起始-L结束`、执行结论必须是 `passed` 或 `failed`、验收结论必须是 `passed`、`failed` 或 `blocked`、测试方式必须是 `自动化测试`、`人工验收` 或 `自动化测试 + 人工验收`。填错时一次列出全部问题的栏目、预期类型或枚举、实际值和修改方法，不只查非空。表 schema 为每个行清单声明每列的类型与允许的枚举值，校验按声明逐列执行；并支持条件可选——测试方式为人工验收时命令参数数组、超时秒数和报告适配器允许空，其余方式必填，不用静态可选列一刀切。工作记录表产生的检查失败标明属于格式问题还是内容问题。 |
| <a id="r-5"></a>R5 | 正式文档与表不一致 | 门禁报告文档被直接修改，列出能确认的差异位置，要求把改动写回工作记录表；写回并重新生成前不放行。程序不把直接修改悄悄覆盖掉。 |
| <a id="r-6"></a>R6 | 执行第二道门 | 程序先按当前表重新生成正式文档（命中手改检测时跳过重写并报告差异），再以工作记录表为唯一输入执行该环节的固定检查；固定检查不读回刚生成的文档。 |
| <a id="r-7"></a>R7 | 判断上游内容变化 | 失效判定读取工作记录表内容；表内容不变时，仅文档重新生成不使下游失效。 |
| <a id="r-8"></a>R8 | 登记测试任务 | 测试项信息（测试项编号、测试方式、命令参数数组、工作目录、超时秒数、报告适配器、正式目标名称、对应验收条件）填在测试记录表中；测试方式为人工验收时，命令参数数组、超时秒数和报告适配器为条件可选、允许空，其余方式必填。登记命令核对表完整并登记全部任务，不再逐条接受命令行登记参数。 |
| <a id="r-9"></a>R9 | 生成索引 | 索引文档由程序按各主题工作记录表汇总生成；AI 不手写索引，也不把手写索引当成事实来源。 |
| <a id="r-10"></a>R10 | 整轮作废 | 本轮工作记录表随轮次作废一起删除；作废时递归删除本轮 records 目录下全部内容（含子目录），不只删顶层文件。正式收工后本轮表保留供核对；从零清场时旧轮次的表保留，不随产物目录删除。 |
| <a id="r-11"></a>R11 | 表版本与流程判定 | 每份工作记录表记录表版本；本轮始终使用开工时的表版本，新版表只对之后新开的轮次生效，进行中轮次不换版。门禁校验表里的表版本等于本轮开工时冻结的版本且为程序当前支持的版本，不接受任意非空值。是否走表流程以开工时该轮是否启用工作记录表为准，不以表当前是否已填写内容判断；新轮次开工时程序记录该轮启用表流程。一旦开工记录该轮启用表流程，任何情况（表未填、为空、缺失、栏目不匹配或解析失败）都不得退回文档模式，只报具体错误并停留当前环节；表尚未填写时门禁报“工作记录表尚未填写”并停留当前环节，不退回旧文档检查。实现上：state 记录开工冻结的表模式标记，门禁据此判定模式；同步环节表时不得因表为空而静默跳过或返回空导致退回文档模式，空表报“工作记录表尚未填写”并停留；判断表是否已填的检查只用于决定是否补生成空表，不用于模式判定。 |
| <a id="r-12"></a>R12 | 旧轮次继续 | 没有工作记录表的旧轮次继续按原有文档检查方式过门，不要求补建表。 |
| <a id="r-13"></a>R13 | 生成正式文档的路径与程序专用键 | 生成文档路径必须落在项目产物目录内；程序拒绝越出项目产物目录的路径，不向项目外部写入文件。生成文档路径和文档哈希是程序专用字段，AI 不得写入；程序不直接信任表内这两个键的任意值——生成路径由程序按产物目录规则计算并校验，文档哈希由程序重算并比对，不读表内可能被改动的哈希来判定是否手改。 |
| <a id="r-14"></a>R14 | 表模式下固定事实的唯一来源 | 表模式下，固定事实以工作记录表为唯一输入：门禁不再从正式文档正文逐字匹配固定标题、表头或字段，也不重新解析程序生成的文档来核对格式或内容。生成文档只供人阅读和供下游环节按程序已记录的事实引用，不再被门禁按 Markdown 解析回事实。具体：实施门禁的文件清单和计划哈希一律从实施记录工作记录表取，不得读回生成的实施记录文档核对；AC 编号一律从验收计划工作记录表取，不得正则解析验收计划文档。本条与 R3 转义配套——生成文档不再被门禁解析，单元格含管道符不会再触发列数报错。 |
| <a id="r-15"></a>R15 | 表模式承接文档模式全部校验 | 引入工作记录表的环节，表模式必须承接文档模式对固定事实的全部校验，不得因走表而跳过任何原有检查。原有文档模式检查的测试方式枚举、测试代码 Workflow-Test 标识存在与计划一致、人工验收步骤形式、代码入口形式、验收条件锚点、执行结论与验收结论枚举等，全部转为表单元格校验、测试代码校验或生成器行为；表模式不得使任何一项原有检查消失。此外表模式必须核对：验收完成时间由程序从状态记录回填并在表或文档表达；验收结果表与状态记录中当前有效的验收记录一致，表全 `passed` 但状态无记录不得放行；测试代码的工作流测试标识仍须校验，不得因走表而删除该校验。实现时须逐环节比对文档模式与表模式的全部校验项，确保不漏，包括但不限于：实施环节的未完成内容必须为“状态：无”并阻断“状态：有”、需求交付追踪表与下游一致性；测试验证环节的 AC 覆盖、测试结果机器字段与状态记录逐字段一致、已登记任务与实际测试改动、当前实施哈希、统一测试入口与回退依据、不得提前填测试通过；主题验收环节的测试执行结果、需求交付追踪表、机器测试记录编号、判定结论、上下游链接、纯人工主题标注“无自动化测试项”。 |
| <a id="r-16"></a>R16 | 生成器按表渲染文档模板全部内容 | 程序按表生成正式文档时，必须渲染该文档模板规定的全部章节和表格，不得整段丢弃、写死模板中的任何表格（如实施记录的设计项、实施顺序、开发检查记录等），也不得用"由代码计划行承载""填在叙述栏"之类的指引句代替模板要求的实际内容。模板中的每一节要么对应表栏位由表生成，要么该节在模板中已同步删除并说明理由；不允许模板要求内容而表没有栏位可填。表栏位与工作记录表启用环节模板章节的对应关系由 R18 维护。 |
| <a id="r-18"></a>R18 | 表栏位与模板章节完整映射（表版本 2） | 每份启用工作记录表的环节模板必须能由对应表栏位完整承载：`impl_record` 增加实施依据（依据类型/具体内容/文档位置）、预期产品结果（叙述）、最低实现设计（设计项/已确认做法/选择理由/对应验收条件）、代码修改计划补回顺序、类函数或配置项、当前逻辑、前置步骤列、开发检查计划（检查命令或方法/检查范围/预期观察结果）、未决问题（叙述，禁止程序硬编码"暂无"）、实施动作记录改为行清单（实施顺序/对应计划步骤/文件/代码位置/实际执行的动作/当步反馈/状态）、开发检查记录改为行清单（检查命令或方法/检查范围/实际反馈/是否需要继续修改）；`acceptance_plan` 增加需求来源（叙述）、产品设计依据（链接清单行表）、验收范围（本主题验收/本主题不验收两列叙述行表）、完成判定（叙述），并在验收条件行清单增加"验收条件名称"列（直白短名）：生成文档的 AC 小节标题 `### AC-01：<名称>` 和需求交付追踪表"验收条件"列的 `AC-01：<具体条件>` 文字都取该列，不再有无处填写的名称；`test_plan` 的测试项行清单并入模板 13 列覆盖表的设计语义列（直白测试名称、前置测试项、测试方式、产品入口、代码入口、测试入口、准备数据、执行动作、观察位置、预期结果、不通过表现、证据要求），保留机器执行列（命令参数数组、工作目录、超时秒数、报告适配器、正式目标名称），测试方式为人工验收时机器列按 R8 条件可选；`test_result` 增加人工验收交接栏（人工验收对象/人工检查方法/自动化已经证明/还需要用户确认，混合测试必填）与测试环境和执行说明（本主题执行范围/执行顺序/未执行项）；`acceptance_result` 增加验收方式、自动化依据、机器测试记录编号、用户实际回答、人工确认、验收记录编号列（自动化不需要人工字段时程序写"不适用"；确认时间与记录编号由程序回填，与《验收并完成交付》R5 一致）；人工验收步骤计划字段（验收对象/开始前条件/操作步骤/观察内容/预期结果/用户需要回答）由 `acceptance_plan` 新增"人工验收步骤"行清单承载（按验收条件编号关联），生成器按模板渲染进结果文档，结果表不复述；`spike_conclusion` 增加可复用资产行清单（资产目录/用途/运行方法/依赖与非敏感输入/不保留内容/支撑验收条件）；`bug_record` 增加真实复现条件（叙述）、修复仍存在的不确定性（叙述）、修复与验收结果（叙述）栏位，与缺陷记录模板八节对齐。索引与追踪表口径：`qa/索引.md` 测试结果列的"无自动化测试项"标注由程序按测试项表"测试方式"列判定，不靠 AI 手写；需求交付追踪表的"验收条件"列文字取 acceptance_plan 表的编号+名称列，其余列维持程序按既有规则更新（追踪表与索引均为程序生成物，不要求建表）。以上栏位调整构成表格式变更，表版本升为 2；开工时 state 同时冻结本轮表版本号，进行中轮次不因程序升级改变已冻结的版本判定；版本 2 只对开工时冻结为版本 2 的新轮次生效（沿用 R11 冻结机制），版本 1 表与旧轮次保持现状不迁移。生成文档必须包含模板规定的全部章节且内容来自表栏位。 |
| <a id="r-21"></a>R21 | 模板与规范随表口径同步 | 表栏位映射（R18）落地时，对应环节的 `Template_Repository` 模板与 `Standardized_Repository` 规范必须同步改写为表口径：模板保留作为生成文档结构基准和栏位映射依据，删除"AI 手写文档/固定字段同行"等只对文档模式有意义的指令，改为指向对应表栏位；规范说明填写方法时以表栏位为主语。模板章节与表栏位不一致视为产品缺陷，按 R16 处理，不允许任何一方迁就另一方静默漂移。 |
| <a id="r-19"></a>R19 | 表门禁的实质内容校验 | 表模式门禁除 R4 的类型与枚举检查外，必须检查内容是否有实质，判定标准全部由程序内维护的表 schema 声明，不在运行时猜：① 占位词表——程序维护一份明确清单（至少含"无""暂无""待定""待补充""见状态文件""见测试结果""功能正常""正确处理""符合预期"及仅由标点或编号组成的值），单元格值命中即按内容问题拒绝；模板明确允许整栏写"暂无"的栏目（未决问题、实施中问题与处理、针对性回归范围、未执行项等"确无内容"语义栏）除外，但叙述栏出现"暂无"视为该栏为空，仍受③约束；② 最小信息量——自由描述列（计划修改内容、实际修改的代码逻辑、数据状态或输出的实际变化、修改理由、前置步骤、通过标准、不通过标准、实际结果说明、验收目标说明、测试范围说明、结果说明、验收说明、结论说明、同步说明、缺陷说明、各新增叙述栏等）由表 schema 逐栏声明最低长度与形态（例如不少于 15 个字符且不是编号引用），编号引用列（对应验收条件、测试项编号、前置测试项等）与枚举/机器列不受此约束；③ 必填行清单与叙述栏为空数组即内容问题拒绝：门禁必填清单为——impl_record 的实施依据、预期产品结果、代码修改计划、实际代码修改、实施动作记录、开发检查计划与检查记录、未决问题（允许写"暂无"但要按①的除外规则显式声明）、test_plan 的测试项与测试范围说明、acceptance_plan 的需求来源、验收目标说明、产品设计依据、验收范围、验收条件、人工验收步骤（存在人工或混合条件时）、完成判定、test_result 的结果说明与人工验收交接（混合主题时）、acceptance_result 的验收结果与验收说明、spike_conclusion 的穿刺项与结论说明、bug_record 全部叙述栏、design_sync 的核对项与同步说明；轮次级表（spike_conclusion、design_sync、bug_record）在对应环节被跳过或未启用时不检查；④ 表存在但缺少映射到模板章节的必填栏位按格式问题拒绝；⑤ 某主题应启用表而表文件不存在时按内容问题报"某主题缺少某表"，不静默跳过；⑥ 纯流程主题豁免——验收重做、发布核对等本轮不产生代码修改的主题，其 impl_record"代码修改计划"行的"文件"列填固定标记"无代码修改（流程动作）"时，该主题的实施依据、预期产品结果、代码修改计划、未决问题仍按①-④检查（必须有实质内容，写清流程动作是什么、何时执行、结果如何核对），"实际代码修改、实施动作记录、开发检查计划与检查记录"不要求非空；门禁的三方文件集合核对该主题只核对计划标记行存在，不把标记当作文件路径，也不要求它解释任何真实代码差异；标记行同时出现在有真实代码行的表中时按普通行报错，防止用标记绕过代码记录。失败时一次列出全部不合格栏位的位置、实际值、期望形态和修改方法（与全局失败输出要求一致）。程序只承诺拦截"无实质内容"，不评判文字质量高低；深度仍由第三道门用户确认。 |
| <a id="r-20"></a>R20 | 填写说明与模板要求同源 | 程序生成表时写入的每个"填写说明"必须写到能让不了解背景的填写者一次填对的深度：写明该栏位要填什么、从哪里取得、必须与什么保持一致（例如正式目标名称必须与报告适配器输出的目标名逐字一致；代码位置必须与最终文件真实行号范围一致；对应验收条件只允许引用本主题验收计划表存在的编号）。模板"内容边界"中对字段的每一条硬性要求，必须在对应栏位的填写说明中可找到；说明文本由程序从表 schema 与模板要求生成，不允许一句话示例代替。 |
| <a id="r-17"></a>R17 | 生成文档的导航锚点 | 程序按表生成正式文档时，必须为每个固定编号（验收条件 `AC-xx`、测试项 `TC-xx`、主题、章节）产出稳定导航锚点（如 `<a id="ac-xx">`）和一致标题，保证文档内与跨文档链接（需求交付追踪表、索引、上下游文档）能跳转到目标；锚点 ID 来自表里的固定编号，不依赖标题文字；门禁检查本地链接目标真实存在，发现锚点缺失或链接跳不到目标时报具体位置。产品设计的每份功能文档规则表中，每条规则（`R1`、`R19` 等）的编号单元格同样必须带对应锚点（如 `<a id="r-19"></a>R19`），使验收条件等下游链接能直接导航到该条规则而不只是章节开头；功能文档缺少被链接的规则锚点时按链接不可达报告。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI | 执行当前环节材料加载命令 | 程序列出材料，并为需要机器事实的主题生成或补齐工作记录表 |
| 2 | AI | 调查事实后在表中填写数据和叙述 | 固定栏目保持程序预填内容不变 |
| 3 | 程序 | 按当前表生成正式文档 | 产物目录出现格式正确的正式文档 |
| 4 | AI | 执行第二道门 | 程序重新生成文档、核对表与文档一致、检查栏目和格式，一次给出全部问题或通过结论 |
| 5 | 用户 | 确认当前环节结果 | 确认后进入下一环节；表和文档随轮次保留 |
| 6 | 用户 | 确认收工或作废 | 收工保留本轮表；作废删除本轮表 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 栏目名写错或缺失 | AI 填表时改错、漏填或多写了栏目 | 门禁拒绝并指出具体栏目、预期名称和修改方法 | 不需要猜测哪句话不符合格式 |
| 编号重复 | 同一主题的表中出现重复的测试项或验收条件编号 | 门禁拒绝并列出重复编号 | 每个编号只对应一个条目 |
| 空位没有填写 | 必填栏目为空或仍是占位说明 | 门禁拒绝并列出全部未填栏目 | 一次看到还缺什么 |
| 正式文档被直接修改 | 文档内容与按表生成的结果不一致 | 门禁要求把改动写回表；不覆盖文档，也不放行 | 手改内容不会悄悄丢失 |
| 表被写成非法内容 | 表文件无法解析或字段类型错误 | 门禁报告解析错误位置和预期格式 | 不出现程序崩溃堆栈 |
| 重复生成表 | AI 再次执行生成动作 | 已填内容保留，只补缺失固定栏目 | 不会因重复生成丢失已填事实 |
| 旧轮次无表 | 轮次在功能上线前开始 | 该轮继续按原有方式检查 | 进行中工作不受影响 |
| 环节不需要机器事实 | 环节没有对应的表定义 | 不生成表，仍按原有方式加载材料和检查 | 不产生无意义的空文件 |
| 某主题缺少本环节应启用的表 | 表模式下该主题的表不存在却被后续检查跳过 | 门禁报"某主题缺少某表"具体错误并停留当前环节，不静默跳过该主题的检查，也不退回文档模式（R11） | 缺表不会让整段检查凭空消失 |
