# 【功能】工作记录表与正式文档生成

## 1. 背景

完整研发环节需要 AI 在正式文档里提供程序可以核对的固定事实：工作流编号、验收主题、修改的文件和行号、测试项命令、验收条件编号等。过去这些事实和给人看的叙述写在同一份文档里，程序靠逐字匹配固定标题、字段行和表格来读取。AI 重新生成文档时措辞稍有偏差，门禁就找不到固定内容，于是反复出现"改一句、重查、又错在别处"的循环。

因此，本功能把"程序要核对的固定内容"和"给人看的叙述"分开：程序在环节开始时生成一份工作记录表，把固定栏目建好、把程序已知的事实（轮次编号、主题名）预先填好；AI 只在空位里填写数据和叙述；正式文档由程序按表生成。固定内容不再经过 AI 的手，门禁也不再在文章里找句子。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 开始填写环节事实 | 项目负责人、项目维护者 | 完整研发环节需要记录机器可核对的事实 | 拿到已经建好栏目、填好编号的工作记录表 | AI 只填空位，不复制模板或手写固定标题 |
| 生成正式文档 | 项目负责人、项目维护者 | AI 已经填完工作记录表 | 得到格式正确的正式文档 | 标题、编号行和表格由程序生成，叙述放进对应章节 |
| 检查环节事实 | 项目负责人、项目维护者 | AI 执行环节第二道门 | 程序核对表里的栏目、格式和编号 | 填错时指出具体栏目、预期格式和修改方法，不在文章里逐字找内容 |
| 修改已填写内容 | 项目负责人、项目维护者 | 用户看过正式文档后要求修改内容 | 修改被程序接受且不丢失 | AI 修改工作记录表，程序重新生成正式文档 |
| 处理被直接修改的正式文档 | 项目负责人、项目维护者 | 正式文档被绕过表直接编辑 | 保住手改内容，不悄悄覆盖 | 门禁指出文档与表不一致，要求把改动写回表后才放行 |
| 判断上游是否变化 | 项目负责人、项目维护者 | 后续环节核对上游内容是否被改动 | 只让真实变化使下游失效 | 失效判断按工作记录表内容计算，文档重新生成不等于内容变化 |
| 登记测试项 | 项目维护者 | 测试验证环节登记自动化测试任务 | 一次填完全部测试项 | 测试项、命令、工作目录、超时和报告适配器都填在表里，登记命令核对表而不再逐条手敲参数 |
| 查看主题清单 | 项目负责人、项目维护者 | 需要查看环节下的全部主题入口 | 打开索引文档 | 索引由程序按表汇总生成，AI 不手写 |

## 3. 功能边界

### 3.1 支持范围

- 在完整研发环节开始时，为本环节需要机器事实的每个主题生成一份工作记录表；表保存在 `.workflow_loop/records/<轮次编号>/` 下。
- 工作记录表预填程序已知的事实（轮次编号、主题名、表版本），每个空位写明要填的内容、格式和示例。
- 程序按表生成对应的正式文档：固定标题、编号行和表格由程序写入，AI 填写的叙述放进对应章节；产物目录中只出现正式文档，不出现机器文件。
- 门禁检查工作记录表：栏目名写错、多写、少写、编号重复、格式不符时，一次指出每个问题的位置、预期和修改方法。
- 程序在每次生成正式文档时记录文档内容；门禁发现正式文档与按表重新生成的结果不一致时，报告文档被直接修改，要求把改动写回表后重新生成，不直接放行也不直接覆盖。
- 第二道门检查前，程序先按当前表重新生成正式文档，再执行检查。
- 上游内容变化判定按工作记录表内容计算。
- 测试项的命令、工作目录、超时和报告适配器填写在测试记录表中；登记命令核对表并登记任务，不再逐条接受命令行参数。
- 索引文档由程序按各主题工作记录表汇总生成。
- 每份工作记录表带有表版本；一轮从开工到结束使用开工时的表版本，新表版本只对之后新开的轮次生效。
- 已经开始但未引入工作记录表的旧轮次继续按原有方式检查，不中途迁移。

### 3.2 不支持范围

- 不评判 AI 填写的叙述内容写得好不好；叙述质量由用户在第三道门确认。
- 不在产物目录（`spec/`、`acceptance/`、`qa/`、`impl/`、`bug/`）存放机器文件。
- 不允许 AI 绕过表直接生成或修改正式文档的固定部分。
- 不为无需开发任务生成工作记录表。
- 不自动迁移进行中的旧轮次。
- 不把工作记录表当成允许修改文件的白名单；额外文件仍按实际改动规则处理。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 完整研发环节需要记录机器事实 | 程序在 AI 首次加载该环节材料时生成工作记录表：栏目全部建好，轮次编号和主题名已预填，每个空位写明填写内容、格式和示例。首次加载时本环节主题尚未确定的，待主题确定后程序在下一次环节命令时补生成本环节各主题的工作记录表。表已存在时不重新生成空表，只补齐缺失的固定栏目，不覆盖已填内容。 |
| R2 | AI 填写环节事实 | AI 只修改工作记录表的空位：数据填进数据栏，叙述一段存一条。AI 不修改程序预填的固定栏目，不在正式文档中手写固定标题、编号行或表格。 |
| R3 | 生成正式文档 | 程序按当前表生成正式文档：固定部分由程序排版，叙述内容放进对应章节。产物目录只有正式文档。生成 Markdown 表格时，程序对每个单元格内容里的管道符 `|` 和换行做转义（管道符转义为 `\\|`，换行替换为 `<br>`），保证生成的表格列数和行数不被单元格内容破坏；转义在全部生成器出口统一执行，包括测试结果文档生成器。 |
| R4 | 门禁检查表 | 程序检查栏目名、填写格式、编号唯一性，并逐列校验单元格的类型和枚举值：命令参数数组必须是 JSON 数组、超时秒数必须是整数、代码位置必须符合 `L起始-L结束`、执行结论必须是 `passed` 或 `failed`、验收结论必须是 `passed`、`failed` 或 `blocked`、测试方式必须是 `自动化测试`、`人工验收` 或 `自动化测试 + 人工验收`。填错时一次列出全部问题的栏目、预期类型或枚举、实际值和修改方法，不只查非空。表 schema 为每个行清单声明每列的类型与允许的枚举值，校验按声明逐列执行；并支持条件可选——测试方式为人工验收时命令参数数组、超时秒数和报告适配器允许空，其余方式必填，不用静态可选列一刀切。工作记录表产生的检查失败标明属于格式问题还是内容问题。 |
| R5 | 正式文档与表不一致 | 门禁报告文档被直接修改，列出能确认的差异位置，要求把改动写回工作记录表；写回并重新生成前不放行。程序不把直接修改悄悄覆盖掉。 |
| R6 | 执行第二道门 | 程序先按当前表重新生成正式文档（命中手改检测时跳过重写并报告差异），再以工作记录表为唯一输入执行该环节的固定检查；固定检查不读回刚生成的文档。 |
| R7 | 判断上游内容变化 | 失效判定读取工作记录表内容；表内容不变时，仅文档重新生成不使下游失效。 |
| R8 | 登记测试任务 | 测试项信息（测试项编号、测试方式、命令参数数组、工作目录、超时秒数、报告适配器、正式目标名称、对应验收条件）填在测试记录表中；测试方式为人工验收时，命令参数数组、超时秒数和报告适配器为条件可选、允许空，其余方式必填。登记命令核对表完整并登记全部任务，不再逐条接受命令行登记参数。 |
| R9 | 生成索引 | 索引文档由程序按各主题工作记录表汇总生成；AI 不手写索引，也不把手写索引当成事实来源。 |
| R10 | 整轮作废 | 本轮工作记录表随轮次作废一起删除；作废时递归删除本轮 records 目录下全部内容（含子目录），不只删顶层文件。正式收工后本轮表保留供核对；从零清场时旧轮次的表保留，不随产物目录删除。 |
| R11 | 表版本与流程判定 | 每份工作记录表记录表版本；本轮始终使用开工时的表版本，新版表只对之后新开的轮次生效，进行中轮次不换版。门禁校验表里的表版本等于本轮开工时冻结的版本且为程序当前支持的版本，不接受任意非空值。是否走表流程以开工时该轮是否启用工作记录表为准，不以表当前是否已填写内容判断；新轮次开工时程序记录该轮启用表流程。一旦开工记录该轮启用表流程，任何情况（表未填、为空、缺失、栏目不匹配或解析失败）都不得退回文档模式，只报具体错误并停留当前环节；表尚未填写时门禁报“工作记录表尚未填写”并停留当前环节，不退回旧文档检查。实现上：state 记录开工冻结的表模式标记，门禁据此判定模式；同步环节表时不得因表为空而静默跳过或返回空导致退回文档模式，空表报“工作记录表尚未填写”并停留；判断表是否已填的检查只用于决定是否补生成空表，不用于模式判定。 |
| R12 | 旧轮次继续 | 没有工作记录表的旧轮次继续按原有文档检查方式过门，不要求补建表。 |
| R13 | 生成正式文档的路径与程序专用键 | 生成文档路径必须落在项目产物目录内；程序拒绝越出项目产物目录的路径，不向项目外部写入文件。生成文档路径和文档哈希是程序专用字段，AI 不得写入；程序不直接信任表内这两个键的任意值——生成路径由程序按产物目录规则计算并校验，文档哈希由程序重算并比对，不读表内可能被改动的哈希来判定是否手改。 |
| R14 | 表模式下固定事实的唯一来源 | 表模式下，固定事实以工作记录表为唯一输入：门禁不再从正式文档正文逐字匹配固定标题、表头或字段，也不重新解析程序生成的文档来核对格式或内容。生成文档只供人阅读和供下游环节按程序已记录的事实引用，不再被门禁按 Markdown 解析回事实。具体：实施门禁的文件清单和计划哈希一律从实施记录工作记录表取，不得读回生成的实施记录文档核对；AC 编号一律从验收计划工作记录表取，不得正则解析验收计划文档。本条与 R3 转义配套——生成文档不再被门禁解析，单元格含管道符不会再触发列数报错。 |
| R15 | 表模式承接文档模式全部校验 | 引入工作记录表的环节，表模式必须承接文档模式对固定事实的全部校验，不得因走表而跳过任何原有检查。原有文档模式检查的测试方式枚举、测试代码 Workflow-Test 标识存在与计划一致、人工验收步骤形式、代码入口形式、验收条件锚点、执行结论与验收结论枚举等，全部转为表单元格校验、测试代码校验或生成器行为；表模式不得使任何一项原有检查消失。此外表模式必须核对：验收完成时间由程序从状态记录回填并在表或文档表达；验收结果表与状态记录中当前有效的验收记录一致，表全 `passed` 但状态无记录不得放行；测试代码的工作流测试标识仍须校验，不得因走表而删除该校验。实现时须逐环节比对文档模式与表模式的全部校验项，确保不漏，包括但不限于：实施环节的未完成内容必须为“状态：无”并阻断“状态：有”、需求交付追踪表与下游一致性；测试验证环节的 AC 覆盖、测试结果机器字段与状态记录逐字段一致、已登记任务与实际测试改动、当前实施哈希、统一测试入口与回退依据、不得提前填测试通过；主题验收环节的测试执行结果、需求交付追踪表、机器测试记录编号、判定结论、上下游链接、纯人工主题标注“无自动化测试项”。 |
| R16 | 生成器按表渲染文档模板全部内容 | 程序按表生成正式文档时，必须渲染该文档模板规定的全部章节和表格，不得整段丢弃或写死模板中的任何表格（如实施记录的设计项、实施顺序、开发检查记录等）。表能表达的固定字段全部由表生成，模板中表暂未覆盖的固定结构由生成器按模板补齐，不静默省略。 |
| R17 | 生成文档的导航锚点 | 程序按表生成正式文档时，必须为每个固定编号（验收条件 `AC-xx`、测试项 `TC-xx`、主题、章节）产出稳定导航锚点（如 `<a id="ac-xx">`）和一致标题，保证文档内与跨文档链接（需求交付追踪表、索引、上下游文档）能跳转到目标；锚点 ID 来自表里的固定编号，不依赖标题文字；门禁检查本地链接目标真实存在，发现锚点缺失或链接跳不到目标时报具体位置。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI | 执行当前环节材料加载命令 | 程序列出材料，并为需要机器事实的主题生成或补齐工作记录表 |
| 2 | AI | 调查事实后在表中填写数据和叙述 | 固定栏目保持程序预填内容不变 |
| 3 | 程序 | 按当前表生成正式文档 | 产物目录出现格式正确的正式文档 |
| 4 | AI | 执行第二道门 | 程序重新生成文档、核对表与文档一致、检查栏目和格式，一次给出全部问题或通过结论 |
| 5 | 用户 | 确认当前环节结果 | 确认后进入下一环节；表和文档随轮次保留 |
| 6 | 用户 | 确认收工或作废 | 收工保留本轮表；作废删除本轮表 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 栏目名写错或缺失 | AI 填表时改错、漏填或多写了栏目 | 门禁拒绝并指出具体栏目、预期名称和修改方法 | 不需要猜测哪句话不符合格式 |
| 编号重复 | 同一主题的表中出现重复的测试项或验收条件编号 | 门禁拒绝并列出重复编号 | 每个编号只对应一个条目 |
| 空位没有填写 | 必填栏目为空或仍是占位说明 | 门禁拒绝并列出全部未填栏目 | 一次看到还缺什么 |
| 正式文档被直接修改 | 文档内容与按表生成的结果不一致 | 门禁要求把改动写回表；不覆盖文档，也不放行 | 手改内容不会悄悄丢失 |
| 表被写成非法内容 | 表文件无法解析或字段类型错误 | 门禁报告解析错误位置和预期格式 | 不出现程序崩溃堆栈 |
| 重复生成表 | AI 再次执行生成动作 | 已填内容保留，只补缺失固定栏目 | 不会因重复生成丢失已填事实 |
| 旧轮次无表 | 轮次在功能上线前开始 | 该轮继续按原有方式检查 | 进行中工作不受影响 |
| 环节不需要机器事实 | 环节没有对应的表定义 | 不生成表，仍按原有方式加载材料和检查 | 不产生无意义的空文件 |
