# 【功能】生成产品设计文档

## 1. 背景

Workflow Loop 的产品设计阶段完成需求讨论和共同理解确认后，需要形成统一的产品总说明和功能说明，供后续代码设计、开发、测试和验收使用。

因此，用户确认产品设计后，需要把已经确认的内容整理成规定结构的产品设计文档。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零生成产品设计文档 | 产品提出者 | 从零产品设计已经得到用户确认 | 建立完整的产品总说明和功能文档 | 后续阶段获得经过确认的产品设计依据 |
| 更新已有产品设计文档 | 产品提出者、已有项目维护者 | 本次产品变化已经得到用户确认 | 只更新受影响的产品内容 | 文档准确反映新增、修改和删除，未受影响内容保持不变 |
| 根据已有代码建立产品设计文档 | 已有项目维护者 | 项目已有代码但缺少完整产品文档，当前行为已经通过现有文档、代码和安全运行校准 | 一次建立当前产品设计 | 文档反映用户当前能够实际使用的产品行为 |
| 修 bug 前初始化产品设计 | 已有项目维护者 | 修 bug 时发现项目设计尚未初始化 | 先建立现有产品设计，作为缺陷复现和修复依据 | 修复过程有明确的产品行为和规则依据 |

## 3. 功能边界

### 3.1 支持范围

- 用户确认共同理解后，生成或修改产品总说明和功能文档。
- 生成包含九章的产品总说明。
- 为每件可以独立完成的用户事情生成包含七章的功能文档。
- 在产品总说明中维护功能清单和真实文档链接。
- 修改已有产品时，只更新用户已经确认受影响的文档。
- 已有代码但缺少产品文档时，根据经过校准的当前产品行为建立全部必要文档。
- 修 bug 时，项目设计未初始化才建立产品设计文档。

### 3.2 不支持范围

- 不负责确认前的事实调查和需求讨论。
- 不生成代码架构、接口、数据库、实施步骤、测试记录或验收记录。
- 不在用户确认共同理解前生成或修改产品设计文档。
- 不根据提示词、文件名、代码结构或当前运行结果推断产品诞生原因和历史设计原因。
- 修 bug 需要改变产品行为、产品规则或功能边界时，不继续按修 bug 生成文档，必须改为修改已有产品。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 开始生成或修改文档 | 必须已经存在用户明确确认的共同理解。 |
| R2 | 写产品诞生背景或历史设计原因 | 只能使用用户已经确认的内容或明确的历史文档；当前代码和运行结果不能作为历史原因依据。 |
| R3 | 写当前产品行为 | 可以使用现有产品文档、代码和运行结果核实；发现冲突时继续查证，不自行选择一种解释。 |
| R4 | 生成产品总说明 | 必须包含产品背景与目标、术语、用户与场景、产品边界、产品组成与主要流程、产品通用规则、产品功能、相关文档、修改记录九章。 |
| R5 | 生成功能文档 | 必须包含背景、场景、功能边界、规则、使用过程、异常情况、修改记录七章。 |
| R6 | 判断是否拆成功能 | 一份功能文档对应一件可以独立完成的用户事情，不按按钮、页面或代码模块拆分。 |
| R7 | 一条规则对整个产品或多个功能生效 | 写入产品总说明的“产品通用规则”，不在多份功能文档中重复。 |
| R8 | 产品功能清单增加功能 | 必须同时存在对应功能文档和可用链接。 |
| R9 | 没有相关内容 | 写“暂无”，不得编造背景、目标、规则、异常情况或功能设计原因。 |
| R10 | 修改已有产品 | 只修改用户已经确认受影响的内容；删除功能前必须取得用户确认。 |
| R11 | 修 bug | 产品设计未初始化时建立产品设计文档；已经初始化时使用现有文档；需要改变产品行为时改为修改已有产品。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI 产品设计师 | 接收用户已经确认的共同理解，并确认当前属于哪种场景 | 明确需要新建、修改、删除或保持不变的文档 |
| 2 | AI 产品设计师 | 分别核对产品历史依据和当前行为依据 | 历史原因不会从代码推断，当前行为不会在证据冲突时直接定论 |
| 3 | AI 产品设计师 | 生成或修改产品总说明的全部九章 | 产品全貌、产品通用规则、功能入口、相关文档和修改记录完整 |
| 4 | AI 产品设计师 | 按独立用户事情拆分功能，并为每个功能填写全部七章 | 每件独立用户事情都有对应功能文档 |
| 5 | AI 产品设计师 | 在产品总说明中建立功能清单和真实链接 | 用户可以从产品总说明进入每份功能文档 |
| 6 | AI 产品设计师 | 检查章节、事实依据、用户与执行角色、边界、规则归位、链接和技术内容 | 文档结构完整，没有编造、重复、冲突或技术实现内容 |
| 7 | 用户 | 检查生成或修改后的产品设计文档 | 用户确认后，产品设计文档成为后续阶段的产品依据 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 共同理解尚未确认 | 用户还没有明确确认产品设计总结 | 停止生成或修改文档，继续需求讨论 | 不会提前生成未确认的产品设计 |
| 产品历史没有依据 | 产品诞生背景或历史设计原因没有用户确认，也没有明确历史文档 | 停止填写相关内容并向用户确认，或者明确标记未确认 | 当前代码不会被当成产品历史依据 |
| 当前产品行为无法确认 | 现有文档、代码和运行表现缺失或互相冲突 | 继续查证，并把仍无法确定的差异交给用户决定 | 推测不会被写成当前产品事实 |
| 已有项目无法安全运行 | 缺少运行条件，或者运行需要生产账号、真实数据、付费服务或外部写入 | 说明无法运行的原因；高风险运行先取得用户同意 | 未验证的产品行为会被明确标记 |
| 功能链接失效 | 产品功能清单指向不存在的文件 | 创建缺失文档或修正链接后再完成 | 产品总说明中的功能入口均可使用 |
| 产品通用规则重复 | 同一规则同时出现在多份功能文档 | 移到产品总说明并从功能文档中删除重复内容 | 同一产品规则只维护一处 |
| 修 bug 时产品设计已经初始化 | 已有完整、经过确认的产品设计 | 不重新生成产品设计文档，直接使用现有文档 | 修复以现有产品设计为依据 |
| 修 bug 需要改变产品行为 | 修复方案改变产品规则、功能边界或用户可见结果 | 停止按修 bug 处理，改为修改已有产品 | 产品变化会先经过产品设计确认 |
| 删除功能未获确认 | 修改已有产品时准备删除功能，但用户没有明确同意 | 保留原功能和文档，继续讨论影响 | 不会擅自删除现有产品功能 |
