# Workflow Loop — 产品总说明

## 1. 产品背景与目标

### 1.1 产品背景

用户让 AI 修改软件项目时，真正需要管理的不是某一份设计文档，而是从项目接入、需求确认、代码修改到测试验收和正式收工的完整过程。只靠提示词提醒 AI 自觉执行，会出现材料没读、环节跳过、旧结论继续沿用、测试结果没有真实执行依据、修改失败后无法恢复等问题。

Workflow Loop 因此把这套过程安装到项目中。AI 负责执行命令、读取材料、调查和修改；用户负责确认产品决定、重要执行范围和最终结果；程序负责保存状态并用门禁阻止不满足固定条件的流程继续推进。

但不是每个项目任务都需要修改产品或代码。修改说明文档、调查项目、执行已准备好的提交或发布等无需开发任务，如果仍被强制走完设计、实施、测试和验收全链路，会产生与任务无关的步骤和文档。Workflow Loop 因此同时提供一条简单的无需开发流程。

### 1.2 产品目标

- 用户只需提出需求，不需要记忆或手动执行日常工作流命令。
- 用户可以从公开仓库的中文 README 了解产品能力、使用边界和环境要求，并使用当前操作系统对应的正式安装入口开始使用。
- 已经安装 Workflow Loop 的项目可以在发布新版本后单独更新，不自动影响其它项目。
- 用户可以从一个项目中卸载 Workflow Loop，或单独卸载电脑上的全局命令。
- 项目维护者可以用一条命令把当前仓库内容作为新版本发布，不必重复手工修改版本、提交、推送和创建发布标签。
- 从安装到项目开始，到 `done`（正式收工）或 `abort`（整轮作废）为止，每个正常环节都有明确的进入条件、执行者、产物、检查和下一步。
- 完整研发流程只保留会形成独立决定或独立结果的用户可见环节，避免为尚未执行的代码预设计或可连续完成的测试动作增加单独确认。
- 无需开发的任务在用户确认路线后，通过“逐题聊清、直接执行、核对结果”完成，不生成与任务无关的研发过程文档。
- 产品设计、现状架构基线（如有）、验收计划、代码计划、代码实施、代码结果、测试计划、测试代码、测试结果和验收结果使用同一组已经确认的依据；最终代码设计只在交付收尾时根据真实实现同步。
- 程序能够检查文件、状态、顺序、链接、执行记录和其它固定事实；需要产品判断和证据质量判断的内容仍由 AI 调查并由用户确认。
- 修改需要退回上游时，只重做真正受影响的内容；整轮不再继续时，项目能够恢复到本轮开始前。
- macOS、Linux 和原生 Windows PowerShell 都能安装并运行同一套工作流。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 工作流轮次 | 用户提出一项工作后，从开工到正式收工或整轮作废的一次完整过程。程序标识为 Workflow Run。 |
| 工作意图 | 本轮要完成的事情，分为从零创建、修改产品、修复缺陷和无需开发任务四种。程序分别使用 `from_scratch`、`product_change`、`bugfix` 和 `light_task`；`light_task` 表示“无需开发任务”，不表示工作量一定小。 |
| 环节 | 三种完整研发流程路径上的具名工作阶段。程序标识为 Stage，例如产品设计、代码实施、测试验证和整体验收。无需开发任务不拆分这些研发环节。 |
| 门禁 | 完整研发流程的当前环节未满足固定条件时，阻止进入下一环节的程序关卡。每个正式环节依次经过讨论完成、程序检查和用户确认三道门；无需开发任务不使用这套逐环节门禁。 |
| 校验凭据 | 程序检查通过后保存的当前依据摘要，包含本次检查真正使用的文件和状态。用户确认时，如果这些依据没有变化，程序直接复用检查结果，不再重复完整检查。 |
| 测试验证 | 程序标识为 `qa` 的单一用户可见环节。用户确认测试范围后，AI 连续完成测试计划、测试代码、正式执行和结果整理；测试完成后用户再确认最终结果。 |
| 代码实施三段 | 一个代码实施环节内部的三个连续步骤：代码计划、代码实施和代码结果。它们不是三个独立环节；用户只确认计划和最终结果，中间不增加门禁。 |
| 产物模板 | 规定一份长期保存的正式文档最终要包含哪些章节、字段和内容边界的文件。 |
| 工作规范 | 规定 AI 在当前环节怎样调查、讨论、执行和检查的文件。 |
| 状态快照 | `state.json`，保存本轮现在进行到哪里、哪些门禁已通过以及当前仍有效的执行和验收记录。 |
| 追加历史 | `journal.jsonl`，按发生顺序保存本轮的重要动作、失败、退回、失效和确认历史。 |
| 统一测试入口 | 当前项目用于执行最终全量测试的一条项目专属命令或脚本，由测试验证环节根据项目真实技术栈确认。 |
| 正式收工 | 完整研发流程的所有必经环节通过，或无需开发任务的结果得到用户确认后，执行 `done`，记录本轮已完成并允许开始下一轮。 |
| 整轮作废 | 执行 `abort` 停止本轮。三种完整研发轮次恢复已登记的受管内容；无需开发轮次不保存回退副本，作废时保留项目和外部系统的实际状态。 |
| 项目更新 | 在一个已经安装 Workflow Loop 的项目根目录，把电脑上的全局命令和当前项目管理文件更新到同版本的新正式版本。 |
| 项目卸载 | 从当前项目删除 Workflow Loop 管理内容，不删除项目业务代码和正式产物。 |
| 全局卸载 | 从当前电脑删除共享的全局 `workflow` 命令，不删除任何项目文件。 |
| 人工发布 | 项目维护者主动把当前仓库内容作为一个新正式版本提交、推送并创建发布标签；“人工”表示由维护者承担跳过发布前检查的风险。 |

## 3. 用户与场景

### 3.1 用户

| 用户 | 与产品的关系 | 主要需求 |
|---|---|---|
| 项目负责人 | 提出产品需求并决定产品目标、范围和是否接受最终结果 | 清楚知道当前做到哪里、需要确认什么以及最终交付是否满足需求 |
| 项目维护者 | 使用 AI 修改已有项目、修复缺陷或继续未完成工作 | 让修改依据、代码、测试和验收保持一致，并能在失败或作废时恢复 |
| 验收人 | 对需要人工判断的验收条件和整体验收作出决定 | 获得可以实际操作、观察和复核的验收说明，而不是只被询问“是否通过” |

### 3.2 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 了解并把工作流安装到项目 | 项目负责人、项目维护者 | 用户访问公开仓库，目标项目尚未安装 Workflow Loop | 先了解产品和环境要求，再用一条与当前终端匹配的命令完成电脑侧和项目侧安装 | 用户能找到真实可用的正式安装入口；安装范围提前可见，全部成功后项目可以开工 |
| 从零创建产品 | 项目负责人 | 项目准备从零开始建立产品和代码 | 从产品设计开始完成代码、测试和验收 | 所有必经环节通过后正式收工 |
| 修改已有产品 | 项目负责人、项目维护者 | 已有产品需要新增、修改或删除用户可见行为 | 只修改受影响设计和实现，并验证完整产品没有回归 | 受影响主题重新完成，未受影响结果按规则保留，最终全量测试通过 |
| 修复产品缺陷 | 项目维护者 | 已有行为偏离已经确认的产品设计 | 复现缺陷、查明根因、完成修复和回归 | 缺陷只有在主题验收、最终全量回归和整体验收全部通过后关闭 |
| 完成无需开发任务 | 项目负责人、项目维护者 | 任务不改变产品规则、源代码、测试代码或会影响运行的配置 | 聊清目标后直接完成文档、调查或已准备好的操作 | 用户不走完整研发链路，仍能确认执行范围和最终结果 |
| 继续进行中的工作 | 项目负责人、项目维护者 | 项目已经存在尚未结束的工作流轮次 | 继续当前环节，而不是误开另一轮 | AI 说明当前状态和实际下一步 |
| 返回上游修正 | 项目负责人、项目维护者 | 后续环节发现上游设计、计划、代码或测试需要改变 | 先退回正确环节，再修改并使受影响结果失效 | 不会拿旧结论继续通过后续门禁 |
| 中途整轮作废 | 项目负责人、项目维护者 | 用户决定本轮全部修改都不要 | 恢复本轮开始前的受管内容 | 本轮标记为已作废，项目可以重新开工 |
| 更新已安装项目 | 项目维护者 | Workflow Loop 发布了更高正式版本，项目仍在使用旧版本 | 只更新当前项目和电脑全局命令 | 当前项目管理文件与全局命令达到同一个更高版本，项目代码、正式产物和运行状态保留 |
| 人工发布正式版本 | 项目维护者 | 当前仓库内容已经由维护者自行判断可以发布，并已决定一个新的版本号 | 用一条命令完成版本更新、提交、推送和发布标签创建 | 当前仓库内容进入远程默认分支，新标签触发现有公开发布流程 |
| 卸载当前项目 | 项目维护者 | 某个项目不再使用 Workflow Loop | 从目标项目根目录强制卸载 | 当前项目的 Workflow Loop 管理内容被删除，业务代码和正式产物保留 |
| 卸载电脑全局命令 | 项目维护者 | 这台电脑不再需要共享的 Workflow Loop 命令 | 删除全局命令和命令搜索路径 | 所有项目文件保留，但依赖该全局命令的项目暂时不能执行工作流命令 |

## 4. 产品边界

<a id="41-支持范围"></a>
### 4.1 支持范围

- 公开源码仓库固定为 `https://github.com/yuzyf/workflow_loop`；支持由该仓库的 GitHub Release 和 PyPI 共同提供正式安装，当前正式版本为 `0.3.1`。
- 公开仓库提供中文 `README.md`（项目说明文档），面向准备把工作流安装到自己项目的维护者，说明产品定位、能力与边界、工作流程、环境要求、正式安装、最小使用示例、命令含义、源码开发、仓库目录和详细设计入口。
- 公开仓库和 Python 分发包使用同一句项目简介“为 AI 驱动的软件开发提供有状态、可验证、可回退的工作流管理。”，作者为 `yuzyf`，使用 MIT 许可证，版权文字为 `Copyright (c) 2026 yuzyf`。
- 支持 macOS、Linux 和原生 Windows PowerShell。
- 支持从零创建、修改产品、修复缺陷和无需开发任务四种工作意图。
- 支持按项目事实生成本轮环节路径，并继续已有的进行中轮次。
- 支持无需开发任务在用户确认路线后，逐题聊清、直接执行、核对结果并结束。
- 支持每个环节加载 AI 必读的产物模板、工作规范、全局写作规范和附加材料。
- 支持产品设计、首次项目设计初始化、技术不确定性验证、缺陷复现、验收计划、代码实施、测试验证、主题验收、最终全量回归、整体验收和最终代码设计同步。从零创建的代码计划同时确定开工所需的最低限度实现设计；修改产品的代码计划以现状架构基线和真实代码为依据。
- 支持按用户确认的目标退回上游、使受影响结果失效并重新完成必要环节。
- 支持本轮代码和文档修改的回退基线，以及整轮作废恢复。
- 支持状态查询、追加历史、需求到测试和验收结果的追踪。
- 支持从项目根目录把全局命令和当前项目管理文件更新到最新正式版本或指定的更高版本。
- 支持项目维护者从 Workflow Loop 源码仓库用一个新版本号直接发布当前内容。
- 支持从项目根目录强制卸载当前项目，及单独卸载电脑上的全局命令。

### 4.2 不支持范围

- 不替用户决定产品目标、产品范围、风险取舍、人工验收结果或整体验收结果。
- 不用无需开发任务修改正式产品规则、源代码、测试代码，以及会改变运行、构建、测试、部署或依赖的配置。
- 不声称程序能够证明 AI 已经阅读、理解或正确遵守材料；程序只验证材料清单已经提供且没有在讨论后被替换。
- 不用关键词检查、文件哈希或命令文字冒充产品语义、测试断言和证据质量判断。
- 不提供一条适用于所有项目的固定全量测试脚本；Qt、Node、Python 等项目使用各自真实工具链。
- 不在安装时自动安装 Python；没有 Python 3.11 或更高版本时，说明要求并停止安装。
- 不在第一版自动处理绕过工作流直接修改文件、同时运行多个修改状态的命令或断电写坏状态文件等非正常使用；更新或卸载过程中断属于用户需要根据命令报告重新处理的异常。
- 不保存已经作废的本轮正式产物副本；已经形成结论并登记的可复用穿刺代码及其最小非敏感依赖不属于这条清理范围，仍按穿刺规则保留。
- 更新不保存旧版本文件备份，不能恢复被覆盖的 Workflow Loop 管理文件；卸载不恢复安装前文件。
- 人工发布不执行本地测试、构建、发布前状态检查或二次确认；维护者需要自行承担当前内容、远程状态和公开发布失败的风险。

## 5. 产品组成与主要流程

<a id="51-产品组成"></a>
### 5.1 产品组成

| 产品部分 | 作用 | 关联功能 |
|---|---|---|
| 说明、发布与接入 | 通过公开仓库说明产品和环境要求，允许维护者直接发布当前仓库内容，由 GitHub Release 与 PyPI 提供同一正式版本，再把全局命令与项目骨架作为一次安装完成，并提供后续更新和卸载入口 | 发布正式版本、安装到项目、更新已安装项目、卸载 Workflow Loop |
| 轮次管理 | 判断继续旧工作还是按工作意图开始新一轮，并保存当前状态 | 开始或继续一轮工作 |
| 阶段材料与门禁 | 给 AI 指出当前必读材料，用程序检查固定条件，并等待用户确认 | 推进并确认工作环节 |
| 无需开发任务 | 在不修改产品或代码时，通过路线确认、逐题讨论、直接执行和结果确认完成工作 | 处理无需开发任务 |
| 设计与调查 | 确认产品行为、代码设计、缺陷事实和技术不确定性 | 维护产品设计、维护代码设计、复现产品缺陷、验证技术不确定性 |
| 计划与实施 | 先明确验收结果，再完成包含必要实现设计的代码实施，并保护修改前内容 | 制定验收与测试计划、实施并保护项目修改、维护代码设计 |
| 测试与验收 | 在一个测试验证环节内确认范围、形成计划、复用或修改测试代码、执行主题测试并生成结果，再完成人工验收和最终全量测试 | 制定验收与测试计划、编写并执行测试、验收并完成交付 |
| 返回与结束 | 退回受影响环节，或以正式收工、整轮作废结束当前轮次 | 返回上游修正、作废并恢复工作流、验收并完成交付 |

<a id="52-主要流程"></a>
### 5.2 主要流程

1. 用户从公开仓库的中文 README 了解产品与环境要求，再在目标项目根目录执行当前操作系统对应的正式安装命令；安装器说明全部写入范围，用户确认后完成电脑侧和项目侧安装。
2. 用户直接向 AI 提出需求。AI 自动检查是否已有进行中轮次；有则继续，没有则根据事实推荐从零创建、修改产品、修复缺陷或无需开发任务，由用户确认后开始。
3. 前三种工作意图根据项目现状生成完整环节路径，研发主干统一按“验收计划、代码实施、测试验证”推进。代码实施内部依次完成代码计划、代码实施和代码结果；从零创建的代码计划还要确定项目入口、模块职责、共享状态、依赖和测试入口等最低限度实现设计；修改产品的代码计划要根据现状架构基线和真实代码确定实现方案。无需开发任务不生成这条研发路径：AI 每次只问一个问题，用户确认讨论完毕后直接执行，核对结果并等待用户确认完成。
4. 完整研发流程的每个正式环节先由程序列出 AI 必读材料的绝对路径和用途。AI 读取全部材料，调查真实项目，并与用户聊清当前问题。
5. 完整研发流程中，用户确认当前环节已经聊清楚后，第一道门允许 AI 生成文档、修改代码或准备执行；第二道门检查固定条件并保存校验凭据；AI 把结果交给用户，用户明确同意后第三道门只核对凭据仍与当前依据一致，再进入下一环节。依据没有变化时不重复完整检查。
6. 后续发现上游需要改变时，AI 先调查并说明应退回哪里，用户确认后由程序清除受影响的旧结果，再从目标环节继续。
7. 测试验证环节开始时，用户确认一次测试范围和通过标准；AI 随后按“计划检查、复用或修改测试代码、冻结测试代码清单、登记任务、正式执行、生成结果”的顺序连续完成。程序按机器执行记录生成或回填测试结果，用户确认一次最终结果后进入主题验收。全部主题验收完成后，程序在当前完整代码上运行项目统一测试入口。
8. 用户完成整体验收后，AI 根据最终代码同步代码架构设计；最后执行正式收工。
9. 用户在正式收工前决定整轮不要时，执行整轮作废。完整研发轮次恢复开工前的受管内容；无需开发轮次保留当时的实际状态并结束。
10. Workflow Loop 发布更高版本后，用户进入目标项目根目录，执行 `workflow update` 或对应系统的更新脚本；程序先显示当前版本、目标版本和覆盖范围，确认后更新全局命令及当前项目管理文件。
11. 用户不再使用某个项目时，在该项目根目录执行 `workflow uninstall`；用户不再使用这台电脑的全局命令时，执行 `workflow uninstall --global`。两种卸载都先显示删除范围并确认一次。
12. 项目维护者决定跳过本地发布检查时，在 Workflow Loop 源码仓库执行 `uv run python scripts/release.py <新版本号>`；脚本更新当前发布身份和依赖锁定结果，纳入当前全部未忽略修改，提交并推送默认分支，再创建并推送对应版本标签，由现有远程发布流程继续处理。

<a id="6-产品通用规则"></a>
## 6. 产品通用规则

| 规则 | 适用范围 | 具体说明 |
|---|---|---|
| 日常命令由 AI 执行 | 安装后的全部工作流环节 | 用户直接表达需求和确认决定，不负责记忆命令。AI 可以显示准确命令，但必须同时说明命令要解决什么、会做什么、不会做什么、执行结果和用户是否需要参与。 |
| 三道门按顺序执行 | 三种完整研发流程的每个正式环节 | 第一道门记录当前问题已经聊清楚并允许开始产出；第二道门检查程序能够判断的固定条件并保存校验凭据；第三道门只在用户看过当前结果并明确同意后推进。第三道门只核对当前依据是否仍与凭据一致，不在状态未变时重新执行完整检查。 |
| 同一状态只完整校验一次 | 全部门禁 | 同一环节的受管文件、相关状态和检查规则没有变化时，程序复用最近一次通过的校验凭据。只有凭据绑定的依据变化、凭据缺失或检查规则版本变化时，才重新执行完整检查，并一次列出具体变化。 |
| 门禁失败一次说全 | 全部完整研发环节的第一、第二和第三道门，以及验证失效和退回检查 | 一次命令必须展示当前能够独立确认的全部问题。这条规则同时覆盖门内的文档、状态、代码、测试、链接、追踪和执行记录检查，不允许只在最外层改写提示。每项问题都要写明检查项、具体文件和行号或具体状态、预期、实际、证据、影响范围及下一动作，不能只报告总指纹变化或“相关内容需要重新处理”等笼统原因。因前置问题而无法可靠检查的项目必须标为“未检查”并写明依赖，不能猜测为失败。相同状态下重复执行同一命令时，问题清单和顺序保持一致，并明确要求先修改，不能引导 AI 原样重试。 |
| 下一条命令唯一且完整 | 全部工作流命令输出 | 每次命令结束时只给出当前唯一有效的下一条完整命令，同时说明由谁执行、该命令是否会自动执行测试或其它实际动作，以及什么结果算成功。AI 必须原样执行这条命令，不追加管道、截断、重定向或命令串联，以免丢失问题清单或读错退出状态。没有独立文档的环节不能使用“可以写产出文件”等通用提示；命令名称和适用范围必须准确，不能让 AI 通过试错寻找入口。 |
| 复用已有代码是成功路径 | 代码实施和测试验证 | 现有产品代码或测试代码已经满足当前计划时，用户可以明确确认复用。程序保存复用依据并继续，不要求制造无意义的文件变化；确认后相关代码再次变化时，旧复用决定失效。 |
| 代码实施三段式 | 代码实施 | 先完成代码计划，再连续执行代码修改，最后形成代码结果。代码计划写清文件、顺序、风险和完成标准；代码实施中不新增用户门禁；代码结果必须逐项说明计划与实际是否一致、实际改动和未完成内容。 |
| 验证绑定只包含所属内容 | 计划、测试和验收失效检查 | 每份校验凭据只绑定该环节负责的内容。测试计划只绑定测试范围、入口、步骤和通过标准，不绑定后续测试结果链接、执行状态或验收状态；正常的下游更新不能被误判为测试计划变化。 |
| 测试验证作为单一环节 | 从零创建、修改产品和修复缺陷 | 用户在环节开始时确认一次测试范围和通过标准，AI 随后连续完成计划、测试代码、正式执行和结果整理，程序在内部步骤之间自动检查；完成后用户只确认一次最终测试结果。安装依赖、使用生产凭据或修改外部数据等额外风险动作仍须单独取得用户同意。 |
| 测试计划和结果分开保存 | 测试验证 | 测试计划记录执行前准备验证什么，测试结果记录机器实际执行了什么。结果文档由程序根据当前机器记录生成或回填固定事实，AI 只补充人能理解的说明，不能重复手抄命令、入口、编号和输出事实。 |
| 测试验证不依赖最终代码设计 | 测试验证 | 测试验证读取现状架构基线（如有）、已经确认的代码计划和代码结果、真实代码及测试配置；最终代码设计尚未同步时也可以完成测试。 |
| 核心代码快照保持最小范围 | 实施、测试和验证失效 | 实施快照只包含现状代码设计、用户确认的本轮代码计划和最终代码结果明确登记的核心代码文件；测试快照只包含测试计划登记的测试文件、统一测试入口和本轮明确修改的测试配置。程序不遍历整个项目或按后缀猜测范围；未登记路径全部忽略，包括依赖安装内容、构建产物、缓存和运行数据。 |
| 无需开发任务保持简单 | 无需开发任务 | 只保留路线确认、逐题聊清、直接执行和结果确认。不生成验收计划、测试计划或实施记录，不保存回退副本，不加入文件哈希门禁或固定全量测试。 |
| 材料必须先读 | 每个环节开始时 | 程序输出必读文件的绝对路径、用途和顺序；AI 使用文件读取工具读取全文。门禁不能把文件清单记录冒充阅读证明。 |
| 模板、规范和门禁各负其责 | 全部环节 | 产物模板只规定长期保存的文档最终长什么样；工作规范只规定 AI 怎样工作；门禁代码只执行可以明确判断的固定约束。没有独立长期产物的环节不为凑数创建模板。 |
| 用户决定产品与验收 | 产品设计、风险选择、人工验收、整体验收 | AI 先调查并给出建议，程序保存确认事实，但不能替用户作出决定。 |
| 正式产物使用中文文件名 | 用户阅读和维护的正式文档 | `spec`、`acceptance`、`qa`、`impl` 和 `bug` 等固定目录名保持英文；产品说明、计划、结果、索引和记录文件使用稳定、安全的中文文件标识。程序命令和机器状态文件保持英文标识并当场解释中文含义。 |
| 研发主干顺序统一 | 从零创建、修改产品和修复缺陷 | 验收计划先说清什么结果算完成，然后进入代码实施的代码计划、代码实施、代码结果，再进入单一测试验证环节完成测试计划、测试代码、主题执行和结果整理。新轮次和正在进行的旧轮次都使用这一顺序，不保留拆分测试阶段的选项。 |
| 穿刺可复用资产保留 | 技术不确定性穿刺 | 能够产生穿刺结论且以后可复用的代码，连同重现结论必需的最小非敏感样本、配置、依赖说明和执行脚本，继续保存在 `.workflow_loop/spike_tmp/<工作流编号>/<穿刺项标识>/`。工作完成后不自动删除，只有用户明确要求才清理；敏感信息、缓存、日志和纯结果输出不得保留。 |
| 穿刺资产进入全局追踪 | 技术穿刺、验收计划、代码实施和测试验证 | 需求交付追踪表增加穿刺结论与可复用内容记录，只关联实际支撑的验收条件；一项穿刺支撑多条验收条件时，在对应多行重复链接。后续复用必须重新运行，不能把历史结论直接当作当前结论；不能运行时标记“待修订”但不自动删除。 |
| 项目设计初始化时机 | 从零创建和已有项目 | 首次接入已有项目在项目设计初始化确认后记录初始化完成；从零创建只有最终代码完成并确认最终代码设计同步后才设置“项目设计已初始化”，旧已完成项目保留原标记。 |
| 正式文档链接真实可用 | 工作流管理的正式文档 | 本地链接必须能打开已存在的目标文件；需要定位到文档内具体位置时，必须使用文档中已明确写出的稳定定位编号，不依赖标题文字自动生成的位置。尚未生成的未来产物只写普通路径并标明“待生成”，不提前写成可点击链接。 |
| 历史标准坏链接受控修复 | 旧版工作流模板生成的正式文档 | 历史链接修复必须使用单独动作，先展示准备修改的文件、原链接和目标位置，用户确认后才修复能够确定为旧模板产生的标准写法。执行时要么全部修改成功，要么保持原文档不变；修改后重新扫描并确认没有新增坏链接。用户手写或目标不明确的链接只报告，不自动改写；项目更新本身不修改正式产物。 |
| 公开产品身份保持一致 | 公开仓库、README、Python 包和正式发布 | GitHub 仓库和本地项目目录使用 `workflow_loop`，Python 导入包使用 `workflow_loop`，用户可见产品名使用 `Workflow Loop`，PyPI 分发包和命令版本身份使用 `workflow-loop`。 |
| 公开说明和分发元数据保持一致 | 公开仓库、README（项目说明文档）、Python 包和许可证 | 项目简介固定为“为 AI 驱动的软件开发提供有状态、可验证、可回退的工作流管理。”，作者固定为 `yuzyf`，许可证固定为 MIT，版权文字固定为 `Copyright (c) 2026 yuzyf`，项目主页和源码地址都指向 `https://github.com/yuzyf/workflow_loop`。 |
| 每次公开发布使用唯一版本号 | GitHub 正式发布页、PyPI、README、安装脚本、命令身份和项目安装标记 | 当前公开发布统一使用 `0.3.1`。以后需要公开新内容时，必须使用一个未在 PyPI 发布过的新版本号，并同步更新本次发布涉及的全部版本位置；不能覆盖或重发已有版本。下一个具体版本号在对应发布需求中决定。 |
| 人工发布以命令调用作为确认 | 发布正式版本 | 维护者执行 `uv run python scripts/release.py <新版本号>` 就表示确认按当前仓库内容发布并自行承担风险。脚本不在本地执行测试、构建、远程版本查询或二次确认；它仍会拒绝覆盖本地已有的同名标签，任一步实际操作失败时立即停止，不强制覆盖，也不自动回滚已经完成的提交、推送或标签。 |
| 人工发布纳入当前修改 | 发布正式版本 | 脚本把当前仓库中全部未被忽略的修改纳入发布提交，不只提交脚本自己改动的版本文件。历史发布记录和历史验收产物不因版本替换被批量改写。 |
| 当前阶段才可推进 | 全部门禁 | 命令只能操作状态快照中的当前环节，不能提前确认后续环节或跳过必经环节。 |
| 先退回再改上游 | 已确认的设计、计划、代码或测试需要变化时 | AI 调查原因并提出目标环节，用户确认后执行返回命令；程序使受影响门禁、执行记录和结果失效，然后才允许修改。 |
| 只重做直接受影响主题 | 修改产品、代码或测试后 | AI 根据具体依赖和实际影响指出需要重做的主题；不能只因整个代码快照不同就删除无关主题结果。最终全量回归始终在最新完整代码上重新执行。 |
| 项目专属统一测试入口 | 测试验证与最终全量回归 | 测试验证环节根据项目真实技术栈确认或生成环境准备和统一入口。没有入口、无法启动、超时或退出码非零都不能通过最终全量回归。修改前不额外要求整套测试先全部通过。 |
| 测试事实由程序记录 | 正式主题测试与最终全量回归 | 正式测试由程序直接执行登记的参数数组并记录命令、环境、时间、退出码和代码版本；结果文档中的固定事实由程序从机器记录生成或回填，AI 不能手写“已通过”或重复抄录机器字段代替执行。 |
| 实施前保存真实回退内容 | 实施代码、测试代码、统一测试入口和项目配置 | 修改前保存原文件内容或“原本不存在”，整轮作废时据此恢复；代码计划调整不能用已经改过的内容覆盖原始副本。 |
| 安装和作废必须完整 | 安装与整轮作废 | 安装要么全部成功，要么恢复确认前状态；作废要么全部恢复成功后标记已作废，要么明确失败，不能留下“看似成功”的半完成状态。 |
| 正式收工不重复确认 | 最后一个环节或无需开发任务完成后 | 完整流程最后一个环节的第三道门，或无需开发任务的结果确认，已经是最后一次用户确认；`done` 只登记本轮完成、记录结束时间并允许下一轮，不再询问一次相同问题。 |
| 更新只作用于当前项目 | 项目更新 | 更新命令必须从目标项目根目录执行；只更新该项目和电脑全局命令，不自动修改其它已安装项目。 |
| 更新版本方向 | 项目更新 | `workflow update` 默认使用 PyPI 最新正式版本；`--version` 只能指定高于或等于当前项目版本的正式版本，不允许降级。目标版本等于当前版本时不修改文件。 |
| 更新覆盖范围 | 项目更新 | 直接覆盖 `AGENTS.md`、`Template_Repository`（模板仓库）和 `Standardized_Repository`（规范仓库），只更新 `project.json`（项目级状态文件）中的安装版本；保留该文件的其它项目级状态，以及 `state.json`（当前轮次状态）、`journal.jsonl`（操作历史）、`rollback/`（回退资料）、业务代码和正式产物。 |
| 更新无备份 | 项目更新 | 更新不保存旧版本文件。更新失败时不回滚，必须报告全局命令版本和项目版本，用户可以重新执行更新。 |
| 更新允许进行中轮次 | 项目更新 | 当前项目有进行中的 Workflow Run（工作流轮次）时仍可更新；模板或规范变化后，后续工作流命令要求重新读取受影响材料并重新确认结论。 |
| 卸载当前项目 | 项目卸载 | `workflow uninstall` 无论当前轮次状态如何都允许执行；确认后删除 `AGENTS.md`、整个 `.workflow_loop/` 和安装残留，不删除业务代码、正式产物或电脑全局命令。 |
| 卸载电脑全局命令 | 全局卸载 | `workflow uninstall --global` 只删除电脑上的全局 `workflow` 命令和命令搜索路径，不删除任何项目文件；确认前必须说明其它项目将暂时不能运行工作流。 |
| 重复更新和卸载 | 更新、卸载 | 已是目标版本时更新不修改文件；项目已经没有管理内容时卸载按成功处理；只剩部分管理内容时，卸载删除检测到的残留。 |
| 发布更新和卸载脚本 | 公开发布 | 每个正式版本在 GitHub Release 附带 `update.sh`、`update.ps1`、`uninstall.sh` 和 `uninstall.ps1`；旧版本没有对应命令时，用脚本在项目根目录完成第一次更新或卸载。 |

## 7. 产品功能

| 功能 | 一句话说明 | 对应场景 | 详细文档 |
|---|---|---|---|
