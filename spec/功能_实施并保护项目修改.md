# 【功能】实施并保护项目修改

## 1. 背景

代码实施既要解决用户已经确认的问题，也要保证整轮放弃时能够恢复。只写任务清单就直接改代码，会让计划与实际脱节；只保存文件哈希而不保存原内容，整轮作废时也无法真正恢复。

因此，本功能在同一个实施环节中固定分成“代码计划、代码实施、代码结果”三个连续步骤：先确认全部主题的代码计划，随后连续修改代码，最后记录并核对实际结果。代码计划说明预期行为、主要改法、风险和完成标准，不是允许修改文件的白名单。从零创建时，代码计划同时写明项目入口、模块职责、共享状态、依赖和测试入口等最低限度实现设计。用户只确认代码计划和代码结果，中间不增加门禁。恢复依据是独立能力：Git 工作区或用户主动建立的备份可以支持整轮作废，但缺少恢复依据不能阻止代码门禁。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 制定代码计划 | 项目维护者 | 产品设计、现状架构基线和验收计划已经确认 | 先确定具体文件、代码改法、顺序、风险和完成标准 | 每项计划都能追溯到产品设计、现状代码和验收条件 |
| 按计划实施产品修改 | 项目维护者 | 代码计划已经确认 | 连续修改真实代码并执行必要的开发检查 | 每项实际代码变化都能追溯到产品设计、验收条件和修改理由 |
| 发现额外实现文件 | 项目维护者 | 实施中发现完成已确认行为还需要修改计划外文件 | 直接修改并在代码结果中记录文件、理由和验收关联 | 不重设基线、不重新讨论；门禁按实际改动检查该文件 |
| 核对代码结果 | 项目维护者 | 代码修改已经完成 | 对照实际改动记录每个文件、理由、验证证据和未完成内容 | 代码结果能说明最终交付事实，用户只在此处确认一次 |
| 调整实施中的代码计划 | 项目维护者 | 实施时发现原代码改法需要调整，但产品行为和验收条件不变 | 更新计划说明或直接在代码结果说明实际做法 | 不增加用户门禁，不把正常发现当成失败 |
| 复用已经完成的实施代码 | 项目维护者 | 返回实施环节后，现有代码仍符合最新上游计划 | 复核并明确接受现有代码，不制造无意义修改 | 实施环节重新确认，后续测试仍重新执行 |
| 建立恢复保障 | 项目维护者 | 项目需要承诺整轮自动恢复 | 使用 Git 工作区、用户备份或其它可信恢复点保存恢复依据 | 整轮作废时只恢复能够真实证明的内容 |
| 多主题共享一段代码 | 项目维护者 | 一段公共逻辑同时服务多个验收主题 | 只在一个主题中完整记录修改，其他主题链接并说明依赖 | 公共代码不重复维护，同时每个主题仍能追溯 |

## 3. 功能边界

### 3.1 支持范围

- 根据已确认的产品设计、已有项目现状架构基线、验收计划和穿刺结论制定代码计划，不依赖尚未制定的测试计划或测试项。从零创建时，代码计划本身承担最低限度实现设计。
- 使用 `impl/索引.md` 继承验收索引中的主题顺序和前置关系。
- 为每个主题维护 `impl/<主题文件标识>_实施记录.md`，在同一文档中分开保存代码计划、代码实施过程和代码结果；已引入工作记录表的轮次中，该文档由程序按工作记录表生成，AI 在表中填写代码计划、实际改动和代码结果。
- 按已确认计划修改真实生产代码，并记录实际文件、代码符号、处理逻辑、数据、状态、输出和开发检查反馈。
- 产品行为和验收条件不变时，允许在实施环节内调整代码改法和增加实际文件，不增加用户确认或重新开始实施。
- 代码门禁读取实际改动表，要求每个实际改动文件都有修改理由、验收条件关联和足够的测试证据；不要求实际文件与计划文件完全相等。
- 首次进入代码实施时完整展示“计划是预期、额外文件可修改、实际改动需说明和验证”的过程；后续门禁只展示本次实际改动和缺失证据。
- 恢复依据与代码门禁分开。Git 工作区、用户主动建立的备份或其它可验证恢复点可以支持整轮作废；没有可靠依据时程序明确说明自动恢复范围，不把它伪装成代码门禁失败。

### 3.2 不支持范围

- 不在实施环节重新确定、改名、拆分或合并验收主题。
- 不因实现困难降低验收条件或改变产品规则，也不在实施环节预先编造测试范围或测试项。
- 不把实施过程中的局部测试、类型检查、静态检查或构建反馈写成正式测试结果。
- 不在本功能中执行正式主题测试、主题验收、最终全量回归或整体验收。
- 不用整项目压缩包、文件修改时间或文件名猜测本轮修改范围。
- 不因文件没有出现在最初计划中而拒绝代码门禁、清除讨论状态或要求重设基线。
- 不把依赖安装内容、构建输出、缓存、日志或临时运行数据登记为核心代码。
- 不负责执行整轮作废和恢复；恢复依据由用户选择的 Git 工作区、备份或其它恢复点提供，实际恢复由“作废并恢复工作流”功能完成。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| <a id="r-1"></a>R1 | 开始代码计划 | 必须先有已经确认的产品设计和验收计划；已有项目使用当前现状架构基线，有穿刺结论时同时作为实施依据。从零创建必须在本计划中写清最低限度实现设计。测试计划和测试项在实施完成后制定，不是实施前提。 |
| <a id="r-2"></a>R2 | 代码计划讨论开始 | 智能体先说明用户要解决的实际问题、最终产品结果、全部主题、主题依赖、共享代码、已确认依据和仍未解决的问题。 |
| <a id="r-3"></a>R3 | 讨论单个主题 | 必须写清该主题的用户问题、完成结果、验收条件、真实代码位置和当前逻辑、准备修改的具体逻辑、数据或状态或输出变化、依赖和公共代码。 |
| <a id="r-4"></a>R4 | 仍有会影响实施的未决问题 | 继续调查和讨论，或者返回对应上游环节；未解决前不能确认计划或修改代码。 |
| <a id="r-5"></a>R5 | 生成代码计划和结果文档 | 每个验收主题一份实施记录，包含实施依据、代码计划、代码实施记录、代码结果和直接上下游文档；不能按目录、函数或孤立任务另建主文档。 |
| <a id="r-6"></a>R6 | 生成实施索引 | `impl/索引.md` 只继承并展示验收索引的主题关系和文档入口，不重新制定主题顺序，也不保存实施运行状态。 |
| <a id="r-7"></a>R7 | 开始代码实施 | 当前工作流的全部主题都必须先完成代码计划并由用户确认，不能边计划一个主题边提前修改另一个主题的代码。 |
| <a id="r-8"></a>R8 | 开始代码实施 | 代码计划确认后可以直接修改代码；不执行 `workflow gate impl --prepare-code`，也不要求代码基线先通过。 |
| <a id="r-9"></a>R9 | 使用恢复保障 | 需要整轮自动恢复时，使用 Git 工作区、用户主动备份或其它真实恢复点；恢复保障独立记录，不作为代码门禁前置条件。 |
| <a id="r-10"></a>R10 | 恢复依据不足 | 程序明确说明哪些内容无法自动恢复；仍允许按实际改动、验收条件和测试证据执行代码门禁。 |
| <a id="r-11"></a>R11 | 按代码计划实施 | 实际代码必须满足已确认的产品行为和验收条件，代码结果必须与最终代码一致；计划文件之外的必要改动允许存在，但必须记录理由和验证证据。 |
| <a id="r-12"></a>R12 | 代码实施中调整代码改法 | 产品行为和验收条件不变时继续实施；可更新计划说明，但不重新确认计划、不重设基线。 |
| <a id="r-13"></a>R13 | 发现额外修改路径 | 直接把额外路径写入代码结果，记录它为何支撑已确认验收条件；不能因路径不在计划中阻止实施。 |
| <a id="r-15"></a>R15 | 实施中发现上游需要改变 | 从零创建或修改产品时，产品行为变化返回产品设计；修复缺陷必须改变产品行为时作废本轮，再开始修改产品轮次。验收条件变化返回验收计划，新的技术不确定性由用户决定是否返回穿刺；必须先完成正确的返回或作废，再修改上游。 |
| <a id="r-16"></a>R16 | 已经离开实施环节后需要改代码计划 | 使用 `workflow return --to impl --reason <具体原因>` 返回实施环节；命令中文含义是“记录原因并使受影响下游结果失效后重新实施”。 |
| <a id="r-17"></a>R17 | 形成代码结果 | 写清实际文件、覆盖真实差异的最终文件行号范围、实际逻辑、数据或状态或输出变化、每个文件的修改理由、对应产品设计和验收条件、测试证据及未完成内容；未完成内容没有时写“状态：无”。 |
| <a id="r-18"></a>R18 | 记录开发检查 | 只保存实际命令或方法、检查范围、反馈和是否还需修改；这些内容是开发反馈，不是正式测试通过证据。 |
| <a id="r-19"></a>R19 | 多主题共享代码 | 在一个相关主题实施记录中完整说明公共代码；其它主题说明它怎样满足本主题并链接详细位置，不能把细节只放在索引。 |
| <a id="r-20"></a>R20 | 已有代码和从零代码 | 已有代码必须查看真实文件、调用关系和测试；从零且尚无代码时，把位置标为“新增”，不能编造当前逻辑。 |
| <a id="r-21"></a>R21 | 当前代码已经是有效实施结果 | 使用 `workflow gate impl --accept-existing-code`；该命令中文含义是“复核并接受现有实施代码”，不表示跳过实施或测试。确认后代码必须保持不变。 |
| <a id="r-22"></a>R22 | 测试验证修改测试代码 | 测试验证按实际测试改动、验收关联和真实执行证据判断，不把测试文件回退清单作为测试门禁前置。 |
| <a id="r-23"></a>R23 | 测试验证修改统一测试入口 | 入口脚本或配置变化必须记录其测试范围影响和真实执行证据；需要自动恢复时使用独立恢复保障，不能等同于测试门禁基线。 |
| <a id="r-24"></a>R24 | 本轮正常收工或整轮作废完成 | 临时回退副本和清单由结束功能清理，不作为长期产物保留，也不归档已经作废的文件内容。 |
| <a id="r-25"></a>R25 | 当前工作流进行中 | 同一工作区出现无关改动时，程序把它与本轮实际改动分开显示；不能把无关路径当成本轮失败，也不能承诺能够自动恢复它。 |
| <a id="r-26"></a>R26 | 通过代码结果检查 | 程序检查主题文档、可取得的实际改动、代码结果、验收关联和测试证据；智能体核对最终代码和结果记录；用户确认代码结果后进入测试验证环节。 |
| <a id="r-27"></a>R27 | 取得实际改动 | Git 项目读取当前提交、已暂存、未暂存和未跟踪文件形成实际改动表；无法取得可信完整改动表时明确标为“未能自动完整确认”，不伪造文件结论。 |
| <a id="r-28"></a>R28 | 显示代码门禁过程 | 第一次进入实施时完整显示五步过程；代码门禁显示实际文件、修改理由、验收关联、测试证据和缺失项，不重复整段说明。 |
| <a id="r-29"></a>R29 | 检查实施变化 | 每个能够确定属于本轮的实际改动文件都必须有代码结果记录、修改理由和验收关联；缺少测试证据时列为失败。计划中未修改的文件、计划外但已说明的文件都不是失败原因。 |
| <a id="r-30"></a>R30 | 额外文件改变产品范围 | 额外文件带来未确认的用户行为、产品规则或验收条件时，返回正确上游环节；仅为实现已确认行为增加文件时留在实施环节。 |
| <a id="r-31"></a>R31 | 已引入工作记录表的轮次制定代码计划或形成代码结果 | AI 在程序生成的实施工作记录表中填写计划文件、实际改动文件、行号范围、修改理由、验收关联、测试证据和未完成状态；实施记录文档由程序按表生成，AI 不手写固定标题和表格。详见[工作记录表与正式文档生成](./功能_工作记录表与正式文档生成.md)。 |
| <a id="r-32"></a>R32 | 已引入工作记录表的轮次实施记录表覆盖模板全部字段 | 实施记录表的实际代码修改栏补“对应计划步骤”列以与模板 8 列对齐；代码修改计划栏按模板补齐顺序、类函数或配置项、当前逻辑、数据状态输出变化、前置步骤等列，不得比模板少列。同时在实施记录工作记录表中增加“设计项”和“开发检查记录”行清单，使 2.2 最低实现设计和 3.4.2 开发检查记录都由表生成、不留占位句；实施计划哈希据表内容计算，不再读生成的实施记录文档。生成器对照实施记录模板逐表渲染全部固定表格（设计项、实施顺序、开发检查记录等），占位句不算渲染，不整段丢弃或写死。详见[工作记录表与正式文档生成](./功能_工作记录表与正式文档生成.md) R16。 |
| <a id="r-33"></a>R33 | 纯流程主题的代码结果核对豁免 | 某主题本轮不产生代码修改（验收重做、发布核对等流程动作）时，其实施记录表"代码修改计划"行的"文件"列填固定标记"无代码修改（流程动作）"；代码门禁的三方文件集合核对该主题只核对计划标记行存在，不把标记当文件路径，也不要求实际代码修改、实施动作记录、开发检查计划与检查记录非空；实施依据、预期产品结果、代码修改计划说明与未决问题仍必须有实质内容；标记行与真实代码行混在同一张表时按普通行核对，不允许用标记绕过代码记录。详见[工作记录表与正式文档生成](./功能_工作记录表与正式文档生成.md) R19⑥。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 程序 | 指出代码计划模板、实施工作规范、代码开发规范和相关上游文档路径 | 智能体获得实施前必须读取的全部材料 |
| 2 | 智能体 | 读取产品设计、现状架构基线、验收计划、穿刺结论和真实代码 | 建立全部主题的代码计划依据和代码影响范围 |
| 3 | 智能体、用户 | 先确认整轮实施范围，再逐个主题确认具体文件、代码符号、逻辑变化、数据与状态变化、前置步骤、公共代码、顺序、风险和完成标准 | 所有会影响代码实施的问题在动手前得到解决 |
| 4 | 智能体 | 生成实施索引和全部主题的代码计划 | 每个代码修改步骤能追溯到产品设计、现状代码和验收条件 |
| 5 | 用户 | 确认全部主题代码计划已经聊清楚 | 程序展示代码门禁完整过程；AI 可以直接开始实现 |
| 6 | 智能体 | 按确认计划连续修改真实代码；发现额外文件时直接修改并记录理由 | 正常发现不增加门禁或重新确认 |
| 7 | 智能体 | 根据最终代码补充实际代码修改、修改理由、验收关联、测试证据和未完成内容 | 代码结果说明真正改了什么，不用计划冒充事实 |
| 8 | 程序、智能体 | 程序检查实际改动表和文档证据；智能体核对最终代码、结果记录和每项验收条件 | 只暴露缺理由、缺验收关联或缺测试证据的具体项 |
| 9 | 用户 | 阅读代码结果和检查结论并明确确认 | 程序进入测试验证环节；正式测试和验收尚未发生 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 实施依据尚未确认 | 产品设计、代码设计或验收计划仍有未决内容 | 停止实施并返回对应上游环节 | 不会用代码实现替用户补需求和完成标准 |
| 全部主题计划尚未确认 | 只有部分主题写完代码计划 | 不允许准备代码基线或修改任何主题的生产代码 | 多主题实施不会出现先改代码、后补总体计划 |
| 计划文件路径不明确 | 文档只写模块名，无法定位真实文件或新增路径 | 补充具体文件和代码位置后再准备基线 | 程序不会猜测应该备份哪些文件 |
| 恢复依据不足 | 项目没有 Git 隔离工作区、用户备份或其它可信恢复点 | 显示不能自动恢复的范围，但不阻止实施或代码门禁 | 用户知道恢复风险，不会被虚假的基线失败打断 |
| 实施中发现额外文件 | 完成已确认行为需要改计划外文件 | 继续实施，在代码结果中补充文件、理由、验收关联和测试证据 | 正常发现不会重设基线或要求重新确认计划 |
| 代码计划需要调整 | 代码改法变化，但产品行为和验收条件不变 | 更新计划说明或在代码结果说明实际做法 | 不需要无意义地退回上游或增加用户门禁 |
| 产品或验收范围发生变化 | 实施发现产品行为或验收条件必须改变 | 从零创建或修改产品按对应上游返回；修复缺陷必须改产品时作废本轮并另开修改产品轮次；随后才更新文档和处理受影响结果 | 实施人员不能自行降低需求，也不会让修复缺陷返回本轮不存在的产品设计环节 |
| 实际代码缺少理由或证据 | 实际改动文件没有修改理由、验收关联或足够测试证据 | 只列出缺失的文件和证据，补齐后重新执行代码门禁 | 文件在计划外本身不是失败原因 |
| 开发检查失败 | 局部测试、构建、类型检查或静态检查发现问题 | 调查是代码、计划、测试还是环境问题，在正确环节修正 | 失败只作为开发反馈，不会生成正式通过结果 |
| 工作区混入无关修改 | 当前轮次进行中时，同一目录出现另一项需求的受管修改 | 停止继续混合修改，改用独立代码目录处理无关工作 | 整轮回退不会误删或覆盖另一项需求 |
| 安装或构建产物变化 | 运行依赖安装、开发服务器、构建、覆盖率或缓存工具 | 这些未登记路径不进入核心代码快照，不会使实施失效 | 不会因依赖安装、构建或缓存产物反复退回实施 |
| 核心代码摘要变化 | 已登记核心代码的整体摘要与确认时不同 | 比较逐文件快照后再决定失效范围 | 一次看到具体新增、修改、删除或类型变化的全部路径，不只看到“代码变了” |
| 纯流程主题无代码可记 | 主题本轮只执行流程动作（验收重做、发布核对等） | 计划行"文件"列填"无代码修改（流程动作）"标记，门禁豁免代码结果类栏位（R33） | 不会被"实际改动缺少记录"误拦，也不给真实代码改动留绕过口子 |
