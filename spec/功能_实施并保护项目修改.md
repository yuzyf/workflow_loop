# 【功能】实施并保护项目修改

## 1. 背景

代码实施既要解决用户已经确认的问题，也要保证整轮放弃时能够恢复。只写任务清单就直接改代码，会让计划与实际脱节；只保存文件哈希而不保存原内容，整轮作废时也无法真正恢复。

因此，本功能在同一个实施环节中固定分成“代码计划、代码实施、代码结果”三个连续步骤：先确认全部主题的代码计划，再保存计划修改文件的真实原内容，随后连续修改代码，最后记录并核对实际结果。从零创建时，代码计划同时写明项目入口、模块职责、共享状态、依赖和测试入口等最低限度实现设计。用户只确认代码计划和代码结果，中间不增加门禁。统一测试入口、产品代码和测试代码由各自首次修改前的环节共同补齐一份本轮回退清单，为后续整轮作废提供可靠恢复依据。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 制定代码计划 | 项目维护者 | 产品设计、现状架构基线和验收计划已经确认 | 先确定具体文件、代码改法、顺序、风险和完成标准 | 每项计划都能追溯到产品设计、现状代码和验收条件 |
| 按计划实施产品修改 | 项目维护者 | 代码计划已经确认且回退基线已经保存 | 连续修改真实代码并执行必要的开发检查 | 每项代码变化都能追溯到产品设计、代码计划和验收条件 |
| 核对代码结果 | 项目维护者 | 代码修改已经完成 | 对照计划和真实代码记录实际改动、偏差和未完成内容 | 代码结果能说明计划与实际是否一致，用户只在此处确认一次 |
| 调整实施中的代码计划 | 项目维护者 | 实施时发现原代码改法需要调整，但产品行为和验收条件不变 | 停止修改，更新并重新确认代码计划 | 最新实施仍受确认计划约束，原始回退副本不被覆盖 |
| 复用已经完成的实施代码 | 项目维护者 | 返回实施环节后，现有代码仍符合最新上游计划 | 复核并明确接受现有代码，不制造无意义修改 | 实施环节重新确认，后续测试仍重新执行 |
| 保存修改前内容 | 项目维护者 | 统一测试入口、生产代码、测试代码或相关配置即将首次修改 | 保存原内容或“原本不存在”的记录 | 整轮作废时可以准确恢复或删除本轮新增文件 |
| 多主题共享一段代码 | 项目维护者 | 一段公共逻辑同时服务多个验收主题 | 只在一个主题中完整记录修改，其他主题链接并说明依赖 | 公共代码不重复维护，同时每个主题仍能追溯 |

## 3. 功能边界

### 3.1 支持范围

- 根据已确认的产品设计、已有项目现状架构基线、验收计划和穿刺结论制定代码计划，不依赖尚未制定的测试计划或测试项。从零创建时，代码计划本身承担最低限度实现设计。
- 使用 `impl/索引.md` 继承验收索引中的主题顺序和前置关系。
- 为每个主题维护 `impl/<主题文件标识>_实施记录.md`，在同一文档中分开保存代码计划、代码实施过程和代码结果。
- 在全部主题计划确认后、任何生产代码修改前，保存计划修改文件的原内容或“原本不存在”记录。
- 按已确认计划修改真实生产代码，并记录实际文件、代码符号、处理逻辑、数据、状态、输出和开发检查反馈。
- 产品行为和验收条件不变时，允许在实施环节内更新并重新确认代码修改计划。
- 让代码实施和测试验证环节在各自首次修改前，把产品代码、统一测试入口、测试文件和相关配置加入同一份整轮回退清单。
- 核心代码快照只包含现状架构基线已登记的真实文件，以及本轮已确认代码计划和最终代码结果中的文件。
- 为每个纳入快照的路径保存当时是否存在、文件类型和内容摘要，以便后续直接列出新增、修改、删除或类型变化。

### 3.2 不支持范围

- 不在实施环节重新确定、改名、拆分或合并验收主题。
- 不因实现困难降低验收条件或改变产品规则，也不在实施环节预先编造测试范围或测试项。
- 不把实施过程中的局部测试、类型检查、静态检查或构建反馈写成正式测试结果。
- 不在本功能中执行正式主题测试、主题验收、最终全量回归或整体验收。
- 不用整项目压缩包、文件修改时间或文件名猜测本轮修改范围。
- 不遍历整个项目并根据文件后缀猜测核心代码；不把未登记路径的变化当成实施失效原因。
- 不把依赖安装内容、构建输出、缓存、日志或临时运行数据登记为核心代码。
- 不负责执行整轮作废和恢复；本功能负责准备可靠回退依据，实际恢复由“作废并恢复工作流”功能完成。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 开始代码计划 | 必须先有已经确认的产品设计和验收计划；已有项目使用当前现状架构基线，有穿刺结论时同时作为实施依据。从零创建必须在本计划中写清最低限度实现设计。测试计划和测试项在实施完成后制定，不是实施前提。 |
| R2 | 代码计划讨论开始 | 智能体先说明用户要解决的实际问题、最终产品结果、全部主题、主题依赖、共享代码、已确认依据和仍未解决的问题。 |
| R3 | 讨论单个主题 | 必须写清该主题的用户问题、完成结果、验收条件、真实代码位置和当前逻辑、准备修改的具体逻辑、数据或状态或输出变化、依赖和公共代码。 |
| R4 | 仍有会影响实施的未决问题 | 继续调查和讨论，或者返回对应上游环节；未解决前不能确认计划或修改代码。 |
| R5 | 生成代码计划和结果文档 | 每个验收主题一份实施记录，包含实施依据、代码计划、代码实施记录、代码结果和直接上下游文档；不能按目录、函数或孤立任务另建主文档。 |
| R6 | 生成实施索引 | `impl/索引.md` 只继承并展示验收索引的主题关系和文档入口，不重新制定主题顺序，也不保存实施运行状态。 |
| R7 | 开始代码实施 | 当前工作流的全部主题都必须先完成代码计划并由用户确认，不能边计划一个主题边提前修改另一个主题的代码。 |
| R8 | 准备代码回退基线 | 执行 `workflow gate impl --prepare-code`；该命令中文含义是“按已确认计划保存实施代码的修改前内容”。成功前不得修改计划中的生产文件。 |
| R9 | 保存已有文件 | 在 `.workflow_loop/rollback/<工作流编号>/` 保存真实原内容；状态快照只保存副本路径、原文件哈希和计划文件清单，不能只存哈希却声称可以恢复。 |
| R10 | 保存计划新增文件 | 登记“本轮开始前不存在”，整轮作废时删除本轮新增文件；不能为不存在的文件伪造空白原内容。 |
| R11 | 校验回退基线 | 副本缺失、路径无法确认、原文件在保存前后发生未说明变化或哈希不一致时，不允许开始实施。 |
| R12 | 按代码计划实施 | 实际代码必须符合当前确认的代码计划，代码结果也必须与最终代码一致；实际做法变化时先更新并重新确认计划，最终代码变化时同步更新代码结果，不能用“计划与实际有差异”放行。 |
| R13 | 代码实施中只调整代码改法 | 如果产品行为和验收条件不变，立即停止继续修改，更新代码计划并由用户重新确认，再次准备代码基线后继续。原文件副本必须保留，不能被实施中的内容覆盖。 |
| R14 | 新计划增加修改路径 | 只有该路径尚未修改时，才补充保存其原内容或不存在记录；已经修改但没有原始副本的路径不能事后补成可靠基线。 |
| R15 | 实施中发现上游需要改变 | 从零创建或修改产品时，产品行为变化返回产品设计；修复缺陷必须改变产品行为时作废本轮，再开始修改产品轮次。验收条件变化返回验收计划，新的技术不确定性由用户决定是否返回穿刺；必须先完成正确的返回或作废，再修改上游。 |
| R16 | 已经离开实施环节后需要改代码计划 | 使用 `workflow return --to impl --reason <具体原因>` 返回实施环节；命令中文含义是“记录原因并使受影响下游结果失效后重新实施”。 |
| R17 | 形成代码结果 | 写清实际文件、覆盖真实差异的最终文件行号范围、实际逻辑、数据或状态或输出变化、与代码计划的偏差和未完成内容，以及对应产品设计、代码计划和验收条件；未完成内容没有时写“状态：无”。 |
| R18 | 记录开发检查 | 只保存实际命令或方法、检查范围、反馈和是否还需修改；这些内容是开发反馈，不是正式测试通过证据。 |
| R19 | 多主题共享代码 | 在一个相关主题实施记录中完整说明公共代码；其它主题说明它怎样满足本主题并链接详细位置，不能把细节只放在索引。 |
| R20 | 已有代码和从零代码 | 已有代码必须查看真实文件、调用关系和测试；从零且尚无代码时，把位置标为“新增”，不能编造当前逻辑。 |
| R21 | 当前代码已经是有效实施结果 | 使用 `workflow gate impl --accept-existing-code`；该命令中文含义是“复核并接受现有实施代码”，不表示跳过实施或测试。确认后代码必须保持不变。 |
| R22 | 准备测试代码修改 | 测试验证环节在首次修改测试代码前把已有测试文件和测试配置加入同一回退清单，程序检查新增文件并登记为原本不存在。 |
| R23 | 准备统一测试入口修改 | 测试验证环节必须先保存入口脚本原内容或不存在记录，并保存原项目入口配置；不能等修改后再补基线。 |
| R24 | 本轮正常收工或整轮作废完成 | 临时回退副本和清单由结束功能清理，不作为长期产物保留，也不归档已经作废的文件内容。 |
| R25 | 当前工作流进行中 | 同一工作区不能同时混入与当前需求无关的受管文档、代码、测试和配置修改；需要并行无关工作时使用独立代码目录。 |
| R26 | 通过代码结果检查 | 程序检查主题文档、代码计划、代码变化、回退副本和代码结果；智能体双向核对计划、最终代码和结果记录；用户确认代码结果后进入测试验证环节。 |
| R27 | 确定核心代码快照范围 | 取当前代码设计的已登记文件、本轮用户确认的代码计划文件和最终实施记录文件的并集。范围外文件不参与核心代码快照。 |
| R28 | 保存核心代码快照 | 程序保存逐文件路径、存在状态、文件类型和内容摘要，再由这些事实生成整体摘要；不得只保存一个无法说明变化来源的总摘要。 |
| R29 | 检查实施变化 | 只对核心代码范围内的路径比较代码计划、真实变化和代码结果；异常时一次按计划未修改、计划外核心代码修改、已修改但未记录、已记录但无真实变化分类列全部路径。 |
| R30 | 未登记文件发生变化 | 核心代码快照不处理该变化，不因它退回实施或清除测试结果。确实属于产品实现时，先将真实路径补入代码计划并由用户确认。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 程序 | 指出代码计划模板、实施工作规范、代码开发规范和相关上游文档路径 | 智能体获得实施前必须读取的全部材料 |
| 2 | 智能体 | 读取产品设计、现状架构基线、验收计划、穿刺结论和真实代码 | 建立全部主题的代码计划依据和代码影响范围 |
| 3 | 智能体、用户 | 先确认整轮实施范围，再逐个主题确认具体文件、代码符号、逻辑变化、数据与状态变化、前置步骤、公共代码、顺序、风险和完成标准 | 所有会影响代码实施的问题在动手前得到解决 |
| 4 | 智能体 | 生成实施索引和全部主题的代码计划 | 每个代码修改步骤能追溯到产品设计、现状代码和验收条件 |
| 5 | 用户 | 确认全部主题代码计划已经聊清楚 | 程序允许准备回退基线，但仍不允许直接跳过基线改代码 |
| 6 | 程序 | 按计划文件清单保存已有文件真实内容和新增文件的不存在记录，并为已登记核心代码保存逐文件快照 | 本轮获得可恢复的真实原内容，后续也能列出准确变化路径 |
| 7 | 智能体 | 按确认代码计划连续修改真实代码，运行必要的局部检查；计划需要调整时先停下并重新确认 | 代码变化始终受当前计划约束，中间不增加用户门禁 |
| 8 | 智能体 | 根据最终代码补充实际代码修改、开发检查记录、计划偏差和未完成内容 | 代码结果说明真正改了什么，不用计划冒充事实 |
| 9 | 程序、智能体 | 程序检查代码变化、文件清单、回退副本和文档一致性；智能体双向核对代码计划、最终代码、代码结果和每项验收条件 | 漏改、越界修改、缺失副本和计划差异会在推进前暴露 |
| 10 | 用户 | 阅读代码结果和检查结论并明确确认 | 程序进入测试验证环节；正式测试和验收尚未发生 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 实施依据尚未确认 | 产品设计、代码设计或验收计划仍有未决内容 | 停止实施并返回对应上游环节 | 不会用代码实现替用户补需求和完成标准 |
| 全部主题计划尚未确认 | 只有部分主题写完代码计划 | 不允许准备代码基线或修改任何主题的生产代码 | 多主题实施不会出现先改代码、后补总体计划 |
| 计划文件路径不明确 | 文档只写模块名，无法定位真实文件或新增路径 | 补充具体文件和代码位置后再准备基线 | 程序不会猜测应该备份哪些文件 |
| 代码在基线前已经变化 | 计划确认前或副本保存前，目标文件出现未说明修改 | 停止并调查来源；只有用户明确确认当前代码是新的实施前现状时，才能重设基线并重新确认计划 | 已修改内容不会被冒充成原始副本 |
| 回退副本缺失或哈希不一致 | 已有文件没有真实副本，或者保存记录与文件不一致 | 阻止实施门禁，先修复回退基线 | 整轮恢复能力不可靠时不会继续扩大修改 |
| 新计划加入已修改但未备份的路径 | 实施过程中发现还需修改一个已经动过的未登记文件 | 停止实施；不能事后把当前内容当成原内容，需根据真实情况返回或由用户决定处理 | 回退清单不会保存错误基线 |
| 代码计划需要调整 | 代码改法变化，但产品行为和验收条件不变 | 在实施环节更新计划、重新确认并再次准备基线，保留首次原始副本 | 不需要无意义地退回上游，也不会绕过用户确认 |
| 产品或验收范围发生变化 | 实施发现产品行为或验收条件必须改变 | 从零创建或修改产品按对应上游返回；修复缺陷必须改产品时作废本轮并另开修改产品轮次；随后才更新文档和处理受影响结果 | 实施人员不能自行降低需求，也不会让修复缺陷返回本轮不存在的产品设计环节 |
| 实际代码与计划不一致 | 最终实现多改、漏改或采用未经确认的逻辑 | 停止通过门禁，修正代码或重新确认合法计划后再核对 | 不会用差异说明代替计划一致性 |
| 开发检查失败 | 局部测试、构建、类型检查或静态检查发现问题 | 调查是代码、计划、测试还是环境问题，在正确环节修正 | 失败只作为开发反馈，不会生成正式通过结果 |
| 工作区混入无关修改 | 当前轮次进行中时，同一目录出现另一项需求的受管修改 | 停止继续混合修改，改用独立代码目录处理无关工作 | 整轮回退不会误删或覆盖另一项需求 |
| 安装或构建产物变化 | 运行依赖安装、开发服务器、构建、覆盖率或缓存工具 | 这些未登记路径不进入核心代码快照，不会使实施失效 | 不会因依赖安装、构建或缓存产物反复退回实施 |
| 核心代码摘要变化 | 已登记核心代码的整体摘要与确认时不同 | 比较逐文件快照后再决定失效范围 | 一次看到具体新增、修改、删除或类型变化的全部路径，不只看到“代码变了” |

## 7. 修改记录
