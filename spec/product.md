# Workflow Loop — 产品总说明

## 1. 产品背景与目标

### 1.1 产品背景

用户使用 AI 进行产品开发时，需要先确认产品要解决什么问题、支持哪些行为，再根据这些产品决定设计代码和安排开发。

产品设计和初步代码设计完成后，仍可能存在只能通过真实接口、真实文件、目标平台或实际运行才能确认的技术事实。如果这些不确定性直接进入实施计划，后续可能按照错误的接口返回、性能判断或平台能力开发。

Workflow Loop 因此需要同时管理产品设计和技术不确定性验证：先形成用户确认的产品依据，再在进入计划前把确实需要实际验证的不确定性转成真实证据。

### 1.2 产品目标

- 进入代码设计前，产品背景、目标、用户、场景、边界、规则和功能拆分已经得到用户确认。
- 进入实施或修复计划前，会影响设计和计划的技术不确定性已经得到真实验证，或者用户已经明确接受剩余风险和后续检查安排。
- 产品设计、代码设计、穿刺结论、实施计划、测试和验收使用同一组已确认事实，不互相矛盾。
- 从零开发、修改已有产品、已有代码但缺少设计文档和修复产品缺陷时，都使用符合当前情况的工作流程。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 共同理解 | 用户已经明确确认的产品背景、目标、用户、场景、边界、规则和功能拆分。 |
| 产品总说明 | 项目根目录 `spec/product.md`，记录产品全貌、产品通用规则和各功能文档入口。 |
| 功能说明文档 | 项目根目录 `spec/feature_<english-name>.md`，每份文件说明一件可以独立完成的用户事情；文件名使用小写英文和下划线，正文使用中文。 |
| 技术不确定性 | 当前缺少事实证据、无法直接确认，并且不同结果会改变代码设计、实施计划或验证方式的具体事项。 |
| 穿刺 | 使用真实场景中的接口、文件、平台、数据规模或操作路径，取得技术不确定性的实际证据。 |
| 穿刺清单 | `spec/spike_index.md`，记录本次经用户选择的穿刺项及其完成状态。 |
| 运行校准 | 实际运行已有项目或相关功能，用真实表现确认当前产品和代码怎样工作。 |

## 3. 用户与场景

### 3.1 用户

| 用户 | 与产品的关系 | 主要需求 |
|---|---|---|
| 产品提出者 | 提出新产品或产品变化，并决定产品目标、边界、规则和功能范围 | 在进入开发前确认完整的产品设计，并决定哪些技术不确定性需要验证 |
| 已有项目维护者 | 维护已有产品、代码和产品文档，或者负责修复产品缺陷 | 查清当前产品和代码实际情况，在制定修改或修复计划前确认关键技术事实 |

### 3.2 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零设计产品 | 产品提出者 | 项目还没有经过确认的产品设计 | 从产品诞生需求开始确定完整产品设计 | 形成用户确认的产品总说明和功能文档 |
| 修改已有产品 | 产品提出者、已有项目维护者 | 已有产品设计，本次需要新增、修改或删除产品行为 | 查清现状并确认本次产品变化 | 只更新受影响的产品设计内容，未受影响内容保持不变 |
| 已有代码但缺少产品文档 | 已有项目维护者 | 项目已有代码，但没有完整、可信的产品设计文档 | 通过现有文档、代码和运行结果确认当前产品设计 | 形成反映当前实际行为的产品总说明、功能文档和代码设计 |
| 为开发验证技术不确定性 | 产品提出者、已有项目维护者 | 产品设计和初步代码设计已经确认，但仍有必须实际运行才能确认的技术事实 | 决定哪些不确定性需要穿刺，并取得真实证据 | 代码设计和实施计划不再依赖未经验证的猜测 |
| 为修 bug 验证技术不确定性 | 已有项目维护者 | bug 已经复现并确认根因，但修复仍依赖未知的接口返回、平台行为或其他技术事实 | 在制定修复计划前验证具体不确定性 | 修复计划依据真实结果；需要改变产品行为时停止修 bug 并改走修改产品流程 |

## 4. 产品边界

### 4.1 支持范围

- 支持从零讨论并确认产品设计。
- 支持根据已有产品文档和代码修改产品设计。
- 支持已有代码但没有产品文档时，通过查看代码和运行校准建立产品与代码设计。
- 支持用户确认共同理解后，生成或修改产品总说明和功能文档。
- 支持从零开发、修改产品和修 bug 时识别并验证真实场景中的技术不确定性。
- 支持用户明确决定本次没有需要验证的不确定性时跳过穿刺。
- 支持把穿刺确认的事实回写到受影响的产品设计和代码设计。

### 4.2 不支持范围

- 产品设计功能不负责代码架构、接口、数据库、实施步骤、测试记录和验收记录。
- 穿刺不使用自造接口返回、模拟业务数据或理想化文件证明真实行为。
- 穿刺不修改正式源代码、正式页面、正式配置或数据库迁移。
- 不在未经同意时执行扣费、发送内容、修改外部数据或删除数据的验证操作。
- 修 bug 需要改变产品行为、产品规则或功能边界时，不继续按修 bug 处理，必须改为修改已有产品。

## 5. 产品组成与主要流程

### 5.1 产品组成

| 产品部分 | 作用 | 关联功能 |
|---|---|---|
| 产品设计 | 查明产品需求并保存用户确认的产品行为和规则 | 生成产品设计文档 |
| 初步代码设计 | 根据产品设计说明准备怎样组织代码、模块和调用过程 | 验证技术不确定性的输入依据 |
| 穿刺验证 | 识别必须实际验证的技术不确定性，取得真实证据并同步受影响的设计 | 验证技术不确定性 |
| 后续开发流程 | 根据确认后的产品设计、代码设计和穿刺结论制定计划、实施、测试和验收 | 使用前述功能的确认结果 |

### 5.2 主要流程

1. AI 根据用户需求和项目现状选择从零开发、修改产品或修 bug。
2. 从零开发和修改产品先形成用户确认的产品设计，再形成初步代码设计；已有项目缺少设计时先查看代码并运行校准。
3. 修 bug 先复现缺陷并确认根因。
4. AI 查看产品设计、代码设计、相关代码、测试、日志和已有运行结果，找出仍缺少真实证据的技术不确定性。
5. AI 逐项说明候选，用户决定执行哪些穿刺项，或者决定全部跳过。
6. AI 使用真实场景执行验证，记录实际命令、输入、观察结果、限制和结论。
7. 穿刺结果影响产品设计或代码设计时，先取得用户决定，再更新对应文档。
8. 所有穿刺项不再阻塞后续后，用户统一确认结果和更新后的设计，工作流进入实施计划或修复计划。

## 6. 产品通用规则

| 规则 | 适用范围 | 具体说明 |
|---|---|---|
| 产品决定由用户确认 | 产品背景、目标、边界、规则和功能范围 | AI 可以提供建议，但不能代替用户作出产品决定。 |
| 穿刺选择由用户确认 | 穿刺候选、执行清单和全部跳过 | AI 负责调查和建议，用户决定执行哪些穿刺项。 |
| 先查事实再提出不确定性 | 已有代码项目 | AI 必须先查看相关代码、测试、日志和运行结果；已经能确认的内容不进入穿刺。 |
| 穿刺只使用真实场景 | 所有穿刺项 | 验证对象必须是产品实际会遇到的接口、文件、平台、数据规模、操作路径或故障条件。 |
| 有外部影响的操作再次确认 | 会扣费、发送、写入或删除外部数据的验证 | 用户选择穿刺项不等于授权这些操作，执行前必须再次取得明确同意。 |
| 设计与证据保持一致 | 产品设计、代码设计和穿刺结论 | 穿刺推翻原有设计假设时，不能保留互相冲突的文档继续进入计划。 |
| 修 bug 不改变产品设计 | 修复产品缺陷 | 需要改变用户可见行为、产品规则或功能边界时，结束修 bug 流程并改为修改产品。 |
| 临时验证内容不进入正式代码 | 穿刺产生的脚本、样本和原始输出 | 用户确认结果后清理临时目录；正式代码在后续实施阶段根据确认事实编写。 |
| 门禁只操作当前阶段 | 所有工作流阶段 | 命令指定的阶段必须等于当前正在进行的阶段，不能提前通过后续阶段；调用错误阶段时，系统同时显示当前阶段和正确的下一步命令。 |
| 用户确认前重新校验 | 所有阶段的第三道门 | 门2通过后产物仍可能变化；进入下一阶段前必须重新校验当前文件，失效时停留在当前阶段。 |
