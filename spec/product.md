# Workflow Loop 产品设计阶段 — 产品总说明

## 1. 产品背景与目标

### 1.1 产品背景

用户使用 AI 进行产品开发时，在进入代码设计和开发前，需要先确认产品为什么要做、谁会使用、在什么场景使用、支持什么、不支持什么，以及需要拆成哪些功能。

项目可能是从零开始，也可能已有产品需要修改、已有代码但缺少产品文档，或者正在修复产品缺陷。Workflow Loop 因此需要一个产品设计阶段，根据项目现状完成需求讨论、共同理解确认和产品设计文档生成，为后续代码设计、开发、测试和验收提供同一份产品依据。

### 1.2 产品目标

- 进入代码设计前，产品背景、目标、用户、场景、边界、规则和功能拆分已经得到用户确认。
- 从零设计和修改产品时形成新的确认结果；已有代码但缺少文档时建立经过现状校准的产品设计；修复产品缺陷时使用已有产品设计，尚未初始化则先建立。
- 产品总说明和功能文档内容完整、互相链接且没有冲突，后续阶段不需要各自解释产品要求。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 共同理解 | 用户已经明确确认的产品背景、目标、用户、场景、边界、规则和功能拆分。 |
| 产品总说明 | 项目根目录 `spec/product.md`，记录产品全貌、产品通用规则和各功能文档入口。 |
| 功能说明文档 | 项目根目录 `spec/feature_<english-name>.md`，每份文件说明一件可以独立完成的用户事情；文件名使用小写英文和下划线，正文使用中文。 |
| 产品通用规则 | 对整个产品或多个功能共同生效的用户可见行为。 |
| 运行校准 | 在安全的本地条件下实际运行已有项目并走主要使用路径，用真实产品表现确认当前产品怎样工作。 |

## 3. 用户与场景

### 3.1 用户

| 用户 | 与产品的关系 | 主要需求 |
|---|---|---|
| 产品提出者 | 提出新产品或产品变化，并决定产品目标、边界、规则和功能范围 | 在进入开发前确认完整的产品设计 |
| 已有项目维护者 | 维护已有产品、代码和产品文档，或者负责修复产品缺陷 | 查清当前产品设计，只修改本次真正受影响的内容 |

### 3.2 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零设计产品 | 产品提出者 | 项目还没有经过确认的产品设计 | 从产品诞生需求开始确定完整产品设计 | 形成用户确认的产品总说明和功能文档 |
| 修改已有产品 | 产品提出者、已有项目维护者 | 已有产品设计，本次需要新增、修改或删除产品行为 | 查清现状并确认本次产品变化 | 只更新受影响的产品设计内容，未受影响内容保持不变 |
| 已有代码但缺少产品文档 | 已有项目维护者 | 项目已有代码，但没有完整、可信的产品设计文档 | 通过现有文档、代码和安全运行确认当前产品设计 | 形成反映当前实际行为的产品总说明和功能文档 |
| 修复产品缺陷 | 已有项目维护者 | 产品行为不符合已经确认的产品设计 | 使用已有产品设计作为复现和修复依据 | 产品设计未初始化时先建立现状设计；需要改变产品行为时改为修改已有产品 |

## 4. 产品边界

### 4.1 支持范围

- 支持从零讨论并确认产品设计。
- 支持根据已有产品文档和代码修改产品设计。
- 支持已有代码但没有产品文档时，通过查看代码和安全运行建立产品设计。
- 支持用户确认共同理解后，生成或修改产品总说明和功能文档。
- 支持修复产品缺陷时，在项目设计未初始化的情况下先建立现有产品设计。

### 4.2 不支持范围

- 不负责代码架构、接口、数据库、实施步骤、测试和验收文档。
- 不在用户确认共同理解前生成或修改产品设计文档。
- 不在未经同意时使用生产账号、真实数据、付费服务或修改外部数据。
- 修复产品缺陷需要改变产品行为、产品规则或功能边界时，不继续按修 bug 处理，必须改为修改已有产品。

## 5. 产品组成与主要流程

### 5.1 产品组成

| 产品部分 | 作用 | 与功能的关系 |
|---|---|---|
| 需求讨论 | 查明当前事实，并逐个讨论需要用户决定的内容 | 生成产品设计文档的前置过程 |
| 共同理解确认 | 总结产品背景、目标、用户、场景、边界、规则和功能拆分，并等待用户明确确认 | 生成产品设计文档的触发条件 |
| 产品设计文档 | 保存产品总说明和各功能说明文档，作为后续阶段的产品依据 | 生成产品设计文档的产出 |

### 5.2 主要流程

1. AI 根据用户需求和项目现状判断属于从零设计、修改已有产品、已有代码但缺少文档，还是修复产品缺陷。
2. 从零设计时从产品诞生需求开始讨论；已有项目先读取现有文档和代码，具备安全运行条件时实际运行并确认当前行为。
3. AI 只把无法从环境确认、且需要取舍的产品决定交给用户逐个确认。
4. 修复产品缺陷需要改变产品规则、功能边界或用户可见行为时，停止按修 bug 处理，改为修改已有产品。
5. AI 总结产品背景、目标、用户、场景、边界、组成、产品通用规则、功能拆分和未确认内容。
6. 用户明确确认共同理解。
7. AI 生成或修改产品总说明和功能文档，用户检查后将其作为后续阶段的产品依据。

## 6. 产品通用规则

| 规则 | 适用范围 | 具体说明 |
|---|---|---|
| 产品决定由用户确认 | 产品背景、目标、边界、规则和功能范围 | AI 可以提供建议，但不能代替用户作出产品决定。 |
| 先确认再生成文档 | 所有产品设计文档 | 只有用户明确确认共同理解后，才能生成或修改产品总说明和功能文档。 |
| 高风险运行先取得同意 | 已有代码项目 | 运行需要生产账号、真实数据、付费服务或会修改外部数据时，必须先取得用户同意。 |
| 区分历史原因与当前行为 | 所有产品设计内容 | 产品诞生背景和历史设计原因只能来自用户确认或明确历史文档；当前行为可以通过现有文档、代码和运行结果核实。 |
| 不编造产品内容 | 所有产品设计内容 | 无法确认的背景、目的、规则或功能设计原因必须继续询问或明确标记，不能把推测写成事实。 |
| 修 bug 不改变产品设计 | 修复产品缺陷 | 产品设计未初始化时先建立现状设计；已经初始化时使用现有设计。需要改变产品行为时改为修改已有产品。 |
