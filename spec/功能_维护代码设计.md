# 【功能】维护代码设计

## 1. 背景

产品设计说明“产品要怎样工作”，代码设计说明“代码实际怎样实现”。从零创建在动手写代码前需要确定项目入口、模块职责、共享状态、依赖和测试入口，这些决定只有放入可执行的代码计划才能同时约束文件、顺序和完成标准。修改已有产品时，实现方案要以现状架构基线和真实代码为起点。

因此，本功能有三个有效产出点：从零创建的最低限度实现设计写入代码计划；已有项目首次接入时根据真实代码建立现状基线；最终全量回归和整体验收通过后，根据真实交付代码同步 `spec/代码架构设计.md`。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零确定最低限度实现设计 | 项目负责人、项目维护者 | 从零创建的验收计划已经确认，正式代码尚未开始实施 | 在代码计划中确定项目入口、模块职责、共享状态、依赖和测试入口 | 实施人员获得可以直接落到文件、顺序和完成标准的整体方向 |
| 初始化已有项目的产品与架构 | 已有项目维护者 | 修改产品或修复缺陷时，项目设计架构尚未初始化 | 从文档、代码、测试和可安全运行的实际表现建立当前设计 | 产品设计、代码设计和调查证据互相一致，项目初始化状态得到确认 |
| 根据穿刺结论调整实施方案 | 项目维护者 | 真实验证确认了接口、平台、性能、数据或异常限制 | 在代码计划中更新受影响的实现决定 | 后续实施使用已经被真实证据确认的方案 |
| 最终同步详细代码设计 | 项目维护者 | 主题验收、最终全量回归和整体验收都已通过 | 核对产品功能与最终代码，并补齐真实映射 | 架构文档准确反映最终交付代码；没有结构变化时也留下核对结论 |

## 3. 功能边界

### 3.1 支持范围

- 使用同一份 `spec/代码架构设计.md` 保存首次初始化得到的现状基线和最终详细设计，不为每轮未来修改提前写一份独立预设计。
- 从零创建时，在代码计划中记录动手开发必需的项目入口、模块职责、共享状态、依赖和测试入口，作为实施依据。
- 已有项目首次初始化时查看真实代码、现有测试和配置；具备安全运行条件时运行相关产品行为，并生成 `spec/项目设计初始化证据.md`。
- 已有项目首次初始化时，以产品设计中由用户确认的功能清单为唯一范围，把每个功能逐项写入代码架构设计的功能章节和初始化证据。
- 修改产品时直接使用当前产品设计、现有代码和验收计划进入实施，不在验收计划前修订未来架构。
- 技术穿刺改变实现依据时，把结论同步到代码计划；只有已经实现并通过验收的结构才写入最终代码设计。
- 所有工作意图在最终全量回归和整体验收通过后完成详细代码设计同步。
- 架构图表达代码分层和依赖；每个产品功能另行表达从用户动作或系统事件到明确结果的完整代码过程。
- 已有代码位置使用真实文件、类、函数、类型或接口；从零创建尚不存在的位置写入代码计划，不在长期代码设计中冒充已有实现。
- 把每个功能完整代码过程中明确列出的真实文件作为项目核心代码路径；本轮代码计划和实施记录可以增加新的核心代码路径。

### 3.2 不支持范围

- 不替代产品设计决定用户可见行为、产品规则、功能边界或异常结果。
- 不在代码设计环节直接修改生产代码、测试代码或测试结果。
- 不根据目录名、类名或现有实现推断产品诞生原因和历史设计原因。
- 不把只列目录和模块名称、没有处理逻辑和产品映射的清单当成代码设计。
- 不因架构文件已经存在而跳过已有项目初始化或最终详细同步。
- 不把产品使用流程画成架构依赖图，也不把普通工具函数全部列为架构关键节点。
- 不扫描整个项目目录，也不根据文件后缀自动扩大核心代码范围。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 从零创建准备实施 | 必须先有用户已经确认的产品设计和验收计划；代码计划至少写明项目入口、模块职责、共享状态、依赖和测试入口，缺少这些整体决定时不能开始写正式代码。 |
| R2 | 维护架构文档 | `spec/代码架构设计.md` 只保存首次初始化确认的当前结构和交付完成后根据真实代码同步的最终结构，不把每轮尚未执行的代码方案当成长期架构事实。 |
| R3 | 从零项目尚无代码 | 计划新增位置只写在代码计划中；不强制运行不存在的程序，也不能把计划位置写成已有实现。 |
| R4 | 首次处理已有代码项目 | 必须查看相关文档、代码、测试和配置；具备安全运行条件时运行实际产品，用真实表现校准代码理解。 |
| R5 | 已有项目无法安全运行 | 写清不能运行的原因、已用证据和未确认范围；涉及生产数据、真实账号、付费或外部写入时，必须先取得用户确认。 |
| R6 | 判断是否需要项目设计初始化 | 只读取 `.workflow_loop/project.json` 中的 `project_design_initialized`，中文含义为“项目设计架构是否已初始化”；不能用某个文件是否存在代替。 |
| R7 | 项目设计初始化完成 | 产品总说明、功能文档、代码架构设计和初始化证据都通过检查并经用户确认后，才把初始化状态写为完成。 |
| R8 | 描述一层代码架构 | 必须写清这层承接的产品职责、负责与不负责的内容、关键代码位置、对外约定、依赖方向和验证位置。 |
| R9 | 识别架构关键节点 | 只选择多个功能共同经过，或者会影响产品规则、阶段推进、状态一致性或外部交互的代码位置；必须写清上游触发、关键处理、下游调用、数据或状态结果、失败结果和验证位置。 |
| R10 | 描述产品功能的代码过程 | 按明确场景从用户动作或系统事件写到用户或调用方得到结果；每个程序节点都要落到文件和代码符号，并说明输入、判断、调用、状态或数据变化、失败结果和验证。 |
| R11 | 记录已有项目结论 | 区分运行确认、测试确认、代码确认、文档或用户确认、未确认和证据冲突；读过代码不能写成已经运行确认。 |
| R12 | 修改产品设计已经确认 | 验收计划先确定完成标准，代码实施再根据现状架构基线和真实代码形成代码计划并修改代码。 |
| R13 | 穿刺取得新的技术事实 | 先由用户决定采用的实现办法，再把受影响的入口、职责、依赖、数据转换和异常处理写入代码计划；仍未决定的实现办法会阻塞代码实施。穿刺结论不直接改写最终代码设计。 |
| R14 | 进入最终代码设计同步 | 只有最终全量回归和整体验收都通过后，才进入 `update_code_design`，中文含义为“同步最终代码设计”。 |
| R15 | 最终同步代码设计 | 只核对并更新设计文档，不修改生产代码；每个当前产品功能都必须能映射到真实代码位置和验证位置。 |
| R16 | 最终代码结构没有变化 | 仍然执行最终同步，并在架构文档记录本轮核对了哪些功能和代码、为什么无需修改结构。 |
| R17 | 最终同步发现代码没有实现已确认要求 | 返回实施环节修正代码，不能把代码现状反写成产品规则。 |
| R18 | 最终同步发现用户可见行为、规则、边界、使用过程或异常发生变化 | 从零创建和修改产品返回产品设计环节重新确认；修复缺陷时整轮作废，再以修改产品工作意图开新一轮。 |
| R19 | 记录架构完成状态 | 首次接入已有项目在项目设计初始化确认后记录“项目设计已初始化”；从零创建只有最终代码设计同步确认后才记录“项目设计已初始化”和“详细架构完成”。从零创建的代码计划不单独写入架构完成状态。旧项目已经完成的初始化标记继续保留。 |
| R20 | 推进代码设计相关动作 | 项目设计初始化和最终同步由程序检查文件、结构、链接和真实代码位置，并由用户确认；从零创建的最低限度实现设计随代码计划一起确认。 |
| R21 | 首次初始化取得功能基准 | 读取产品设计中已经由用户确认的入口归属、排除理由和功能清单；这份清单是本次初始化的唯一范围，代码设计不能另建清单或自行增减功能。 |
| R22 | 按初始化基准建立代码设计 | 产品总说明中的功能、功能文档、代码架构设计中的功能章节和初始化证据中的功能清单必须逐项一致；每个纳入的功能都必须有完整代码过程和真实证据，任何一处遗漏或额外增加都不能完成初始化。 |
| R23 | 登记核心代码范围 | 核心代码路径只来自当前代码设计的真实代码位置，以及用户确认的本轮代码计划和最终实施记录。程序不根据后缀、Git 状态或整目录遍历自动增加路径。 |
| R24 | 路径不在核心代码范围 | 该路径不参与核心代码快照，也不因其变化使实施、测试或验收结果失效。若它实际决定产品行为，必须先在代码设计或本轮代码计划中明确登记。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 程序 | 指出当前代码设计环节必须读取的产物模板、工作规范、全局写作规范和相关产物路径 | 智能体知道本环节必须先读哪些材料以及准备形成什么结果 |
| 2 | 智能体 | 读取已经确认的产品设计；已有项目同时读取相关代码、测试、配置和历史证据，并逐项使用已确认的入口归属、排除理由和功能清单 | 建立产品功能到代码职责的覆盖清单，不产生第二份初始化范围 |
| 3 | 智能体、用户 | 首次初始化时按已确认功能清单核对真实模块、依赖、关键节点、共享代码、数据与状态处理、异常结果和验证位置；从零创建时在实施环节确认最低限度实现设计 | 长期架构只记录真实现状，实施前仍必须确定的整体方向进入代码计划 |
| 4 | 用户 | 首次初始化或最终同步时确认本环节已经聊清楚；从零创建时随代码计划确认 | 程序只为真实的初始化和最终同步开放代码设计产出，不增加独立预设计确认 |
| 5 | 智能体 | 按当前场景初始化已有项目或同步最终详细设计；从零创建和修改产品的未来方案写入代码计划 | `spec/代码架构设计.md` 反映已经确认的真实代码设计，并为每个功能列出真实核心代码路径；初始化场景按已确认功能清单同时形成调查证据 |
| 6 | 程序、智能体 | 程序检查固定结构、链接、代码路径和当前环节要求；智能体按已确认清单逐个核对产品总说明、功能文档、代码设计功能章节、初始化证据和完整代码过程 | 缺失功能、额外功能、缺失映射、证据冲突和产品或代码不一致会在推进前暴露 |
| 7 | 用户 | 阅读本轮项目设计初始化或最终同步的变化和检查结果并明确确认 | 程序记录对应的初始化或最终同步状态，并进入下一环节 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 产品设计或验收计划尚未确认 | 从零创建准备实施，但产品目标、规则、功能或完成标准仍未确认 | 停止代码计划并回到对应上游 | 不会在“做什么”和“什么算完成”未确定时先决定代码结构 |
| 已有项目无法运行 | 缺少环境、依赖、账号、设备或安全运行条件 | 使用能够取得的代码、测试和文档证据，明确未确认范围；需要外部副作用时先询问用户 | 文档不会把未运行的结论写成运行确认 |
| 现有文档、代码和运行结果冲突 | 多种证据对同一行为给出不同结论 | 继续调查并把无法消除的冲突交给用户决定 | 架构文档明确记录冲突，不会擅自选择一种解释 |
| 架构文件存在但初始化状态未完成 | 已有 `spec/代码架构设计.md`，项目级初始化字段仍为未完成 | 仍执行完整项目设计初始化并生成调查证据 | 旧文件不能冒充本次已经确认的初始化结果 |
| 代码位置不存在或无法定位 | 文档写出的文件、类、函数、类型或接口在已有项目中找不到 | 修正文档或继续调查后再通过程序检查 | 架构节点都能回到真实代码；计划新增位置会明确标识 |
| 穿刺结论与实施假设冲突 | 实际证据与现状理解或代码计划假设不一致 | 用户先决定是否改变产品行为，再把新的实现办法写入代码计划；仍有阻塞时不进入验收计划 | 后续计划不会继续使用已经被证伪的方案，最终代码设计只记录真实交付 |
| 最终代码未实现已确认要求 | 详细同步时发现功能缺失或实现不符合设计 | 返回实施环节，并使受影响的后续结果按规则失效 | 不会为了让架构文档一致而降低产品要求 |
| 最终代码出现产品变化 | 详细同步时发现用户可见结果与已确认产品设计不同 | 从零创建和修改产品返回产品设计；修复缺陷时作废当前轮次并新开修改产品流程 | 产品变化重新由用户确认，不会伪装成单纯架构调整 |
| 最终代码没有结构变化 | 本轮修改只改变局部逻辑，没有改变分层、节点或依赖 | 保留架构主体，补充本轮核对结论 | 仍完成详细同步，不会因“无变化”跳过收尾 |
| 已有项目入口未归类 | 首次初始化发现用户入口或系统触发入口没有归入功能，也没有排除理由 | 停止生成初始化产物，补充归类或排除理由并重新取得用户确认 | 功能清单不会在入口覆盖不完整时成为初始化基准 |
| 初始化功能映射不一致 | 产品总说明、功能文档、代码设计功能章节或初始化证据与已确认功能清单不一致 | 停止初始化，按同一清单修正文档和映射后重新检查 | 任何功能漏写或多写时都不会把初始化标记为完成 |
| 核心代码路径未登记 | 代码设计或代码计划只写模块名，没有真实文件路径 | 停止后续快照确认，先补齐明确路径 | 程序不会扫描整个项目来猜测核心代码 |
