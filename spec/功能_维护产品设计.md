# 【功能】维护产品设计

## 1. 背景

Workflow Loop 的产品设计阶段需要先调查已有事实，再和用户确认产品背景、目标、用户、场景、边界、规则和功能拆分，最后形成统一的产品总说明和功能说明，供后续代码计划、代码实施、测试验证和验收使用。

因此，本功能不只是“把文字写进文件”，而是维护当前有效的产品设计：从零建立时完整形成设计；修改产品时只改变本轮真正受影响的内容；首次处理缺少设计的已有项目时，根据真实代码和可运行行为建立可信现状。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 从零生成产品设计文档 | 产品提出者 | 从零产品设计已经得到用户确认 | 建立完整的产品总说明和功能文档 | 后续阶段获得经过确认的产品设计依据 |
| 更新已有产品设计文档 | 产品提出者、已有项目维护者 | 本次产品变化已经得到用户确认 | 只更新受影响的产品内容 | 文档准确反映新增、修改和删除，未受影响内容保持不变 |
| 根据已有代码建立产品设计文档 | 已有项目维护者 | 项目已有代码但缺少完整产品文档，当前行为已经通过现有文档、代码和安全运行校准 | 一次建立当前产品设计 | 文档反映用户当前能够实际使用的产品行为 |
| 修复缺陷前初始化产品设计 | 已有项目维护者 | 修复缺陷时发现项目设计尚未初始化 | 先建立现有产品设计，作为缺陷复现和修复依据 | 修复过程有明确的产品行为和规则依据 |

## 3. 功能边界

### 3.1 支持范围

- 用户确认共同理解后，生成或修改产品总说明和功能文档。
- 生成包含九章的产品总说明。
- 为每件可以独立完成的用户事情生成包含七章的功能文档。
- 在产品总说明中维护功能清单和真实文档链接。
- 首次处理已有项目时，从真实用户入口和系统触发入口归纳功能清单；每个入口都归入一个功能，或者明确记录不属于当前产品功能的理由，并在写正式文档前由用户确认这份清单。
- 正式产物使用 `spec/产品总说明.md` 和 `spec/功能_<功能文件标识>.md` 中文文件名；功能显示名称与跨平台安全、稳定的文件标识分别保存。
- 修改已有产品时，只更新用户已经确认受影响的文档。
- 只改变产品通用规则或整体边界时，允许功能文档保持不变。
- 已经交付的功能从当前产品移除时，从产品总说明取消链接，但保留原功能文档并明确标记已移除和删除依据。
- 已有代码但缺少产品文档时，根据经过校准的当前产品行为建立全部必要文档。
- 产品文档可以写用户实际选择、上传、下载或查看的文件类型等用户可见对象，以及用户操作后能够观察到的行为和结果。
- 修复缺陷时，项目设计未初始化才建立产品设计文档。

### 3.2 不支持范围

- 不把事实调查和需求讨论另做成一份独立功能文档；它们属于维护产品设计的工作过程，最终长期保存的是确认后的产品设计。
- 不在产品文档中写内部代码文件路径、接口路由、数据库对象、类、函数、代码模块、实施步骤、测试记录或验收记录；这些内容分别进入初始化证据、代码设计或后续过程文档。
- 不在用户确认共同理解前生成或修改产品设计文档。
- 不根据提示词、文件名、代码结构或当前运行结果推断产品诞生原因和历史设计原因。
- 修复缺陷需要改变产品行为、产品规则或功能边界时，不继续按缺陷修复生成文档，必须改为修改已有产品。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| <a id="r-1"></a>R1 | 开始生成或修改文档 | 必须已经存在用户明确确认的共同理解。 |
| <a id="r-2"></a>R2 | 写产品诞生背景或历史设计原因 | 只能使用用户已经确认的内容或明确的历史文档；当前代码和运行结果不能作为历史原因依据。 |
| <a id="r-3"></a>R3 | 写当前产品行为 | 可以使用现有产品文档、代码和运行结果核实；发现冲突时继续查证，不自行选择一种解释。 |
| <a id="r-4"></a>R4 | 生成产品总说明 | 必须包含产品背景与目标、术语、用户与场景、产品边界、产品组成与主要流程、产品通用规则、产品功能、相关文档、修改记录九章。 |
| <a id="r-5"></a>R5 | 生成功能文档 | 必须包含背景、场景、功能边界、规则、使用过程、异常情况、修改记录七章。 |
| <a id="r-6"></a>R6 | 判断是否拆成功能 | 一份功能文档对应一件可以独立完成的用户事情，不按按钮、页面或代码模块拆分。 |
| <a id="r-7"></a>R7 | 一条规则对整个产品或多个功能生效 | 写入产品总说明的“产品通用规则”，不在多份功能文档中重复。 |
| <a id="r-8"></a>R8 | 产品功能清单增加功能 | 必须同时存在对应功能文档和可用链接。 |
| <a id="r-9"></a>R9 | 没有相关内容 | 写“暂无”，不得编造背景、目标、规则、异常情况或功能设计原因。 |
| <a id="r-10"></a>R10 | 修改已有产品 | 只修改用户已经确认受影响的内容；只改变产品通用规则或整体边界时，不得为了通过门禁制造无关功能文档修改。 |
| <a id="r-11"></a>R11 | 修复缺陷 | 产品设计未初始化时建立产品设计文档；已经初始化时使用现有文档；需要改变产品行为时改为修改已有产品。 |
| <a id="r-12"></a>R12 | 生成正式文件名 | 产品总说明固定使用中文文件名；每份功能文档使用已经登记的稳定中文文件标识，危险字符、路径分隔符、重名和 Windows 保留名必须安全处理，不能直接把显示名称拼入路径。 |
| <a id="r-13"></a>R13 | 移除已经交付的功能 | 用户确认移除后，从当前产品功能清单删除链接；原功能文档保留，顶部标记“已移除”，并记录移除日期、工作流编号和原因，使历史链接仍可复核。 |
| <a id="r-14"></a>R14 | 删除本轮新建但从未交付的功能 | 用户在本轮正式确认前取消该功能时，可以直接删除本轮新建的功能文档，并从产品总说明移除入口。 |
| <a id="r-15"></a>R15 | 判断当前有效功能 | 后续环节只读取产品总说明当前链接的功能文档；目录中保留的已移除历史文档不属于当前产品设计。 |
| <a id="r-16"></a>R16 | 首次处理已有项目 | 从真实用户入口和系统触发入口归纳功能清单；每个入口必须归入一件可以独立完成的用户事情，或者写清排除理由。用户确认后，这份清单成为本次初始化基准。 |
| <a id="r-17"></a>R17 | 按初始化基准生成设计 | 产品总说明中的功能、功能文档、代码架构设计中的功能章节和初始化证据中的功能清单必须逐项一致；任何一处多一项、少一项或名称无法对应时，初始化不能完成。 |
| <a id="r-18"></a>R18 | 判断产品文档内容边界 | 只写用户可见对象、行为、规则和结果。用户实际选择、上传、下载或查看的文件类型可以写；内部代码路径、接口路由、数据库对象、类、函数和代码模块不能写。程序只检查能够明确识别的固定格式，存在语义歧义时由智能体说明并交给用户确认。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | AI 产品设计师 | 读取产品设计模板、工作规范、现有产品文档和与本次变化有关的真实代码或运行证据 | 明确已知事实、需要用户决定的内容和本轮可能受影响的设计 |
| 2 | AI 产品设计师、用户 | 一次讨论一个产品决定，并核对产品历史依据和当前行为依据 | 历史原因不会从代码推断，当前行为不会在证据冲突时直接定论 |
| 3 | AI 产品设计师 | 总结当前共同理解、未决问题和准备新增、修改、移除或保持不变的功能；首次处理已有项目时，同时列出每个真实入口归入的功能或排除理由 | 用户能够在写文档前确认完整范围和初始化功能清单 |
| 4 | 用户 | 确认当前产品问题已经聊清楚；首次处理已有项目时，同时确认功能清单作为初始化基准 | 第一道门只允许 AI 开始写文档，不代表文档已经通过 |
| 5 | AI 产品设计师 | 生成或修改产品总说明的全部九章，并按独立用户事情维护七章功能文档 | 产品全貌、通用规则、当前功能入口和修改记录完整 |
| 6 | 程序、AI 产品设计师 | 程序检查文件、结构、链接和固定规则；AI 检查事实、边界、规则归位和语义一致性 | 可以机械判断和需要产品判断的内容分别得到检查 |
| 7 | 用户 | 检查生成或修改后的产品设计文档 | 用户明确确认后，当前链接的产品设计文档成为后续阶段的依据 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 共同理解尚未确认 | 用户还没有明确确认产品设计总结 | 停止生成或修改文档，继续需求讨论 | 不会提前生成未确认的产品设计 |
| 产品历史没有依据 | 产品诞生背景或历史设计原因没有用户确认，也没有明确历史文档 | 停止填写相关内容并向用户确认，或者明确标记未确认 | 当前代码不会被当成产品历史依据 |
| 当前产品行为无法确认 | 现有文档、代码和运行表现缺失或互相冲突 | 继续查证，并把仍无法确定的差异交给用户决定 | 推测不会被写成当前产品事实 |
| 已有项目无法安全运行 | 缺少运行条件，或者运行需要生产账号、真实数据、付费服务或外部写入 | 说明无法运行的原因；高风险运行先取得用户同意 | 未验证的产品行为会被明确标记 |
| 功能链接失效 | 产品功能清单指向不存在的文件 | 创建缺失文档或修正链接后再完成 | 产品总说明中的功能入口均可使用 |
| 产品通用规则重复 | 同一规则同时出现在多份功能文档 | 移到产品总说明并从功能文档中删除重复内容 | 同一产品规则只维护一处 |
| 修复缺陷时产品设计已经初始化 | 已有完整、经过确认的产品设计 | 不重新生成产品设计文档，直接使用现有文档 | 修复以现有产品设计为依据 |
| 修复缺陷需要改变产品行为 | 修复方案改变产品规则、功能边界或用户可见结果 | 停止按缺陷修复处理，改为修改已有产品 | 产品变化会先经过产品设计确认 |
| 删除功能未获确认 | 修改已有产品时准备删除功能，但用户没有明确同意 | 保留原功能和文档，继续讨论影响 | 不会擅自删除现有产品功能 |
| 只修改通用规则 | 本轮变化只影响产品总说明中的共同规则或整体边界 | 更新产品总说明并保留无关功能文档原样 | 门禁不会要求制造一次无意义的功能文档修改 |
| 已交付功能被移除 | 用户确认当前产品不再提供已有功能 | 从当前功能清单移除入口，原功能文档标记已移除并保留历史 | 当前设计不再把该功能当成有效功能，旧链接仍能说明过去定义 |
| 功能名称不能安全用作路径 | 显示名称包含斜杠、冒号、问号、保留名或与已有名称清理后重名 | 生成并保存安全文件标识，重名依次追加编号 | 标题保留完整名称，文件不会覆盖其它功能或在某个平台无法创建 |
| 已有项目入口未归类 | 发现用户入口或系统触发入口没有归入功能，也没有排除理由 | 补充归类或说明排除理由，并重新由用户确认初始化功能清单 | 未覆盖入口不会在初始化完成后才暴露为漏写功能 |
| 初始化产物功能不一致 | 产品总说明、功能文档、代码架构设计功能章节或初始化证据与已确认功能清单不一致 | 停止初始化，按同一基准补齐或删除错误内容后重新检查 | 缺失功能或多写功能时不会把初始化标记为完成 |
| 产品文档混入内部实现 | 产品文档出现内部代码路径、接口路由、数据库对象、类、函数或代码模块 | 把内部实现移到初始化证据、代码计划或最终代码设计；保留用户实际可见的文件类型、操作和结果 | 产品文档保持面向用户，代码证据仍有正确存放位置 |
