# 【功能】开始或继续一轮工作

## 1. 背景

用户安装 Workflow Loop 后，应当直接向智能体提出项目任务，不需要先理解或手工输入工作流命令。产品必须判断项目是否已有一轮进行中的工作：有则继续原流程，没有才根据本次目标推荐工作意图，并在用户确认后开始新一轮。

开始完整研发轮次时，产品还必须把用户目标和项目现状组合成完整环节路径，避免用“新项目”“已有项目”之类混合状态和目标的菜单决定流程。无需开发任务则只开始简单轮次，不生成完整研发路径。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 检查当前工作状态 | 产品提出者、项目维护者 | 用户刚提出需求，智能体尚不知道是否有进行中的工作 | 找到当前轮次或可选的新工作类型 | 只读检查状态，不误开新一轮 |
| 继续进行中的工作 | 产品提出者、项目维护者 | 当前项目存在状态为“进行中”的工作流轮次 | 从当前有效环节继续 | 当前版本轮次原位继续；`stage_path_version < 2`（环节路径版本早于 2）的进行中轮次先完成一次可解释迁移，再从确实未完成或已失效的内部步骤继续 |
| 从零开始 | 产品提出者 | 本次要从零交付新项目或新能力 | 清理旧过程产物后建立完整设计并开发 | 经过清场确认后进入产品设计 |
| 修改产品 | 产品提出者、项目维护者 | 已有产品需要新增、修改或移除行为 | 按当前项目设计状态进入修改流程 | 必要时先初始化项目设计，再修改产品 |
| 修复缺陷 | 项目维护者 | 需要定位并修复一个具体缺陷 | 复现根因、修复并完成全部验证 | 必要时先初始化项目设计，再进入缺陷复现 |
| 完成无需开发任务 | 产品提出者、项目维护者 | 任务不改变产品规则、代码、测试或会影响运行的配置 | 聊清后直接执行 | 不生成完整研发路径和过程文档 |
| 上一轮已经结束 | 产品提出者、项目维护者 | 上一轮已经正式收工或作废 | 开始新的独立工作 | 新状态覆盖旧快照，历史仍保留在流水日志 |

## 3. 功能边界

### 3.1 支持范围

- 智能体自动检查当前项目是否存在进行中的工作流轮次。
- 没有进行中轮次时，支持“从零做”“修改产品”“修复缺陷”“无需开发任务”四种互斥工作意图。
- 根据前三种工作意图和项目设计是否已初始化，生成本轮完整环节路径；无需开发任务只记录简单轮次状态。
- 支持从当前目录向上找到已安装的项目根。
- 支持继续原轮次、查看当前状态和正确的下一步。
- 支持把 `stage_path_version < 2`（环节路径版本早于 2）的进行中轮次一次性迁移到当前环节顺序，并保留能证明仍有效的产物和机器证据。
- 从零做存在旧产物时，先让用户确认清场范围，再以可恢复方式开始。
- 新一轮开始后显示轮次编号、工作意图、当前位置和下一步含义；完整研发轮次同时显示环节路线。

### 3.2 不支持范围

- 不在开始命令中静默安装 Workflow Loop。
- 不允许同一项目同时存在两轮状态为“进行中”的工作。
- 不把“项目是否安装”“是否已有代码”和“本次要做什么”混成一个场景选项。
- 不保留旧的四场景入口，也不接受旧入口名称的兼容映射。
- 不要求用户手工执行日常 `workflow` 命令。
- 不在只读状态检查时初始化轮次、清场或创建状态文件。
- 不在第一版解决多个进程同时修改同一项目状态的问题；同一项目不得同时执行两个会写状态的命令。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| <a id="r-1"></a>R1 | 用户提出项目任务 | 智能体读取 `AGENTS.md` 智能体契约后，自动执行 `workflow start` 状态检查；用户不负责输入该命令。 |
| <a id="r-2"></a>R2 | 执行无工作意图的状态检查 | 只能读取安装状态和当前轮次，不能创建或修改 `state.json` 当前轮状态。 |
| <a id="r-3"></a>R3 | 存在进行中轮次 | 禁止开始新轮次；产品必须显示当前环节和继续方式。`stage_path_version < 2`（环节路径版本早于 2）时，第一条会写状态的继续命令先完成迁移；只读状态检查只预览迁移结果。用户也可以决定正式收工或整轮作废。 |
| <a id="r-4"></a>R4 | 不存在进行中轮次 | 智能体根据用户目标和项目事实推荐工作意图并说明理由；用户确认进入哪种任务后，智能体才执行带工作意图的开始命令。 |
| <a id="r-5"></a>R5 | 选择工作意图 | 只允许 `from_scratch` 从零做、`product_change` 修改产品、`bugfix` 修复缺陷和 `light_task` 无需开发任务四种值；英文标识是程序参数，用户看到时必须同时看到中文含义。 |
| <a id="r-6"></a>R6 | 修改产品或修复缺陷 | 读取 `project.json` 项目状态中的设计初始化标记；未初始化时先进入项目设计架构初始化，已初始化时跳过该前置环节。 |
| <a id="r-7"></a>R7 | 从零做 | 必须执行产品设计、可选穿刺、验收计划、代码实施、测试验证、主题验收、最终全量回归、整体验收和最终代码设计同步。代码实施开始前必须在代码计划中写明项目入口、模块职责、共享状态、依赖和测试入口等最低限度实现设计。 |
| <a id="r-8"></a>R8 | 修改产品 | 必须执行产品设计、可选穿刺、验收计划、代码实施、测试验证、验收和最终同步。项目未初始化时先完成项目设计初始化；已有初始化基线时，代码计划直接依据现状架构基线和真实代码确定实现方案。 |
| <a id="r-9"></a>R9 | 修复缺陷 | 必须先复现缺陷并确认根因，再经过可选穿刺、验收计划、代码实施、测试验证、验收和最终同步；项目未初始化时先补项目设计。 |
| <a id="r-10"></a>R10 | 从零做发现旧产物 | 先显示将删除的受管设计和过程产物，用户明确确认后才能清场；模板和阶段规范不能被清除。 |
| <a id="r-11"></a>R11 | 执行从零做的清场开工 | 删除前保存原内容和项目状态；新轮次状态、清场和项目字段修改作为同一事务完成，失败时恢复旧状态和旧文件。 |
| <a id="r-12"></a>R12 | 开始命令成功 | 状态写为“进行中”，保存轮次编号、工作意图和当前位置。完整研发轮次同时保存环节路径，下一步是读取当前环节材料；无需开发轮次的下一步是直接开始逐题讨论。 |
| <a id="r-13"></a>R13 | 上一轮已正式收工或作废 | 允许开始新轮次；新的 `state.json` 当前轮状态整份覆盖旧快照，旧过程只保留在追加式流水日志中。 |
| <a id="r-14"></a>R14 | 显示技术命令 | 必须先用直白中文解释当前目的、命令会做什么、由谁执行、用户是否需要参与及成功后的下一步，不能只显示英文命令或环节名。 |
| <a id="r-15"></a>R15 | 生成正式产物 | 本轮后续面向用户的正式产物最终使用中文文件名；`spec` 等固定目录、程序命令和机器状态文件继续使用英文。 |
| <a id="r-16"></a>R16 | 用户确认无需开发任务 | 开始 `light_task`（无需开发任务）轮次，不准备完整研发路径、研发过程文档或回退副本。 |
| <a id="r-17"></a>R17 | `stage_path_version < 2`（环节路径版本早于 2）的进行中轮次 | 迁移器保留已确认的产品设计、验收计划、现状架构基线和能证明仍有效的实施、测试计划及机器证据；历史代码设计草稿只作为代码计划的调查材料，拆分的测试状态合并进 `qa`（测试验证）内部步骤。缺失、冲突或与当前依据不一致的内容才失效；迁移成功后把 `stage_path_version`（环节路径版本）写为 2，后续读取不重复迁移。 |
| <a id="r-18"></a>R18 | 设置项目设计初始化标记 | 首次接入已有项目在项目设计初始化确认后设置；从零创建不能在代码计划确认时设置，只有最终代码完成并确认最终代码设计同步后才设置。旧项目已经完成的标记继续保留。 |
| <a id="r-19"></a>R19 | 确定从零清场范围 | 只检查项目根的 `spec/`、`acceptance/`、`qa/`、`impl/`、`bug/` 和 `需求交付追踪表.md`。五个目录只有含文件时才进入清单；命中的目录整目录删除，追踪表单独删除。业务代码、测试、Git 数据、`.workflow_loop/` 中的模板与规范及其它项目内容不在清场范围内。 |
| <a id="r-20"></a>R20 | 从零清场确认并重置项目状态 | 检测到清场内容时，第一次开始命令只展示精确清单，不删除、不创建轮次；用户确认后由 AI 使用 `--confirm-clean` 开工。无清场内容时不增加确认。每次从零开工都把 `project_design_initialized`（项目设计是否已初始化）设为否，即使原值为是；只有最终代码设计同步确认后才能重新设为是。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 用户 | 在已安装项目中向智能体提出需求 | 用户只说明想完成什么，不需要选择内部环节或输入命令 |
| 2 | 智能体 | 读取智能体契约并自动检查当前工作状态 | 产品只读查找项目根、安装标记和当前轮次 |
| 3 | 产品 | 判断是否存在进行中的轮次 | 有则显示原轮次和下一步；使用旧顺序时同时显示保留的验收计划和实施结果、迁移到测试验证环节的内容，以及确实需要重新核对的部分；没有则允许确定新工作意图 |
| 4 | 智能体、用户 | 智能体根据实际目标推荐从零做、修改产品、修复缺陷或无需开发任务，用户确认 | 用户在进入任务前知道为什么选择该路线 |
| 5 | 产品 | 为完整研发任务组成统一环节路径、迁移进行中的旧路径，或为无需开发任务建立简单轮次 | 新轮次和进行中轮次使用同一研发顺序；无需开发任务不增加多余环节 |
| 6 | 智能体、用户 | 从零做存在旧产物时，查看并确认清场范围 | 用户拒绝时不删除文件、不创建新轮次；用户同意时进入可恢复的清场事务 |
| 7 | 产品 | 创建进行中状态并显示路径向开工摘要 | 用户看到本轮怎样走、当前在哪里、接下来由智能体做什么 |
| 8 | 智能体 | 完整研发轮次加载并读取第一个环节的材料；无需开发轮次直接逐题聊清任务 | 新轮次按用户确认的路线开始 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 项目未完整安装 | 找不到完整 `.workflow_loop/` 骨架或版本标记 | 立即停止，不创建状态文件 | 说明当前项目尚不能开工，需要先完成官方安装 |
| 已有进行中轮次 | 又尝试带新工作意图开始 | 拒绝覆盖当前状态 | 显示当前轮次、当前环节和继续、收工或作废的选择 |
| 工作意图不明确 | 用户需求不足以区分四种工作意图 | 智能体继续询问目标，不猜测开始 | 在用户确认前不创建新轮次 |
| 使用旧入口参数 | 调用已经删除的四场景入口 | 明确报错并显示当前四种工作意图 | 不静默映射到可能错误的新流程 |
| 从零清场未确认 | 检测到旧设计或过程产物，但用户拒绝或尚未回答 | 保持项目不变，不开始新轮次 | 显示尚未开工和仍需确认的清场范围 |
| 清场开工中途失败 | 删除旧产物、修改项目状态或写入新状态任一步失败 | 根据事务记录恢复旧文件、旧项目字段和旧状态 | 只有恢复完成后才说明开工失败且项目已还原 |
| 上次清场事务未完成 | 强制终止后残留可恢复事务 | 先按事务记录恢复或完成已提交事务的清理 | 未恢复前不允许继续正常命令或覆盖状态 |
| 状态文件无法读取 | 当前轮状态损坏或字段不完整 | 停止，不把未知状态当成没有进行中轮次 | 说明无法确认当前工作状态，需要先修复真实问题 |
