# 【功能】开始或继续一轮工作

## 1. 背景

用户安装 Workflow Loop 后，应当直接向智能体提出项目任务，不需要先理解或手工输入工作流命令。产品必须判断项目是否已有一轮进行中的工作：有则继续原流程，没有才根据本次目标推荐工作意图，并在用户确认后开始新一轮。

开始完整研发轮次时，产品还必须把用户目标和项目现状组合成完整环节路径，避免用“新项目”“已有项目”之类混合状态和目标的菜单决定流程。无需开发任务则只开始简单轮次，不生成完整研发路径。

## 2. 场景

| 场景 | 使用者 | 发生条件 | 想完成的事情 | 预期结果 |
|---|---|---|---|---|
| 检查当前工作状态 | 产品提出者、项目维护者 | 用户刚提出需求，智能体尚不知道是否有进行中的工作 | 找到当前轮次或可选的新工作类型 | 只读检查状态，不误开新一轮 |
| 继续进行中的工作 | 产品提出者、项目维护者 | 当前项目存在状态为“进行中”的工作流轮次 | 从原来停下的环节继续 | 原轮次、已有产物和已通过结果不被覆盖 |
| 从零开始 | 产品提出者 | 本次要从零交付新项目或新能力 | 清理旧过程产物后建立完整设计并开发 | 经过清场确认后进入产品设计 |
| 修改产品 | 产品提出者、项目维护者 | 已有产品需要新增、修改或移除行为 | 按当前项目设计状态进入修改流程 | 必要时先初始化项目设计，再修改产品 |
| 修复缺陷 | 项目维护者 | 需要定位并修复一个具体缺陷 | 复现根因、修复并完成全部验证 | 必要时先初始化项目设计，再进入缺陷复现 |
| 完成无需开发任务 | 产品提出者、项目维护者 | 任务不改变产品规则、代码、测试或会影响运行的配置 | 聊清后直接执行 | 不生成完整研发路径和过程文档 |
| 上一轮已经结束 | 产品提出者、项目维护者 | 上一轮已经正式收工或作废 | 开始新的独立工作 | 新状态覆盖旧快照，历史仍保留在流水日志 |

## 3. 功能边界

### 3.1 支持范围

- 智能体自动检查当前项目是否存在进行中的工作流轮次。
- 没有进行中轮次时，支持“从零做”“修改产品”“修复缺陷”“无需开发任务”四种互斥工作意图。
- 根据前三种工作意图和项目设计是否已初始化，生成本轮完整环节路径；无需开发任务只记录简单轮次状态。
- 支持从当前目录向上找到已安装的项目根。
- 支持继续原轮次、查看当前状态和正确的下一步。
- 从零做存在旧产物时，先让用户确认清场范围，再以可恢复方式开始。
- 新一轮开始后显示轮次编号、工作意图、当前位置和下一步含义；完整研发轮次同时显示环节路线。

### 3.2 不支持范围

- 不在开始命令中静默安装 Workflow Loop。
- 不允许同一项目同时存在两轮状态为“进行中”的工作。
- 不把“项目是否安装”“是否已有代码”和“本次要做什么”混成一个场景选项。
- 不保留旧的四场景入口，也不接受旧入口名称的兼容映射。
- 不要求用户手工执行日常 `workflow` 命令。
- 不在只读状态检查时初始化轮次、清场或创建状态文件。
- 不在第一版解决多个进程同时修改同一项目状态的问题；同一项目不得同时执行两个会写状态的命令。

## 4. 规则

| 编号 | 条件 | 规则 |
|---|---|---|
| R1 | 用户提出项目任务 | 智能体读取 `AGENTS.md` 智能体契约后，自动执行 `workflow start` 状态检查；用户不负责输入该命令。 |
| R2 | 执行无工作意图的状态检查 | 只能读取安装状态和当前轮次，不能创建或修改 `state.json` 当前轮状态。 |
| R3 | 存在进行中轮次 | 禁止开始新轮次；产品必须显示当前环节和继续方式，也可以由用户决定正式收工或整轮作废。 |
| R4 | 不存在进行中轮次 | 智能体根据用户目标和项目事实推荐工作意图并说明理由；用户确认进入哪种任务后，智能体才执行带工作意图的开始命令。 |
| R5 | 选择工作意图 | 只允许 `from_scratch` 从零做、`product_change` 修改产品、`bugfix` 修复缺陷和 `light_task` 无需开发任务四种值；英文标识是程序参数，用户看到时必须同时看到中文含义。 |
| R6 | 修改产品或修复缺陷 | 读取 `project.json` 项目状态中的设计初始化标记；未初始化时先进入项目设计架构初始化，已初始化时跳过该前置环节。 |
| R7 | 从零做 | 必须执行产品设计、初步代码设计、可选穿刺、验收计划、测试计划、实施、测试代码、测试执行、主题验收、最终全量回归、整体验收和最终代码设计同步。 |
| R8 | 修改产品 | 必须执行产品设计、设计期代码修订、可选穿刺及完整的计划、实施、测试、验收和最终同步；项目未初始化时先补项目设计。 |
| R9 | 修复缺陷 | 必须先复现缺陷并确认根因，再经过可选穿刺及完整的计划、实施、测试、验收和最终同步；项目未初始化时先补项目设计。 |
| R10 | 从零做发现旧产物 | 先显示将删除的受管设计和过程产物，用户明确确认后才能清场；模板和阶段规范不能被清除。 |
| R11 | 执行从零做的清场开工 | 删除前保存原内容和项目状态；新轮次状态、清场和项目字段修改作为同一事务完成，失败时恢复旧状态和旧文件。 |
| R12 | 开始命令成功 | 状态写为“进行中”，保存轮次编号、工作意图和当前位置。完整研发轮次同时保存环节路径，下一步是读取当前环节材料；无需开发轮次的下一步是直接开始逐题讨论。 |
| R13 | 上一轮已正式收工或作废 | 允许开始新轮次；新的 `state.json` 当前轮状态整份覆盖旧快照，旧过程只保留在追加式流水日志中。 |
| R14 | 显示技术命令 | 必须先用直白中文解释当前目的、命令会做什么、由谁执行、用户是否需要参与及成功后的下一步，不能只显示英文命令或环节名。 |
| R15 | 生成正式产物 | 本轮后续面向用户的正式产物最终使用中文文件名；`spec` 等固定目录、程序命令和机器状态文件继续使用英文。 |
| R16 | 用户确认无需开发任务 | 开始 `light_task`（无需开发任务）轮次，不准备完整研发路径、研发过程文档或回退副本。 |

## 5. 使用过程

| 步骤 | 执行者 | 操作或行为 | 产品响应或结果 |
|---|---|---|---|
| 1 | 用户 | 在已安装项目中向智能体提出需求 | 用户只说明想完成什么，不需要选择内部环节或输入命令 |
| 2 | 智能体 | 读取智能体契约并自动检查当前工作状态 | 产品只读查找项目根、安装标记和当前轮次 |
| 3 | 产品 | 判断是否存在进行中的轮次 | 有则显示原轮次和下一步；没有则允许确定新工作意图 |
| 4 | 智能体、用户 | 智能体根据实际目标推荐从零做、修改产品、修复缺陷或无需开发任务，用户确认 | 用户在进入任务前知道为什么选择该路线 |
| 5 | 产品 | 为完整研发任务组成环节路径，或为无需开发任务建立简单轮次 | 完整研发任务不遗漏必经环节，无需开发任务不增加多余环节 |
| 6 | 智能体、用户 | 从零做存在旧产物时，查看并确认清场范围 | 用户拒绝时不删除文件、不创建新轮次；用户同意时进入可恢复的清场事务 |
| 7 | 产品 | 创建进行中状态并显示路径向开工摘要 | 用户看到本轮怎样走、当前在哪里、接下来由智能体做什么 |
| 8 | 智能体 | 完整研发轮次加载并读取第一个环节的材料；无需开发轮次直接逐题聊清任务 | 新轮次按用户确认的路线开始 |

## 6. 异常情况

| 异常情况 | 发生条件 | 产品处理 | 用户看到的结果 |
|---|---|---|---|
| 项目未完整安装 | 找不到完整 `.workflow_loop/` 骨架或版本标记 | 立即停止，不创建状态文件 | 说明当前项目尚不能开工，需要先完成官方安装 |
| 已有进行中轮次 | 又尝试带新工作意图开始 | 拒绝覆盖当前状态 | 显示当前轮次、当前环节和继续、收工或作废的选择 |
| 工作意图不明确 | 用户需求不足以区分四种工作意图 | 智能体继续询问目标，不猜测开始 | 在用户确认前不创建新轮次 |
| 使用旧入口参数 | 调用已经删除的四场景入口 | 明确报错并显示当前四种工作意图 | 不静默映射到可能错误的新流程 |
| 从零清场未确认 | 检测到旧设计或过程产物，但用户拒绝或尚未回答 | 保持项目不变，不开始新轮次 | 显示尚未开工和仍需确认的清场范围 |
| 清场开工中途失败 | 删除旧产物、修改项目状态或写入新状态任一步失败 | 根据事务记录恢复旧文件、旧项目字段和旧状态 | 只有恢复完成后才说明开工失败且项目已还原 |
| 上次清场事务未完成 | 强制终止后残留可恢复事务 | 先按事务记录恢复或完成已提交事务的清理 | 未恢复前不允许继续正常命令或覆盖状态 |
| 状态文件无法读取 | 当前轮状态损坏或字段不完整 | 停止，不把未知状态当成没有进行中轮次 | 说明无法确认当前工作状态，需要先修复真实问题 |
