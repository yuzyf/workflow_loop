# 实施阶段工作规范

## 1. 阶段职责

实施阶段把已经确认的产品结果、验收条件和测试范围落实为真实代码。它同时包含两部分：先确认实施前计划，再依据已经确认的计划修改代码并记录实际修改。

本阶段使用 `Template_Repository/impl/impl.md` 生成 `impl/index.md` 和各主题实施文档。不重新确定验收主题，不降低验收条件，不把正式测试和主题验收塞进实施阶段。

## 2. 开始前调查

先读取：

1. 当前工作流状态、工作流编号和全部验收主题。
2. `acceptance/index.md`，确认主题顺序和前置主题。
3. 所有 `acceptance/<topic>_plan.md`，确认用户结果、验收范围和验收条件。
4. `qa/index.md` 和所有 `qa/<topic>_plan.md`，确认测试计划已经继承同一组主题关系。
5. 产品设计、代码设计、穿刺结论和 `traceability.md`。

已有代码时必须查看真实文件、类、函数、调用关系和已有测试。项目具备运行条件时，运行项目或相关检查来核对事实；不能只看文档猜代码。

从零开始且没有实现代码时：

- 不能编造“当前逻辑”。
- 计划中的代码位置写成“新增”。
- 依据使用已确认的产品设计、代码设计、验收计划、测试计划和穿刺结论。
- 没有可运行的现有代码或测试时写“暂无”；有可运行的脚本或测试时仍必须运行并记录事实。

## 3. 第一性原理需求检查

实施计划讨论开始前，先说明：

- 用户要解决的实际问题。
- 用户最终要得到的产品结果。
- 本次全部验收主题及主题关系。
- 每个主题对应的验收条件和测试项。
- 需要修改的代码范围和共用代码。
- 仍可能改变实施结果的问题。

对所有会影响文件、函数、处理逻辑、数据、状态、输出或测试范围的问题逐个询问用户，直到双方达成共识。已经能从已确认文档、真实代码或运行结果确定的事实不重复询问，也不能为了“问全”提出与实施无关的问题。

## 4. 全局讨论和主题讨论

### 4.1 先做全局检查

先向用户汇总七项内容：用户问题、最终产品结果、全部主题、主题依赖、共用代码、已确认依据、未解决问题及需要返回的阶段。

### 4.2 再逐个主题讨论

每次只讨论一个需要用户决定的问题，并给出具体建议。每个主题依次确认：

1. 主题要解决的用户问题和完成后的用户结果。
2. 对应的验收条件和测试项。
3. 具体文件、类、函数或新增代码位置。
4. 当前代码逻辑；从零项目说明“暂无现有逻辑”。
5. 修改后的具体处理逻辑。
6. 数据、状态和输出怎样变化。
7. 主题依赖和公共代码怎样处理。
8. 未解决问题及处理阶段。

用户确认一个主题的实施前计划后，才能写入对应文档；所有主题的计划都确认后，才能通过 `workflow gate impl --discuss-done`。

## 5. 三道门

### 第一道门：讨论完成

`workflow gate impl --discuss-done` 只在以下条件满足时通过：

- `impl/index.md` 存在，并继承 `acceptance/index.md` 的主题关系。
- 当前全部主题都有实施文档。
- 每份主题文档都有实施依据、实施前计划、开发检查计划、未决问题和上下游文档。
- 未决问题为“暂无”。
- 代码状态与进入 `impl` 时的基线一致，尚未开始修改代码。

### 第二道门：实施完成检查

用户确认讨论完成后才能修改代码。修改代码时：

- 按主题和依赖关系推进，不自动并行修改同一文件或公共函数。
- 适合时使用测试驱动开发（TDD，先写能失败的测试，再写实现），但测试只是开发反馈。
- 定期运行相关测试、类型检查或其他项目已有检查。
- 实施完成后把真实文件、类、函数、逻辑、数据、状态和输出写入实施后记录。
- 不在实施文档中写正式测试通过或主题验收通过。

调 `workflow gate impl` 时，程序必须检查：

- 实施文档完整。
- 每个主题的实施后记录和未完成内容完整。
- 不存在“计划与实际的差异”章节。
- 当前代码相对实施前基线确实发生变化。

### 第三道门：用户确认

代码检查通过后，向用户说明实际修改内容和开发检查反馈。用户确认后调 `workflow gate impl --confirmed`，再进入 `test_code`。提交或推送代码不是本阶段固定门禁，只有用户明确要求时才执行。

## 6. 发现问题时返回

- 产品行为不清楚：返回 `spec`。
- 验收条件不清楚：返回 `acceptance_plan`。
- 测试范围不清楚：返回 `test_plan`。
- 真实技术行为不确定：由用户决定是否返回 `spike`。
- 只是实施方案需要调整：停在 `impl`，更新实施前计划并重新取得用户确认。

任何返回都不能修改原来的确认事实。更新后的计划确认后，实施后记录只对应最新的实施前计划。

## 7. 公共代码和主题关系

`impl/index.md` 只继承并展示 `acceptance/index.md` 的主题关系，不重新制定顺序。公共代码同时服务多个主题时，只在一个主题文档中完整记录文件、函数和逻辑；其他主题只记录依赖关系、对应验收条件和测试项，并链接到详细记录。

如果发现新的跨主题依赖，先停止实施，检查是否影响产品行为、验收条件或测试范围；不能只在实施文档中偷偷增加依赖。

## 8. 代码开发规范

计划确认后的具体代码修改规则见：

- `Standardized_Repository/impl/code_implementation.md`

`workflow discuss` 在 `impl` 阶段会额外加载该文件。本文只规定实施阶段如何讨论计划、执行门禁和记录结果，不把代码修改规则混进实施文档模板。

## 9. 文档边界

本文件负责实施阶段的讨论、门禁和记录，不规定具体代码写法。

代码的模块、接口、依赖、接缝、状态、副作用、错误处理和测试面，统一按
`Standardized_Repository/impl/code_implementation.md` 执行。

本阶段不从外部项目引入流程或编码规则。外部资料即使可以帮助理解，也不能成为本项目的门禁依据；本项目的产品设计、代码设计、测试计划、实施计划和代码开发规范必须在本项目文档中明确写出。

调用 `workflow gate impl --discuss-done` 前，必须先调用 `workflow discuss`，让当前工作流加载本阶段的实施计划模板、实施流程规范和代码开发规范。第一道门会检查这三份材料是否已经为当前工作流加载；没有加载时不能结束实施计划讨论。
如果实施计划确认前发现代码已经变化，不能继续重复调第一道门。只有用户确认当前代码应作为新的实施前现状时，才可以调 `workflow gate impl --rebaseline`；重设后如果代码再次变化，仍然必须停止并重新处理基线。

如果代码已经是本次实施结果，用户不需要伪造新的代码变化。完成第一道门和实施后记录后，用户可以调 `workflow gate impl --accept-existing-code` 明确确认当前代码；确认后代码再次变化仍然必须被门禁拒绝。
