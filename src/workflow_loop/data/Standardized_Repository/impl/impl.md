# 实施阶段工作规范

## 1. 阶段职责

实施阶段把已经确认的产品结果和验收条件落实为真实代码。它同时包含两部分：先确认实施前计划，再依据已经确认的计划修改代码并记录实际修改。

本阶段使用 `Template_Repository/impl/impl.md` 生成 `impl/索引.md` 和各主题实施记录。不重新确定验收主题，不降低验收条件，不把正式测试和主题验收塞进实施阶段。

本阶段位于验收计划之后、测试计划之前。测试计划和 `TC`（测试项编号）此时尚不存在，不得作为实施依据；实施确认完成后进入 `test_plan`（测试计划阶段）。

## 2. 开始前调查

先读取：

1. 当前工作流状态、工作流编号和全部验收主题。
2. `acceptance/索引.md`，确认主题顺序和前置主题。
3. 所有 `acceptance/<主题文件标识>_验收计划.md`，确认用户结果、验收范围和验收条件。
4. 产品设计、代码设计、穿刺结论和 `需求交付追踪表.md`。

已有代码时必须查看真实文件、类、函数、调用关系和已有测试。项目具备运行条件时，运行项目或相关检查来核对事实；不能只看文档猜代码。

从零开始且没有实现代码时：

- 不能编造“当前逻辑”。
- 计划中的代码位置写成“新增”。
- 依据使用已确认的产品设计、代码设计、验收计划和穿刺结论。
- 没有可运行的现有代码或测试时写“暂无”；有可运行的脚本或测试时仍必须运行并记录事实。

### 上游变化后重新进入本阶段

如果终端说明本次是因为上游变化或从后续阶段返回 `impl`（代码实施阶段），本阶段首先做的是**重新核对**，不是默认重新开发代码：

1. 说明是哪一个上游阶段发生了什么变化。
2. 对照最新验收条件核对现有实施计划、实施记录和真实代码；后续已有测试计划只能作为问题证据，不能反过来成为实施依据。
3. 全部仍一致时，保留现有代码和实施记录，由用户调 `workflow gate impl --accept-existing-code` 明确确认既有代码。
4. 存在不一致时，只修改受影响的计划、代码和实施记录，再走正常实施门禁。

不得为了证明“重新实施”而制造无意义代码变化。旧的测试执行、主题验收和全量回归结果已经失效，后续阶段仍必须重新执行。

恢复进入 `impl` 时程序会自动保存当前代码哈希作为变化比较基线，但哈希本身不能用于回退。不要把 `workflow gate impl --rebaseline` 当成默认步骤；只有用户明确确认当前代码是新的实施前现状时才使用它。真正修改代码前，仍必须通过 `workflow gate impl --prepare-code` 保存计划修改文件的真实内容。

## 3. 第一性原理需求检查

实施计划讨论开始前，先说明：

- 用户要解决的实际问题。
- 用户最终要得到的产品结果。
- 本次全部验收主题及主题关系。
- 每个主题对应的验收条件。
- 需要修改的代码范围和共用代码。
- 仍可能改变实施结果的问题。

对所有会影响文件、函数、处理逻辑、数据、状态或输出的问题逐个询问用户，直到双方达成共识。已经能从已确认文档、真实代码或运行结果确定的事实不重复询问，也不能为了“问全”提出与实施无关的问题。

## 4. 全局讨论和主题讨论

### 4.1 先做全局检查

先向用户汇总七项内容：用户问题、最终产品结果、全部主题、主题依赖、共用代码、已确认依据、未解决问题及需要返回的阶段。

### 4.2 再逐个主题讨论

每次只讨论一个需要用户决定的问题，并给出具体建议。每个主题依次确认：

1. 主题要解决的用户问题和完成后的用户结果。
2. 对应的验收条件。
3. 具体文件、类、函数或新增代码位置。
4. 当前代码逻辑；从零项目说明“暂无现有逻辑”。
5. 修改后的具体处理逻辑。
6. 数据、状态和输出怎样变化。
7. 主题依赖和公共代码怎样处理。
8. 未解决问题及处理阶段。

用户确认一个主题的实施前计划后，才能写入对应文档；所有主题的计划都确认后，才能通过 `workflow gate impl --discuss-done`。

## 5. 三道正式门和实施前回退门

### 第一道门：讨论完成

`workflow gate impl --discuss-done` 只在以下条件满足时通过：

- `impl/索引.md` 存在，并继承 `acceptance/索引.md` 的主题关系。
- 当前全部主题都有实施记录。
- 每份主题文档都有实施依据、实施前计划、开发检查计划、未决问题和上下游文档。
- 未决问题为“暂无”。
- 代码状态与进入 `impl` 时的基线一致，尚未开始修改代码。

### 实施前回退门：保存真实文件内容

第一道门通过后，必须调 `workflow gate impl --prepare-code`。`--prepare-code` 的中文含义是“准备实施代码回退基线”。程序必须：

1. 从全部 `impl/<主题文件标识>_实施记录.md` 的“代码修改计划”读取计划修改的文件路径。
2. 检查路径是当前项目内的具体文件，不能是目录、通配符、模块名或“相关文件”等模糊写法。
3. 检查当前代码仍与第一道门通过时一致，防止保存到已经修改过的内容。
4. 对现有文件保存修改前的真实内容；对计划新增文件保存“原本不存在”的记录。
5. 保存回退清单、副本位置和内容哈希，再重新读取副本核对完整性。

任一计划路径无法确认、文件副本缺失、保存失败或哈希不一致时，本门不能通过，也不能开始修改代码。通过后才能实施。

本门只保存实施计划明确列出的文件，不复制整个项目，也不创建整个项目的压缩包。它服务于整个工作流执行 `workflow abort` 时回退本次修改；用户只取消一个功能时，仍按重新确认后的实施计划定向删除或调整该功能代码，不恢复整个工作流。

实施确认并完成后续 `test_plan`（测试计划阶段），再进入 `test_code`（测试代码阶段）。此时程序会把已有测试文件和测试配置加入同一份回退清单，并在测试代码门禁时登记本阶段新增的测试文件。AI 不需要手工维护这部分清单，但 impl 的回退清单必须先存在且完整，否则不能开始 test_code。

### 第二道门：实施完成检查

第一道门和实施前回退门都通过后才能修改代码。修改代码时：

- 按主题和依赖关系推进，不自动并行修改同一文件或公共函数。
- 运行语法、类型、静态检查或已有局部检查作为开发反馈；本阶段不编写正式测试代码，也不产生正式测试事实。
- 实施完成后把真实文件、类、函数、逻辑、数据、状态和输出写入实施后记录。
- 不在实施文档中写正式测试通过或主题验收通过。

调 `workflow gate impl` 时，程序必须检查：

- 实施文档完整。
- 每个主题的实施后记录和未完成内容完整。
- 不存在“计划与实际的差异”章节。
- 实施前回退清单和文件副本仍然存在，内容哈希没有变化。
- 实际修改的代码文件都在已经确认的实施计划和回退清单中；发现计划外修改时不能放行。
- 当前代码相对实施前基线确实发生变化。

### 第三道门：用户确认

代码检查通过后，向用户说明实际修改内容和开发检查反馈。用户确认后调 `workflow gate impl --confirmed`，再进入 `test_plan`（测试计划阶段）。提交或推送代码不是本阶段固定门禁，只有用户明确要求时才执行。

## 6. 发现问题时返回

- 产品行为不清楚：返回 `spec`。
- 验收条件不清楚：返回 `acceptance_plan`。
- 测试范围不清楚：返回 `test_plan`。
- 真实技术行为不确定：由用户决定是否返回 `spike`。
- 只是实施方案需要调整：停在 `impl`，更新实施前计划并重新取得用户确认。

任何返回都不能修改原来的确认事实。更新后的计划确认后，实施后记录只对应最新的实施前计划。

## 7. 公共代码和主题关系

`impl/索引.md` 只继承并展示 `acceptance/索引.md` 的主题关系，不含测试计划列，也不重新制定顺序。公共代码同时服务多个主题时，只在一个主题文档中完整记录文件、函数和逻辑；其他主题只记录依赖关系和对应验收条件，并链接到详细记录。

如果发现新的跨主题依赖，先停止实施，检查是否影响产品行为或验收条件；不能只在实施文档中偷偷增加依赖。

## 8. 代码开发规范

计划确认后的具体代码修改规则见：

- `Standardized_Repository/impl/code_implementation.md`

`workflow discuss` 在 `impl` 阶段会额外加载该文件。本文只规定实施阶段如何讨论计划、执行门禁和记录结果，不把代码修改规则混进实施文档模板。

## 9. 文档边界

本文件负责实施阶段的讨论、门禁和记录，不规定具体代码写法。

代码的模块、接口、依赖、接缝、状态、副作用、错误处理和测试面，统一按
`Standardized_Repository/impl/code_implementation.md` 执行。

本阶段不从外部项目引入流程或编码规则。外部资料即使可以帮助理解，也不能成为本项目的门禁依据；本项目的产品设计、代码设计、验收计划、实施计划和代码开发规范必须在本项目文档中明确写出。

实施阶段的固定结束条件是：实施计划列出的文件集合、真实代码差异集合、实施后记录中的文件集合完全一致；每一项都写清具体文件、精确位置、实际逻辑，以及数据、状态或输出变化。开发检查只用于发现实施问题，不等于正式测试。尚未生成的测试计划和结果文档只写普通相对路径加“（待生成）”，不能写 Markdown 链接。

调用 `workflow gate impl --discuss-done` 前，必须先调用 `workflow discuss`，让当前工作流加载本阶段的实施计划模板、实施流程规范和代码开发规范。第一道门会检查这三份材料是否已经为当前工作流加载；没有加载时不能结束实施计划讨论。
如果实施计划确认前发现代码已经变化，不能继续重复调第一道门。只有用户确认当前代码应作为新的实施前现状时，才可以调 `workflow gate impl --rebaseline`；重设后如果代码再次变化，仍然必须停止并重新处理基线。

第一道门通过后不能直接开始改代码。必须先调 `workflow gate impl --prepare-code`，由程序根据实施文档保存计划修改文件的真实内容并通过完整性检查。没有通过实施前回退门时，`workflow gate impl` 必须拒绝实施完成校验。

如果代码已经是本次实施结果，用户不需要伪造新的代码变化。完成第一道门和实施后记录后，用户可以调 `workflow gate impl --accept-existing-code` 明确确认当前代码；确认后代码再次变化仍然必须被门禁拒绝。
