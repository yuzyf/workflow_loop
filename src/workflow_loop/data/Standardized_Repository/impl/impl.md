# 代码实施阶段工作规范

## 1. 阶段目标和固定顺序

本阶段把已经确认的产品结果和验收条件落实为真实代码，固定按下面三个内部步骤连续完成：

1. **代码计划**：调查真实代码，写入“实施前计划（代码计划）”，写清最低实现设计、文件、符号、具体逻辑和开发检查，并让用户确认一次。
2. **代码实施**：保存计划文件的修改前内容后，AI 按已确认计划连续修改代码，并在“实施后记录（代码实施与代码结果）”中记录动作，不增加逐步用户确认。
3. **代码结果**：在同一份实施记录的“代码结果”小节根据最终真实代码填写结果，程序完整校验后，让用户确认一次。

用户只确认代码计划和代码结果。代码实施过程中只有出现必须改变已确认计划的事实时，才停下来重新确认计划；不能把日常进度拆成新的用户环节。

代码计划是本轮实施决定的前置记录：

- 从零开发时，在 `impl/<主题文件标识>_实施记录.md` 的“代码计划”中写清最低实现设计。
- 修改已有产品时，以现有架构文档和真实代码为约束，在代码计划中写清本轮新增或改变的实现决定。
- 代码、测试和验收完成后，`update_code_design`（最终代码设计同步）根据真实实现更新 `spec/代码架构设计.md`。

本阶段使用 `Template_Repository/impl/impl.md` 生成 `impl/索引.md` 和各主题实施记录，并遵守 `Standardized_Repository/impl/code_implementation.md`。本阶段不重新确定验收主题，不降低验收条件，不制定测试项，也不写正式测试或验收结论。

填写实施记录的固定字段时，标签和值必须在同一行，例如 `- 工作流编号：<workflow_id>` 和 `- 验收主题：<验收主题>`。标签单独占一行时，下一行内容不会被读取为该字段值，必须把值移回标签同一行。

## 2. 开始前调查

先读取并核对：

1. 当前工作流编号、全部验收主题和主题关系。
2. `acceptance/索引.md` 和全部主题验收计划中的用户结果、范围及 `AC`（验收条件）。
3. 产品设计、有效穿刺结论和 `需求交付追踪表.md`。
4. 现有 `spec/代码架构设计.md`；文件不存在时明确写“暂无现有代码设计”，不能编造。
5. 真实产品代码、调用入口、配置、相关测试和项目已有开发命令。

已有代码时必须查看真实文件、类、函数、调用关系和现有测试。具备安全运行条件时，运行与本次范围直接有关的现有功能或检查来核对事实；不能只看文档猜代码。

从零开发且没有实现代码时：

- 当前逻辑写“暂无现有逻辑”，代码位置写明确的计划新增路径和符号。
- 在“最低实现设计”中写清模块职责、入口和调用顺序、数据状态、副作用、错误和边界。
- 只设计当前验收条件真正需要的部分，不为了“架构完整”预建无关层次、接口或扩展点。
- 没有可运行内容时如实写“暂无”；不能用空命令或伪结果冒充开发检查。

实施记录或既有设计与真实代码冲突时，以已确认产品行为和真实代码事实为调查依据，先查清冲突属于产品定义、验收条件、代码计划还是现有实现，不能自行挑一个方便的版本继续。

## 3. 代码计划

### 3.1 先说明要解决什么

计划讨论开始前，用直白中文汇总：

1. 用户要解决的实际问题和最终产品结果。
2. 全部验收主题、主题依赖和每条验收条件。
3. 当前代码怎样工作；从零项目写“暂无现有逻辑”。
4. 需要修改或新增的文件、类、函数、配置和共享代码。
5. 最低实现设计中的模块职责、接口、调用顺序、状态、副作用、错误和边界。
6. 可复用穿刺资产怎样重新运行并为哪些验收条件提供依据。
7. 仍会改变文件集合、逻辑、数据、状态或输出的未决问题。

能从已确认文档、真实代码或运行结果查明的事实先自行查明，不重复询问用户。每次只讨论一个真正需要用户决定的问题，并给出建议和理由。

### 3.2 逐主题写代码计划

每个主题都必须写清：

- 预期产品结果。
- 最低实现设计；修改已有产品时只写本轮变化，从零开发时必须完整到足以编码。
- 每个计划文件和精确符号、当前逻辑、计划逻辑、数据状态或输出变化、对应验收条件和前置步骤。
- 开发检查命令或方法、检查范围和预期观察结果。
- 未决问题；没有时写“暂无”。

公共代码同时服务多个主题时，只在一个主题完整记录修改，其余主题通过依赖和验收条件引用它，不能复制多份近似计划。

### 3.3 用户确认代码计划

所有主题计划完整后，向用户展示计划和影响。用户确认后由 AI 执行：

```text
workflow gate impl --discuss-done
```

第一道门只确认代码计划已经聊清楚，不表示代码已经修改。计划中的文件是预期，不是允许修改的白名单。计划确认后可以直接开始实施；发现额外文件时直接修改，并在代码结果中说明文件、修改理由、对应验收条件和测试证据。

`workflow gate impl --prepare-code` 仍可作为独立恢复备份动作，但不是代码门禁前置，也不决定代码门禁是否通过。

## 4. 代码实施

AI 按计划和主题依赖连续实施：

- 可以修改完成已确认产品行为所需的任何项目文件；计划外文件必须在代码结果中解释。
- 同一文件或公共函数按依赖顺序处理，不让多个主题并行覆盖。
- 每完成一个计划步骤，立即填写“实施动作记录”，写清实际文件、精确位置、动作、当步反馈和状态。
- 运行语法、类型、静态检查或与修改位置直接相关的局部检查，并记录真实反馈。
- 开发检查只是实施反馈，不是正式测试事实，不写“正式测试通过”或“主题验收通过”。

代码实施不需要逐步询问用户。出现下面任一情况时必须停止：

- 需要改变已确认接口、核心逻辑、数据状态、错误结果或用户可见结果。
- 发现产品行为或验收条件本身不清楚。
- 现有穿刺结论不足，必须重新取得真实技术证据。

只是代码改法或文件集合需要调整、但产品行为和验收条件不变时，继续实施，并在代码结果中记录实际做法；不要求重新确认计划或重设基线。

### 复用既有代码

上游变化后重新进入 `impl` 时，先核对最新产品设计和验收条件与现有计划、结果、真实代码是否仍一致：

- 全部一致时，不制造无意义代码变化；补齐当前记录后，由用户明确确认复用，再执行 `workflow gate impl --accept-existing-code`。
- 有直接不一致时，只修改受影响主题和代码路径。

`workflow gate impl --rebaseline` 仅为历史轮次兼容保留，不再是当前代码门禁的补救步骤。

## 5. 代码结果

代码完成后，根据最终真实代码填写：

1. 每个计划步骤对应的真实文件、覆盖真实差异的最终文件行号范围、最终逻辑、数据状态或输出变化和验收条件。行号范围写成 `L18-L57`；局部删除写成 `基线 L18-L31`。同一文件的每个不连续差异块都要被至少一条记录覆盖。
2. 全部开发检查的命令或方法、范围、真实反馈和是否仍需修改。
3. 未完成内容；没有时写“状态：无”。有未完成事项时写“状态：有”，并逐项说明事项、原因、影响和下一步；这种状态不能通过实施门禁。

代码计划、实施动作、真实文件差异和代码结果必须一一对应。结果与计划不一致时不能建立“计划与实际差异”章节绕过确认，必须回到代码计划处理。

完成记录后由 AI 执行：

```text
workflow gate impl
```

第二道门一次完整检查实施文档、可取得的实际文件变化和代码结果。通过后，AI 向用户展示代码计划、实施动作摘要、实际文件差异、每个文件的修改理由、验收关联、测试证据和开发检查反馈；不再重复执行开发检查。计划外文件本身不是失败原因。

用户确认代码结果后，由 AI 执行：

```text
workflow gate impl --confirmed
```

第三道门只比较第二道门保存的校验凭据，确认责任文件和状态没有变化；不重复完整校验。通过后进入 `qa`（测试验证）。提交或推送代码不是固定门禁，只有用户明确要求时才执行。

## 6. 发现问题时返回

- 产品行为、规则或边界不清楚：返回 `spec`（产品设计）。
- 验收条件不能判断：返回 `acceptance_plan`（验收计划）。
- 代码实现错、缺少或记录与真实代码不符：留在或返回 `impl`（代码实施）。
- 测试范围、测试代码、任务登记、执行或结果有问题：返回 `qa`（测试验证），并按具体变化源回到其内部对应步骤。
- 必须运行真实外部场景才能确定技术事实：由用户决定是否返回 `spike`（穿刺）。

返回只使有直接证据的受影响主题和结果失效。不能因为文件同目录、主题有间接依赖或“可能受影响”就扩大清理范围。

## 7. 文档和流程边界

- 实施文档只绑定产品设计、验收条件、有效穿刺结论、现有架构约束和真实代码，不依赖尚未生成的测试计划或 `TC`（测试项编号）。
- `impl/索引.md` 只继承 `acceptance/索引.md` 的主题关系并提供文档入口，不复制实现步骤或运行结果。
- 尚未生成的 QA 和验收文档只写普通相对路径加“（待生成）”，文件存在后再改成 Markdown 链接。
- 最终代码设计同步以前，代码计划是本轮实现决定的唯一前置记录；最终同步只把已经实现、测试和验收的真实结构写回架构文档。
- 调用 `workflow gate impl --discuss-done` 前必须先执行 `workflow discuss`，完整读取本阶段模板、规范和代码开发规范。材料变化时旧讨论确认失效，必须重新读取和确认。

## 8. 门禁失败时的诊断

门禁失败时，一次列出当前输入下全部可以独立确认的真实问题，不能在第一项失败后停止其它不依赖它的检查。每项都必须保留位置、预期、实际、证据、影响和改法：位置指向实际文件、章节、表格行、字段或状态；证据说明实际读取到的内容、差异或检查结果；改法说明应修改什么以及为什么。

某项检查依赖已失败或缺失的前置事实，继续检查不能得出可靠结论时，标为“未检查”，写明真实依赖的前置检查，以及前置修复后会检查什么。未检查不是错误，也不能被说成通过。

每项的改法使用文字，不能各自附带可执行命令。全部诊断条目之后只保留一条当前可执行的下一步命令；该命令要说明执行者、会修改的文件或状态、成功条件和成功后进入的阶段。
