# 缺陷复现阶段工作规范

## 目的

在制定修复计划前，用真实场景确认缺陷现象和根因。`reproduce`（缺陷复现阶段）负责回答“问题怎样发生、为什么发生”；后续 `spike`（穿刺阶段）只验证修复仍依赖的具体技术不确定性。

## 一、真实复现要求

- 必须使用真实环境、真实输入和真实代码路径确认缺陷，不得只做推测。
- 使用用户实际遇到问题的环境、输入、文件、接口响应、设备或等价的真实样本。
- 不得用自己编造的数据跑通一条假流程后声称缺陷已经复现。
- 具备安全运行条件时必须实际运行，并记录命令、操作、日志或输出。
- 需要生产账号、付费调用、远程写入或危险操作时，先取得用户同意。
- 无法复现时写清阻塞原因并继续讨论，不能把“可能是”写成已确认根因。

## 二、开始前调查

开始时先查看：

1. 用户描述的缺陷现象、触发条件和期望结果。
2. 对应产品功能文档和代码架构文档。
3. 实际入口、调用链、状态变化、错误处理和日志位置。
4. 已有测试、历史缺陷记录和能够安全运行的现有功能。

## 三、逐项确认事实

每次只讨论一个没有确认的问题，直到以下内容明确：

- 缺陷发生在哪个真实场景。
- 使用什么环境和真实输入可以稳定触发。
- 实际结果与期望结果分别是什么。
- 修复后用户应该恢复得到什么结果，并据此确定一个验收主题。
- 根因是什么，落在哪段代码、配置、数据或外部服务。
- 哪些日志、运行输出、测试或代码事实证明了这个根因。
- 修复仍缺少哪些事实；已经确定的内容不要放进后续穿刺。

无法复现或根因没有确认时，继续调查或向用户说明具体阻塞。不能为了推进流程写假结论。

## 四、生成文档

用户确认共同理解后，使用 `Template_Repository/reproduce/reproduce.md`：

1. 新增或修改一份缺陷记录。
2. 更新 `bug/index.md` 并链接本次缺陷记录。
3. 一份缺陷记录只写一个验收主题。
4. 缺陷复现阶段只填写原始事实，不提前填写后续修复和验收结果。

程序负责检查文件变化、文件名、固定字段、章节和索引链接；本规范不重复这些门禁实现。程序不能判断证据是否伪造，用户在第三道门确认前必须核对证据是否真实。

## 五、完成前对抗性审查

- 是否真的运行了用户所说的场景，而不是只读代码后猜测。
- 是否使用真实输入或真实样本，而不是自己制造方便通过的数据。
- 实际结果和期望结果是否明确不同。
- 根因是否说明了具体错误为什么会产生，而不是只重复错误现象。
- 根因位置是否能让维护者找到对应代码、配置、数据或外部服务。
- 根因证据是否足以排除其他主要可能。
- “修复仍存在的不确定性”是否只保留真正未知、会影响修复设计的事实。
- 验收主题是否直接写修复后的用户结果，而不是代码任务或根因名称。
- 是否更新 `bug/index.md` 并链接本次记录。
