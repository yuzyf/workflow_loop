# 缺陷复现规范

## 目的

在制定修复计划前，用真实场景确认缺陷现象和根因。`reproduce`（缺陷复现阶段）负责回答“问题怎样发生、为什么发生”；后续 `spike`（穿刺阶段）只验证修复仍依赖的具体技术不确定性。

## 一、真实复现要求

- 使用用户实际遇到问题的环境、输入、文件、接口响应、设备或等价的真实样本。
- 不得用自己编造的数据跑通一条假流程后声称缺陷已经复现。
- 具备安全运行条件时必须实际运行，并记录命令、操作、日志或输出。
- 需要生产账号、付费调用、远程写入或危险操作时，先取得用户同意。
- 无法复现时写清阻塞原因并继续讨论，不能把“可能是”写成已确认根因。

## 二、缺陷记录结构

文件名固定为 `bug/<YYYY-MM-DD_HHmm-缺陷描述>.md`，正文固定为：

```markdown
# 【缺陷】<缺陷名称>

- 工作流编号：<当前 workflow_id，也就是当前工作流编号>
- 复现状态：已复现
- 根因状态：已确认
- 验收主题：<修复后用户应该得到的唯一结果名称>

## 1. 缺陷现象

<用户在什么操作中看到了什么问题。>

## 2. 真实复现条件

- 运行环境：<系统、版本、配置、设备或外部服务条件>
- 真实输入：<真实文件、请求、状态或操作；敏感内容可以脱敏，但不能改造成虚构样本>

## 3. 复现步骤

1. <从真实入口开始的操作>
2. <直到缺陷出现>

## 4. 实际结果

<实际输出、状态、日志、界面或错误。>

## 5. 期望结果

<根据已确认产品设计，本来应该得到什么。>

## 6. 根因

- 根因说明：<导致缺陷的具体判断、状态、数据、配置或外部行为>
- 根因位置：<具体代码文件和符号，或配置、数据、外部服务位置>
- 根因证据：<运行输出、日志、测试、代码路径或用户确认怎样证明这个结论>

## 7. 修复仍存在的不确定性

<没有则写“暂无”；有则逐项写清未知事实，供后续穿刺讨论。>

## 8. 修复与验收结果

本节由后续阶段按实际结果追加。缺陷复现阶段不得填写，也不能改写前七节。

- 主题测试和主题验收通过后，追加实施记录、测试结果和主题验收结果链接，最终状态写“主题验收通过，待全量回归”。
- 最终全量回归失败后，追加回归结果链接，最终状态写“回归失败，重新处理中”。
- 最终全量回归和整体验收都通过后，追加两个结果链接，最终状态写“已修复并验收”。
- 同一阶段重复确认时更新原阶段记录，不能重复追加相同内容。
```

“复现状态”和“根因状态”只有在事实已经确认后才能写固定值。没有确认时继续调查，不生成假结论过门禁。

## 三、索引结构

`bug/index.md` 至少包含：

```markdown
# Bug 索引

| Bug 记录 | 现象 | 根因 | 状态 |
|---|---|---|---|
| [<缺陷名称>](./<YYYY-MM-DD_HHmm-缺陷描述>.md) | <一句话现象> | <一句话根因> | 根因已确认 |
```

本阶段必须更新索引，并链接本次新增或修改的缺陷记录。

## 四、程序门禁检查

程序检查：

- `bug/index.md` 和至少一份缺陷记录在讨论完成后发生变化。
- 缺陷记录文件名符合规定。
- 索引链接了本次缺陷记录。
- 工作流编号与当前工作流一致。
- 复现状态为“已复现”，根因状态为“已确认”。
- 验收主题存在且不是“暂无”“待补充”等占位内容。
- 七个复现章节存在，并写清真实环境、真实输入、根因说明、根因位置和根因证据。
- 第八节只能在后续阶段追加，不能作为缺陷复现阶段的通过条件。
- 后续程序只能追加或更新第八节和 `bug/index.md` 状态，不能改写前七节。

程序不能判断证据是否伪造。用户在第三道门确认前，必须核对复现过程和根因证据是否真实。

## 五、完成前对抗性审查

- 是否真的运行了用户所说的场景，而不是只读代码后猜测。
- 是否使用真实输入或真实样本，而不是自己制造方便通过的数据。
- 实际结果和期望结果是否明确不同。
- 根因是否说明了具体错误为什么会产生，而不是只重复错误现象。
- 根因位置是否能让维护者找到对应代码、配置、数据或外部服务。
- 根因证据是否足以排除其他主要可能。
- “修复仍存在的不确定性”是否只保留真正未知、会影响修复设计的事实。
- 验收主题是否直接写修复后的用户结果，而不是代码任务或根因名称。
- 是否更新 `bug/index.md` 并链接本次记录。
