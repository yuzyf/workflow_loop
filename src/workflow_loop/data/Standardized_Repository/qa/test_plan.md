# 测试计划阶段工作规范

## 1. 阶段职责

测试计划阶段发生在实施代码和实施记录确认之后。目的不是猜将来怎样实现，而是根据已确认验收条件和当前真实代码，写出可以直接落实为测试代码的明确计划。

固定顺序是：验收计划 -> 实施计划与实施代码 -> 测试计划 -> 测试代码 -> 正式主题测试。本阶段不改产品代码、不写测试代码、不执行正式测试，也不填写测试结果。

## 2. 开始前调查

先读取并核对：

1. 当前工作流、全部验收主题和主题关系。
2. 每份验收计划中的显式 `AC`（验收条件）锚点、开始前状态、触发动作、可检查结果、通过标准和不通过标准。
3. 每份已确认实施记录的实际文件、精确代码位置、真实逻辑，以及数据、状态或输出变化。
4. 对应真实产品代码、调用入口、已有测试、测试配置和统一测试入口。
5. `需求交付追踪表.md` 中当前主题的交付状态。

实施记录与真实代码不一致时返回 `impl`（代码实施阶段），不能在测试计划里猜。验收条件无法判断通过或不通过时返回 `acceptance_plan`（验收计划阶段）。产品行为没有定义时返回 `spec`（产品设计阶段）。

## 3. 固定 13 列

每份 `qa/<主题文件标识>_测试计划.md` 的“验收条件覆盖”表只能使用以下表头，名称和顺序不能改变：

```markdown
| 验收条件链接 | 测试项 | 前置测试项 | 测试方式 | 产品入口 | 代码入口 | 测试入口 | 准备数据 | 执行动作 | 观察位置 | 预期结果 | 不通过表现 | 证据要求 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| [AC-01：完成条件](../acceptance/<主题文件标识>_验收计划.md#ac-01) | <a id="tc-01"></a>[TC-01 直白测试名称](#tc-01) | 无 | 自动化测试 | <真实产品入口> | `src/<文件>::<函数或类>` | `tests/<文件>::<测试函数或场景>` | <具体数据和前置状态> | <通过产品入口执行的动作> | <具体返回值、数据库、文件、页面或状态> | <明确的值、数量、存在性或状态> | <明确的缺失、残留、错误值或错误状态> | <结构化报告和可复核事实> |
```

字段要求：

- `产品入口`：用户或调用方真实触达产品的方式，不能写私有辅助函数。
- `代码入口`：实施后的真实产品文件和可定位符号，固定写成 `项目相对文件::可定位标识`。
- `测试入口`：自动化或混合测试将使用的明确测试文件和目标，也写成 `项目相对文件::可定位标识`。文件可以在下一阶段新建，但路径和目标必须现在确定。
- `准备数据`、`执行动作`、`观察位置`：共同说明测试从什么状态开始、实际做什么、到哪里检查。
- `预期结果`：必须与验收条件的通过标准一致，写具体值、数量、存在性或状态。
- `不通过表现`：明确哪些实际结果算失败，不能只写“不符合预期”。
- `证据要求`：写正式执行后要保存的结构化报告事实和必要业务证据。

不允许“实施后确认”“待补充”“相关测试”“功能正常”“符合预期”等占位或模糊内容。无法填写时必须停止并返回负责该事实的阶段。

## 4. 覆盖和依赖

- 每条 `AC` 至少对应一个 `TC`（测试项）；一个 `TC` 只绑定一条主要 `AC`。
- 测试方式只能是“自动化测试”“人工验收”或“自动化测试 + 人工验收”。能由程序稳定判断的结果不能为了省事改成人工验收。
- 前置测试项只写同一主题内必须先通过的直接 `TC`；没有依赖写“无”，不能形成循环。
- 测试必须调用真实产品入口并检查验收条件定义的可观察状态，不能只检查角色字符串、手工设置属性或复述实现逻辑。
- 针对性回归只包含本次修改直接影响的已有行为；无直接证据的其他旧功能交给最终全量回归。

## 5. 固定产出

本阶段产出：

- 每个主题一份 `qa/<主题文件标识>_测试计划.md`。
- `qa/索引.md`，继承 `acceptance/索引.md` 的主题和直接前置关系。
- 项目级 `.workflow_loop/project.json` 中的统一全量测试入口。

测试计划的上游验收计划和实施记录已经存在，可以使用真实 Markdown 链接。尚未生成的测试结果只写反引号包裹的普通相对路径和“（待生成）”；文件存在后才改成链接。纯人工验收主题写“无自动化测试项”。

本阶段只更新 `需求交付追踪表.md` 的测试项信息，不提前填写测试代码、正式测试结果或验收结果。

## 6. 登记项目全量测试入口

先从真实项目配置、脚本或持续集成配置查明统一入口，不按项目类型猜测。用 `workflow test entry` 登记参数数组，不手工编辑 `project.json`，也不在本阶段执行入口。

命令参数数组不经过 Shell。需要管道、重定向、环境变量展开或多条命令时，把逻辑放进项目自己的受管脚本，再登记脚本。缺少依赖、服务或凭据时写清缺什么和影响，由用户决定怎样准备；不能用一条实际跑不通的命令冒充入口。

最终全量回归的唯一执行命令是 `workflow gate regression_test`，它会自动执行这里登记的统一入口。`workflow test run` 只执行已经登记的主题测试，不能用于最终全量回归。

## 7. 完成前检查

- 全部主题和全部验收条件是否被精确覆盖。
- 每份覆盖表是否恰好 13 列，且每个字段都有具体内容。
- 每个自动化或混合 `TC` 是否有真实产品入口、真实代码入口和明确测试入口。
- 准备数据、执行动作、观察位置、预期结果和不通过表现是否能直接执行和判断。
- 测试项依赖是否存在、无循环且只写直接依赖。
- 已有上游是否链接有效，未来下游是否只写普通路径和“（待生成）”。
- 是否没有编写测试代码、执行正式测试或填写测试结果。

门禁失败时必须一次列出所有可以独立确认的问题；因前置问题无法继续的检查明确写“未检查”及依赖原因。最后只给一条当前可执行的下一命令，并说明执行者、状态或文件副作用、成功条件和成功后的阶段。
