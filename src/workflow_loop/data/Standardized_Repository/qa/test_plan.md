# 测试验证阶段工作规范

测试验证环节引入工作记录表时，测试项（命令参数数组、工作目录、超时秒数、报告适配器）填在 `test_plan_<主题文件标识>.json` 中，登记命令核对表并一次登记全部任务；测试计划与测试结果文档由程序按表和机器记录生成。

## 1. 阶段目标和用户确认

`qa`（测试验证）固定按下面顺序完成：

1. 确认测试范围和通过标准。
2. 完成或复用测试代码。
3. 登记项目全量测试入口和本轮主题测试任务。
4. 用当前代码真实执行测试。
5. 根据机器记录生成测试结果。

用户只在两个位置确认：

- **开始确认**：一次确认全部主题的测试范围和通过标准。
- **结束确认**：一次确认测试范围、真实机器记录、自动化结果和人工待验收边界。

测试代码、任务登记、执行和结果整理在两次用户确认之间连续完成。范围或通过标准发生变化时，回到开始确认。

本阶段不修改产品代码，不执行人工验收，不把局部开发检查或历史通过记录写成正式测试结果。

## 2. 开始前调查

先读取并核对：

1. 当前工作流编号、全部验收主题和主题关系。
2. 每份验收计划中的显式 `AC`（验收条件）、开始前状态、触发动作、可检查结果、通过标准和不通过标准。
3. 每份已确认实施记录中的代码计划、实施动作、代码结果和开发检查。
4. 当前真实产品代码、调用入口、已有测试、测试配置和统一测试入口。
5. `需求交付追踪表.md` 中当前主题的实施结果和穿刺结论。
6. 可复用穿刺资产的用途和运行方法；需要使用时必须从原目录重新运行，不能直接沿用旧结论。

实施记录与真实代码不一致时返回 `impl`（代码实施）。验收条件无法判断时返回 `acceptance_plan`（验收计划）。产品行为没有定义时返回 `spec`（产品设计）。

## 3. 第一步：确认测试范围

### 3.1 固定计划产物

在开始确认前完成：

- 每个主题一份 `qa/<主题文件标识>_测试计划.md`。
- `qa/索引.md`，继承 `acceptance/索引.md` 的主题和直接前置关系。
- 项目级 `.workflow_loop/project.json` 中的统一全量测试入口。

每份测试计划的“验收条件覆盖”表固定使用 13 列：

```markdown
| 验收条件链接 | 测试项 | 前置测试项 | 测试方式 | 产品入口 | 代码入口 | 测试入口 | 准备数据 | 执行动作 | 观察位置 | 预期结果 | 不通过表现 | 证据要求 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| [AC-01：完成条件](../acceptance/<主题文件标识>_验收计划.md#ac-01) | <a id="tc-01"></a>[TC-01 直白测试名称](#tc-01) | 无 | 自动化测试 | <真实产品入口> | `src/<文件>::<函数或类>` | `tests/<文件>::<测试函数或场景>` | <具体数据和前置状态> | <通过产品入口执行的动作> | <具体返回值、数据库、文件、页面或状态> | <明确的值、数量、存在性或状态> | <明确的缺失、残留、错误值或错误状态> | <结构化报告和可复核事实> |
```

字段要求：

- `产品入口` 是用户或调用方真实触达产品的方式。
- `代码入口` 和自动化或混合测试的 `测试入口` 使用 `项目相对文件::可定位标识`。
- `准备数据`、`执行动作` 和 `观察位置` 共同说明从什么状态开始、做什么、到哪里检查。
- `预期结果` 与验收条件的通过标准一致，写具体值、数量、存在性或状态。
- `不通过表现` 明确什么实际结果算失败。
- `证据要求` 写正式执行后必须保存的结构化报告事实和必要业务证据。

不允许“实施后确认”“待补充”“相关测试”“功能正常”或“符合预期”等占位或模糊内容。

### 3.2 覆盖和依赖

- 每条 `AC` 至少对应一个 `TC`（测试项）；一个 `TC` 只绑定一条主要 `AC`。
- 测试方式只能是“自动化测试”“人工验收”或“自动化测试 + 人工验收”。
- 能由程序稳定判断的结果不能为了省事改成人工验收。
- 前置测试项只写同一主题内必须先通过的直接 `TC`；没有依赖写“无”，不能形成循环。
- 测试必须调用真实产品入口并检查验收条件定义的可观察状态，不能只检查常量、手工设置属性或复述实现逻辑。
- 针对性回归只包含本次修改有直接影响证据的已有行为；其他旧功能交给最终全量回归。

### 3.3 登记项目全量测试入口

先从真实项目配置、脚本或持续集成配置查明统一入口，再由 AI 使用 `workflow test entry` 登记参数数组。命令不经过 Shell；需要管道、重定向、环境变量展开或多条命令时，把逻辑放进项目自己的受管脚本。

范围确认时只登记统一入口，不执行它。最终全量回归只由 `workflow gate regression_test` 执行；`workflow test run` 只运行本轮已经登记的主题测试。

### 3.4 用户开始确认

AI 一次展示全部主题的测试范围、测试方式、通过标准、测试入口、依赖和人工验收边界。用户确认后由 AI 执行：

```text
workflow gate qa --discuss-done
```

第一道门检查计划结构、实施结果、真实入口和主题覆盖，并保存测试范围凭据。通过后不再逐项询问是否可以写测试代码、登记或执行；测试计划是预期，不是测试文件白名单。

## 4. 第二步：完成或复用测试代码

按已确认计划逐项核对现有测试：

- 入口、断言、准备数据和观察位置与当前 `AC`、`TC` 一致时可以直接复用。
- 缺少覆盖或标识时，只修改测试代码、测试样本和测试配置。
- 每个自动化或混合测试入口都要有完整 `Workflow-Test` 标识，字段与测试计划一致。
- 发现产品代码需要修改时返回 `impl`，不能在 QA 中顺手改产品代码。

可以运行单个测试函数、类或文件作为测试代码开发反馈，但这不是正式执行：不登记机器记录，不生成测试结果，不据此写通过。

测试代码完成并核对后直接进入任务登记。实施中发现额外测试文件、夹具、辅助脚本或配置时，直接记录其测试项和验收条件，不重设测试基线。

## 5. 第三步：登记主题测试任务

对每个自动化或混合 `TC`，由 AI 使用 `workflow test prepare` 登记：

- 当前主题和 `TC`。
- 精确测试入口。
- 参数数组命令。
- 项目内工作目录。
- 超时时间。
- `vitest-junit` 或 `pytest-junitxml` 结构化报告适配器。
- 当前主题内的直接前置测试项。

登记只保存待执行任务，不运行测试，也不等于通过。全部自动化任务登记完整后直接执行测试。

## 6. 第四步：真实执行

由 AI 原样执行：

```text
workflow test run
```

程序按登记内容运行当前代码，解析结构化报告，并记录命令、工作目录、时间、退出码、输出哈希、报告哈希、精确匹配入口、执行数、跳过数、失败数、错误数、产品代码哈希和测试代码哈希。

一个自动化测试项只有同时满足以下条件才通过：

- 结构化报告的入口集合与计划精确一致。
- 实际执行数大于 `0`。
- 跳过数、失败数和错误数都为 `0`。
- 退出码为 `0`。
- 命令、工作目录和测试入口与登记一致。
- 机器记录绑定的产品代码和测试代码仍是当前版本。

失败、超时、阻塞或未执行时，不生成通过结果，也不能改写失败输出为通过。先判断问题属于产品代码、QA 范围、测试代码、任务登记、临时环境还是上游产品和验收定义，再处理对应内部步骤或返回阶段。

## 7. 第五步：生成测试结果

全部自动化或混合测试项通过后，严格根据当前机器记录生成 `qa/<主题文件标识>_测试结果.md`。命令、工作目录、执行时间、退出码、报告适配器、报告路径与哈希、实际执行数、跳过数、失败数、错误数、精确匹配入口和代码哈希都从机器记录填写，不从终端文字概括或人工改写。

纯人工主题不生成测试结果文档，直接把人工范围交给主题验收。自动化和人工混合主题只记录自动化执行事实，人工部分保持待验收。

## 8. 结束校验和用户确认

结果整理完成后由 AI 执行：

```text
workflow gate qa
```

第二道门一次完整校验测试计划、测试代码、任务登记、机器记录、结果文档和追踪关系。通过后保存校验凭据。

AI 随后向用户展示测试范围、真实机器记录、自动化测试结果、未执行或阻塞情况和人工待验收边界。用户确认后由 AI 执行：

```text
workflow gate qa --confirmed
```

第三道门只比较第二道门凭据，不重新解析全部文档、不重新扫描链接，也不再次运行测试。通过后进入 `topic_acceptance`（主题验收）。

## 9. QA 内部失效和返回

变化只清除有直接证据的受影响主题和结果：

- 测试计划或通过标准变化：回到 QA 范围步骤，重新确认范围；旧任务和结果失效。
- 测试代码变化：保留仍有效的范围，回到测试代码步骤；重新登记并执行受影响测试。
- 任务、执行输入或测试结果变化：保留仍有效的范围和测试代码，只清除受影响任务、机器结果和下游验收。
- 共享测试运行器、共享测试配置或统一入口变化且能证明影响全部主题时，全部主题重新执行。
- 仅在同一目录、同一文件或存在间接依赖，不足以自动扩大失效范围。

临时依赖、服务或凭据问题留在 QA，环境恢复后重试。产品行为不清楚返回 `spec`，验收条件不清楚返回 `acceptance_plan`，产品代码错误返回 `impl`，真实技术行为不确定时由用户决定是否返回 `spike`。

## 10. 完成前对抗性检查

- 全部主题和验收条件是否被精确覆盖。
- 测试计划是否固定 13 列且没有占位或模糊内容。
- 测试代码是否对应当前计划且没有修改产品代码。
- 每个自动化或混合 `TC` 是否有完整任务和当前有效机器记录。
- 结构化报告是否精确匹配入口且真实执行数大于 `0`。
- 正式结果字段是否逐项对应机器记录。
- 是否把局部开发反馈、历史通过或终端文字冒充正式测试事实。
- 是否把人工验收部分提前写成通过。
- `qa/索引.md`、上下游链接和 `需求交付追踪表.md` 是否指向当前事实。

失败时一次列出当前输入下所有可以独立确认的问题；被前置问题阻断的检查明确写“未检查”和原因。输出末尾只给一条当前可执行的下一命令。
