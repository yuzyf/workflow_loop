# 测试验证阶段：任务登记、执行与结果规范

## 1. 目的和边界

本文件规定 `qa`（测试验证）内部怎样登记测试任务、真实执行并形成结果。测试范围和通过标准已经在 QA 开始时由用户一次确认；本步骤不重新设计范围，不修改产品代码或测试代码，不执行人工验收，也不再增加执行前用户门禁。

- `workflow test prepare` 的中文含义是“登记待执行测试”。它保存一个测试项的命令、工作目录、超时和报告适配器，不运行测试。
- `workflow test run` 的中文含义是“正式运行已登记测试”。它使用受控进程执行器运行当前任务并写机器记录。

只有 `workflow test run` 产生的当前有效记录才是正式测试事实。登记、局部开发检查或历史通过都不等于本轮通过。

## 2. 登记前核对

AI 必须核对：

1. 当前工作流编号、全部验收主题和主题关系。
2. 当前已确认测试计划中的 `AC`（验收条件）、`TC`（测试项）、测试方式和前置测试项。
3. 实施记录中的代码结果和当前真实产品代码。
4. 测试代码中的完整 `Workflow-Test` 标识。
5. 测试入口、测试配置、运行环境和项目全量测试入口。
6. `需求交付追踪表.md` 中当前主题的范围和实施状态。

测试计划、测试标识、真实入口或当前代码不一致时，不开始登记。范围和通过标准需要改变时回到 QA 范围步骤；只是测试代码错误时留在 QA 测试代码步骤修正。

上游变化后重新进入 QA 时，旧机器记录只有在凭据仍与当前范围、产品代码和测试代码完全一致时才可能保留。任何直接受影响的任务必须重新登记并执行，不能因为过去曾通过就进入主题验收。

## 3. 登记测试任务

每个自动化或混合测试项都使用：

```text
workflow test prepare --topic <主题> --tc <TC编号> --cwd <项目内工作目录> --timeout <秒数> --report-adapter <报告适配器> -- <命令和参数>
```

`report-adapter` 的中文含义是“结构化测试报告适配器”，只支持 `vitest-junit` 和 `pytest-junitxml`，必须按项目真实测试框架选择。

### 3.1 工作目录

- 每个任务都登记项目内工作目录；项目根使用程序规定的项目根写法。
- 工作目录不能离开项目，也不能使用项目外绝对路径。
- 正式结果必须逐字使用机器记录中的工作目录。
- 不同工作目录会改变配置查找、相对路径和测试发现，不能省略。

### 3.2 参数数组命令

登记命令是参数数组，直接交给进程执行器，不经过 Shell：

- 不接受管道、重定向、命令串联、命令替换或通配符展开。
- 需要这些能力时，把逻辑放进项目自己的受管脚本，再登记脚本。
- 命令必须直接包含当前 `TC` 的测试入口或定位参数。
- 不能登记 `python -c`、`node -e` 等临时代码，也不能用与测试入口无关但返回 `0` 的命令冒充测试。
- 单个任务默认超时 600 秒；实际需要调整时，在 QA 开始确认的范围里说明。

### 3.3 依赖和外部影响

- 只登记同一主题内直接前置 `TC`，不重复间接依赖。
- 共用数据库、端口、设备、账号或临时目录的任务必须串行。
- 范围确认时已经说明的本地测试写入不再逐项确认。
- 新出现的扣费、发送、外部数据写入或删除不属于普通测试执行；执行前必须向用户说明实际影响并取得明确确认。

全部任务登记完成后直接执行 `workflow test run`。

## 4. 正式执行

由 AI 原样执行：

```text
workflow test run
```

程序负责：

- 按主题和 `TC` 依赖顺序执行。
- 对无前置主题且环境互不影响的主题按项目并行配置执行。
- 使用参数数组和 `shell=False` 启动受控进程。
- 超时后终止整棵进程树。
- 截断并保存输出摘要，计算完整输出哈希。
- 记录平台标识和真实可执行文件。
- 清除同报告路径的旧报告，自动补充固定报告参数并解析本次结构化报告。
- 绑定执行当时的产品代码哈希和测试代码哈希。

同一任务已经有未失效的当前成功记录时不重复执行。失败、重试或已明确失效的任务才重新运行。

## 5. 通过条件

一个自动化测试项只有同时满足下面全部条件才算通过：

- 结构化报告中的测试入口集合与当前测试计划精确一致，没有漏跑或多跑。
- 实际执行数大于 `0`。
- 跳过数、失败数和错误数都等于 `0`。
- 实际命令、工作目录、测试入口和登记内容一致。
- 退出码为 `0`。
- 机器记录绑定的产品代码和测试代码与当前代码一致。

终端出现“通过”但缺少结构化报告、实际执行数为 `0`、入口不匹配或代码哈希失效，都不能生成正式通过结果。

## 6. 正式结果文档

一个主题的全部自动化或混合测试项通过后，根据当前机器记录生成 `qa/<主题文件标识>_测试结果.md`。结果中的以下字段必须逐项对应机器记录：

- 机器记录编号。
- 工作目录、测试入口、执行命令和超时。
- 运行环境、开始时间、结束时间和时长。
- 退出码、输出摘要、输出哈希和输出字节数。
- 报告适配器、报告哈希和报告字节数。
- 精确匹配测试入口、实际执行数、跳过数、失败数和错误数。
- 产品代码哈希和测试代码哈希。

测试入口和命令使用紧凑单行 JSON 数组；输出摘要使用 JSON 字符串；不四舍五入时长，不截短哈希，不改写机器字段。

“实际结果”只解释机器事实证明了验收条件的哪一部分，不能替代、修改或补充程序没有记录的事实。

纯人工主题不生成测试结果文档。混合主题只能写“自动化测试结果：通过”和“人工验收状态：待主题验收”，并写清自动化已证明什么、还需用户判断什么。

## 7. 失败、超时和阻塞

任务失败、超时、环境无法启动或前置项未通过时：

- 不生成当前主题的正式通过结果。
- 清除该任务已经失效的当前成功记录。
- 删除已经失效的主题测试结果文档。
- Journal（追加式流水）只记录必要执行事实和失败原因，不保存敏感信息或完整终端输出。
- 依赖失败任务的后续任务停止；无直接依赖的其他主题继续。

失败输出只用于诊断，不能被节选或重新解释成通过。退出码不是 `0` 就没有通过。

问题处理位置：

- 产品代码错误或实现遗漏：返回 `impl`。
- 测试范围、方式、通过标准或依赖错误：回到 QA 范围步骤并重新确认。
- 测试代码、断言或标识错误：保留仍有效范围，回到 QA 测试代码步骤。
- 任务命令、工作目录、超时或报告适配器错误：保留范围和测试代码，重新登记受影响任务。
- 当前机器结果失效：保留范围和测试代码，重新执行受影响任务。
- 验收条件无法判断：返回 `acceptance_plan`。
- 产品行为没有定义：返回 `spec`。
- 临时环境问题：留在 QA，环境恢复后重试。

只清除有直接影响证据的主题、任务和下游结果。仅在同一目录、同一文件、存在间接依赖或“可能有影响”不算扩大范围的证据。共享运行器、共享测试配置或统一入口变化并且能证明影响全部主题时，才使全部主题的机器记录失效。

## 8. QA 结束门禁

所有需要自动化的主题都有当前通过结果，纯人工主题的交接边界也明确后，由 AI 执行：

```text
workflow gate qa
```

第二道门一次完整检查：

- 测试计划结构和 `AC` 到 `TC` 覆盖。
- 测试代码和 `Workflow-Test` 标识。
- 任务登记。
- 当前机器记录和结构化报告事实。
- 正式测试结果文档。
- `qa/索引.md`、上下游链接和 `需求交付追踪表.md`。

通过后，AI 向用户展示测试范围、机器记录、自动化结果和人工待验收边界。用户确认后由 AI 执行 `workflow gate qa --confirmed`。第三道门只比较第二道门凭据，不重新执行测试或完整校验。

## 9. 完成前检查

- 每个自动化或混合 `TC` 是否有当前有效机器记录。
- 结构化报告是否精确匹配入口，实际执行数是否大于 `0`。
- 跳过数、失败数、错误数和退出码是否满足通过条件。
- 结果文档是否逐字段对应当前机器记录。
- 是否有失败、超时、阻塞或未执行项却写成通过。
- 是否把局部反馈、历史结果或终端文字冒充正式事实。
- 混合测试是否错误地把人工部分写成已经通过。
- 追踪表是否只更新受影响 `AC` 的测试项和测试结果。

门禁失败时一次列出当前输入下全部可以独立确认的问题；被前置问题阻断的检查写“未检查”和原因，末尾只给一条当前可执行的下一命令。
