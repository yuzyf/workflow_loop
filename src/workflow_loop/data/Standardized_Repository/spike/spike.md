# 穿刺阶段规范

## 目的

在验收计划和代码计划前，找出仍缺少真实证据、并会改变产品决定、代码计划、测试方式或验收方式的技术不确定性。用户决定执行哪些穿刺项；AI 用真实场景取得证据并记录结论。

穿刺对象是不确定性，不是功能名称，也不是所有技术问题。已经能从现有代码、测试、日志或运行结果确认的内容不需要穿刺。

穿刺不会成为新的产品代码阶段。需要最小脚本、探针或样本时，可以保留在：

```text
.workflow_loop/spike_tmp/<workflow_id>/<穿刺项文件标识>/
```

该目录中的代码和样本用于重新取得证据，后续复用时必须按登记的运行方法重新执行；不能把旧穿刺结论直接当成当前代码的测试通过。

## 一、先调查，再判断是否需要穿刺

1. 读取已经确认的产品总说明、功能文档和现有代码设计；从零开发没有现有代码设计时写清“暂无”。
2. 修改产品和修 bug 时，查看相关代码、现有测试、日志、依赖文档和已有运行结果。
3. 项目具备运行条件时，先运行与当前问题有关的现有功能。运行已经回答的问题，不得重复列为穿刺候选。
4. 修 bug 时读取缺陷记录和复现结果，不重复验证已经确认的表现和根因。
5. 无法运行时，写清缺少什么以及因此仍无法确认什么。
6. 从零开发且代码不存在时，不强制运行项目，但仍检查产品设计、已选依赖和将进入代码计划的最小实现约束。

技术不确定性必须同时满足：

- 当前缺少事实证据，不能从已有资料直接确认。
- 必须通过真实调用、真实运行或实际测量才能确认。
- 不同结果会改变产品设计、代码计划、修复方法、测试或验收方式。

不满足这三点时，不进入穿刺候选。

## 二、整理候选并消除重复

逐项比较真实场景、不确定内容、证据类型和结果用途。实质相同的候选合并为一项；只是另一个候选的验证问句时也合并。

后一项必须等前一项结果出来才知道是否需要时，不提前列为必做项。执行中发现新不确定性，先向用户说明，再由用户决定是否加入。

## 三、逐项和用户确认候选

每个候选用直白话说明：

1. 候选名称和真实场景。
2. 已经确认的事实。
3. 当前具体不知道的行为、返回内容或限制。
4. 为什么现有事实不能回答。
5. 准备使用的真实请求、文件、平台、数据规模或操作路径。
6. 验证结果将改变哪个产品决定、代码计划、测试或验收方式。
7. 是否会写外部数据、扣费、发送内容或删除内容。
8. AI 是否建议执行以及理由。

候选没有被用户选择前，不写入正式清单，也不分配 `SP-001` 编号。

AI 判断没有需要穿刺的不确定性时，必须说明检查过的文件、代码和运行结果，以及为什么事实已经足够。只有用户明确决定全部跳过，才能执行：

```text
workflow gate spike --skip
```

跳过时不生成穿刺清单或结论文档，不生成虚假资产，不把“跳过”写成“已确认结论”。

## 四、确认执行清单

用户逐项决定后，AI 汇总最终清单并说明独立性和执行顺序。用户确认后执行：

```text
workflow gate spike --discuss-done
```

第一道门只确认执行范围。通过后：

1. 创建 `spec/穿刺清单.md`。
2. 为每个项目分配唯一 `SP-001`、`SP-002` 编号。
3. 创建对应结论文档，先填写前四部分。
4. 需要可复用代码或样本时，只在当前工作流和穿刺项隔离目录创建资产；不创建项目根临时文件。

穿刺发生在验收计划之前，因此资产表中的“支撑验收条件”统一写“待验收计划关联”。本阶段不猜 `AC`（验收条件）编号，也不检查尚未生成的需求交付追踪表。验收计划形成后，再把真正受到穿刺结论支撑的每条验收条件登记到需求交付追踪表；一个穿刺支撑多个 `AC` 时逐条登记，多个穿刺共同支撑一个 `AC` 时在同一行列出全部直接依据。

## 五、选择最小且真实的验证方法

按以下顺序选择：

1. 现有命令、现有程序或已有日志。
2. 第三方工具或真实接口调用。
3. 只有前两项不能暴露所需结果时，编写最小脚本、逻辑原型、解析程序、构建探针或性能测量程序。

临时代码、真实场景样本、复现输入和必要运行说明统一放入：

```text
.workflow_loop/spike_tmp/<workflow_id>/<穿刺项文件标识>/
```

资产目录只能保存重新运行所需的代码、最小非敏感输入和说明：

- 不保存密钥、令牌、密码、会话信息或真实敏感数据。
- 不保存缓存、日志、完整终端输出、纯结果报告、构建产物或虚拟环境。
- 资产必须有清楚的用途、完整可执行的运行方法、依赖和非敏感输入说明、明确的不保留内容。
- 每项最多登记一个隔离资产目录，不能让多个穿刺项共用同一登记路径。

## 六、真实场景要求

验证必须使用产品实际会遇到的接口、输入文件、运行平台、数据规模、操作路径或故障条件。

不得使用以下内容证明真实行为：

- 自己编造的接口响应或业务数据。
- 手工构造的理想文件。
- 与目标平台无关的玩具环境。
- 小规模结果直接推断真实规模性能。
- 只测试临时代码自身，不触达真实产品对象。

真实样本可以脱敏或裁剪，但不能改变待验证的格式、结构、规模或故障特征。无法取得真实场景时，结论只能写“仍未确认”。

## 七、外部影响和敏感信息

用户选择穿刺项不自动授权扣费、发送、创建或修改外部数据、删除数据。存在外部影响的步骤，执行前再次说明对象、实际影响、预计费用和是否可撤销，取得明确确认后才能执行。

密钥、令牌、密码、会话信息和原始敏感输入不得写入结论文档、资产目录或日志。

## 八、执行并记录证据

每完成一项，立即填写：

- 实际执行时间。
- 操作系统、目标平台、工具和依赖版本。
- 实际命令。
- 真实输入或样本的来源、类型、大小、数量或哈希。
- 关键原始输出、返回字段、测量数据、失败行为和限制。
- 结果状态和后续影响。

结果状态只能是：

- `已确认`：证据足以确认真实行为，并能据此作出后续决定。
- `限制已确认`：原方案不可行或只能部分满足要求，但限制已经足以支持改方案、缩小范围或修改计划。
- `仍未确认`：证据仍不足。

“结果状态”只说明证据确认到了什么；“是否阻塞后续”单独说明能否进入验收计划。任何项目写“是否阻塞后续：是”时，第二道门不能通过。

## 九、结论进入后续环节

穿刺只取得证据，不在当前阶段修改正式产品代码。

- 结果改变用户可见行为、功能范围或产品规则时，先返回或进入 `spec`（产品设计）由用户确认。
- 结果影响接口、数据、模块、状态、算法、平台限制或异常处理时，写进后续 `impl` 的代码计划。
- 代码计划确认后，AI 才能在正式代码中重新实现穿刺验证的必要逻辑；不能把缺少正式错误处理、测试和边界设计的临时代码直接复制进生产代码。
- 所有已登记资产和结论文档保留到工作流需要它们的阶段。后续重新运行得到的新事实要写入对应阶段记录，不能静默覆盖原穿刺结论。

修 bug 时，原产品行为不变且只需调整修复方法时可继续；只有改变产品行为、产品规则或功能边界才能继续时，结束当前 bugfix 流程后改用 product_change。

## 十、三道门

### 门 1：确认执行清单

命令：

```text
workflow gate spike --discuss-done
```

只确认用户选定的穿刺项，不表示结论已经形成。

### 门 2：校验产物和资产

命令：

```text
workflow gate spike
```

程序检查：

- 清单和结论文档属于当前工作流，编号和链接一致。
- 固定字段和值合法，清单没有“待验证”。
- 没有项目仍阻塞后续。
- 结果状态、实际证据、影响和后续阶段填写完整。
- 可复用资产目录严格位于 `.workflow_loop/spike_tmp/<workflow_id>/<穿刺项文件标识>/`，是普通目录，包含可重新运行的文件且没有敏感、缓存、日志或纯结果内容。
- 资产表包含资产路径、用途、运行方法、依赖与非敏感输入、不保留内容；支撑验收条件写“待验收计划关联”。
- 当前工作意图为 `bugfix` 时，没有项目要求修改产品设计。

程序不能判断证据是否真实、候选是否语义重复或资产用途是否足够；这些由 AI 和用户负责。

### 门 3：用户确认并推进

命令：

```text
workflow gate spike --confirmed
```

程序只在第二道门凭据仍有效时推进。推进时：

- 保留已登记且通过校验的资产目录和结论文档。
- 只清理当前工作流下没有登记的半成品目录或文件。
- 不删除其他工作流的 `.workflow_loop/spike_tmp/<其他 workflow_id>/`。
- 不删除能重新取得结论的代码；后续使用前仍必须重新运行。
- 不把“本轮未执行穿刺”变成虚假结论或资产登记。

## 十一、完成前检查

每次门禁前检查：

- 工作流编号、穿刺项编号和结论文档链接一致。
- 所有固定章节、字段、实际命令、环境、真实输入、观察结果、失败和限制都存在。
- 没有模拟返回、自造数据、理想文件或敏感信息。
- 没有任何项目仍阻塞后续。
- 资产路径、用途、运行方法、依赖与非敏感输入和不保留内容完整，支撑验收条件写“待验收计划关联”。
- 没有提前编造验收条件编号，也没有要求本阶段检查尚未生成的需求交付追踪表。
