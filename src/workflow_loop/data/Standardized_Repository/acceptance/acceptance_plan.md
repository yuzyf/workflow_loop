# 验收计划阶段工作规范

## 目的

根据用户已经确认的需求，和用户确定本次全部验收主题、主题之间的前置关系，并逐个写清什么算完成。最终文档使用 `Template_Repository/acceptance/acceptance_plan.md`，生成 `需求交付追踪表.md`、`acceptance/索引.md` 和各主题验收计划。

本阶段不修改产品规则，不设计代码，不制定测试步骤或实施任务，也不执行验收。

## 一、开始前调查

先读取并核对：

1. 当前工作流编号、工作类型和用户已经确认的需求。
2. `spec/产品总说明.md`、受影响的功能文档和本次产品设计修改记录。
3. 项目已经存在 `spec/代码架构设计.md` 时，读取其中与本次需求有关的真实架构；同时读取穿刺结论和已有运行证据。架构文档不存在时不为制定验收计划提前创建。
4. 修 bug 时读取当前工作流对应的缺陷复现记录。
5. 已有 `需求交付追踪表.md` 时读取历史内容，避免覆盖旧工作流。
6. 项目已经保存的主题名称和文件标识映射，避免给同一主题分配第二个文件标识。

已有代码的项目还要查看相关代码和测试。现有证据不足且具备安全运行条件时，实际运行相关使用路径。代码和运行结果只能说明当前事实，不能替代用户决定最终产品行为。

能从文件、代码和运行结果查明的事实先自行查明，不让用户重复说明。

## 二、确定验收主题

### 需求来源必须全部覆盖

先把本次工作流的需求来源逐项列出：用户本次提出的每条需求、本次产品设计修改记录中的每项变化、修 bug 时的缺陷记录。再说明每一项分别由哪个验收主题覆盖。

- 每项需求来源至少被一个主题覆盖，不允许出现没有主题负责的需求。
- 每个主题至少对应一项真实需求来源，不允许出现没有来源的主题。
- 本次不做的内容必须由用户明确决定不做，并说明后续怎样处理；不能靠不提它来跳过。

覆盖关系先向用户说明清楚，用户确认没有遗漏后，才开始讨论验收条件。

### 主题名称在项目内永久唯一

- 一个验收主题名称在整个项目内只表示一件事，跨轮次也不改变含义。
- 程序为每个主题名称保存一个稳定的中文文件标识；同一主题在后续轮次继续使用原名称和原文件标识。
- 不能用同一个名称在不同轮次表示不同内容，也不能给同一件事换名称重新登记一个新主题。
- 需要表达的内容确实和历史主题不同时，取一个新名称，不改写历史主题的含义。
- 文档标题和正文写完整中文主题名称；文件名和链接使用已保存的文件标识。

### 从零开发和修改产品

先提出完整主题清单。每个主题说明：

- 覆盖哪部分用户需求或产品设计变化。
- 完成后用户会得到什么结果。
- 为什么需要独立验收。

先让用户确认主题是否完整、重复和拆分合理，再讨论验收条件。

主题清单确认后，继续逐个确认主题关系：

- 哪个主题必须等待另一个主题的用户结果后才能验收。
- `前置主题`只写直接前置主题。已经通过其他前置主题间接包含的依赖不重复写一遍。例如主题 C 依赖主题 B、主题 B 依赖主题 A 时，主题 C 的前置主题只写主题 B。
- 没有依赖关系的主题写“无”，不强行安排等待关系。
- 不能形成循环依赖。
- `展示顺序`只用于让读者按固定顺序阅读；真正的等待关系写在“前置主题”列。
- 本次确认的关系写入 `acceptance/索引.md`；后续 `qa/索引.md` 和 `impl/索引.md` 只能继承，不能重新改写。

### 修 bug

直接复用缺陷复现阶段已经确认的验收主题，不重新命名、拆分、合并或增加主题。

一份缺陷记录实际包含多个无关缺陷时，返回缺陷复现阶段拆开。修复必须改变产品行为、规则或边界时，停止修 bug 流程，改为修改产品。

## 三、逐个主题讨论

每次只讨论一个需要用户决定的问题，并给出推荐答案和具体理由。每个主题依次确认：

1. 本主题完成后用户最终得到什么结果。
2. 本主题包含哪些新增、修改、删除或直接受影响的行为。
3. 哪些内容不属于本主题，由其他主题或最终全量回归负责。
4. 执行动作前必须具备并能核实什么状态。
5. 谁通过哪个产品入口执行什么触发动作。
6. 动作后到哪里检查哪些数据、文件、页面、返回值或状态。
7. 哪些结果同时成立才通过，出现哪些结果就不通过。
8. 这个结果来自哪条产品设计或缺陷依据。

讨论时检查本次变化涉及的场景、规则、使用过程和异常情况，但不机械凑齐固定分类。没有相关设计时不编造验收条件。

每个行为都必须使用上述可检查字段，不只针对删除、清空或覆盖。

写文档时，每个 `AC-xx` 标题前紧邻显式锚点 `<a id="ac-xx"></a>`，锚点编号与标题一致，保证后续实施记录、测试计划和追踪表可以稳定导航到这一条验收条件。

“开始前状态”“触发动作”“可检查结果”“通过标准”“不通过标准”和“产品设计依据”都是固定字段。标签和值必须写在同一行，例如 `- 触发动作：用户点击提交`；标签单独占一行时，下一行的文字不是该字段值，必须改回标签同一行。

一个主题的以上内容全部由用户确认后，才开始讨论下一个主题。不能先把全部主题的条件写完再一次性交给用户确认，也不能因为主题看起来简单就跳过确认。

## 四、发现问题时的处理

- 产品在某个条件下应该怎样处理没有定义：返回产品设计阶段确认产品规则。
- 主题之间重复或边界不清：返回主题清单重新讨论。
- 验收条件不能明确判断通过或不通过：继续讨论具体条件和结果。
- 实现困难、代码现状不同或测试失败：不能降低已经确认的验收条件。
- 用户提出当前范围之外的新需求：不加入当前工作流，后续按修改产品处理。

## 五、生成前确认

向用户总结：

- 本次全部验收主题，以及每项需求来源由哪个主题覆盖。
- 主题之间的前置关系和展示顺序。
- 每个主题覆盖的需求和最终结果。
- 每个主题的验收范围。
- 每条验收条件的开始前状态、触发动作、可检查结果、通过标准、不通过标准和依据。
- 当前仍未解决的问题。

只有用户明确确认总结正确后，才按照验收计划文档模板生成 `需求交付追踪表.md`、`acceptance/索引.md` 和各主题验收计划。

验收计划引用尚未生成的下游文档时，只写反引号包裹的普通相对路径和“（待生成）”；文件存在后再改为 Markdown 链接。

## 六、门禁失败时怎样报告

一次检查应列出所有当前可以独立确认的真实问题。每项分别写位置、预期、实际、证据、影响和改法，位置必须指向实际文件、章节、表格或字段；不得用笼统原因覆盖已经取得的格式、路径或内容事实。

后续检查依赖已失败或缺失的前置事实时，写“未检查”，说明依赖哪项前置检查及前置修复后会检查什么，不把它说成错误或通过。每项只给文字改法；完整输出的末尾只给一条当前可执行的下一步命令。
