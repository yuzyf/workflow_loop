# 验收计划阶段工作规范

## 目的

根据用户已经确认的需求，和用户确定本次全部验收主题、主题之间的前置关系，并逐个写清什么算完成。最终文档使用 `Template_Repository/acceptance/acceptance_plan.md`，生成 `traceability.md`、`acceptance/index.md` 和各主题验收计划。

本阶段不修改产品规则，不设计代码，不制定测试步骤或实施任务，也不执行验收。

## 一、开始前调查

先读取并核对：

1. 当前工作流编号、工作类型和用户已经确认的需求。
2. `spec/product.md`、受影响的功能文档和本次产品设计修改记录。
3. `spec/architecture_code_design.md`、穿刺结论和已有运行证据。
4. 修 bug 时读取当前工作流对应的缺陷复现记录。
5. 已有 `traceability.md` 时读取历史内容，避免覆盖旧工作流。

已有代码的项目还要查看相关代码和测试。现有证据不足且具备安全运行条件时，实际运行相关使用路径。代码和运行结果只能说明当前事实，不能替代用户决定最终产品行为。

能从文件、代码和运行结果查明的事实先自行查明，不让用户重复说明。

## 二、确定验收主题

### 从零开发和修改产品

先提出完整主题清单。每个主题说明：

- 覆盖哪部分用户需求或产品设计变化。
- 完成后用户会得到什么结果。
- 为什么需要独立验收。

先让用户确认主题是否完整、重复和拆分合理，再讨论验收条件。

主题清单确认后，继续逐个确认主题关系：

- 哪个主题必须等待另一个主题的用户结果后才能验收。
- 没有依赖关系的主题写“无”，不强行安排等待关系。
- 不能形成循环依赖。
- `展示顺序`只用于让读者按固定顺序阅读；真正的等待关系写在“前置主题”列。
- 本次确认的关系写入 `acceptance/index.md`；后续 `qa/index.md` 和 `impl/index.md` 只能继承，不能重新改写。

### 修 bug

直接复用缺陷复现阶段已经确认的验收主题，不重新命名、拆分、合并或增加主题。

一份缺陷记录实际包含多个无关缺陷时，返回缺陷复现阶段拆开。修复必须改变产品行为、规则或边界时，停止修 bug 流程，改为修改产品。

## 三、逐个主题讨论

每次只讨论一个需要用户决定的问题，并给出推荐答案和具体理由。每个主题依次确认：

1. 本主题完成后用户最终得到什么结果。
2. 本主题包含哪些新增、修改、删除或直接受影响的行为。
3. 哪些内容不属于本主题，由其他主题或最终全量回归负责。
4. 在什么条件下触发验收。
5. 触发后必须看到或核实到什么结果。
6. 这个结果来自哪条产品设计或缺陷依据。

讨论时检查本次变化涉及的场景、规则、使用过程和异常情况，但不机械凑齐固定分类。没有相关设计时不编造验收条件。

## 四、发现问题时的处理

- 产品在某个条件下应该怎样处理没有定义：返回产品设计阶段确认产品规则。
- 主题之间重复或边界不清：返回主题清单重新讨论。
- 验收条件不能明确判断通过或不通过：继续讨论具体条件和结果。
- 实现困难、代码现状不同或测试失败：不能降低已经确认的验收条件。
- 用户提出当前范围之外的新需求：不加入当前工作流，后续按修改产品处理。

## 五、生成前确认

向用户总结：

- 本次全部验收主题。
- 主题之间的前置关系和展示顺序。
- 每个主题覆盖的需求和最终结果。
- 每个主题的验收范围。
- 每条验收条件的触发条件、预期结果和依据。
- 当前仍未解决的问题。

只有用户明确确认总结正确后，才按照验收计划文档模板生成 `traceability.md`、`acceptance/index.md` 和各主题验收计划。

阶段顺序、主题登记、固定字段、文件结构和门禁由程序处理，本规范不重复程序步骤。
