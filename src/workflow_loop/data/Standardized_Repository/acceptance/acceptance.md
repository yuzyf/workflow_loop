# 主题验收阶段工作规范

## 目的

按照已经确认的主题验收计划，核对当前实现和测试证据是否满足每一条验收条件。只有全部条件通过后，才生成 `acceptance/<topic>_result.md`。

本阶段不修改需求、产品规则、验收主题或验收条件，不运行已经由 `test_execution` 完成的自动化测试，也不允许“遗留”“部分通过”或“带条件通过”。

## 一、开始前调查

读取：

1. 当前工作流编号和当前验收主题。
2. `acceptance/<topic>_plan.md` 中的验收目标、范围和全部验收条件。
3. 自动化或混合主题对应的 `qa/<topic>_result.md` 及当前有效执行记录。
4. 与本主题有关的实施记录、产品设计和 `traceability.md`。

自动化测试没有通过、测试结果已经失效、实施记录缺失或验收计划本身不能判断时，不开始主题验收。

开始验收前先按第一性原理重新理解用户要得到的结果。AI 必须把验收计划、真实产品入口、实施记录和当前测试证据对应起来；用户提出问题、回答含糊或实际结果与预期不一致时，继续询问发生条件、实际结果、期望结果和影响范围，直到双方对当前事实和处理方式达成共识。没有共识时不能自行记录通过或失败。

主题按 `acceptance/index.md` 的依赖关系分别验收。没有依赖关系的主题可以分别推进；存在前置主题时，前置主题没有通过前不能验收当前主题。某个主题失败只影响该主题和实际依赖它的主题。

## 二、确定每条条件的验收方式

- 纯自动化条件：程序根据当前有效主题测试记录自动建立验收记录，不让用户重复确认自动化测试已经证明的内容。
- 混合条件：使用自动化测试结果，并只让用户检查自动化无法判断的部分。
- 纯人工条件：由用户按照明确步骤实际检查，不伪造测试结果文件。

每条验收条件必须使用验收计划中的原编号和原内容，不能在本阶段增加、删除、合并或降低条件。

## 三、执行人工验收

需要人工确认时，AI 必须先向用户展示：

1. 验收对象。
2. 开始前必须具备的条件。
3. 用户需要执行的具体操作步骤。
4. 每一步需要观察的内容。
5. 验收计划要求的明确预期结果。
6. 当前已经具备的自动化或运行证据。
7. 用户需要回答的具体问题。

不能只问“是否通过”，也不能使用“检查是否正常”“确认符合预期”等无法执行的话。用户不需要额外填写验收记录；用户回答后，AI 调用 `workflow acceptance record`，把用户实际回答、实际结果、确认时间和可选证据绑定当前工作流、主题和 `AC-xx`。证据不强制截图、日志或文件哈希；没有独立证据文件时，具体观察说明就是证据。AI 不能替用户填写通过。

## 四、未通过时返回

任一验收条件未通过、无法验证或受到阻塞时，不生成正式主题验收结果，也不能进入最终全量回归。失败回答只写入 Journal 和追踪表的退回记录，不成为当前有效验收结果。AI 调查实际原因并给出建议，用户确认后才返回对应阶段：

- 实现不符合验收条件：返回 `impl`，修正后重新经过 `test_code` 和 `test_execution`。
- 测试代码错误或缺少覆盖：返回 `test_code`；测试计划本身缺项时返回 `test_plan`。
- 测试没有执行、执行结果失效或临时环境阻塞：留在或返回 `test_execution` 处理。
- 验收条件遗漏、矛盾或不能判断：返回 `acceptance_plan`。
- 产品要求无法实现、需要删除或改变：返回 `spec`，由用户重新确认产品设计，再重新经过后续阶段。
- 用户只取消一个功能或验收主题：使用 `workflow return --to spec --topic "<主题>" --reason "<具体原因>"`，删除对应产品设计，并在后续 `impl` 中定向删除只服务于该功能的代码；不能中止整个工作流，也不能覆盖其他主题需要的公共代码。
- 用户决定不再继续整个工作流：执行 `workflow abort`。修 bug 时不能把未修复缺陷标记为完成。

不能通过删除失败证据、降低验收条件、填写“部分通过”或生成未通过结果文件让门禁放行。

## 五、形成正式结果

一个主题的全部验收条件都已经通过后，不等待其他独立主题，立即：

1. 向用户逐条说明验收方式、实际结果和证据。
2. 读取 State Snapshot 中当前有效的逐条验收记录，使用主题验收结果文档模板生成 `acceptance/<topic>_result.md`。
3. 确认文档正好覆盖验收计划中的全部 `AC-xx`，每条判定和总结果都为“通过”。
4. 更新 `traceability.md` 中本主题对应的验收结果链接。

AI 负责把程序事实写成人能理解的结果，不能改写程序记录中的用户回答、确认时间或测试结果。固定字段、工作流编号、主题覆盖、程序记录一致性、结果状态、追踪表更新和阶段推进由程序门禁检查。全部主题都有当前有效结果后，用户再通过 `workflow gate topic_acceptance --confirmed` 确认可以进入最终全量回归；这不是让用户重复验收纯自动化条件。

结果文档中的“实际结果”“验收证据”“用户实际回答”“确认时间”和“程序记录”必须逐项对应 State Snapshot（状态快照）中的当前有效记录。纯人工主题没有自动化结果文件时，在验收依据和上下游文档中明确写“无自动化测试项”，不能伪造 `qa/<topic>_result.md`。

## 六、完成前对抗性审查

- 是否把自动化测试结果和人工验收混在同一阶段重复执行。
- 是否遗漏验收计划中的任何一条条件。
- 是否让 AI 替用户完成必须由用户判断的验收。
- 是否存在未通过、无法验证或阻塞，却仍生成正式结果文件。
- 是否为了完成工作流降低或删除验收条件。
- 是否发现产品要求不可行后，没有返回产品设计阶段。
- 是否使用空泛结论代替实际观察和证据。
