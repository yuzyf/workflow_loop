# 最终产品、架构与代码设计同步规范

## 目的

在实施、主题测试、主题验收、最终全量回归和整体验收都完成后，核对产品设计、功能文档、架构设计和真实代码，把已经验证的真实结构写回 `spec/architecture_code_design.md`，让维护者看到每个产品功能怎样落到实际代码。

本阶段更新的是设计文档，不是生产代码。最终文档结构使用 `Template_Repository/code_design/code_design.md`。本文件只说明本阶段怎样调查、分类和更新，不重复架构文档模板。

## 调查范围

读取并相互对照：

- 已确认的产品总说明和功能文档。
- 当前架构设计文档中的计划内容和差异记录。
- 实际代码、真实文件路径、类、函数、类型和接口。
- 实施记录、主题测试结果、主题验收结果、最终全量回归状态和整体验收结果。
- 需求交付追踪表中当前工作流的全部阶段结果。

## 一、先判断发现的差异属于哪一类

必须先逐项比较产品要求、功能文档、初步架构和真实代码，不能直接从代码目录改文档。

| 发现的情况 | 本阶段处理 | 是否可以在本阶段完成 |
|---|---|---|
| 只改变代码分层、模块关系、调用链或共享代码职责，用户可见功能和规则没有变化 | 更新架构分层、关键节点、功能流程图和功能到代码的映射 | 可以 |
| 用户可见功能、规则、边界、使用过程或异常结果发生变化 | 停止当前阶段，返回 `spec`（产品设计阶段）重新确认并修改产品总说明或功能文档 | 不可以 |
| 代码没有实现已经确认的产品要求 | 停止当前阶段，返回 `impl`（代码实施阶段）修改代码并重新测试、验收 | 不可以 |
| 功能文档没有写清已经确认且已经验收的产品行为 | 返回 `spec`（产品设计阶段）补齐功能文档，再让后续依据重新确认 | 不可以 |
| 只发现架构文档没有写全，但产品行为和真实代码没有变化 | 补齐真实代码位置、调用逻辑、状态、异常和验证依据 | 可以 |

不能为了让文档和代码看起来一致，把代码实际行为直接写成新的产品规则。

## 二、更新要求

- 用实际代码替换已经完成并验证的计划代码；不能只写“已完成”。
- 每个产品功能都要写清真实入口、关键代码环节、判断、调用、状态或数据处理、异常结果和验证位置。
- 每个架构模块都要说明它服务哪些产品功能、产品通用规则或系统约束。
- 每个产品功能都必须建立“功能 → 场景 → 代码入口 → 文件 → 类或函数 → 关键逻辑 → 状态或数据 → 异常 → 测试或运行证据”的映射。
- 功能到代码的映射写入 `spec/architecture_code_design.md`，不是另造一份脱离架构文档的映射表。
- 架构图只表达实际代码分层、职责和依赖方向；功能流程图表达一个具体场景的执行过程。
- 仍未实现、未验证或文档与代码冲突的内容必须保留在差异记录中，不能写成最终事实。
- 没有架构变化时，也要在最终同步结论中写清“架构未变化”，并更新本轮真实代码映射和核对依据。
- 不在本阶段修改生产代码，不在本阶段直接修改 `spec/product.md` 或 `spec/feature_*.md`。
- 不在本阶段新增产品规则，不根据代码擅自修改产品设计；发现产品变化时必须按上一节返回 `spec`。

## 三、最终同步结论

最终架构文档必须包含“最终同步结论”章节，并填写：

- 当前工作流编号。
- 本次是“架构变化”还是“架构未变化”。
- 产品设计核对为“一致”。
- 功能文档核对为“一致”。
- 代码实现核对为“一致”。
- 功能到代码映射为“完整”。
- 未处理差异为“暂无”。
- 可以复核的产品、实施、测试、验收和回归依据。

## 四、结束前检查

- 每项代码设计是否能追溯到产品功能、产品通用规则或系统约束。
- 每个功能流程节点是否能定位到真实代码和具体逻辑。
- 每个产品功能是否都有真实代码入口和完整映射。
- 是否区分了架构变化、产品功能变化和代码未实现。
- 计划、当前实现、测试证据和验收结果是否区分清楚。
- 是否记录仍存在的产品、代码、测试或运行差异。
- 是否把功能变化错误地留在最终架构文档中，而没有返回 `spec`。
- 是否把代码未实现错误地留在文档中，而没有返回 `impl`。
- 追踪表的最终代码设计列由程序在阶段确认时更新，不在文档中伪造链接结果。

## 指令

最终设计同步：核对产品设计、功能文档、架构设计和真实代码；架构有变化时更新架构和功能到代码的映射，架构无变化时记录核对结论；发现功能变化返回 `spec`，发现代码未实现返回 `impl`。确认无未处理差异后，写入/更新 `spec/architecture_code_design.md`。
