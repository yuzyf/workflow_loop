# 代码架构文档编写规范

## 目的

根据已经确认的产品设计、真实代码、测试和运行证据，建立或同步 `spec/代码架构设计.md`，让它只描述当前实现。

代码设计不是独立于产品设计的技术清单。产品功能、产品通用规则、功能边界、使用过程和异常情况决定代码需要承担什么职责；代码分层、模块、接口、状态和测试负责把这些产品要求实现出来。

本规范说明怎样核对和编写代码架构文档。文档结构以代码架构设计文档模板为准。

## 一、适用场景

### 1. 根据已有代码建立现状架构

适用于 `project_design_init`（项目设计初始化）阶段。

- 本规范规定产品与代码怎样对应，以及代码架构文档怎样形成。
- 代码调查、运行校准和证据标记还必须遵守 `project_design_init` 的专用规范。
- 已有实现必须使用真实代码路径和真实符号，不能把未实现名称写成现状。

### 2. 根据真实交付同步架构文档

适用于 `update_code_design`（最终代码设计同步）阶段：

- 以已确认的产品文档、实施记录、测试结果和真实代码为依据。
- 只更新受本轮真实变化影响的架构层、关键节点、功能流程、共享代码和差异记录。
- 已实现内容写成当前事实；没有证据的内容不能写成已完成。
- 不因一次局部变化重写与本轮无关的架构说明。

## 二、讨论原则

1. 能从产品文档、代码、测试或运行结果查明的事实，先自行查明，不让用户重复说明。
2. 产品规则和功能范围以已确认的产品设计为准；发现产品文档互相冲突时，先指出冲突，不能自行选一个方便实现的版本。
3. 技术取舍需要用户决定时，每次只讨论一个问题，并给出推荐方案、直接理由和实际影响。
4. 先讨论产品为什么需要某项代码职责，再讨论代码放在哪里、怎样协作。不能先按目录列模块，再硬找产品理由。
5. 不强制所有产品使用同一种架构分层、同一张表或同一种图。根据当前产品选择能说明清楚的表达方式。
6. 用户确认共同代码设计之前，不生成或修改正式架构文档。

## 三、从产品设计建立代码覆盖清单

读取产品总说明和全部功能文档，整理所有实际影响代码的内容：

- 产品功能和每个功能中的场景。
- 产品通用规则和功能独有规则。
- 支持范围和不支持范围。
- 使用过程中的触发条件、参与者、输入、输出和顺序。
- 异常情况中的判断条件、处理方式和用户可见结果。
- 明确的系统约束，例如只能本地运行、必须持久化状态或必须调用某个外部系统。

产品历史背景如果不形成代码约束，不要求映射。整理完成后检查每项产品内容是否都有代码承接；没有承接的内容必须标记为待设计、待实现或未确认，不能直接忽略。

## 四、由产品职责推导代码架构

### 1. 划分代码层

根据产品职责决定代码需要分成哪些层。每一层必须回答：

- 它承接哪些产品功能、规则或系统约束。
- 它负责什么，不负责什么。
- 哪些上层代码可以调用它。
- 它可以依赖哪些下层代码。
- 为什么需要单独成层，而不是仅因为目录已经存在。

架构图只画层、职责和依赖方向。不要在架构图里混画某个功能的执行步骤。

### 2. 找出架构关键节点

架构关键节点是多个功能共同经过，或者行为改变会影响产品规则、阶段推进、状态一致性或外部交互的代码位置，例如统一入口、路由、状态存储、规则校验或外部服务适配。

每个关键节点必须确定：

- 对应的产品职责。
- 上游触发条件和输入。
- 真实的文件、类、函数、类型和接口。
- 关键判断和下游调用。
- 读取或写入的状态和数据。
- 失败结果和验证位置。

不要把每个普通工具函数都升级成架构关键节点。

### 3. 反向检查模块用途

完成初步分层后，从代码模块反向检查：

- 这个模块具体服务哪个产品功能、产品规则或系统约束。
- 删除它会导致哪个产品行为无法完成。
- 它是否和其他模块承担了重复职责。
- 它是否同时承担多个没有关系的职责，应该拆开。

无法回答用途的模块不能作为正式架构设计保留。

## 五、逐个功能设计完整代码过程

按照产品功能和场景逐个设计，不按照文件目录逐个说明。

### 1. 明确场景范围

先用产品语言写清当前设计的是哪个功能、哪个场景、由什么事件开始、以什么结果结束。一个场景可能多次进入程序，不能强制假设只有一个代码入口。

### 2. 画功能流程或时序

图中同时保留产品过程和代码映射：

- 用户、AI、外部系统或定时事件节点写明触发动作。
- 每个程序处理节点直接标出文件路径、函数或类型，以及该节点的关键处理。
- 状态文件、数据库、外部服务或输出文件在实际读写时画出。
- 判断必须画出不同结果，不能把成功和失败藏在一段说明里。
- 线条只表示当前场景的明确执行顺序，避免无顺序的交叉连线。

### 3. 解释每个程序节点

对图中每个程序节点写清：

- 谁在什么条件下传入什么。
- 代码从哪个文件中的哪个函数、类、类型或接口进入。
- 代码按什么顺序判断和调用。
- 哪一步读取或写入什么状态、字段、文件或外部数据。
- 成功返回什么，失败返回什么。
- 哪个测试或运行结果验证这一节点。

只列函数名不算完成；必须说明具体逻辑。状态和数据变化必须放在实际发生的步骤中，不能脱离流程单独列一个看不懂的字段。

### 4. 落实规则和异常

逐条对照产品规则和异常情况，确认：

- 判断条件在哪个流程节点出现。
- 哪个文件和符号执行判断。
- 不满足条件时是否停止、重试、回滚或保留已有内容。
- 调用方或用户最终得到什么结果。

没有代码承接的产品规则必须明确标记，不能用“统一处理”“合理返回”等抽象说法掩盖。

### 5. 补充必要的内部逻辑

只有维护者仅看完整功能流程仍无法理解关键实现时，才继续展开单个函数内部逻辑。可选用：

- 函数签名，说明参数、返回结果、副作用和错误。
- 伪代码，说明关键判断和调用顺序。
- 流程图，说明分支和循环。
- 时序图，说明多对象或外部系统交互。
- 状态图，说明有效状态和迁移条件。
- 少量代码骨架，固定重要接口或类型形状。

## 六、设计共享代码

多个功能确实需要共同使用同一种机制时，再设计共享代码。必须写清：

- 它共同落实哪些产品功能或产品通用规则。
- 为什么分别实现会导致重复、冲突或状态不一致。
- 哪些代码可以调用它，哪些代码不能调用它。
- 它负责的状态、数据、错误和验证。
- 修改它会影响哪些功能。

不要为了“架构完整”预先设计当前产品不需要的通用框架。

## 七、确定验证方式

验证必须回到产品设计，不能只写“增加测试”。对每个关键产品要求至少说明：

- 使用哪个真实测试文件或运行入口。
- 测试触发哪个代码入口。
- 测试准备什么状态或输入。
- 预期得到什么产品结果和代码结果。
- 异常和边界怎样验证。

没有真实测试或运行证据时，明确标记未覆盖，不编造验证位置。

## 八、确认共同代码设计

写正式架构文档前，向用户总结：

1. 产品设计如何决定整体代码分层。
2. 每层承担的产品职责、代码职责和依赖方向。
3. 哪些位置是架构关键节点，为什么关键。
4. 每个产品功能经过哪些代码环节完成。
5. 产品规则、状态、数据和异常分别在哪里落实。
6. 多个功能共同使用哪些代码。
7. 准备怎样验证。
8. 哪些内容未确认或与现状冲突。

仍有未决问题时继续一次讨论一个问题。只有用户明确确认共同设计后，才生成或修改 `spec/代码架构设计.md`。

## 九、完成前对抗性审查

- 是否每项代码设计都能说明它服务的产品内容。
- 是否有产品功能、规则、边界、使用步骤或异常没有代码承接。
- 是否把目录结构误当成架构职责。
- 是否只列文件或函数名，没有说明具体逻辑。
- 是否把功能执行顺序混进架构分层图。
- 是否有程序流程节点没有对应到具体代码。
- 是否把状态和数据变化写成脱离步骤的孤立字段。
- 是否把不存在的代码写成当前实现，或者把未经运行和测试的判断写成已验证。
- 是否存在多个模块重复负责同一判断或状态写入。
- 是否设计了当前产品没有需要的通用框架。
- 不参加前面讨论的维护者，能否只看当前文档理解产品代码为什么这样写。
