# 全局工作流生命周期规范

本规范说明一轮工作怎样推进、回头、取消和结束。所有环节都要遵守它。

## 零、整体流程顺序

一轮工作先确认工作意图，再按意图进入对应流程：

- 从零做：产品设计 -> 技术穿刺（没有技术不确定性时跳过） -> 验收计划。
- 修改产品：项目设计初始化（项目尚未初始化时） -> 产品设计 -> 技术穿刺（没有技术不确定性时跳过） -> 验收计划。
- 修复缺陷：项目设计初始化（项目尚未初始化时） -> 缺陷复现 -> 技术穿刺（没有技术不确定性时跳过） -> 验收计划。
- 无需开发任务：讨论并确认任务 -> 执行 -> 核对并确认结果 -> 正式收工；涉及难以撤销的操作时，执行前单独确认该操作。

前三类需要开发的工作确认验收计划后，共用以下后续流程：代码实施（代码计划 -> 代码实施 -> 代码结果） -> 测试验证（范围 -> 测试代码 -> 任务登记 -> 执行 -> 结果） -> 主题验收 -> 最终全量回归 -> 整体验收 -> 最终代码设计同步 -> 正式收工。代码实施阶段在代码计划中记录完成当前验收条件所需的最低实现设计、文件、符号和关键决定；QA（测试验证）范围根据已确认的代码结果和真实代码填写。

代码实施阶段只确认代码计划和代码结果；测试验证阶段只确认开始范围和结束结果。实施、测试代码、任务登记、执行和结果整理在两次确认之间连续完成。代码、测试和验收完成后，最终代码设计同步根据真实实现更新架构文档。

最终全量回归分两步：先执行 `workflow gate regression_test --discuss-done`，再执行 `workflow gate regression_test`。第二条命令会自动运行项目统一测试入口。`workflow test run` 用于主题测试；最终全量回归只使用上述两条门禁命令。

## 一、后续环节发现问题时返回上游

### 先停下来查清楚

计划、实施、测试或验收环节发现问题时，AI 先停止推进，不继续往下走，也不先动手改上游内容。

然后调查问题真正属于哪一层：

- 产品行为、规则或边界本身没有定义或定义错了：属于产品设计（spec）。
- 产品行为清楚，但“什么算完成”写得不对或漏了：属于验收计划（acceptance_plan）。
- 产品代码没实现、实现错了或实施记录和真实代码不符：属于代码实施（impl）。
- 验收条件清楚，但测试范围、测试代码、任务登记、执行或结果整理不正确：属于测试验证（qa）；返回后按具体变化源进入 QA 内部对应步骤，不重做仍有效的范围、测试代码或结果。
- 依赖没装、服务没起、凭据过期这类临时环境问题：留在当前环节，环境恢复后重试，不返回上游。

失败的错误文字往往指向表面现象，不是根因。要看真实代码、真实记录和真实配置，不靠错误信息猜。

### 向用户说明再返回

调查清楚后，AI 用直白中文向用户说明六件事：

1. 具体是什么问题。
2. 支持这个判断的证据，例如哪个文件的哪段代码、哪条执行记录、哪个配置项。
3. 建议返回哪个环节，写中文名称加英文标识，例如“测试验证（qa）”。
4. 直接受影响的主题有哪些，以及每个主题受到的具体影响。
5. 返回后哪些结果会失效，需要重做。
6. 哪些内容仍然成立，重新核对后可以继续用。

用户确认后，由 AI 执行一次 `workflow return --to <阶段> --topic <主题> --reason <原因>`；全部主题都受影响时用 `--all-topics`。用户不需要自己敲这条命令。

### 程序只校验一件事

程序只检查返回目标是不是本轮实际环节路径中、当前环节之前的真实环节。目标不在路径里或不是更早环节时，返回被拒绝。

返回约束：

- 不从原因文字猜测返回目标。原因是写给人看的，目标由用户确认。
- 不根据主题之间的依赖关系自动扩大失效范围。只有能拿出具体影响证据的主题才重做；只有间接依赖、没有具体证据时保留原结果，交给最终全量回归统一检查。
- QA 内部失效也按变化来源处理：范围变化才回到范围确认；测试代码变化保留仍有效范围；任务或结果变化保留仍有效范围和测试代码，只重新登记、执行并清理直接受影响的结果。
- 不先改内容再补返回登记。先返回，再改；已经改过再补登记不算合法返回。

## 二、取消一个功能不等于整轮不要

这是两件事，处理方式完全不同。

**只取消一个功能**：本轮其他功能还要继续。这时返回产品设计（spec）调整产品设计，删掉这个功能的产品要求；再按重新确认后的实施计划，定向删除或修改只服务于该功能的代码。其他功能和仍被共享的公共代码保留不动。不走整轮回退。

**整轮不要**：用户明确说整个需求不做了。这时 AI 先说明作废会恢复什么、删除什么、哪些内容不受影响，用户确认后执行一次 `workflow abort`。

判断不清时问用户，不擅自把“砍掉一个功能”升级成整轮作废。

## 三、整轮作废怎样恢复

程序先做完整预检，再动手恢复。

预检检查本轮是否有可用的恢复依据：正式文档、项目级字段、测试入口配置和入口脚本、生产代码、测试代码和相关配置中，逐项记录哪些内容有真实副本或“本轮开始前不存在”的事实。缺少某项依据时，作废前明确列出该项不能自动恢复；这不会阻止代码或测试门禁，也不能声称能够恢复未知旧内容。

预检通过后逐项处理：本轮修改过的旧文件恢复原内容，本轮新建的文件删除。回退清单以外的文件一律不动，用户在本轮期间改的无关文件不受影响。

作废掉的内容不归档，不建历史目录，不保留副本，正文也不写进状态文件和流水日志。

中途失败时，轮次保持“进行中”，已完成和未完成的项逐项保存。再次执行作废时只继续未完成的项，已经恢复成功的文件不再覆盖第二遍，避免盖掉第一次恢复之后用户的新修改。

只有全部恢复完成、校验通过、临时副本清理干净之后，程序才把这一轮标记为已作废。

## 四、正式收工

最终代码设计同步（update_code_design）第三道门的用户确认，就是整轮最后一次确认。

用户确认后，AI 立即执行一次 `workflow done` 正式收工。程序只做两件事：记录完成时间，清理本轮临时回退副本。全部正式产物保留，不删除，不归档。

最终代码设计同步确认后直接执行 `workflow done`（正式收工命令），不增加新的用户确认。

清理失败时，轮次保持完成前的状态。修复问题后重试，只继续做清理，不重新走整体验收，也不重新要求最终同步确认。

## 五、通用要求

用户不手动执行日常命令。`workflow` 命令由 AI 执行，用户只做决定。

AI 每次执行命令前，先用直白中文说明四件事：

1. **目的**：为什么现在要执行它。
2. **动作**：它实际会做什么，会改哪些文件或状态。
3. **边界**：它不做什么，哪些内容不受影响。
4. **用户是否需要参与**：需要用户先做什么、看什么、回答什么，还是不需要用户动手。

不要只把命令名念一遍。用户看完说明就应该知道接下来会发生什么。

### 失败输出要求

任何门禁、校验、失效检查、返回或执行失败，都必须在一次输出中列出当前输入下所有可以独立确认的问题，不能只报第一项后让 AI 反复重试。每个问题至少写清：位置、期望、实际、证据、影响和下一步处理。输出顺序保持稳定，重复运行相同输入时不能随机换序。

某项检查依赖已经失败或缺失的前置事实时，不猜结论，明确写“未检查”，并说明依赖哪个前置问题。全部问题之后只给一条当前可执行的下一命令，同时写清执行者、会修改的状态或文件、成功条件，以及成功后进入的阶段。AI 必须原样单独执行这条命令，不加 `head`、`tail`、管道、分号或 `echo`，避免掩盖真实退出码和完整错误。

### 文档链接要求

只有目标文件已经存在时才写 Markdown 链接。后续阶段尚未生成的文档只写反引号包裹的普通项目相对路径和“（待生成）”；不得创建指向不存在文件的链接。文件生成后，再把对应普通路径改成可导航链接。
