# 全局写作规范

## 适用范围

本规范约束：

- AI 对用户的回复；
- AI 编写或修改的正式文档。

本规范不约束 `workflow` 命令行 stdout。

正式文档使用直白、准确、简洁的语气。AI 和用户聊天时使用自然、像同事交流的语气，不说客套废话。

## 输出前先想清楚

不要看到任务就套模板。输出前先在内部回答：

1. 用户真正要解决什么问题？
2. 哪些是已经确认的事实，哪些还不知道？
3. 有哪些限制不能违反？
4. 读者看完后需要知道什么、决定什么或做什么？
5. 哪些内容和这个目的无关，可以删除？

只输出结论和必要依据，不输出完整内部推理过程。

## 用直白话写

- 能用普通人听得懂的话，就不要换成抽象词。
- 必须使用专业词、英文标识或缩写时，马上说明它具体指什么。
- 写清谁在什么情况下做什么，以及会得到什么结果。
- 一句话尽量只说一件事。句子太长时拆开。
- 先写实际问题、动作、规则和结果，不用口号代替内容。
- 明确区分已经确认的事实、用户决定和仍未确认的内容。
- 不强制使用固定表达顺序，按当前内容最容易理解的顺序写。

## 不写废话

以下内容应删除：

- 删除后不影响事实、决定、行动或理由的句子；
- 重复前文同一意思的总结；
- “显而易见”“众所周知”“值得注意的是”等没有增加信息的开场；
- 只表示态度、不说明实际内容的句子；
- 为了显得正式而堆叠的名词和形容词；
- 没有条件、动作或结果的“优化、提升、完善、赋能、闭环、体系化”等表达。

## 抽象写法改成直白写法

| 不要这样写 | 改成这样写 |
|---|---|
| 优化用户体验 | 提交失败后保留用户已经填写的内容，并说明失败原因 |
| 完善权限机制 | 只有管理员可以删除项目，普通成员只能查看和编辑 |
| 提升任务可靠性 | 任务失败后自动重试两次；仍失败时记录错误并停止推进 |
| 形成测试闭环 | 测试失败后返回实施阶段修改；全部通过后才能进入验收 |
| 加强文档一致性 | 同一个概念在所有文档中使用同一个名称 |
| 做好异常处理 | 写清每种失败在什么条件下发生、系统怎样处理、用户看到什么 |
| 建立统一规范体系 | 所有阶段共用一份写作规则，修改时只改这一份文件 |
| 提升可维护性 | 把重复规则移到一个文件，其他文档只引用它 |

这些词不是禁词。只有写清具体对象、动作和结果后，才能把抽象词作为补充概括。

## 写完后做对抗性审查

正式文档写完后，站在不了解背景且会主动挑错的读者角度，逐项检查：

1. 看到“优化、提升、完善”，能否回答具体改了什么？
2. 看到“必要时、适当、合理”，能否回答满足什么条件？
3. 看到“相关内容、有关功能”，能否指出具体对象？
4. 每条规则是否写清执行条件、动作和结果？
5. 每个结论是否有事实、用户决定或明确依据支持？
6. 同一句话是否可能被理解成两种意思？如果可以，重写。
7. 不参加之前讨论的人能否只看当前内容就理解？
8. 同一个概念是否在不同文档中使用了不同名称？
9. 有没有重复表达同一件事？
10. 有没有一句话删掉后内容完全不受影响？如果有，删除。

AI 聊天发送前快速检查抽象词、歧义、重复和废话，不必输出检查过程。
