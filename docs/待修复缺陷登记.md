# 待修复缺陷登记

本文件登记已经确认、但当前轮次范围之外的缺陷，供后续轮次在缺陷复现环节直接取用。
它不是工作流产物：不带工作流编号，不进入任何环节门禁，也不代表缺陷已经进入修复流程。
某条缺陷开始修复时，把它的事实抄进该轮缺陷记录工作记录表，并在本文件标注去向。

## BUG-13 计划文件路径非法时门禁抛异常而不是进问题清单

- 登记日期：2026-09-02
- 发现轮次：2026-09-02-0752-bugfix（本轮已过代码实施第二道门，未纳入修复范围）
- 状态：待修复

### 现象

实施记录工作记录表的「代码修改计划」行把工作流过程文档（`.workflow_loop/` 下的文件）
填进「文件」列时，`workflow gate impl` 不输出问题清单，而是输出一行

```text
错误：命令执行失败（ValueError: ...，“文件”列：代码修改计划不能把工作流过程文档当成实施代码：...）
工作流状态没有被本次失败修改；先处理上面指出的原因。
```

同一次门禁里其它可以独立确认的问题不再报出，用户和 AI 只能看到这一条。

### 真实观察

2026-09-02 本轮实施环节真实发生，顺序如下：

1. 08:57 执行 `workflow gate impl`，得到 3 条结构化问题：两条「实施结果列出该文件，但没有从
   入场观察中检测到变化」和一条「实际代码修改」的路径非法。当时「代码修改计划」里同样有一个
   非法路径，但没有出现在这份清单里。
2. 按这 3 条改完后再执行同一条命令，才以上面的异常形式报出计划行的路径问题。
3. 修掉计划行后第四次执行才通过。

### 复现方法

在本仓库执行下面的步骤，可稳定复现（脚本会自动还原表内容）：

1. 把当前轮次实施记录表「代码修改计划」第一行的「文件」列临时改成
   `.workflow_loop/Standardized_Repository/qa/test_plan.md`。
2. 调用 `workflow_loop.rollback.planned_code_paths(项目根, 当前主题列表)`。

实测输出：抛出 `ValueError`，文字为
`...impl_record_....json:1，“文件”列：代码修改计划不能把工作流过程文档当成实施代码：...`。
同一状态下 `compute_plan_hash` 正常返回，说明只有取计划路径这条链会抛。

### 实际结果与期望结果

- 实际结果：计划行的路径问题以异常形式穿过门禁，被命令层的兜底处理打印成一行错误；它没有和
  同一次检查发现的其它问题合并输出，用户需要多跑一轮才能看到。
- 期望结果：计划行的路径问题作为一条 `error` 诊断进入本次报告，与其它问题一次列全，写明位置
  （表文件、行号、列名）、预期、实际、证据、影响和下一动作。

### 根因

- 根因说明：`rollback.py::_normalized_relative_path` 对非法路径统一 `raise ValueError`。
  「实际代码修改」一侧的调用方在 `validate_actual_implementation_changes_report`（约 1419 行）
  用 `try/except ValueError` 把它转成了 `impl.implementation_record.path_invalid` 诊断，而
  「代码修改计划」一侧经由 `planned_code_paths`（1447 行）向上抛，沿途只有
  `verification.py::stage_responsibility_paths`（约 186 行）捕获，门禁调用链上的
  `validate_prepared`（1808 行）、`prepare_impl`（2016 行）和
  `validate_existing_implementation_paths`（2667 行）都不捕获。
- 根因位置：`src/workflow_loop/rollback.py::_normalized_relative_path` 与
  `src/workflow_loop/rollback.py::planned_code_paths` 之间缺少与实际改动一侧对等的诊断转换。
- 根因证据：本轮真实门禁输出；沙盒中对同一非法路径分别调用两条链，
  `planned_code_paths` 抛 `ValueError`、`compute_plan_hash` 正常返回。

### 违反的产品规则

- [推进并确认工作环节 R20](../spec/功能_推进并确认工作环节.md#r-20)：一次列出当前能够独立确认的
  全部问题，不能发现第一项后就停止报告。
- [推进并确认工作环节 R22](../spec/功能_推进并确认工作环节.md#r-22)：每项失败写清检查项、具体位置、
  预期、实际、证据、影响和下一动作。

### 修复方向（未确认，供下一轮讨论）

把计划路径解析改成与实际改动一侧同样的处理：调用方捕获 `ValueError` 并生成带位置和列名的
结构化诊断，与本次其它问题合并输出。不改变判定本身，只改变失败的报告方式。

## BUG-14 发布脚本不更新 spec 目录里的版本文字

- 登记日期：2026-09-02
- 发现轮次：2026-09-02-0752-bugfix（本轮只同步了架构文档自身，未纳入修复范围）
- 状态：待修复

### 现象

执行 `uv run python scripts/release.py <新版本号>` 发布新版本后，`spec/` 下记录当前版本的
产品文档不会跟着更新。截至 2026-09-02，实际版本已是 `0.3.7`，而这两份文档仍写 `0.3.1`：

- `spec/产品总说明.md`：4.1 支持范围、第 6 章“每次公开发布使用唯一版本号”规则。
- `spec/功能_安装到项目.md`：R2、R3、R9、R10、R11、R15、R19、R21 及两条安装命令示例。

### 真实观察

本轮最终设计同步阶段核对时发现：`pyproject.toml` 与 `src/workflow_loop/__init__.py` 都是
`0.3.7`，而上述两份文档写 `0.3.1`，相差六个版本。架构文档 `spec/代码架构设计.md` 原本同样
停在 `0.3.1`，本轮已在该阶段同步为 `0.3.7`。

### 复现方法

1. 读 `scripts/release.py` 的 `CURRENT_VERSION_FILES` 常量，确认其中没有任何 `spec/` 路径。
2. 比较 `pyproject.toml` 的 `version` 与 `spec/产品总说明.md` 中的版本文字。

### 实际结果与期望结果

- 实际结果：发布脚本只替换十个固定身份文件和项目状态里的安装版本，产品文档中的版本文字保持不变，
  每发一版就多差一版。
- 期望结果：当前发布身份统一更新，或者产品文档不再逐处写死版本号而改为引用单一来源。

### 根因

- 根因说明：`scripts/release.py::update_release_identity` 按固定路径清单做精确替换，清单里
  只有打包配置、包身份、README、六个维护脚本和自动发布配置，没有 `spec/` 下的产品文档；而
  这些文档在正文和规则表里逐处写死了版本号。
- 根因位置：`scripts/release.py` 的 `CURRENT_VERSION_FILES` 常量。
- 根因证据：常量内容与两份文档的实际版本文字直接比对可确认。

### 违反的产品规则

- [安装到项目 R10](../spec/功能_安装到项目.md#r-10)：源码发行版本、GitHub 发布标签、安装脚本、
  全局工具要求、命令版本和项目安装标记必须全部严格等于本次发布版本。
- [产品总说明第 6 章](../spec/产品总说明.md#6-产品通用规则)：每次公开发布必须同步更新本次发布
  涉及的全部版本位置。

### 修复方向（未确认，供下一轮讨论）

两种做法二选一，需要用户决定：把 `spec/` 下写死版本号的位置纳入发布脚本的替换清单；或者让产品
文档不再写死版本号，改为指向单一版本来源。前者改动小但清单要持续维护，后者一次性解决但要改动
多处文档表述。

## BUG-15 旧轮次无编号日志被恢复为当前轮次的退回原因

- 登记日期：2026-09-07
- 发现轮次：2026-09-04-0743-bugfix
- 状态：待修复；不属于本轮六项填表与链接缺陷范围，未修改恢复逻辑。
- 现象：本轮首次进入验收计划和代码实施阶段时，程序显示“为什么重新进入当前阶段”，并称原测试、验收结果不能继续使用；本轮当时尚未产生这些结果。
- 真实证据：项目追加式日志中，2026-07-30T02:27:11+00:00 的“验证失效”记录没有工作流编号，来源为代码实施；2026-07-27 的验收计划记录也没有工作流编号。2026-09-07 在内存中读取本轮状态、清空内存中的恢复说明，再调用命令模块的旧日志恢复函数，得到“已恢复”为真，原因就是上述七月的实施失效原因。没有改写磁盘状态或日志。
- 根因位置：`src/workflow_loop/cli.py` 中的 `restore_recovery_context_from_journal`（从旧日志补回恢复说明的函数）。
- 根因说明：函数接受“无工作流编号或编号等于当前轮次”的历史记录，但没有进一步限定无编号记录所属的开工时间范围。当前源阶段尚未完成时，会将历史轮次的失效事件重新解释为当前轮次的恢复原因。
- 期望结果：旧格式兼容仍能恢复同一轮次的说明，但不能跨开工边界引用其他轮次的失效记录；首次进入阶段不显示不存在的退回过程。
- 后续复现：用现有日志和一份内存状态副本调用上述函数，分别核对本轮开始前、开始后的无编号记录；再测试显式工作流编号和已经处理的恢复记录。不能删除历史日志来掩盖问题。

## BUG-16 表模式的测试登记下一步缺少必要选项

- 登记日期：2026-09-07
- 发现轮次：2026-09-04-0743-bugfix
- 状态：待修复；本轮仅记录，不修改测试登记指引代码。
- 现象：测试范围确认且九项测试计划已填好后，状态命令给出的下一步是 `workflow test prepare`（登记测试）；原样执行却报缺少逐条登记参数，不能完成登记。
- 真实证据：本轮状态输出明确列出尚待登记的九项测试。2026-09-07 原样执行登记命令，退出码为 1，提示逐条登记需要主题、测试项、报告适配器与实际命令；补充 `--from-tables`（从工作记录表读取）后九项全部登记成功，随后正式执行九项全部通过。首次失败没有登记任何测试。
- 根因位置：`src/workflow_loop/cli.py` 第 304 行的测试阶段下一步文字，与第 3294 行的逐条登记参数检查；测试代码实施规范末尾也给出同一个不完整命令。
- 根因说明：状态指引已经根据工作记录表计算缺少的测试项，却仍打印逐条登记入口的裸命令；该入口没有自动按表登记的默认行为，而是要求明确选择从表读取或提供完整逐条参数。
- 期望结果：表模式直接给出可以执行成功的从表登记命令，逐条模式则明确说明所需参数；正常使用者不应先执行一次必然失败的命令才能取得完整指引。
- 后续复现：建立已确认范围、已填完整测试计划但尚未登记的测试阶段，逐字执行状态输出中的下一步，断言第一次即可登记全部计划项；另核对非表模式仍保留逐条登记能力。

## BUG-17 最终同步表不能生成阶段要求的正式架构文档

- 登记日期：2026-09-07
- 发现轮次：2026-09-04-0743-bugfix
- 状态：待修复；本轮不改生成器，只保留记录表事实并按表同步正式架构。
- 现象：最终设计同步要求只填工作记录表、由程序生成正式文档，阶段产出指定为代码架构设计；实际同步表却只有核对项和同步说明，程序只生成内部记录，正式架构的本轮编号和核对依据仍为旧值。
- 真实证据：在独立临时项目建立完整同步表和含旧轮次编号的架构文档，调用 `records.sync_stage_tables`（按当前阶段的表生成文档）；返回问题为空，实际生成路径为 `.workflow_loop/records/guidance-regression/design_sync_design_sync.md`，输出集合不含正式架构文档，原架构逐字节保持不变。诊断没有改动本项目的状态或正式文档。
- 根因位置：`src/workflow_loop/records.py` 的设计同步表定义、`_expected_document_path`（计算生成出口）和 `_generate_document_v2`（按表生成文档）；`src/workflow_loop/artifact_validation.py::validate_final_code_design_document`（最终架构校验）却直接要求正式架构第九章含当前轮次与精确机器编号。
- 根因说明：表结构没有覆盖架构正文和最终结论的固定字段，生成出口也没有连接阶段要求的正式架构路径；填表、生成和最终校验三者没有使用同一份可生成的结构。
- 期望结果：明确架构正文与固定同步字段的来源；按表更新正式架构并保护既有正文和手改，最终校验使用同一来源，不能要求填写者自行再手写一套固定字段。
- 本轮处理边界：同步事实只写入本轮工作记录表；由一次性按表转换更新已有架构中的对应内容，保留原章节和表格，再通过原有最终门禁。该方式只是完成本轮文档，不代表产品生成器缺陷已经修复。
- 后续复现：在最终同步阶段填全程序下发的表后原样执行阶段门禁，检查正式架构是否更新为当前工作流编号、完整机器记录集合和真实代码映射；再次生成还须证明正文保护和结果稳定。
